# 01-05 登入狀態與安全

> 相關規格：[規格 01-01 登入](./01-login.mdx)、[規格 01-02 註冊](./02-register.mdx)、[規格 01-03 忘記與重設密碼](./03-reset-password.mdx)、[規格 01-04 個人設定](./04-profile.mdx)、[規格 06-01 使用者管理](../06-admin/01-user-management.mdx)、[規格 07-01 側欄導覽](../07-shared/01-sidebar.mdx)（登出的控制項在側欄上）

## 目標

- 讓使用者在一段時間內持續操作，不必反覆登入
- 讓**該被登出的時候一定被登出**：帳號被停用、密碼被改掉、登入用的識別被換掉，舊的登入狀態都不能繼續通行
- 讓使用者在多個分頁同時操作時，不會被誤判成帳號被盜而整批登出
- 讓同一個信箱不論怎麼寫，在平台上都只對應同一個帳號

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

本頁沒有畫面，也沒有任何人「操作」它；它規定的是其他頁的操作會對 :ref[登入狀態]{id="term.login-state"} 造成什麼結果。

- :ref[平台成員]{id="term.platform-member"}、:ref[系統管理員]{id="term.system-admin"}、:ref[Seeder 管理員]{id="term.seeder-admin"}：R (o)（自己目前是不是登入著）／E (o)（登出自己這一台，也就是結束自己的登入狀態）
- 登出寫成 E 而不是 D：PRD §權限矩陣 給「01 帳號（自己的帳號與個人設定）」的上限是 `R／E (o)`，而且 PRD 明寫「帳號沒有刪除，只有停用與啟用」。結束一段登入狀態不是刪除任何東西——那段紀錄還留著（見 [§登出紀錄只記真正的登出](#登出紀錄只記真正的登出)），所以本頁不超出 PRD
- 系統管理員額外能透過 [規格 06-01](../06-admin/01-user-management.mdx) 停用別人的帳號，連帶讓對方的登入狀態失效；那一頁定操作，本頁定結果
- **沒有任何角色能看到或登出別人的某一台裝置**；使用者自己能不能看到「我有哪些裝置登入著」，見 [§待釐清](#待釐清) Q5
- 權限一律以**當下的**系統角色與帳號狀態判定，不以登入當時的為準，見 [§每一次操作都用最新的身分判定](#每一次操作都用最新的身分判定)

- **自己登出這一台**
  - 觸發：使用者點「登出」
  - 前置條件：使用者在這一台原本是登入狀態
  - 主流程：
    1. 使用者點「登出」
    2. 系統確認這一台的登入狀態還能驗證
    3. 系統讓這一台的登入狀態失效，記下這次登出，並清掉本機留著的登入資料
    4. 使用者回到登入頁；其他裝置維持登入
  - 替代流程：
    - A1（第 2 步）這一台的登入狀態已經不能驗證 → 系統只清掉本機留著的登入資料並把人帶回登入頁，**不聲稱已經讓伺服器端失效，也不把這次記成一次登出**，流程結束（見 [§從這一台登出](#從這一台登出)）
  - 結果：只有這一台要重新登入；平台留下一筆可驗證的登出紀錄

- **安全事件撤銷**
  - 觸發：使用者改密碼、換 Email、重設密碼、連結 Google 帳號，或系統管理員停用帳號
  - 前置條件：該帳號至少有一台裝置是登入狀態
  - 主流程：
    1. 事件本身成功（各自的規則在 [規格 01-03](./03-reset-password.mdx)、[規格 01-04](./04-profile.mdx)、[規格 06-01](../06-admin/01-user-management.mdx)）
    2. 系統判斷這是哪一種事件
    3. 是改密碼 → 其他裝置的登入狀態全部失效，**目前這一台維持登入**
    4. 使用者在這一台不必重新登入，繼續操作
  - 替代流程：
    - A1（第 3 步）不是改密碼——換 Email 驗證成功、重設密碼成功、系統管理員改了這個帳號的 Email、連結 Google 帳號成功，或帳號被停用 → **所有裝置的登入狀態全部失效，包含目前這一台**，使用者回到登入頁，流程結束
  - 例外流程：
    - E1（第 1～3 步任一步）這個事件的任何一步失敗 → 整件事回到原狀：密碼沒換、Email 沒換、登入狀態也沒有任何一台被踢掉，流程結束（見 [§這些改動要麼全部生效、要麼全部不生效](#這些改動要麼全部生效要麼全部不生效)）
  - 結果：失去資格的登入狀態一律不能再通行；只有改密碼這一種保留操作者自己這一台

- **時間到了自然結束**
  - 觸發：使用者做任何一次操作（系統每次都檢查兩條時間限制）
  - 前置條件：使用者先前登入過，而且還沒有自己登出
  - 主流程：
    1. 使用者做下一次操作
    2. 系統確認這段登入狀態有沒有達到絕對上限，以及距上一次使用有沒有超過閒置限制
    3. 其中任一個到了 → 拒絕這次操作，把使用者帶回登入頁
    4. 使用者重新登入，取得新的登入狀態
  - 替代流程：
    - A1（第 2 步）兩個限制都還沒到，而帳號啟用中、角色也沒變 → 正常通行，閒置的那條線往後延，流程結束
    - A2（第 2 步）兩個限制都還沒到，但帳號已被停用或系統角色已變更 → 依**當下**的狀態判定：停用就拒絕並帶回登入頁；角色變更就用新角色的權限，流程結束
  - 結果：沒有任何一段登入狀態能無限期延續；這種結束**不算一次登出**

## 規格

### 一次登入是一段登入狀態

使用者每次登入，平台就開始一段 :ref[登入狀態]{id="term.login-state"}；同一個人在兩台裝置上登入，就是兩段互不相干的登入狀態。

1. 使用者登入成功 → 開始一段新的登入狀態，記下開始時間
2. 使用者在同一台裝置上繼續操作 → 沿用同一段登入狀態，開始時間不變
3. 使用者在另一台裝置登入 → 另外開始一段，兩段各自獨立
4. 一段登入狀態結束的原因可能是：使用者自己登出、安全事件撤銷，或時間到了自然結束（見 [§登入狀態能撐多久](#登入狀態能撐多久)）

- 這三種結束方式**使用者看到的都是回到登入頁**，但平台分得出差別，見 [§登出紀錄只記真正的登出](#登出紀錄只記真正的登出)
- 一段登入狀態要在平台上保留多久才清掉，見 [§待釐清](#待釐清) Q6
- 登入狀態怎麼存放、放在哪裡，不屬於規格；那是後續技術規劃的事

### 登入狀態能撐多久

一段登入狀態有**兩個**各自獨立的時間限制，先到的那個先生效。

| 限制 | 舊 repo 既有的數字 | 會不會因為使用而延後 |
| :--- | :--- | :--- |
| 從登入那一刻起算的**絕對上限** | 90 天（待確認，見 [§待釐清](#待釐清) Q1） | **不會**，用得再頻繁也一樣 |
| 連續**沒有使用平台**就結束 | 7 天（待確認，見 [§待釐清](#待釐清) Q2） | 會，每次使用就重新起算 |

1. 使用者持續使用平台 → 閒置的那個限制一直往後延，登入狀態維持著
2. 使用者連續一段時間沒有使用平台 → 下一次操作被拒絕，帶回登入頁
3. 使用者從登入到現在已達絕對上限 → 下一次操作被拒絕，**即使他剛剛還在操作**
4. 使用者在絕對上限快到時使用 → 閒置的延長**不會越過絕對上限那條線**
5. 使用者重新登入 → 開始新的一段，兩個限制都重新起算

- **兩條限制的規則本身是來源拍板的，但兩個數字還需要你確認**：來源的條文只引用常數名，數字出現在來源指名依賴的 foundation 規格裡，依 D4 那份規格不搬成本專案的規格。見 [§待釐清](#待釐清) Q1 與 Q2
- 標記作業一次可能連續做 30～90 分鐘，兩條限制都遠大於此，正常工作不會被中斷
- 使用者在這兩種情況下看到什麼訊息，見 [§待釐清](#待釐清) Q4

### 登入與申請的嘗試次數

[規格 01-01 登入](./01-login.mdx) 與 [規格 01-03 忘記與重設密碼](./03-reset-password.mdx) 都把「重試／申請次數的限制」交給本頁。

1. 同一個人反覆嘗試登入、反覆申請重設密碼，或反覆延續登入狀態 → **不能無限次**
2. 超過上限 → 暫時擋住，請他稍後再試
3. 擋住的訊息和 [規格 01-01](./01-login.mdx) 的「帳號或密碼錯誤」一樣**不透露帳號存不存在**

- 「不能無限次」這條規則來源已經拍板，但**具體的次數與擋住多久沒有定**，見 [§待釐清](#待釐清) Q3
- 這和 [§已確認決議](#已確認決議) Q15（在個人設定頁改密碼時連錯不鎖定）不衝突：那一條是**已經登入**的人改自己的密碼，身分已經確認過；這一節管的是**還沒登入**的人
- 次數決定之前，本頁不寫任何卡控，也不寫 Scenario

### 每一次操作都用最新的身分判定

使用者能做什麼，一律以**他送出這次操作時**的系統角色與帳號狀態判定，不以他登入時的為準。

1. 使用者的系統角色被改掉 → **下一次操作**就用新角色的權限
2. 使用者的帳號被停用 → 下一次操作就被拒絕
3. 使用者的帳號被重新啟用 → 要重新登入才能繼續，見 [§帳號被停用或重新啟用](#帳號被停用或重新啟用)

- 角色與帳號狀態**不靠「改過幾次」這種計數來判定**，每次都看當下的值；所以被降級的人不會因為登入狀態還沒過期就保有舊權限
- 這和 [規格 06-01 §規格](../06-admin/01-user-management.mdx#規格) 的「編輯帳號」寫的「系統角色的變更在對方下一次操作起生效」是同一條規則，本頁定結果、那一頁定操作
- 使用者看到的角色名稱可能還是舊的，直到他重新整理；**但他能不能做某件事，一律以當下的角色為準**

### 從這一台登出

使用者點「登出」時，只有他現在這一台要重新登入。

1. 這一台的登入狀態還能驗證 → 讓這一段失效、記下這次登出、清掉本機留著的登入資料，回到登入頁
2. 其他裝置 → **不受影響，繼續維持登入**
3. 這一台之後再操作 → 一律被拒絕
4. 這一台的登入狀態已經不能驗證（例如本機留著的資料不見了或已過期）→ 只清掉本機留著的資料並回到登入頁

- 第 4 種情況下，**平台不會聲稱自己已經讓某一段登入狀態失效**，也不把它記成一次登出；畫面上一樣是回到登入頁，使用者感覺不出差別
- 登出**不會動到其他裝置**，也不會因此要求使用者在別的地方重新登入
- 一個人只能登出自己這一台；沒有任何角色能登出別人的某一台裝置，見 [§使用角色](#使用角色)

### 帳號被停用或重新啟用

1. 系統管理員停用一個帳號 → 該帳號**所有裝置**的登入狀態立刻失效
2. 被停用的人下一次操作 → 被拒絕，回到登入頁
3. 被停用的人想重新登入（含用 Google 帳號登入）→ 登不進來
4. 系統管理員之後重新啟用這個帳號 → **停用前的登入狀態不會恢復**，對方要重新登入
5. 停用造成的失效**不算一次登出**

- 這和 [規格 06-01 §規格](../06-admin/01-user-management.mdx#規格) 的「停用與啟用」寫的「對方目前的登入狀態立即失效」「重新啟用時停用前的登入狀態不會恢復」是同一條規則
- 停用自己的那一種情況由 [規格 06-01](../06-admin/01-user-management.mdx) 定（確認後登出並回到登入頁）

### 改密碼只踢掉其他裝置

1. 使用者在 [規格 01-04 §密碼設定](./04-profile.mdx#密碼設定) 改密碼成功 → **其他裝置**的登入狀態失效
2. **目前這一台維持登入**，使用者不必重新登入
3. 其他裝置下一次操作 → 被拒絕，回到登入頁，要用新密碼重新登入
4. 其他裝置也不能用舊的登入狀態延續，延續一樣失敗

- 這是四種高風險事件裡**唯一**保留操作者自己這一台的
- 這條規則是 [規格 01-04 §已確認決議](./04-profile.mdx#已確認決議) Q13 指過來的
- 這種撤銷**不算一次登出**

### 四種改動讓所有裝置重新登入

以下四種事件成功時，該帳號**所有**裝置的登入狀態全部失效，包含操作者現在這一台：

| 事件 | 在哪一頁操作 |
| :--- | :--- |
| 新 Email 驗證成功 | [規格 01-04 §換 Email](./04-profile.mdx#換-email) |
| 密碼重設成功 | [規格 01-03 §設定新密碼](./03-reset-password.mdx#設定新密碼) |
| 系統管理員改了這個帳號的 Email | [規格 06-01 §規格](../06-admin/01-user-management.mdx#規格) 的「編輯帳號」 |
| 連結 Google 帳號成功 | 未撰寫，見 [§待釐清](#待釐清) Q7 |

1. 事件成功 → 所有裝置的登入狀態失效
2. 操作者現在這一台 → 也要回到登入頁重新登入
3. 連結 Google 帳號成功 → 另外把這個帳號原本的本地密碼清掉，之後只能用 Google 登入，直到他自己再設一組密碼（見 [§沒有本地密碼的帳號](#沒有本地密碼的帳號)）
4. 這四種撤銷都**不算一次登出**

- 和 [§改密碼只踢掉其他裝置](#改密碼只踢掉其他裝置) 的差別是刻意的：改密碼的人知道舊密碼、人就在這一台；這四種事件要麼登入用的識別變了，要麼帳號可能已經外流
- 三種結果放在一起對照見 [規格 01-04 §待釐清](./04-profile.mdx#待釐清) Q2，**本頁不代為結案**

### 這些改動要麼全部生效、要麼全部不生效

1. 上面兩節的任何一種事件，在過程中任何一步失敗 → **整件事回到原狀**
2. 回到原狀的意思是：密碼沒換、Email 沒換、也沒有任何一台裝置的登入狀態被踢掉
3. 不會出現「密碼已經換了但其他裝置還登著」或「其他裝置被踢了但密碼沒換」這種半套結果

- 使用者看到的是事件本身的失敗訊息（由各自那一頁定），而且他原本登入著的裝置都還登入著

### 多個分頁同時延續登入狀態

使用者常常同時開著好幾個分頁。它們可能在同一瞬間各自去延續同一段登入狀態，這是**正常現象，不是帳號被盜**。

1. 兩個分頁同時延續同一段登入狀態 → 只有一個會成功取得新的；另一個不會因此被登出
2. 沒成功的那一個 → 短暫等一下同來源其他分頁的結果，然後把原本的操作重試**一次**
3. 重試還是不通 → 最多再延續一次；還是不行就把使用者帶回登入頁
4. 同一次延續被用到第三次 → **不給新的登入狀態，也不把任何其他裝置踢掉**

- 重試的次數**有上限**，不會變成一直重試的迴圈；使用者最壞的結果是被帶回登入頁，不是畫面卡住
- 使用者正常情況下感覺不到這一節；它存在的目的就是讓他感覺不到
- 等待與重試的秒數屬於實作細節，規格只定「有界」與「使用者看到的結果」

### 疑似被盜用時所有裝置一起登出

1. 同一次延續在寬限期外又被使用 → 視為**疑似被盜用**
2. 系統讓該使用者**所有**裝置的登入狀態失效
3. 所有裝置下一次操作 → 被拒絕，回到登入頁
4. 因為登出或安全事件而失效的登入狀態**沒有寬限資格**，不會因此觸發這一節

- 這一節和上一節的差別：上一節是同一瞬間的正常競爭，這一節是過了寬限期之後才又出現，兩者的處置刻意不同
- 使用者會看到自己在所有裝置上突然被登出；要不要告訴他原因，見 [§待釐清](#待釐清) Q4

### 不能通行的登入狀態不說明原因

1. 一段登入狀態不存在、已經失效，或它屬於另一個帳號 → 一律拒絕
2. 拒絕的時候**不透露**那段登入狀態存不存在、屬於誰，或那個帳號的任何資訊
3. 錯誤訊息裡**不出現**使用者原本的登入資料，也不出現其他裝置的任何資訊

- 理由和 [規格 01-01](./01-login.mdx)、[規格 01-03](./03-reset-password.mdx) 刻意不揭露某個 Email 有沒有註冊過是同一個：錯誤訊息不能被當成查詢工具
- 使用者看到的就是「要重新登入」，不會看到為什麼

### Email 的識別規則

同一個信箱不論怎麼寫，在平台上都只對應同一個帳號。

1. 使用者在登入、註冊、受邀或改 Email 時輸入一個信箱 → 系統先把它**正規化**（統一大小寫、統一同一個字的不同寫法），再拿正規化後的值判斷重複
2. 兩個輸入正規化後相同 → 視為同一個信箱；第二個帳號建不起來，改成已被占用的信箱也會被擋
3. 長度上限 254 字 → **在正規化之後才算**，不是照使用者輸入的原樣算
4. 正規化後超過 254 字 → 擋下

- 這條規則四條路通用：[規格 01-01 登入](./01-login.mdx)、[規格 01-02 註冊](./02-register.mdx)、[規格 06-01 的邀請與編輯](../06-admin/01-user-management.mdx)、[規格 01-04 的換 Email](./04-profile.mdx#換-email)
- [規格 06-01](../06-admin/01-user-management.mdx) 已有「大小寫不同的同一信箱」的驗收情境，本頁把它擴大到「同一個字的不同寫法」也算同一個
- 使用者看到的訊息是「這個 Email 已被使用」，不是「正規化後重複」

### 沒有本地密碼的帳號

1. 用 Google 帳號註冊或登入進來的人 → 帳號上可以**沒有**密碼
2. 沒有密碼的人 → 不能用 Email 與密碼登入，只能用 Google
3. 沒有密碼的人想補一組 → 走 [規格 01-04 §密碼設定](./04-profile.mdx#密碼設定)，那一頁不顯示現有密碼欄
4. 本來有密碼的人連結了 Google 帳號 → 原本的密碼被清掉，又回到「沒有密碼」的狀態

- 第 4 條的結果和第 3 條合起來是一個來回：連結 Google 會清掉密碼，使用者之後可以自己再設一組

### 登出紀錄只記真正的登出

平台對「這個人什麼時候登出」只採信**可驗證的明確登出**。

1. 使用者自己點登出、而且當時的登入狀態能驗證 → 記下一次登出
2. 安全事件撤銷（改密碼、換 Email、重設密碼、連結 Google、帳號被停用）→ **不記成登出**
3. 時間到了自然結束 → **不記成登出**
4. 登出時兩種登入資料都不能驗證 → **不記成登出**

- 這條規則有業務後果：**不能用登入狀態失效的時間回推使用者在線多久**。安全撤銷與自然到期的時間不是他離開的時間
- 這會影響標記作業的工時統計，見 [§待釐清](#待釐清) Q8
- 一段登入狀態被記過登出之後就不會再變回有效，稽核保留也不會讓它復活

### 資料欄位

| 欄位 | 型別 | 必填 | 規則 | 使用者看到 |
| :--- | :--- | :--- | :--- | :--- |
| 登入狀態的開始時間 | 日期時間 | 是 | 絕對上限從這一刻起算；之後的使用不會改變它 | 不顯示 |
| 最後一次使用的時間 | 日期時間 | 是 | 閒置限制從這一刻起算；每次使用就更新 | 不顯示 |
| 登入狀態是否已失效 | 是／否 | 是 | 任何原因造成的失效都算，含登出、安全撤銷與自然到期 | 不顯示；失效後的下一次操作會被帶回登入頁 |
| 登出時間 | 日期時間 | 否 | **只記可驗證的明確登出**；有值時該段登入狀態必然已失效，且登出時間不晚於失效時間 | 不顯示 |
| Email | 文字 | 是 | 正規化後判重；上限 254 字，在正規化之後計算 | 登入、註冊與個人設定的 Email 欄 |
| 系統角色 | 單選：平台成員、系統管理員 | 是 | 每次操作以當下的值判定，不以登入時的為準 | 側欄與個人設定顯示的角色 |
| 帳號狀態 | 單選：啟用、停用 | 是 | 每次操作以當下的值判定；停用立刻讓所有登入狀態失效 | 使用者自己看不到；[規格 06-01](../06-admin/01-user-management.mdx) 的列表看得到 |
| 本地密碼 | 文字 | 否 | 可以沒有；沒有時只能用 Google 登入 | [規格 01-04](./04-profile.mdx#密碼設定) 的密碼區塊會因此少一欄 |

- 這一頁不定義任何畫面欄位；上表是其他頁共用的規則依據
- 表中沒有任何一欄是使用者可以直接編輯的

## 卡控機制

| 條件 | 結果 |
| :--- | :--- |
| 登入狀態已達絕對上限 | 拒絕這次操作，帶回登入頁，即使使用者剛剛還在操作 |
| 距上一次使用平台已超過閒置限制 | 拒絕這次操作，帶回登入頁 |
| 登入狀態不存在、已失效，或屬於另一個帳號 | 拒絕，且不透露它存不存在或屬於誰 |
| 帳號已停用 | 拒絕任何操作、拒絕重新登入、也拒絕用 Google 登入 |
| 帳號重新啟用 | 停用前的登入狀態一律不恢復 |
| 系統角色已變更 | 下一次操作就用新角色判定，不沿用登入時的角色 |
| 同一次延續被用到第三次 | 不給新的登入狀態，**也不把其他裝置踢掉** |
| 同一次延續在寬限期外又被使用 | 該使用者所有裝置的登入狀態全部失效 |
| 安全事件的任何一步失敗 | 整件事回到原狀，不留半套結果 |
| 兩個輸入的 Email 正規化後相同 | 擋下，顯示這個 Email 已被使用 |
| Email 正規化後超過 254 字 | 擋下 |
| 登出時兩種登入資料都不能驗證 | 只清掉本機留著的資料，不聲稱已讓伺服器端失效，不記成登出 |
| 想登出別人的某一台裝置 | 任何角色都沒有這個操作，只能停用整個帳號 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到什麼 |
| :--- | :--- |
| 剛剛還在操作，卻突然被要求重新登入 | 這是絕對上限到了；畫面回到登入頁，訊息見 [§待釐清](#待釐清) Q4 |
| 久久沒進來一次 | 超過閒置限制就要重新登入 |
| 每天都進來，持續很久 | 絕對上限到的那一天還是要重新登入一次，之後重新起算 |
| 在絕對上限快到時使用 | 可以操作，但閒置的延長不會越過絕對上限那條線 |
| 同時開很多個分頁，全部一起延續 | 都正常，沒有人被登出；最多一個取得新的，其餘跟著用 |
| 兩個分頁同時延續，其中一個慢了 | 慢的那個短暫等一下就好，原本的操作會自動重試一次 |
| 重試之後還是不通 | 被帶回登入頁，不會一直轉圈或一直重試 |
| 在另一台裝置改了密碼 | 這一台下一次操作被帶回登入頁，要用新密碼登入 |
| 在這一台改了密碼 | 這一台不必重新登入，其他裝置要 |
| 帳號被停用時正在標記 | 下一次操作被拒絕並帶回登入頁 |
| 被停用後又被重新啟用 | 要重新登入；停用前開著的頁面不會自己恢復 |
| 本機留著的登入資料被清掉後點登出 | 一樣回到登入頁，感覺不出差別；平台不會記成一次登出 |
| 用大寫寫自己的 Email 登入 | 登得進來，和小寫是同一個帳號 |
| 註冊時用的信箱和別人只差大小寫 | 擋下，顯示這個 Email 已被使用 |
| 疑似被盜用而所有裝置一起被登出 | 每一台都回到登入頁；原因見 [§待釐清](#待釐清) Q4 |
| 連結 Google 帳號之後想用密碼登入 | 登不進來，因為原本的密碼已被清掉；要先自己設一組 |

## 驗收標準

| Scenario | Given | When | Then |
| :--- | :--- | :--- | :--- |
| 從這一台登出只影響這一台 | 同一帳號在 A、B 兩台裝置都登入著 | 在 A 點「登出」且 A 的登入狀態可驗證 | A 失效並記下一次登出，A 下一次操作被拒絕 |
| 登出不影響其他裝置 | 同上 | 在 A 登出成功之後查看 B | B 繼續維持登入，不必重新登入 |
| 沒有登出別人裝置的操作 | 系統管理員登入著 | 查看他能對別人的帳號做的所有操作 | 找不到任何「登出對方某一台裝置」的操作，只能停用整個帳號 |
| 登入狀態已經不能驗證時登出 | 使用者本機留著的登入資料已經不見或過期 | 點「登出」 | 只清掉本機留著的資料並回到登入頁，不聲稱已讓伺服器端失效，也不記成一次登出 |
| 兩段登入狀態互不相干 | 同一帳號在兩台裝置分別登入 | 查看兩段登入狀態 | 各有自己的開始時間，一段失效不影響另一段 |
| 達到絕對上限就要重新登入 | 一段登入狀態從登入起算已達絕對上限 | 使用者做下一次操作 | 被拒絕並帶回登入頁，即使他剛剛還在操作 |
| 閒置超過限制就要重新登入 | 使用者連續超過閒置限制沒有使用平台 | 他再回來操作 | 被拒絕並帶回登入頁 |
| 持續使用會延長閒置那條線 | 使用者在閒置限制內每天都使用平台 | 他再操作一次 | 正常通行，沒有被要求重新登入 |
| 延長不會越過絕對上限 | 距絕對上限只剩一天 | 使用者使用平台一次 | 操作成功，但有效期間不越過絕對上限那條線 |
| 角色變更從下一次操作起生效 | 使用者原本是系統管理員，登入狀態還有效 | 他被降為平台成員後送出一次管理操作 | 以平台成員的權限判定，操作被拒絕 |
| 停用帳號讓所有裝置立刻失效 | 帳號在兩台裝置都登入著 | 系統管理員停用這個帳號 | 兩台下一次操作都被拒絕，且重新登入與用 Google 登入都不成功 |
| 重新啟用不恢復舊的登入狀態 | 帳號先被停用、原本的登入狀態已失效 | 系統管理員重新啟用這個帳號 | 舊的登入狀態不恢復，使用者要重新登入 |
| 改密碼保留目前這一台 | 同一帳號在 A、B 兩台都登入著 | 在 A 改密碼成功 | A 不必重新登入並能繼續操作，B 下一次操作被拒絕 |
| 改密碼後其他裝置不能延續 | 同上，B 的登入狀態已被撤銷 | B 嘗試延續登入狀態 | 延續失敗，B 回到登入頁 |
| 換 Email 驗證成功後所有裝置重新登入 | 帳號在兩台裝置都登入著 | 新 Email 驗證成功 | 兩台都被帶回登入頁，含操作者現在這一台 |
| 密碼重設成功後所有裝置重新登入 | 帳號在兩台裝置都登入著 | 密碼重設成功 | 兩台都被帶回登入頁 |
| 管理員改了 Email 後所有裝置重新登入 | 某帳號在兩台裝置都登入著 | 系統管理員改掉那個帳號的 Email | 兩台都被帶回登入頁 |
| 連結 Google 後所有裝置重新登入 | 帳號在兩台裝置都登入著 | 成功連結 Google 帳號 | 兩台都被帶回登入頁，含操作者現在這一台 |
| 連結 Google 後不能再用密碼登入 | 帳號原本有密碼 | 成功連結 Google 帳號 | 原本的密碼被清掉，用 Email 與密碼登不進來，只能用 Google |
| 改動中途失敗就全部回到原狀 | 使用者送出改密碼 | 過程中任何一步失敗 | 密碼沒換、沒有任何一台裝置被踢掉 |
| 兩個分頁同時延續不會互相踢掉 | 使用者開著兩個分頁 | 兩個同時延續同一段登入狀態 | 只有一個取得新的，另一個沒有被登出，其他裝置也沒被踢掉 |
| 慢的那個分頁自動重試一次 | 兩個分頁競爭，其中一個沒取得新的 | 它短暫等候同來源另一個分頁的結果 | 原本的操作重試一次並成功，使用者沒有看到錯誤 |
| 重試仍失敗就帶回登入頁 | 重試之後仍然不通 | 再延續一次仍失敗 | 被帶回登入頁，沒有繼續重試 |
| 同一次延續用第三次就不給 | 同一次延續已經被用過兩次 | 第三次使用它 | 不給新的登入狀態，也沒有任何其他裝置被踢掉 |
| 疑似被盜用時所有裝置一起登出 | 同一次延續已過寬限期 | 它又被使用一次 | 該使用者所有裝置的登入狀態全部失效 |
| 安全撤銷的登入狀態沒有寬限資格 | 一段登入狀態是因為登出或安全事件而失效 | 再次使用它 | 直接拒絕，不會因此把所有裝置一起登出 |
| 不能通行的登入狀態不說明原因 | 一段登入狀態不存在、已失效，或屬於另一個帳號 | 拿它去操作 | 被拒絕，訊息裡沒有它存不存在、屬於誰或該帳號的任何資訊 |
| 大小寫不同的同一信箱視為同一個帳號 | 平台已有 `user@example.com` | 有人要用 `User@Example.com` 註冊 | 擋下，顯示這個 Email 已被使用 |
| 同一個字的不同寫法也視為同一個 | 平台已有某個含非英文字母的信箱 | 有人用同一個信箱的另一種寫法註冊 | 擋下，視為同一個信箱 |
| 用大寫寫自己的 Email 登入 | 使用者註冊時用的是小寫 | 用全大寫輸入同一個信箱登入 | 登入成功 |
| 正規化後超過上限就拒絕 | 使用者輸入的信箱正規化後超過 254 字 | 送出 | 擋下 |
| 沒有本地密碼的人只能用 Google | 帳號是用 Google 註冊的、沒有密碼 | 用 Email 與密碼登入 | 登不進來 |
| 登入狀態自然到期不記成登出 | 一段登入狀態因為達到絕對上限或超過閒置限制而結束 | 查看這段登入狀態的登出紀錄 | 沒有登出時間 |
| 安全撤銷不記成登出 | 一段登入狀態因為帳號被停用而失效 | 查看這段登入狀態的登出紀錄 | 沒有登出時間 |

## 待釐清

### Q1. 一段登入狀態從登入起算最長能撐多久？

- [ ] 90 天，沿用舊 repo 既有的唯一數字
- [ ] 其他長度（請說明）

> 建議：第一個。**本頁來源的條文沒有給數字**——`AC-1.1`、`AC-2.1`、`FR-002`、`FR-003`、`SC-009` 五條都要求以這個絕對上限判定、且延續出來的有效期間不得越過它，但五條都只引用常數名。
> 數字出現在來源指名依賴的 foundation 規格的「架構常數」一節：**90 天**。來源指向的設計決策紀錄（ADR-021）只引用同一個常數名，**沒有寫出數字**。
> 所以舊 repo 既有的唯一數字是 90 天，不是沒有數字；但依 D4，foundation 不搬成本專案的規格，而且那份規格自己宣告「保留時間等由 owning feature spec 或 ADR 定義」——偏偏 owning spec 就是本頁的來源，它沒定。
> 這和 [規格 01-03 §待釐清](./03-reset-password.mdx#待釐清) Q1（30 分鐘只出現在歸檔的圖與 ADR）是同一種情況，處理方式也一致：數字當建議，由你拍板才算定案。
> 需要決定的人：維護者

### Q2. 連續多久沒有使用平台就要重新登入？

- [ ] 7 天，沿用舊 repo 既有的唯一數字；每次使用就重新起算
- [ ] 不設閒置限制，只留 Q1 的絕對上限
- [ ] 其他（請說明）

> 建議：第一個。**「有這條限制」這件事來源已經拍板**：`FR-003` 要求延續出來的有效期間不得越過絕對上限，而「取『當下時間加上一個固定長度』與『絕對上限』之中較早者」這個寫法出自 foundation 的對應條文。
> 但**那個固定長度的數字同樣不在本頁來源裡**，而在 foundation 的「架構常數」一節：**7 天**，每次使用就重新起算。來源指向的設計決策紀錄（ADR-021）這一半有寫出數字（7 天，每次使用重設）。
> 和 Q1 同一個理由（D4 沒有授權本頁取用 foundation），所以一併交給你確認。
> 如果選第二個，一台沒鎖螢幕的公用電腦在絕對上限內都還是登入著。
> 需要決定的人：維護者

### Q3. 登入、申請重設密碼與延續登入狀態的嘗試次數上限是多少？

- [ ] 給一組明確的次數與擋住的時間
- [ ] 其他（請說明）

> 建議：第一個，**數字要由你定**。這一題是 [規格 01-01 §待釐清](./01-login.mdx#待釐清) Q1 與 [規格 01-03 §待釐清](./03-reset-password.mdx#待釐清) Q5 指過來的——兩頁都寫「次數的限制留給規格 01-05」。
> foundation 規格明文要求對登入與延續這類入口做次數限制、**且不得無限**，但把具體閾值交給「auth／security 的 owning spec 或 ADR」——而那個 owning spec 就是本頁的來源，**它從頭到尾沒有定任何閾值**。
> 所以這是一條「規則已拍板、數字沒人定」的空缺，而且**三頁都在等它**。數字定下來之前本頁不寫卡控，也不寫 Scenario。
> 擋住的訊息要和 01-01 的「帳號或密碼錯誤」一樣不透露帳號存不存在，否則被擋住本身就會變成查詢工具。
> 需要決定的人：維護者

### Q4. 被動登出時使用者看到什麼？

- [ ] 沿用舊 repo 既有的兩句：「登入已過期，請重新登入」與「驗證失敗，請重新登入」
- [ ] 改寫成別的文案（請說明）
- [ ] 只回到登入頁，不說原因
- [ ] 其他（請說明）

> 建議：第一個。使用者會在四種情況下**沒有自己動手就被登出**：絕對上限到了、閒置超過限制、別的裝置改了密碼或 Email，以及疑似被盜用。
> **本頁來源沒有文案**，但舊 repo 的 `account/001` 另附的實作計畫已經定了兩句中英對照（繁中是「登入已過期，請重新登入」與「驗證失敗，請重新登入」）——那份文件依搬移設計文件的來源對照表是「只讀不搬」，所以它的文案不是規格，但它是既有的字，不必重新發明。
> 這兩句分得出「時間到了」和「憑證不再有效」，而且都不透露帳號資訊，符合 [§不能通行的登入狀態不說明原因](#不能通行的登入狀態不說明原因)。
> 要不要再多一句專講「安全設定有變更」由你決定——目前這兩句會把改密碼、換 Email 與疑似被盜用都歸到第二句。
> 這一題和 [規格 01-03 §待釐清](./03-reset-password.mdx#待釐清) Q4（重設成功後要不要說「所有裝置都會被登出」）是同一組，請一起決定。
> 需要決定的人：維護者

### Q5. 使用者能不能看到自己有哪些裝置登入著、能不能遠端登出某一台？

- [ ] 不提供，維持現況（只能登出自己這一台）
- [ ] 提供一個「登入中的裝置」清單，可以單獨登出某一台
- [ ] 其他（請說明）

> 建議：第一個，因為它**超出 PRD 的範圍**，而且舊 repo 完全沒有這個功能。
> 但這一頁通篇在講「其他裝置」，使用者卻看不到有哪些、也不能主動處理；手機掉了的人唯一的辦法是去改密碼，用副作用達到目的。
> 而登入狀態的絕對上限如果是 Q1 建議的 90 天，「手機掉了但我記得密碼」這個情況可以持續很久。
> 選第二個有 **PRD 連帶影響**（模組地圖要多一個頁面或在 01-04 多一個區塊），建議併進 Issue #85 一起評估。
> 需要決定的人：維護者

### Q6. 一段登入狀態的紀錄要保留多久？

- [ ] 依來源：被標記作業引用著的就留著，最短一年；最長期限之後再定
- [ ] 現在就定一個明確的保留期限
- [ ] 其他（請說明）

> 建議：第一個。來源明寫這一條**自己也還沒定案**（「最短一年，最長期限待定」，並掛著一個待定編號），理由是登入狀態的紀錄被標記作業的工時與責任歷程引用著，不能跟著帳號一起刪掉。
> 這一題的答案會牽動規格 04-01 標記清單與 04-02 標記工作區（都未撰寫），所以現在不急著定，但不能漏掉。
> 需要決定的人：維護者（可能要先等 04 模組的規格）

### Q7. 連結 Google 帳號這件事由哪一份規格擁有？

- [ ] 收進 [規格 01-04 個人設定](./04-profile.mdx)，當成第五個區塊
- [ ] 另開一頁
- [ ] 不做這個功能，本頁相關條文改標為不適用
- [ ] 其他（請說明）

> 建議：第一個。本頁的 [§四種改動讓所有裝置重新登入](#四種改動讓所有裝置重新登入) 列了「連結 Google 帳號成功」，而且來源另外要求它清掉本地密碼；
> 但 **18 頁裡沒有任何一頁定義「怎麼連結 Google 帳號」**——01-01 只有用 Google 登入，01-04 明寫「頁面依序有四個區塊」、沒有它，prototype 也沒有這個畫面。
> 和 [規格 01-03 §待釐清](./03-reset-password.mdx#待釐清) Q6（受邀者設定密碼那個畫面沒人擁有）是同一類的歸屬空缺。

### Q8. 「不能用登入狀態失效的時間推算在線多久」這條要不要在 04 標記作業落地？

- [ ] 要，在 04 的規格明寫工時怎麼算、哪些時間不能當結束時間
- [ ] 不要，只留在本頁
- [ ] 其他（請說明）

> 建議：第一個。來源特別強調這一條：只有可驗證的明確登出才算登出，**安全撤銷與自然到期的時間都不能用來補登出時間或推算上線時長**。
> 這不是技術細節，是一條會改變數字的業務規則——如果工時統計拿「登入狀態失效的時間」當結束時間，被停用或被動登出的人的工時就會被算多；誤差最大可以是 Q1 與 Q2 那兩條限制的長度。
> **這條規則已經在一個地方落地了**：[規格 03-03 §工時紀錄](../03-task-management/03-task-detail.mdx#工時紀錄) 依它自己的來源寫明「速度算不出來時顯示破折號，不用不可信的時長算數字」。所以這一題剩下的是**標記作業那兩頁要不要也寫**（規格 04-01、04-02，都未撰寫）——工時的原始紀錄在那裡產生。
> 需要決定的人：維護者

## Q&A

### Q. 為什麼改密碼保留目前這一台，重設密碼卻連這一台都要重新登入？

改密碼的人知道舊密碼、人就在這台裝置前面，登入用的識別也沒變，沒有理由把他踢出去。重設密碼的人是**忘記**密碼——有可能帳號已經外流，也有可能他正在用的其實不是自己的裝置，所以把既有的登入狀態全部清掉比較安全。

### Q. 為什麼角色變更不需要重新登入，停用卻立刻失效？

兩者都是「下一次操作就生效」，差別只在結果不同：角色變更後他還是合法使用者，只是能做的事變了，所以用新角色繼續；停用之後他不再是合法使用者，所以直接拒絕。判定的時機其實是同一個。

### Q. 為什麼兩個分頁同時操作不算可疑，過了寬限期才算？

同一瞬間的兩個請求幾乎一定是同一個人的兩個分頁——真的被盜用的人，不會剛好在那幾秒內和原主人一起操作。過了寬限期還有人拿同一次延續來用，就代表有人留著一份舊的在手上，那才是該擔心的訊號。

### Q. 為什麼要有兩個時間限制，一個不夠嗎？

它們擋的是兩件不同的事。閒置那條擋「這台電腦已經沒人在用了」——離職的人、公用電腦、換了筆電的人，放著不動就自己結束。絕對上限那條擋「這台一直有人用，但已經用得太久了」——只有一個會往後延的閒置視窗的話，一個天天進來的人可以永遠不必重新登入，那條登入狀態就會無限期存在。

### Q. 為什麼自然到期不算一次登出？

因為「登出」是一個使用者做過的動作，而自然到期是他**沒有**做任何動作的結果。把它記成登出，等於替使用者編造一個他沒做過的行為，而平台後面會拿這個時間去算他工作了多久。

這份來源是 18 份裡**技術密度最高的一份**：它整篇在定系統怎麼存放與驗證登入狀態。依本 skill 鐵律 1，規格只收每一條裡「使用者看得到、或會改變業務結果」的部分，機制留給後續的技術規劃。
