# Tasks

依相依順序排列：相依套件與設定層 → import 契約與寄信入口、Celery 與 worker → 兩層編排與 CI → 本機與 e2e 的 eager 預設、範例檔、常駐文件與整合驗證。每個群組單獨提交後都能 build 並通過自己的測試。測試與實作在同一個 task（TDD，`architecture.mdx` §測試分層）：先寫對應 Scenario 的測試、看它失敗，再實作。後端以 `uv`、JavaScript 以 `pnpm` 安裝，不用 `pip install` 或 `npm install`。行為以 `specs/` 為準，做法以 `design.md`、`system-design.md` 為準；本 change 沒有 API 變更（`api-contract.md`），每個後端群組的最後一個 task 以契約漂移檢查證明這一點。本 change 沒有資料模型異動，不需要 `[@dba]`。

共用指令（`openspec/config.yaml` `operations.apply`，在 repo 根目錄執行）：

- 後端兩輪測試：`cd backend && uv run pytest`（SQLite，回報 pytest 摘要裡的 skipped 數）與 `cd backend && TEST_DATABASE_URL=postgresql+asyncpg://... uv run pytest`（本機 `docker run postgres:16`，應為 0 skipped）
- 後端靜態檢查：`cd backend && uv run lint-imports && uv run ruff check . && uv run ruff format --check . && uv run mypy --strict app`
- 契約漂移：`cd backend && uv run python -m app.scripts.export_openapi && git diff --exit-code -- openapi.json ../docs/diagrams/architecture/api.openapi.json && test -z "$(git status --porcelain -- openapi.json ../docs/diagrams/architecture/api.openapi.json)"`，以及 `pnpm --filter frontend api:generate && git diff --exit-code -- frontend/src/api/generated && test -z "$(git status --porcelain -- frontend/src/api/generated)"`
- 動到 `docs/` 時：**不在 worktree 執行本機 NoteCraft 建置**（會污染共用快取），以本 PR 的 CI `docs-site` job 為證據
