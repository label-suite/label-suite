# PRD 撰寫指南

各章「要寫／不寫」、章節完成度的狀態、待確認的寫法與追問清單。範本見 [../templates/prd.mdx](../templates/prd.mdx)。

## 章節總覽

| # | 章節 | 回答的問題 | 和其他文件的關係 |
| :--- | :--- | :--- | :--- |
| 1 | 文件資訊 | 這份文件寫到哪裡、哪些章節可以拿來展開規格 | 全專案「還有什麼沒定」看這裡的完成度 |
| 2 | 專案概述 | 為什麼做、要達成什麼 | — |
| 3 | 使用者角色 | 誰會用、各自能做什麼 | 角色定義在 glossary；權限矩陣是規格「使用角色」與卡控的上限 |
| 4 | 專案範圍 | 這期做什麼、不做什麼、前提是什麼 | 規格碰到範圍外的需求，列進規格的「待釐清」 |
| 5 | Site Map | 有哪些頁面、誰進得去（使用者視角） | 每個頁面對到模組地圖的一列 |
| 6 | 模組架構與串接 | 有哪些模組、模組之間怎麼交接（業務能力視角） | 模組地圖定義在 `docs/specs/index.mdx`；規格的「業務流程」引用 §跨模組流程、§共用狀態機 |
| 7 | 術語 | 名詞怎麼定義 | 指到 glossary，PRD 內不定義 |

**長度控制**：PRD 只回答上表的問題。發現自己在寫欄位、畫面、提示文字或某一頁的操作步驟，就是寫到規格書的範圍了，改成連到規格。

## 文件資訊

- 基本資訊：專案名稱、文件狀態（草稿／定稿）、負責人、`updatedAt`
- 章節完成度：每章一列，狀態 + 「卡在什麼」（已完成寫「—」）

| 狀態 | badge | 意思 | 規格可以依據嗎 |
| :--- | :--- | :--- | :--- |
| 已完成 | `:badge[已完成]{variant="success" icon="check"}` | 內容齊備，沒有待確認 | 可以 |
| 暫定 | `:badge[暫定]{variant="success" icon="check" outline}` | 結構與規則已定，若干值是暫定（寫出是哪些） | 可以，暫定的值要在規格標註 |
| 待確認 | `:badge[待確認]{variant="warning" icon="warning"}` | 有關鍵問題沒拍板，寫不下去 | 不可以，先決議 |
| 待生成 | `:badge[待生成]{variant="info" icon="info"}` | 文字已定，視覺化標記還沒生成 | 可以 |

文件狀態要改成「定稿」，完成度表必須全部是「已完成」。

## 專案概述

| 要寫 | 不寫 |
| :--- | :--- |
| 問題背景：現在怎麼做、痛點、為什麼是現在 | 公司簡介、市場分析長文 |
| 目標：每條寫「讓 {角色} {達成什麼}」與**衡量方式**（數字、比例、可觀察的行為） | 「提升效率」「更好用」這類無法驗證的形容詞 |

目標用表格：`目標｜受益角色｜衡量方式`。成功指標就是衡量方式，不另開章節。

## 使用者角色

- **角色清單**：每個角色一列，`:ref` 連到 glossary 的定義，加一句「在這個系統裡主要做什麼」；外部角色、系統帳號也要列
- **權限矩陣**：列＝模組（或模組內有差異的功能），欄＝角色，值用 `R／C／E／D`、`(o)`（只限自己的資料）、`—`（無權限）
- 有欄位遮蔽或資料範圍限制時，在矩陣下方用條列寫「誰看不到什麼」，只寫業務規則（例：檢視者看不到客戶的電話與 Email），不寫怎麼做到

| 要寫 | 不寫 |
| :--- | :--- |
| 角色在業務上的差異 | 帳號怎麼建立、登入流程的技術細節 |
| 權限的上限（規格只能更嚴，不能更寬） | 每個按鈕誰看得到（屬於規格） |

## 專案範圍

- **範圍內**：這期要做到的能力，每條一句話，對得到模組地圖的模組
- **範圍外**：容易被誤以為會做、但這期不做的項目，每條附原因或「下一期再議」
- **假設與限制**：成立前提（既有系統、資料來源、組織規則）；前提若不成立會影響什麼

## Site Map

- 樹狀條列：頁面階層，每個節點標出可存取的角色；有 `(o)` 範圍限制的標出來
- 每個節點連到對應的規格；尚未撰寫的頁面寫名稱與預留編號（例：`客戶清單（規格 01-02，未撰寫）`）
- 章節最前面一律放 Site Map 圖（寫法見 [visualize.md](visualize.md)）；條列是唯一來源，圖的資料照條列

| 要寫 | 不寫 |
| :--- | :--- |
| 頁面、階層、可存取角色、入口（從哪裡進來） | 頁面裡的區塊、欄位、按鈕 |

## 模組架構與串接

### 模組地圖

PRD 只放 `::include{id="specs.module-map"}`。地圖本身寫在 `docs/specs/index.mdx`：

```mdx
:::define{id="specs.module-map" label="模組地圖"}
| 編號 | 模組／頁面 | 主要角色 | 說明 |
| :--- | :--- | :--- | :--- |
| 01 | **[客戶管理](./01-customer/index.mdx)** | 管理員、檢視者 | 客戶資料與往來紀錄的維護 |
| 01-01 | 　[客戶聯絡紀錄](./01-customer/01-customer-contact-log.mdx) | 管理員、檢視者 | 在客戶詳情頁登錄與檢視每次聯絡 |
| 01-02 | 　客戶清單（未撰寫） | 管理員、檢視者 | 查詢與篩選客戶 |
:::
```

- 連結用相對於 `docs/specs/index.mdx` 的路徑；嵌入 PRD 後 NoteCraft 會依定義所在的檔案解析，不用改
- 模組列粗體，頁面列前面加全形空白縮排；預留頁面不加連結
- 不放撰寫狀態（狀態在各模組 `index.mdx`），PRD 嵌入時才不會帶出狀態欄

### 跨模組流程

一個業務實體從頭到尾經過哪些模組。**以模組為泳道**（規格書的業務流程以角色為泳道，兩者不要混用）。

```md
- **客戶從建立到停止往來**
  - 起點：{哪個模組、什麼事件}
  - 交接：
    1. 客戶管理 → 聯絡紀錄：{交接的是什麼、什麼條件下發生}
    2. …
  - 終點：{結束時的狀態}
  - 細節：見 [規格 01-01 §業務流程](./01-customer/01-customer-contact-log.mdx#業務流程)
```

- 只寫模組之間的交接與觸發條件，模組內的步驟連到規格
- 交接編號（1、2…）和流程圖上的交接編號一致；流程圖寫法見 [visualize.md](visualize.md)
- 只有一個模組、或模組之間沒有交接時寫「不適用：{原因}」

### 共用狀態機

被兩個以上模組讀寫的業務實體（例：案件、合約）：列出狀態、轉移條件、**每個轉移由哪個模組推進**。
只在單一模組內流轉的狀態寫在該模組的規格，不放這裡。沒有時寫「不適用」。

### 模組依賴（選填）

A 模組的事件或資料會影響哪些模組，用表格：`來源模組｜事件或資料｜受影響模組｜影響`。模組少於三個時通常不需要。

## 術語

只放一句指路與連結；PRD 正文的名詞第一次出現時用 `:ref`。不在 PRD 裡寫 `:::define`。

## 待確認的寫法

```mdx
:badge[待確認]{variant="warning" icon="warning"} 檢視者是否能匯出客戶清單

:::warning{title="待確認：檢視者能不能匯出客戶清單？"}
- 選項：可以，但遮蔽欄位維持遮蔽／不可以
- 建議：不可以。匯出檔離開系統後無法再控管。
- 需要決定的人：業務主管
- 追蹤：[#12](https://github.com/org/repo/issues/12)（有開 Issue 才寫）
:::
```

- 放在受影響的段落旁邊，不集中到文末
- 同一題影響多個章節時，記在最上游的章節，其他章節只放連結
- 有主責模組的問題交給 spec-writing 記在該規格的「待釐清」，PRD 只放連結

## 追問清單

| 章節 | 檢查 |
| :--- | :--- |
| 專案概述 | 痛點是誰的痛點？目標能不能量測？量測的基準值是多少？ |
| 使用者角色 | 有沒有外部角色、系統帳號？同一個人會不會身兼兩個角色？「只看自己的」的「自己」怎麼界定？哪些資料要對哪些角色遮蔽？ |
| 專案範圍 | 有沒有提到但沒說要不要做的功能？既有系統要不要移轉資料？有沒有一定要配合的組織規則或法規？ |
| Site Map | 每個頁面從哪裡進來？有沒有角色看得到頁面但不能操作？ |
| 模組架構與串接 | 模組的邊界在哪？同一份資料由哪個模組負責維護？跨模組的交接誰觸發、失敗時回到哪？有沒有被多個模組共用的狀態？ |
| 衝突（跨章節） | 多份輸入說法不同？這次的修改和既有 PRD 其他章節矛盾？角色或範圍和 AGENTS.md 的 Hard Rules、openspec 設定對不上？既有規格會超出新的權限矩陣或碰到範圍外？ |

衝突一律提問，不自行選邊；提問寫法見 SKILL.md 步驟 4。
