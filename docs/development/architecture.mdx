# 技術架構

`backend/`、`frontend/` 還不存在，本文寫的是「要照著做的架構」；第一個讀者是 OpenSpec 規劃階段的 `sd` 與 `ui-ux`，業務面以 `docs/specs/` 為準（見 [需求文件撰寫](workflow/spec-authoring.md)）。
本文是個人 repo 38 份 ADR 在本 repo 的落地版，每份 ADR 照做、調整或被取代，見文末 [§ADR 效力總表](#adr-效力總表)。
衝突時依序以 `AGENTS.md`、本 repo 的 [ADR](adr/index.mdx)、本文為準，個人 repo 的 ADR 只當參考；業務面一律以 `docs/specs/` 為準。發現不一致就照這個順序做，並回報維護者。

各節的收合區塊是給實作與規劃查的細節，預設收起。

## 技術選型

| 層 | 選型 |
| :--- | :--- |
| 後端 | FastAPI 加 pydantic v2 加 uvicorn；SQLAlchemy 2.0（async）加 Alembic |
| 資料庫 | PostgreSQL 16（正式）／SQLite（Lite），見 [§資料庫雙層](#資料庫雙層) |
| 快取、佇列、背景工作 | Redis 7 加 Celery |
| 寄信 | Resend，可選，見 [§部署與維運](#部署與維運) |

## 認證與授權

身分只認 httpOnly cookie 裡的 token，角色只從資料庫取；權限一律在後端擋，前端隱藏按鈕只是體驗。
為什麼 token 放 cookie、角色每次讀資料庫，見 [ADR-004 的 D1](adr/004-auth-and-security.mdx#d1-認證-token-放在-httponly-cookie) 與 [D2](adr/004-auth-and-security.mdx#d2-授權用的角色每次從資料庫讀)。
`Authorization` header、查詢字串、自訂 header 都不用來推定身分。

| Token | 效期 | Cookie flag | 輪替 |
| :--- | :--- | :--- | :--- |
| Access token（JWT） | 15 分鐘 | `httpOnly`、`Secure`、`SameSite=Lax` | 每次 refresh 重發 |
| Refresh token（不透明 UUID） | 7 天滑動 | `httpOnly`、`Secure`、`SameSite=Lax` | 每次使用輪替，一次性；**輪替之前先從資料庫讀 `is_active`，帳號已停用就拒絕、不發新 token** |
| CSRF token（`HMAC(secret, sid)`） | 與 session 同壽 | `__Host-` 前綴、`Secure`、`SameSite=Lax`、**非 `httpOnly`** | 登入時發，refresh 時重發 |

refresh 的停用檢查是第二道防線，第一道是 [security-agent-rules.mdx 的 S4](rules/security-agent-rules.mdx#s4-遮蔽與-allowlist-在後端) 的 session 與快取失效規則；這一道是為了萬一那一步漏了或失敗。

JWT payload 只放 `sub`、`sid`、`credential_version`、`role`、`iat`、`exp`；`role` 只供顯示，授權不看它。
任務角色不放進 JWT，前端進任務頁後另查成員身分。

### CSRF

會改資料的請求都要帶綁定 session 的 double-submit token，由單一 middleware 驗 HMAC。
每個要素為什麼不能省，見 [ADR-004 的 D3](adr/004-auth-and-security.mdx#d3-csrf-用綁定-session-的-double-submit-token)。

| 要素 | 做法 |
| :--- | :--- |
| token 的值 | `HMAC(server_secret, sid)`，驗 HMAC 而不只比對字串 |
| cookie 名稱 | `__Host-` 前綴 |
| 傳遞方式 | 前端把值複製到自訂 header；這一層的強度等於 CORS allowlist 的嚴格程度（Hard Rule 7） |
| 責任位置 | 單一 middleware，端點不各自處理 |

CSRF cookie 刻意讓 JS 讀得到，是系統裡唯一非 `httpOnly` 的 cookie。負向測試要涵蓋「缺 header」「header 與 cookie 不符」「HMAC 無效」三種。

### 授權四步

為什麼矩陣是授權的輸入，見 [ADR-004 的 D6](adr/004-auth-and-security.mdx#d6-權限矩陣當授權輸入)。

1. 驗目前登入者、帳號是否啟用、`credential_version`、token family 是否仍有效
2. 讀系統角色；任務範圍的操作另讀該任務目前有效的成員身分。系統角色永遠不隱含任務成員身分
3. 把操作解析成已啟用、在白名單內的 permission key 與它所屬的層（系統或任務），要求對應角色的 cell 為 `allowed=true`。未知的 key、缺少的列、層級不符、成員身分失效、矩陣版本列不存在，一律拒絕
4. 檢查附加條件：任務歸屬與狀態、指派與審核者身分、資料集可見性、測試集答案隔離。cell 為 true 也蓋不過這些條件；被隱藏的任務要在不洩漏它存在的前提下回應

### Google SSO

為什麼不引入外部 IdP、為什麼這樣綁定，見 [ADR-004 的 D4](adr/004-auth-and-security.mdx#d4-google-sso-直接走-oidc) 與 [D5](adr/004-auth-and-security.mdx#d5-google-登入綁定既有帳號的條件)。
直接整合 OIDC（`authlib`），不引入外部 IdP；沒設 `GOOGLE_CLIENT_ID` 時按鈕退回 no-op，所以 SSO 是可選的。
Google 回報 `email_verified: true` 時才自動綁定既有 Email 帳號，並在同一筆交易內把 `hashed_password` 設為 `null`、`credential_version` 加一、撤銷所有 session。

## API 契約

唯一的契約真相是規劃階段的 `api-contract.md` 加 FastAPI 匯出的 `openapi.json`，前端的 client 與型別都從它產生。

| 面向 | 做法 |
| :--- | :--- |
| 路徑前綴 | `/api/v1`，資源名直接接在後面，理由見 [ADR-003 的 D5](adr/003-backend-architecture.mdx#d5-api-路徑前綴與成功回應外層) |
| 成功回應 | 包一層 envelope，例 `{"data": {...}, ...}` |
| envelope 的例外 | `204` 無 body、檔案下載與串流不套 envelope；每個例外都要逐一寫進該 change 的 `api-contract.md`，不逐案自由心證 |
| operationId | 用 `generate_unique_id_function` 固定成「動詞加資源」（#51） |
| 前端 client | Orval 由 `openapi.json` 產生到 `frontend/src/api/generated/`（TanStack Query hooks、型別、MSW mock），不手改；Orval 的 mutator 就是單一 HTTP 邊界 |
| Bruno | 可選的手動工具，不是 pre-PR 關卡 |

## 任務設定：`input_type` 加 `outputs[]`

任務類型完全由設定決定，平台核心不得出現任何任務專屬邏輯（Hard Rule 5）。
設定由 `input_type`（`single_item` 或 `item_pair`）加一個 `outputs[]` 陣列組成，不用固定的 `task.type` enum；每個 output type 自帶設定片段、標記 UI 與評分指標。理由見 [ADR-006 的 D1](adr/006-task-config-and-answer-isolation.mdx#d1-任務類型由設定決定核心不寫任務專屬邏輯)與 [D2](adr/006-task-config-and-answer-isolation.mdx#d2-任務設定用-input_type-加-outputs-組合)。

| Output type | 設定片段 | 標記 UI | 評分指標 |
| :--- | :--- | :--- | :--- |
| `single_label` | `label_options[]` | 單選群組 | accuracy、f1_macro、cohen_kappa |
| `multi_label` | `label_options[]`、`max_selections` | 可搜尋的階層多選 | f1_micro、f1_macro、hamming_loss |
| `single_dim` | `dimension_name`、`min`、`max`、`step` | 滑桿 | pearson_r、spearman_rho、mse |
| `multi_dim` | `dimensions[]` | 多個滑桿 | pearson_r（逐維）、mean_mse |
| `sequence_tagging` | `entities[]`、`snap_unit` | 字元 offset span 選取 | span 級指標 |
| `entity_recognition` | `entities[]` 或 `polarity_options[]`、`allow_overlapping`、`scheme` | 實體選取加標籤 | entity_f1、span_f1 |
| `relation_identification` | `relation_types[]`、`source_output` | 實體加關係連線 | triple_f1 |
| `free_text` | `max_length` | 文字區塊 | ROUGE、BERTScore、BLEU |

:::note{title="組合規則與 sequence_tagging 細節" collapsible}
- 依賴以 `source_output` 宣告，被依賴的 output 要先完成；沒有依賴的 output 可任意順序完成
- v1 限制：同一種 output type 每個任務最多一次，output 數量沒有上限
- 多 output 的任務產生分數向量而不是單一分數，IAA 也逐 output type 獨立計算
- `sequence_tagging` 的標記是半開區間的字元 offset span `{ start, end, label }`，不是對齊 token 的標籤；ADR-029 那一列的 `tagging_scheme`、`token_f1`、`token_accuracy` 不採用
- `snap_unit` 只影響拖曳落點，不改變既有 span 的意義，所以不需要凍結 tokenizer 版本；改用 span 的理由見 [ADR-006 的 D3](adr/006-task-config-and-answer-isolation.mdx#d3-序列標記用半開字元-offset-span)
:::

## 測試集答案不外露

標記員能接觸到的任何地方都不得出現標準答案與測試集資訊（Hard Rule 6），架構上分四道，理由見 [ADR-006 的 D4](adr/006-task-config-and-answer-isolation.mdx#d4-答案隔離涵蓋標記員能到達的每個出口)：

| 位置 | 做法 |
| :--- | :--- |
| 資料庫 | 測試集答案存在獨立、受存取控制的資料表，不與一般標記資料同表 |
| Celery worker | `load_answers()` 只在 worker 行程內讀答案，答案不離開 worker |
| 授權 | 測試集答案隔離是授權第四步的附加條件，權限矩陣 cell 為 true 也不能蓋過 |
| 保留政策 | 帶答案的歷史 JSON 跟著它所屬的資料集版本或 run 存續，不做 PII 匿名化、不單獨刪除 |

規劃階段由 clarify 關卡的第 10 個檢查面向把關（見 [OpenSpec 導入決議](workflow/openspec-fullstack-sdd.mdx)）。

## 資料庫雙層

`DATABASE_URL` 有設就走 PostgreSQL，沒設就走 SQLite；schema 一律走 Alembic migration。

| 層 | 資料庫 | 用途 | 啟用方式 |
| :--- | :--- | :--- | :--- |
| Lite | SQLite | 本機試用、單人、評估 | 預設，不需設定 |
| 正式 | PostgreSQL 16 | 多人、並發寫入、部署 | 設 `DATABASE_URL` |

Lite 層的 `./data` 必須是持久化 volume，而且 `backend` 與 `worker` 要掛同一個路徑，否則 worker 寫的資料 API 讀不到。

:::note{title="驅動與設定存放" collapsible}
同一層的 API 與 worker 用不同驅動，因為 Celery 跑在同步執行緒裡，不能用 async engine：

- Lite：API 用 `sqlite+aiosqlite:///./data/label_suite.db`，worker 去掉 `+aiosqlite` 得到同步 URL
- 正式：API 用 `postgresql+asyncpg://...`，worker 推導出 `postgresql+psycopg2://...`

`docker-compose.yml` 預設 Lite，`docker-compose.prod.yml` 提供 PostgreSQL 全套。
任務設定存成 JSONB（Lite 層為 SQLite JSON），新增任務類型不必改 schema；不用 `synchronize` 類的自動同步。
:::

## 非同步任務

評分一律走 Celery：端點只收檔、送進佇列、回 `task_id`，結果另外查。

1. FastAPI 端點驗檔案，送進 `scoring` 佇列，回 envelope 包住的 `{"task_id": "..."}`
2. Celery worker 依序跑 `parse_submission` → `load_answers` → `compute_metrics` → `write_results`
3. `GET /api/v1/submissions/{id}/status` 回任務狀態與結果

:::note{title="Redis 分區與 Celery 參數" collapsible}
Redis 7 同時當 broker、result backend 與應用快取，用 DB 編號隔開：broker `/0`、result `/1`、cache `/2`。快取 DB 的淘汰策略是 `allkeys-lru`；共用實例不設 `maxmemory`。

| 參數 | 值 |
| :--- | :--- |
| 佇列 | 評分走 `scoring`，雜務走 `default` |
| 重試 | 最多三次，退避 60、180、540 秒 |
| 單一評分工作上限 | 300 秒 |
| 結果保留 | result backend 留 24 小時 |
| 收工寬限 | `stop_grace_period` 大於 300 秒；Celery 維持 warm shutdown，不設 `task_acks_late` |

`worker` 與 `backend` 共用同一個 image，所以 NLP 評估套件（`krippendorff`、`seqeval`、`scipy`）要宣告在 `pyproject.toml` 裡。

重試三次代表寫結果那一步會跑不只一次：背景計算的結果表要有「一份輸入最多一份結果」的唯一鍵，寫入用各 dialect 的 `on_conflict` 做 upsert，不先刪後寫（[ADR-003 的 D10](adr/003-backend-architecture.mdx#d10-背景計算的結果寫入做成冪等)）。
:::

## i18n 兩層

支援 `zh-TW`（預設 fallback）與 `en`；前端字串與後端訊息各管各的，不互相抄。

| 層 | 範圍 | 實作 | 規則 |
| :--- | :--- | :--- | :--- |
| 前端 UI 字串 | React 元件直接渲染的文字、前端驗證訊息 | `react-i18next`，依模組分 namespace | 語系檔**不得**放後端 `detail` 字串的副本 |
| 後端回應訊息 | `ErrorResponse` 的 `detail` 與任何回傳給使用者看的字串 | 後端讀 `Accept-Language`，字串放 `app/i18n/<lang>/` | 商業邏輯**不得**內嵌人看得懂的訊息字面值 |

:::note{title="邊界情況" collapsible}
- 前端把後端的 `detail` 當成已本地化的不透明字串直接顯示，不再翻譯或對照 key
- FastAPI 預設的 422 `RequestValidationError` 不在這個契約內，需要本地化時另註冊 handler
- `Accept-Language` 的解析規則（q-value、`*` 通配、`q=0` 拒絕、全部被拒時回 `406`）照抄 ADR-026
:::

## 稽核與可追溯

兩張只新增、不更新也不刪除的表：AI 輔助流程記 `ai_runs`，人發起的領域行為記 `audit_events`；為什麼這樣分見 [ADR-008 的 D5](adr/008-deployment-and-operations.mdx#d5-ai-可追溯用只新增的-ai_runs-表)、[D6](adr/008-deployment-and-operations.mdx#d6-使用者行為記在單一只新增的-audit_events-表)與 [D7](adr/008-deployment-and-operations.mdx#d7-稽核保留至少一個曆年刪除請求就地匿名化同一列)。

| 表 | 記什麼 |
| :--- | :--- |
| `ai_runs` 加其生命週期事件 | AI 輔助流程的 run：模型、prompt 版本、config hash、輸入與輸出快照、工具呼叫、評估結果 |
| `audit_events` | 人發起的領域行為：發布、提交、裁決、投票、成員變更、匯出 |

分界：使用者接受、編輯或拒絕一個 AI 產出，記在 `ai_runs`，不另寫 `audit_events`；人的行為觸發了一個 AI run，則寫 `audit_events` 並帶 `ai_run_id` 關聯。

:::note{title="audit_events 的欄位與保存" collapsible}
| 欄位 | 說明 |
| :--- | :--- |
| `actor_user_id` | 系統行為時為 null |
| `actor_role` | 當時的角色 |
| `action` | 命名空間動詞，例 `task.status_changed` |
| `target_type`、`target_id` | 由註冊表驗證的多型參照，不是實體 FK |
| `task_id` | 任務內的行為才有 |
| `payload_summary` | 去識別化的 JSON |
| `request_id` | |
| `occurred_at` | UTC，伺服器時間 |

- **只新增**：一般 service 寫入只做 insert，update 與 delete 在兩層資料庫都拒絕；要更正就寫新事件
- **保留至少一個日曆年**，沒有自動刪除；任何封存或清除機制都要另外經過審核
- `audit_events` 這個共用表名是 PRD 單數、模組前綴命名慣例的明確例外，不擴及其他表
- 使用者的刪除請求是**就地匿名化同一列**，不把 FK 指向共用墓碑帳號，所以稽核行為人、session、成員身分、歷史與 gold 追溯都保持完整；事件列永遠不刪，過了最短保留期後只能把 PII 欄位墓碑化
:::

## 前端

目錄分 `pages/` 加 `features/`，元件用 shadcn/ui，色值只來自 `tokens.css`；權限一律由後端擋。為什麼是單頁應用、為什麼這樣分層、為什麼用 shadcn/ui、為什麼 token 寫一層對照、為什麼只用 Lucide，見 [ADR-005](adr/005-frontend-architecture.mdx)。

| 面向 | 做法 |
| :--- | :--- |
| 型別 | TypeScript strict，禁止 `any`（Hard Rule 7） |
| 狀態 | 伺服器狀態用 TanStack Query；表單狀態與純 UI 狀態分開放 |
| 目錄分層 | `pages/` 加 `features/` |
| 元件庫 | shadcn/ui 當原語，元件以原始碼形式放進 `components/ui/`；Storybook 未決，見 [§待決](#待決) 第 2 列 |
| 圖示 | **只用** Lucide（`lucide-react`）。不得加入其他圖示庫，不得用 emoji 或自己畫的 SVG 當圖示 |
| design token | 只用語意 token；`frontend/src/styles/` 寫一層對照，把 shadcn 的語意變數指向 `design/prototype/assets/tokens.css`，**`tokens.css` 仍是唯一色值來源**。shadcn 元件不改寫 |
| 畫面狀態 | 每個資料區塊都要寫出 loading、error、empty、無權限（403）四種狀態與被遮蔽欄位的呈現，由 OpenSpec 的 `ui-design` 負責 |
| onboarding | 做空狀態與情境提示；不做導覽與角色導向漸進揭露 |

:::note{title="例外與細節" collapsible}
- Lucide 的例外：prototype 的 HTML 必然把圖示內嵌成 SVG（設計層沒有 npm），只要每個字形都複製自真實的 Lucide 圖示就允許；品牌與 logo 標記（彩色 logo、banner、Google SSO 的 G）不受這條限制
- shadcn 的 dark variant 吃 `html[data-theme="dark"]`，與 prototype 用的屬性相同；色值規則見 `label-suite-design` skill
:::

## 測試分層

三層互補、不重疊：純 UI 邏輯不用 Playwright 測，跨頁旅程不用 Vitest 測；開發一律 TDD。為什麼分三層、前端測試放同目錄、正式 E2E 放根目錄，見 [ADR-007](adr/007-testing-strategy.mdx)。

| 層 | 工具 | 範圍 | 位置 |
| :--- | :--- | :--- | :--- |
| 後端 unit 與 integration | pytest 加 pytest-asyncio 加 httpx | service、router、商業邏輯 | `backend/tests/` |
| 前端元件與 hook | Vitest 加 React Testing Library | 單一元件、hook、角色分派 | 與原始碼同目錄 `*.test.tsx` |
| 正式全端 E2E | Playwright | 跨頁、跨角色的使用者旅程 | 根目錄 `e2e/[module]/[page].spec.ts` |

:::note{title="TDD、fixture 與 prototype 測試" collapsible}
- TDD：先寫會失敗的測試，再寫剛好讓它通過的程式，然後重構。agent 同樣適用，OpenSpec 的 `rules.tasks` 要求測試與實作放在同一個 task，不另拆測試 task
- `e2e/shared/fixtures/` 放各角色的 `storageState` 與 seed helper
- prototype 層的 Playwright 測試不在本 repo：那些測試與 `design/prototype/package.json`、`playwright.config.ts` 依 #16 留在個人 repo；prototype 在本 repo 只當線框，用 `PrototypeFrame` 嵌進規格書
- `data-testid` 的共用契約沿用：prototype HTML 標的 `data-testid` 原字串重用在 React 元件與 `e2e/` 裡
:::

## 部署與維運

Compose 是預設 runtime，Nginx 是唯一公開入口；監控本期不做，備援只做正式層。為什麼這樣選見 [ADR-008](adr/008-deployment-and-operations.mdx)。

| 面向 | 做法 |
| :--- | :--- |
| 本機與 CI | `docker compose up`；CI 用 workflow 的 service container 起 PostgreSQL 與 Redis |
| 正式環境 | Compose 加 Nginx；有的話用 Cloudflare 當 DNS、CDN 與 TLS 邊緣，Nginx 仍要擋安全標頭與隔離內部服務 |
| image | 後端與 worker 共用一個多階段 Dockerfile；前端 build 完由 `nginx:alpine` 服務 `/dist` |
| 寄信 | Resend；沒設 key 時把設定密碼連結印在伺服器 log，由部署者轉給使用者。因此 Lite 層的 log 視為敏感，畫面要讓管理員知道信沒有寄出去（條文見[規格 06-01](../specs/06-admin/01-user-management.mdx#已確認決議) Q9–Q11） |
| 監控 | Prometheus、Grafana、Sentry 本期不做，與 PRD「研究原型、不是生產規模服務」的定位一致；代價是出錯時只能看 log，沒有告警 |
| 備援 | 只做正式層：每日一次 `pg_dump -Fc`，寫到獨立的 backups volume，滾動保留 7 份。Lite 層不做自動備援，使用者自行複製 `./data`。**備份只放在主資料碟上不足以災難復原，異地複製是部署者的責任**；備份檔含測試集答案與個資，存取控制比照原資料庫。為什麼這樣選見 [ADR-008 的 D9](adr/008-deployment-and-operations.mdx#d9-資料備援只做正式層備份產出到獨立-volume) |
| 停機 | `worker` 與 `backend` 的 `stop_grace_period` 都要大於單一評分上限 300 秒，不能留在 Compose 預設的 10 秒；worker 收到 SIGTERM 後不再領新任務，手上的跑完才退。見 [ADR-008 的 D10](adr/008-deployment-and-operations.mdx#d10-worker-收到-sigterm-先做完手上的任務) |
| CI 安全掃描 | 後端 `uv run pip-audit --fail-on high`、前端 `pnpm audit --prod --audit-level high`；SAST（Semgrep）等有程式再接 |
| 相依套件 | dependabot 警示的升級邊界見 [相依套件政策](workflow/dependency-policy.mdx) |
| 發版 | 版號、CHANGELOG、tag、GitHub Release 與 Zenodo DOI 見 `commit-and-release.md` |

:::note{title="安全掃描與分支推進" collapsible}
- Semgrep 上線時至少要蓋兩條專案禁令：CORS 的 `allow_origins=["*"]`，以及寫死的 API key 與 secret（Hard Rule 7、8）
- DAST 與 API fuzzing 先不做，重新討論的條件見 [ADR-008 的 D8](adr/008-deployment-and-operations.mdx#d8-ci-安全掃描先做-scasast-延後)
- 分支與映像推進以 `commit-and-release.md` 為準：目前只有 `main`；staging 與 production 環境存在後改成 `dev` → `release` → `main` 三分支，image 在 `release` 建一次、不重建，`main` 合併後打 `vX.Y.Z` 並在 GHCR 加同 digest 的別名 tag
:::
