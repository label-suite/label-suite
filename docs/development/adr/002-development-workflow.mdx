# ADR-002 開發流程

這份 ADR 管一個 change 的流程骨架：用哪一套產物、維護者在哪裡介入、授權放在哪裡、誰負責哪一步，以及 issue 的狀態記在哪裡。commit 與 PR 的格式、測試與審查的細則不在這裡，見 [commit-and-release.md](../workflow/commit-and-release.md) 與 [testing-agent-rules.mdx](../rules/testing-agent-rules.mdx)。
規則本體在 `AGENTS.md` 的 SDD Workflow 與 Project Board and Dispatch，落地的做法在 [openspec-fullstack-sdd.mdx](../workflow/openspec-fullstack-sdd.mdx)，本文只寫為什麼；衝突時的優先序見 [ADR 索引](index.mdx#衝突時以誰為準)。

## D1 完整九份產物流程一次導入

### 背景

要決定 SDD 流程用哪一套產物、分幾次導入。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 本專案原本用 OpenSpec 內建的 `spec-driven`，只有 proposal、specs、design、tasks 四份產物 | 要在規劃階段加關卡，就得有新的 schema |
| 九份產物的依賴由 OpenSpec CLI 依 schema 強制，`openspec status` 會列出每一份被誰擋住 | 流程的順序靠 schema 保證，不靠 agent 自覺 |
| 沿用的範本與 agent 綁另一套後端框架（NestJS），本專案是 FastAPI | 範本與 agent 要改寫，不能照搬 |
| `ui-design` 與 `api-contract` 的範本允許整份只寫「本次無 UI 變更」「本次無 API 變更」 | `backend/`、`frontend/` 還不存在時，九份流程套在第一個骨架 change 上不會空轉 |
| 個人 repo ADR-033 明文不做每個 change 的 SA、SD、UI-UX 文件，本 repo 的決議相反 | 兩邊說法衝突，必須選一邊 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 九份產物，一次導入 | 依賴由 CLI 強制；`system-design` 與 `ui-design` 可平行；骨架 change 不會空轉 | 十二個 agent、範本與 `openspec/config.yaml` 都要一次建好並改寫成 FastAPI；每個 change 比四份流程多五份產物要產出與審閱 | 採用 |
| B 分三階段導入：現在先做 6 份；可執行的 `backend/` 骨架與 API 出現後 8 份；前端框架定案後 9 份 | 只有 `system-analysis` 與 `clarification` 不依賴 NestJS，`system-design`、`api-contract`、`ui-design` 都綁它，分階段可以等技術棧確定再做 | 新舊兩套流程並存，agent 與人要同時遵守兩套規則 | 不採用：為了避免兩套流程並存 |
| C 維持 `spec-driven` 四份 | 已經在用，不必改 schema | 沒有 `system-analysis`、`system-design`、`ui-design`、`api-contract` 與 `clarification`，也就沒有那個停點的關卡 | 不採用，但保留給文件、工具類的小 change |

### 決定

採用九份產物的 `label-suite-sdd` schema，不分階段導入，並設為 `openspec/config.yaml` 的預設，忘記指定時走較嚴的流程；文件、工具類的小 change 可以帶 `--schema spec-driven` 走四份。規則本體見 `AGENTS.md` 的 SDD Workflow，產物與依賴見 [openspec-fullstack-sdd.mdx 的 §九份產物與依賴](../workflow/openspec-fullstack-sdd.mdx#九份產物與依賴)。

### 後果

**變容易**

- 產物的順序由 `openspec status` 的 `blocked by` 強制，漏寫上游就開不了下游
- 第一個 `backend/` 骨架 change 可以直接走完整流程，不會空轉
- 文件、工具類的小 change 不必產出九份

**變困難**

- 範本、agent 與 `config.yaml` 要一起維護，而且都已改寫成 FastAPI 與本專案的目錄
- 有進行中的 change 時不能改 schema 檔，因為 `requires` 一變，進行中的 change 會多出未完成的產物
- 預設走九份，小 change 要記得自己帶 `--schema spec-driven`，忘了就會多出五份不需要的產物

### 什麼情況要重新討論

- `backend/` 骨架 change 走完之後，九份產物裡有幾份反覆只寫「本次無……」或被略過
- 文件、工具類以外的 change 也開始帶 `--schema spec-driven`

## D2 人工停點只留一個

### 背景

要決定維護者在一個 change 的流程裡，哪幾個點必須親自介入。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 原流程在 propose、apply、archive 三個階段結束時各停一次等使用者確認 | 停點要逐個決定留或不留 |
| 規劃階段的疑問有兩種：需要維護者決定的（Q）與明確的缺陷（P） | 只有 Q 值得叫維護者，P 可以直接回修 |
| `sa` 原本遇到需求依據矛盾或缺漏就停下來回報 | 照做會多出一個停點 |
| 原流程在歸檔前才驗收 | 驗收報告必須在 `/opsx:archive` 之前就產好 |
| 驗收要判的是「每個 Scenario 有沒有被證據覆蓋」 | 那是可機械重現的判定，交給 `acceptance-verifier` 就夠，不必再由人覆驗一次 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 三個階段各停一次：propose、apply、archive 結束時 | 每個階段結束都有人確認 | propose 之後那一停要另外想辦法解除（見 [D3](#d3-授權放在專案自有的指令)） | 不採用 |
| B 兩個停點：clarification 之後逐題問 Q，apply 完成後由維護者親自驗收 | 每個 change 合併前都有人看過 | 維護者成為每一個 change 的瓶頸；而驗收判的是「Scenario 有沒有被證據覆蓋」，那一題人覆驗不會比 `acceptance-verifier` 更準 | 不採用 |
| C `sa` 遇到待決問題就停下回報 | 不會基於有疑問的分析往下做 | 多出一個停點 | 不採用：改成記成待決問題，由 clarify 在那個那個停點次問完 |
| D 驗收留在歸檔前 | 不必改驗收的位置 | 驗收報告來不及在 `/opsx:archive` 之前產好 | 不採用：驗收移到 apply 的最後，`archive` 只留同步主規格與搬檔 |
| E 一個停點：只在 clarification 之後逐題問 Q，驗收通過就自動歸檔並合併 | 維護者只在真的要做決定時被叫；change 不會卡在等人 | 錯誤會直接進 main，靠的是 `acceptance-verifier`、`code-reviewer` 與 CI 三道都沒看漏 | 採用 |

### 決定

只有一個例行的人工停點：在 `clarification.md` 之後，只問需要維護者決定的 Q，P 直接派原角色回修。驗收由 `acceptance-verifier` 判定，通過之後由 `ops` 在合併之前執行 `/opsx:archive`，歸檔改動與程式進同一張 PR，CI 每一個 job 都 completed 且 success、`code-reviewer` 沒有未解決的阻斷意見、PR 可合併 就合併。故障類的中斷不算停點，照停。規則本體見 `AGENTS.md` 的 SDD Workflow「The one checkpoint」，流程見 [openspec-fullstack-sdd.mdx 的 §決議](../workflow/openspec-fullstack-sdd.mdx#決議)與[§故障仍會停](../workflow/openspec-fullstack-sdd.mdx#故障仍會停)。

### 後果

**變容易**

- 維護者在一個 change 裡只被叫一次，其餘的回修、審閱、驗收、歸檔與合併自動進行
- change 不會停在「等人有空驗」的狀態

**變困難**

- 上游矛盾要等到那個停點才浮現，原撰寫角色要回修一輪
- 驗收漏掉的東西會直接進 `main`，攔截全靠 `acceptance-verifier`、`code-reviewer` 與 CI 三道
- `acceptance.md` 的人工驗收步驟仍然必寫，而且沒有人會在合併前替你補上；它改為事後抽查與出事追查的紀錄
- 「只有一個停點」不等於全自動：task 描述有歧義、實作中發現規格有問題、工作超出 `tasks.md` 的範圍、指令出錯，仍然會停下來

### 什麼情況要重新討論

- 出現 `acceptance-verifier` 判為通過、而後續才被發現的缺陷
- 同一類上游矛盾在那個停點之後反覆讓 `sd`、`ui-ux` 或 `proposal` 回修超過一輪
- `backend/` 與 `frontend/` 建立之後：那時驗收要跑真的服務與瀏覽器，機械判定涵蓋得到多少要重新評估

## D3 授權放在專案自有的指令

### 背景

要決定規劃產物完成後，怎麼接著進 apply 而不多停一次；授權寫在哪裡，才不會被 OpenSpec 的更新或 skill 的規則吃掉。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| `openspec-propose` skill 有 planning boundary：規劃完成就停，連請求本身要求實作也不算授權 | 靠請求的措辭授權沒有用 |
| 同一份 skill 明文：`openspec/config.yaml` 的 `context` 不能覆寫 planning boundary | 把授權寫進 `config.yaml` 會被 skill 明文不理 |
| `openspec update` 會覆寫 `.claude/skills/openspec-*/` | 改 skill 本身也不行；實測放進去的標記在 update 之後消失 |
| `openspec update` 不動專案自有的 `.claude/commands/sdd.md` | 這個位置在 update 之後仍然有效 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 在 `config.yaml` 的 `context` 寫「規劃完直接 apply」 | 放在專案設定裡 | skill 明文不理，授權無效 | 不採用 |
| B 改 `openspec-propose/SKILL.md` | 直接改在源頭 | `openspec update` 會整份覆寫 | 不採用 |
| C 專案自有的 `.claude/commands/sdd.md`：不進 propose workflow，直接用 CLI 依 schema 逐份派工，授權範圍寫在 `AGENTS.md` | `openspec update` 不會動它；planning boundary 不會附著 | 要自己維護這個指令；若有人改成呼叫 propose workflow，planning boundary 就重新生效 | 採用 |

### 決定

用選項 C：`/sdd <需求>` 是維護者對單一 change 的授權，涵蓋規劃與實作，不延續到下一個 change；單獨跑 `/opsx:propose` 仍然只授權規劃。授權的範圍與界線見 `AGENTS.md` 的 SDD Workflow「What `/sdd` authorizes」，做法見 [openspec-fullstack-sdd.mdx 的 §三處要特別處理的地方](../workflow/openspec-fullstack-sdd.mdx#三處要特別處理的地方)。

### 後果

**變容易**

- `openspec update` 之後授權仍然有效，不必每次更新都重新補
- 授權的範圍與界線寫在 `AGENTS.md` 一處

**變困難**

- `/sdd` 靠「不進 propose workflow」才成立，指令裡要有防呆：誤進那個 workflow，它的 planning boundary 照樣適用，不能拿 `/sdd` 當跨過停止點的依據
- 每個 change 都要有一次明確的 `/sdd`，授權不會自己延續

### 什麼情況要重新討論

- `openspec update` 之後 `.claude/commands/sdd.md` 被改動或移除
- `openspec-propose` skill 的 planning boundary 條文改變，或 OpenSpec 提供專案層級的授權設定

## D4 規劃、實作、審查與驗收由不同角色負責

### 背景

要決定一個 change 的各步驟由誰做、主 agent 做什麼。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 同一個 session 自己規劃、實作又評估，會出現範圍膨脹、長 session 品質下降、自己給自己打分而放過客觀的失敗 | 規劃、實作與評估要分開 |
| `issue-dispatch` 的合併條件要求一位沒有寫這個變更的審查者通過 | 審查者不能是實作者 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 同一個 session 規劃、實作與評估 | 現狀，不必另外定義角色 | 會出現上面三種失敗 | 不採用 |
| B 三層：Planner、Generator、Evaluator，Evaluator 只用外部的確定性工具、禁止自評 | 範圍在實作前鎖定；評估客觀、可重現 | Planner 的輸出要使用者審過才進 Generator，多一道關；Generator 重啟要重讀整份規格；失敗是二元的 | 不採用：本 repo 以 `AGENTS.md` 的角色表為準，取代的原因沒有記錄；「Evaluator 不自評」由 `code-reviewer` 與 `acceptance-verifier` 承接 |
| C 每一層用獨立的 subagent 呼叫 | 每層的上下文互相隔離 | 增加編排的負擔；個人 repo ADR-017 當時以規模不需要為由延後 | 不採用；本 repo 的角色表（`AGENTS.md` SDD Workflow）另行定義，見決定 |

### 決定

規劃、實作、審查與驗收由不同角色負責，主 agent 只派工：它不自己寫規劃產物（`clarification.md` 是唯一的例外），也不改產品程式。這些角色共用同一張 issue 與同一條分支，依 schema 的順序派工，只有 `system-design` 與 `ui-design` 同時進行。規則本體見 `AGENTS.md` 的 SDD Workflow「Roles」，各角色的定義在 `.claude/agents/`。

### 後果

**變容易**

- 審查者與實作者是不同的角色，「審查通過」是獨立的判斷
- 每份規劃產物有固定的撰寫角色，產物缺了或寫錯，可以派回原角色修正

**變困難**

- 十二個 agent 定義要隨 schema 與 `config.yaml` 一起維護
- 主 agent 不能順手改程式或規劃產物，小修正也要派給對應的角色
- 個人 repo ADR-017 禁止在 Generator 階段使用 `/compact`，`CLAUDE.md` 允許，兩邊相反，本 repo 以 `CLAUDE.md` 為準

### 什麼情況要重新討論

- `backend/` 與 `frontend/` 的第一個 change 走完之後，某個角色從來沒有被派過
- `code-reviewer` 與實作角色之間反覆來回修正超過一輪

## D5 狀態只記在組織層專案板

### 背景

要決定一張 issue 的進度記在哪裡；多個 agent 與維護者要能在同一個地方看到誰在做、做到哪、能不能開工。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 進度可能散在 issue 的標籤、規格階段檔、里程碑文件與各 session 的本機檔案 | 沒有單一處看全部 |
| 多個 session 平行處理不同的 issue，本機檔案會互相覆蓋、另一台電腦也讀不到 | 狀態不能放本機 |
| 本 repo 沒有 `specs/STATUS.md` | 規格階段不需要另一份狀態檔 |
| 一個 issue 能不能開工，要維護者核准 | 狀態要有「已核准」這一格 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A GitHub Projects，組織層，五格 Status | 免費；與 Issue、PR 在同一處，內建 workflow 自動同步 | 沒有離線模式、沒有富文字匯出；檢視（view）的設定目前只能在網頁介面做 | 採用 |
| A2 GitHub Projects，repo 層，十格 Status（個人 repo ADR-027） | 同上 | 一個 repo 一個看板，同一個組織下的其他 repo 看不到；格數多，分不清核准與否、完成與否 | 不採用 |
| B Linear | 使用體驗最好 | 付費（免費版有限）；只靠 webhook 與整合同步，有延遲 | 不採用 |
| C Jira | — | 付費；與 GitHub 只靠 app 同步 | 不採用 |
| D Trello | 免費 | 手動同步，沒有 PR 連結 | 不採用 |
| E Notion Database | 免費版可用 | 手動同步，沒有原生的 issue 同步 | 不採用 |
| F 純 `STATUS.md` | 免費、在 git 裡 | 手動維護，只管規格階段、沒有時程 | 不採用 |

### 決定

用選項 A，而且是組織層的專案 Label Suite，讓 `label-suite` 組織下的 repo 共用一個看板：`Status` 欄（Todo、Ready、In Progress、In Review、Done）是 issue 狀態唯一的紀錄；Ready 是維護者的核准關卡，格數再少就分不清核准與否、完成與否，In Review 涵蓋 PR 階段，不用標籤追蹤狀態，也不另設 `STATUS.md`；相依用 GitHub 的 blocked-by 記，不只寫在內文。卡片進 Ready 要維護者核准。規則本體見 `AGENTS.md` 的 Project Board and Dispatch。

### 後果

**變容易**

- agent 與維護者看同一個欄位；`scripts/dispatch-scan.sh` 可以從 Ready 欄與 blocked-by 找出可以開工的 issue
- 看板上的狀態就是 issue 的狀態，沒有第二份要對照

**變困難**

- 用 `gh` 移動卡片，token 要有 `project` scope
- 檢視的設定只能在網頁介面調，不能寫成腳本
- 做事的 agent 要自己記得移卡片：認領時移 In Progress、開 PR 時移 In Review、合併後移 Done

### 什麼情況要重新討論

- GitHub 提供檢視的 API 之後，檢視的設定可以腳本化
- 看板上的卡片與 issue 的實際狀態反覆對不起來

## D6 後端用 uv、前端用 pnpm

### 背景

兩個語言的執行環境各需要一個套件管理器，而這個選擇直接影響 CI 速度與可重現性。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| CI 要快 | 解析與安裝的速度是主要指標 |
| 建置要可重現 | 必須有 lockfile，不能靠安裝當下的解析結果 |
| `pyproject.toml` 走 PEP 621 | 後端的工具不能自帶另一種專案描述格式 |
| 腳本與 CI 不想先啟用虛擬環境 | 後端的工具要能一行執行（`uv run`） |
| 不要幽靈相依 | 前端的工具要有嚴格解析，npm 的寬鬆解析不符合 |

### 考慮過的選項

後端：

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A uv | Rust 寫的，四個候選裡最快；`uv.lock`；原生支援 PEP 621；有 `uv run` | 2024 才出現，相對新，有些 CI 供應商需要額外設定 | 採用 |
| B pip 加 venv | 來源沒有記錄 | 慢；預設沒有 lockfile；PEP 621 要手動處理；沒有 `uv run` 式的一行執行 | 不採用 |
| C Poetry | 有 `poetry.lock` | 速度中等；自有格式較重；PEP 621 只部分支援；沒有一行執行 | 不採用 |
| D Pipenv | 有 `Pipfile.lock` | 慢；不支援 PEP 621；沒有一行執行；大致已被取代 | 不採用 |

前端：

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A pnpm | 快；用符號連結與硬連結，磁碟占用最小；嚴格解析，沒有幽靈相依；支援 workspace | 需要 contributor 改用 `pnpm add` 而不是 `npm install` | 採用 |
| B npm | 預設就有 | 速度中等；磁碟占用大；沒有嚴格解析 | 不採用 |
| C yarn | 快 | 嚴格模式只部分支援；classic 與 berry 兩個大版本並存 | 不採用 |
| D bun | 四個候選裡最快；磁碟占用最小 | 嚴格模式與 workspace 都只部分支援；仍在成熟中 | 不採用 |

### 決定

後端的 Python 套件用 **uv**，前端的 Node 套件用 **pnpm**。規則本體是 `AGENTS.md` 的 Hard Rule 3。

### 後果

**變容易**

- uv 解析與安裝比 pip 或 poetry 快 10 到 100 倍，CI 快取用 `astral-sh/setup-uv@v5` 就夠
- `uv run` 讓腳本與 CI 步驟不必先啟用虛擬環境
- `uv.lock` 不靠額外工具就給出可重現的建置
- pnpm 的嚴格解析會抓到 npm 會默默放過的幽靈相依
- `pnpm-lock.yaml` 在 CI 快取（`pnpm/action-setup@v4`）上可靠

**變困難**

- contributor 要另外安裝 uv
- 一個倉庫裡兩個套件管理器，contributor 得記得用 `uv add` 與 `pnpm add`
- uv 相對新，有些 CI 供應商需要明確設定

### 什麼情況要重新討論

- `backend/` 或 `frontend/` 的安裝在 CI 上成為最慢的一步
- 要發佈獨立的套件，而選定的工具的發佈流程擋路

## D7 開源開發放在組織的新倉庫

### 背景

Label Suite 要以開源方式開發，而個人倉庫已經累積了論文、會議與 agent 治理的歷史；要決定新倉庫和它的關係。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 個人倉庫已經是公開的 | 「不公開」不是這次要解決的問題 |
| 應用程式碼當時還只是骨架（`backend/` 48 個檔、`frontend/` 32 個檔） | 丟掉程式碼的成本很低，history 不是非留不可 |
| 個人倉庫的 `specs/`、`docs/`、`openspec/` 有 3115 處裸 `#NNN` 參照 | 換倉庫之後裸編號會指錯地方 |
| 四個同類開源專案（doccano、label-studio、argilla、superset）都把前後端放同一個倉庫，而它們的 `docs/` 是使用者文件、不是需求規格 | 新倉庫照收「前後端同一個倉庫」；來源據此主張規格不放 `docs/`，本倉庫沒有照收（見下方的決定） |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 把個人倉庫轉移到組織 | 保住 issue 編號與 history | 會把完整的文件、設計與 agent 工具歷史一起帶進開源倉庫，與乾淨開始相反 | 不採用 |
| B fork 到組織 | 同上 | 同樣帶進歷史，而且 fork 關係會永久連著兩個倉庫 | 不採用 |
| C 在組織開新倉庫 | 外部 contributor 只看到產品本身；幾乎沒有程式碼被丟掉 | 裸 issue 編號要重新限定；兩邊的規格與實作要靠引用對齊 | 採用 |

### 決定

開源開發在組織的新倉庫（本倉庫）進行：history 不匯入，issue 編號從 1 重新開始，版面照 `backend/` 加 `frontend/` 放在根層，授權用 Apache-2.0。

**來源把規格正典留在個人倉庫，本倉庫沒有照收**：`docs/specs/` 就是正典，個人倉庫的 ADR 只當參考。效力記在 [architecture.mdx 的 §附錄：個人 repo ADR 的對照](../architecture.mdx#附錄個人-repo-adr-的對照)，分工記在 [index.mdx 的 §個人 repo 的 ADR](index.mdx#個人-repo-的-adr)。

### 後果

**變容易**

- 開源倉庫沒有論文、會議與 agent 治理的歷史，外部 contributor 只看到產品
- 幾乎沒有應用程式碼被丟掉

**變困難**

- 指向個人倉庫的 issue 要寫成 `singyichen/label-suite#NNN`，裸編號在本倉庫指的是本倉庫的 issue
- 個人倉庫的規格與本倉庫的 `docs/specs/` 一旦都被改，沒有任何機械檢查會發現兩邊分歧

### 什麼情況要重新討論

- 有東西要獨立發佈，根層需要第三個套件目錄
- 個人倉庫的規格又被修改，而本倉庫的 `docs/specs/` 已經是正典
