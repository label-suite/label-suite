# ADR-001 Agent 工程

這份 ADR 管 agent 寫程式時的工程紀律：開工前怎麼找既有實作、碰到錯誤的既有實作怎麼處理。agent 的角色分工與 SDD 流程不在這裡，見 `AGENTS.md` 的 SDD Workflow。
規則本體在 `AGENTS.md` 與 [agent-rules.mdx](../agent-rules.mdx)，本文只寫為什麼；衝突時的優先序見 [ADR 索引](index.mdx#衝突時以誰為準)。

## D1 先搜尋再新增

### 背景

agent 常在已經有同樣功能的地方再寫一份 helper、型別或元件；要決定的是，現在用什麼方式讓「先搜尋」真的發生。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| `backend/`、`frontend/` 還不存在 | 索引既有程式的工具現在沒有東西可索引 |
| 沒有任何 agent hook 接上線，見 [agent-hook-contract.mdx](../agent-hook-contract.mdx) | 用 hook 強制，要先把 hook 的基礎建起來 |
| Session 開始的 hook（H1）只能提醒、不能阻擋 | 在開工那一刻「強制」搜尋，現有的事件做不到 |
| Claude Code 和 Codex 的 hook 能力不一樣 | 只在一邊做得到的強制，另一邊會漏 |
| 「grep 搜過什麼」事後無法從程式驗證 | 證據只能由 agent 自己寫下來，交給審查的人看 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 只靠規則 | 不用任何工具 | 完全靠自覺，審查的人看不到搜過什麼 | 不採用 |
| B 規則加上在 commit body 或 PR 寫明搜過什麼 | 現在就能做；審查的人有東西可以對 | 仍然是人工檢查，寫了不代表真的搜過 | 採用 |
| C 元件索引加上查詢工具：新增前先查有沒有相近的元件，附相似度 | 搜尋變便宜，結果可以重現 | 沒有程式可索引，現在建只是空殼 | 延後：`frontend/` 的第一個模組合併之後 |
| D 開分支或開 session 時用 hook 強制先搜尋 | 不靠自覺 | 現有事件只能提醒；兩個平台不一致；要先寫 hook 契約 | 延後：hook 契約另案處理 |

### 決定

現在用選項 B：開工前先讀那一區既有的匯出、呼叫端與共用工具，新增 helper、型別、常數或相依套件時，在 commit body 或 PR 寫明搜過什麼。規則本體見 [agent-rules.mdx 的 R1](../agent-rules.mdx#r1-先搜尋再新增)。

### 後果

**變容易**

- 審查的人有搜尋紀錄可以對，「這裡已經有一個了」可以在 review 指出來
- 在還沒有程式的時候，不必先維護一套索引工具

**變困難**

- 仍然靠 agent 照實寫；寫了搜過、其實沒搜，只有審查的人看得出來
- PR 多一段要寫、也多一段要讀

### 什麼情況要重新討論

- `frontend/` 或 `backend/` 的第一個模組合併之後：評估選項 C
- agent hook 契約接上線之後：評估選項 D
- review 發現重複的 helper，而那張 PR 寫了「搜過、沒有」

## D2 範圍內直接修正錯誤實作

### 背景

新的改動常會碰到寫錯的既有實作；要決定的是，agent 應該繞過它、另加一條規則補救，還是直接修掉它。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| [R3 最小變更](../agent-rules.mdx#r3-最小變更)：每一行改動都要追得到請求 | 修既有實作要有清楚的界線，不能變成順手重構 |
| 一張 PR 只有一個目的（`AGENTS.md` §Pull Requests） | 修正要和這次的目的同一件事，不能另起一件 |
| 在錯誤實作上疊規則或繞道，規則和繞道只會越來越多 | 只提出來、不修，錯誤會被新程式依賴得更深 |
| [R6 範圍鎖定](../agent-rules.mdx#r6-範圍鎖定後不得以-yagni-刪驗收條件)：已承諾的驗收條件不能縮 | 修正只能加，不能拿來當刪驗收條件的理由 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 一律只提出來、另開 issue（原本 R3 的做法） | diff 最乾淨 | 新程式得繞過錯誤實作，繞道留在程式裡；常常變成再加一條規則補救 | 不採用 |
| B 看到錯就修 | 錯誤最快消失 | diff 漂出範圍，PR 失去單一目的，違反 R3 | 不採用 |
| C 這次改動會碰到的程式路徑內直接修，其餘照 R3 | 錯誤在被依賴之前就修掉；範圍有界線 | 審查的人要判斷修正是不是真的在路徑上 | 採用 |
| D 先把修正加進 issue 的工作項才能修 | 每一項修正都可追溯 | 每次都要回 issue 補一項，成本高，實際上常被省略、改成繞道 | 不採用 |

### 決定

這次要改的行為所呼叫、修改或取代的既有實作如果是錯的，就在同一張 PR 直接修，不加繞道、不另加規則補救，並在 PR 寫明修了什麼、為什麼是錯的；碰不到的地方照 R3，只提出來、另開 issue。規則本體見 `AGENTS.md` 的 Required Behaviors，落地說明見 [agent-rules.mdx 的 R3](../agent-rules.mdx#r3-最小變更)。

### 後果

**變容易**

- 錯誤實作不會被新程式依賴得更深
- 規則數量不會因為補救錯誤實作而一直增加

**變困難**

- 審查的人要判斷每一處修正是不是在這次改動的路徑上
- 修正改到的行為若還有其他呼叫端，這張 PR 要一併顧到，diff 會變大

### 什麼情況要重新討論

- review 一再發現 PR 用這個例外把範圍外的改動帶進來
- 某次路徑內的修正弄壞了其他呼叫端
