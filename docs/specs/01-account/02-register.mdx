## 目標

- 讓還沒有帳號的人自己建立帳號成為 :ref[平台成員]{id="term.platform-member"}，不必等 :ref[系統管理員]{id="term.system-admin"} 邀請
- 在送出之前就把填錯的地方指出來，讓使用者不必送出失敗才知道哪裡要改
- 把密碼的組成規則寫在欄位旁邊，讓使用者第一次就設得出合格的密碼

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

這一頁在登入之前，沒有任何角色能從它讀到或改到既有的業務資料。

- 未登入的訪客：R（只有這一頁本身的內容）／C（建立一個自己的帳號）；讀不到任何既有資料，也不能編輯或刪除任何東西
- :ref[平台成員]{id="term.platform-member"}：自行註冊建立的帳號，:ref[系統角色]{id="term.system-role"} 一律是平台成員（PRD §使用者角色）；這一頁不能選角色
- :ref[系統管理員]{id="term.system-admin"}、:ref[Seeder 管理員]{id="term.seeder-admin"}：不從這一頁產生。管理員要替別人開帳號走 [規格 06-01 使用者管理](../06-admin/01-user-management.mdx)
- 已經登入的人直接開這一頁 → **直接前往儀表板**，比照 [規格 01-01 §已確認決議](./01-login.mdx#已確認決議) Q3

## 規格

### 註冊頁的內容

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者開啟註冊頁 → 顯示頁首（品牌與語言切換）與註冊卡片
2. 卡片裡依序是：標題與副標、姓名欄、Email 欄、密碼欄（下方有組成規則的提示）、確認密碼欄、「建立帳號」按鈕
3. 卡片底部顯示「已有帳號？」與「返回登入」
4. 頁首的語言切換鈕上只顯示目前語言的代號：繁體中文顯示 `ZH`、英文顯示 `EN`

### 填寫與送出

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者填好四個欄位 → 點「建立帳號」
2. 四欄都通過檢查 → 送出按鈕停用並顯示進行中的指示，避免重複送出
3. 送出成功 → **一律顯示「驗證信已寄出」**，見[§驗證信已寄出](#驗證信已寄出)
4. 第 3 條**不論那個 Email 原本有沒有帳號都顯示同一句話**（[§已確認決議](#已確認決議) Q1）
5. 使用者點信裡的連結 → 帳號建立完成，見[§註冊成功](#註冊成功)

- 這一頁建立的帳號一律是平台成員，頁面上沒有選角色的地方
- 送出按鈕停用期間使用者仍可以看到自己填的內容
- 第 4 條是刻意的：**送出表單不等於完成註冊**，而且不透露那個 Email 的狀態

### 欄位檢查與錯誤

<PrototypeFrame page="account/register" caption="註冊" client:idle />

所有能在送出前就判斷的錯誤都在送出前擋下，而且顯示在出問題的那一欄旁邊。

1. 任一欄沒填 → 該欄旁顯示必填的說明
2. 姓名去掉前後空白後為空 → 視為沒填，顯示必填的說明
3. Email 的格式不合法（沒有 `@` 或沒有網域） → Email 欄旁顯示格式的說明
4. 密碼不符合組成規則 → 密碼欄旁顯示規則的說明（見 [§規格 › 密碼規則](#密碼規則)）
5. 確認密碼和密碼不一致 → 確認密碼欄旁顯示不一致的說明
6. 姓名超過 **100 字** → 姓名欄旁顯示長度的說明，不送出（[§已確認決議](#已確認決議) Q4）
7. 使用者在報錯的欄位重新輸入 → 那一欄的錯誤立刻消失
8. 送出之後平台沒有回應 → 顯示一句可以重試的說明，四欄已填的內容**保留**（[§已確認決議](#已確認決議) Q3）

- 姓名與 Email 都在檢查前先去掉前後的空白
- 姓名的長度是 **1–100 字**，與[規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位)、[規格 01-04](./04-profile.mdx#已確認決議) Q3 **三處同一個規則**（[§已確認決議](#已確認決議) Q4 取代原本的 Q6）

### 密碼規則

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者看到密碼欄 → 下方直接顯示組成規則：**至少 8 個字元，含大寫英文、小寫英文與數字**
2. 使用者填的密碼不符合 → 密碼欄旁顯示規則的說明，不送出
3. 使用者切換語言 → 規則的提示也換成另一種語言

- 規則寫在欄位旁邊而不是等送出才說，使用者第一次就設得出合格的密碼
- 這一頁顯示規則；[規格 01-01 登入](./01-login.mdx) 刻意不顯示，因為登入不是設定密碼的時機

### 驗證信已寄出

<PrototypeFrame page="account/register" caption="註冊" client:idle />

送出表單只走到這裡，**帳號還沒有建立**。

1. 送出成功 → 卡片換成「驗證信已寄出」的說明，四個欄位都停用
2. 這一句**不論那個 Email 原本有沒有帳號都一樣**：有帳號的人收到的是一封說明已有帳號的信，沒有帳號的人收到的是驗證連結——**畫面上看不出差別**（[§已確認決議](#已確認決議) Q1）
3. 使用者切換語言 → 這一段說明也跟著換

- 帳號 Email 的長度上限與大小寫規則見 [規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位)：不分大小寫、最多 254 字。比對前要怎麼統一寫法（正規化的做法）由 [規格 01-05 §Email 的識別規則](./05-login-state.mdx#email-的識別規則) 定義，本頁不重複定義
- **原本的「Email 已被使用」那一段不存在了。** 它會揭露「某個 Email 已經在平台註冊過」，而 [規格 01-01 §登入失敗](./01-login.mdx#登入失敗) 刻意不揭露同一件事——任何人在註冊頁輸入一個 Email 就能得到確答，登入頁的保護因此失效。寄驗證信同時解掉這個抵銷（[§已確認決議](#已確認決議) Q1）
- <mark>這一段的文案**來源沒有**，由維護者 2026-11-12 裁定（提案的選項 A）：標題「驗證信已寄出」，說明「我們已經寄了一封信到 `{email}`。請打開信件並點裡面的連結，你的帳號會在那時候建立。」，另一行「沒收到的話，看一下垃圾郵件匣。」**刻意不提連結的有效期**——本頁沒有定義註冊這個連結能撐多久，寫上去就是憑空造一個數字。</mark><sup>[#291](https://github.com/label-suite/label-suite/issues/291)</sup>

### 註冊成功

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者點驗證信裡的連結、而且連結可用 → **帳號在這一刻才建立**
2. 接著 → 使用者**直接進入儀表板**，不必再輸入一次密碼（[§已確認決議](#已確認決議) Q2）
3. 連結不能用（過期、已用過、已被作廢）→ 顯示的訊息與處理方式與[規格 01-03](./03-reset-password.mdx)的一次性連結**同一套**，見那一頁

- 第 2 條的理由：密碼在送出表單時就設好了，再要他輸入一次是多一道手續；而「他記不記得密碼」在他下一次登入就會驗證
- 第 1 條把「帳號什麼時候存在」講清楚：**送出表單不建立帳號**，所以同一個 Email 連點兩次註冊不會產生兩個帳號
- 這一節描述的是**驗證連結落地的那一頁**（`design/prototype/pages/account/verify-email.html`），不是上面那個註冊表單。線框暫時還指著註冊表單：那一頁載入兩秒後就會前往儀表板、而且會寫下登入旗標，嵌在規格裡會變成讀者看不到面板、還被導離登入與註冊頁；要看它請直接開檔並加 `?sim_hold=1`。畫面那一側要先補一道「被嵌在框裡就不要跳轉」的保護（追蹤在 [Issue #297](https://github.com/label-suite/label-suite/issues/297)），之後再把這個線框改指過去。
- <mark>這一節的文案**來源也沒有**，由維護者 2026-11-12 裁定：連結可用時顯示「帳號已建立」與「正在帶你前往儀表板…」；連結不能用時與 01-03 **共用同一句**「連結無法使用，請重新申請」，差別只在按鈕回**註冊頁**（01-03 那邊是回申請頁）。</mark><sup>[#291](https://github.com/label-suite/label-suite/issues/291)</sup>

## 卡控機制

| 條件 | 結果 |
| :--- | :--- |
| 姓名或 Email 去掉前後空白後為空 | 擋下送出，該欄旁顯示必填的說明 |
| 密碼或確認密碼未填 | 擋下送出，該欄旁顯示必填的說明；這兩欄不去空白，全是空白字元時走組成規則或不一致的檢查 |
| Email 格式不合法 | 擋下送出，Email 欄旁顯示格式的說明 |
| 密碼不符合組成規則 | 擋下送出，密碼欄旁顯示規則的說明 |
| 確認密碼與密碼不一致 | 擋下送出，確認密碼欄旁顯示不一致的說明 |
| Email 已經有人使用 | **畫面不得顯示任何不同**——一律是「驗證信已寄出」；那個 Email 收到的是一封說明已有帳號的信 |
| 姓名超過 100 字 | 擋下，姓名欄旁顯示長度的說明 |
| 送出表單 | **不建立帳號**；帳號只在驗證連結被點過之後才建立 |
| 正在送出中 | 送出按鈕停用並顯示進行中的指示，只會送出一次 |
| 註冊成功後 | 四個欄位都停用，不能再改 |
| 使用者想選自己的系統角色 | 畫面上沒有這個選項；一律是平台成員 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到什麼 |
| :--- | :--- |
| 姓名只填空白字元 | 視為沒填，顯示必填的說明 |
| Email 前後有空白 | 先去掉空白再檢查，不因為空白被判格式錯誤 |
| 密碼有 8 個字元但全是小寫 | 顯示規則的說明，不送出 |
| 兩欄密碼都填了但不一致 | 確認密碼欄顯示不一致的說明，密碼欄不報錯 |
| 多個欄位同時出錯 | 每一欄各自顯示自己的說明，不是只顯示第一個 |
| 正顯示「驗證信已寄出」時切換語言 | 那一段說明跟著換語言，不會消失——送出已經完成 |
| 註冊成功後想再改欄位 | 欄位已停用，改不了 |
| 送出後平台沒有回應 | 顯示一句可以重試的說明；四欄的內容都還在，使用者可以重試 |
| 瀏覽器不讓平台記住語言，或記住的值不是兩種語言之一 | 當成繁體中文，不出現錯誤畫面 |
| 兩個人幾乎同時用同一個 Email 送出 | 兩邊看到的都是同一句「驗證信已寄出」；帳號最多只會建立一個，而那要等其中一個連結被點過 |

## 已確認決議

### Q1. 自行註冊要不要有門檻？（已定案，維護者裁定 2026-11-09）

- [x] 要：送出後寄一封驗證信到那個 Email，**點了連結才算完成註冊**
- [ ] 要：改成只接受特定 Email 網域
- [ ] 不要：填完就直接有帳號

> 理由：原本的流程**任何人都能用別人的 Email 註冊**——來源完全沒有驗證 Email 所有權的步驟，而[規格 06-01](../06-admin/01-user-management.mdx)由管理員邀請的帳號反而要靠一封設定密碼信才能用密碼登入，兩條路的把關強度不一致。PRD §假設與限制 也寫「使用者主要是實驗室成員，人數在數十人以內」，但完全開放的自行註冊和這個假設對不上。
> **這一條同時解掉一個跨頁矛盾**：原本的「這個 Email 已經有人使用」會揭露某個 Email 註冊過沒有，而[規格 01-01 §登入失敗](./01-login.mdx#登入失敗)刻意不揭露同一件事——任何人在註冊頁輸入一個 Email 就能得到確答。寄驗證信之後**送出一律顯示「驗證信已寄出」**，畫面上看不出那個 Email 原本的狀態，所以 01-01 的保護不再被抵銷。
> 落在[§填寫與送出](#填寫與送出)第 3、4 條與[§驗證信已寄出](#驗證信已寄出)；<mark>畫面那一側已於 2026-11-12 落地（[Issue #195](https://github.com/label-suite/label-suite/issues/195)，[PR #290](https://github.com/label-suite/label-suite/pull/290)）。</mark><sup>[#291](https://github.com/label-suite/label-suite/issues/291)</sup>

### Q2. 註冊成功後是直接進入儀表板，還是回登入頁自己登入？（已定案，維護者裁定 2026-11-09）

- [x] **點驗證連結後直接進入儀表板**，不必再輸入一次密碼
- [ ] 回到登入頁，請使用者用剛設定的密碼登入一次
- [ ] 密碼改到驗證後才設

> 理由：#195 之前 prototype 的成功訊息寫「帳號建立成功！正在導向儀表板…」，來源也導向儀表板——但來源把它標成「原型行為」，沒有說這是業務決定。（**那一句畫面上已經沒有了**：送出只顯示「驗證信已寄出」，而帳號建立的訊息改在落地頁，文案見[§註冊成功](#註冊成功)。）
> Q1 把流程改成寄驗證信之後，「送出表單」與「完成註冊」已經是兩件事，所以這一題問的其實是**點完連結之後**要不要再登入一次。裁定直接進儀表板：密碼在送出表單時就設好了，再要他輸入一次是多一道手續，而「他記不記得密碼」在他下一次登入就會驗證。
> 落在[§註冊成功](#註冊成功)第 2 條（#183）。

### Q3. 送出後平台沒有回應時顯示什麼？（已定案，維護者裁定 2026-11-09）

- [x] 顯示一句可以重試的說明，四欄內容保留
- [ ] 其他

> 理由：來源因為只做前端原型（明寫尚未串接真實註冊）沒有定義「送出失敗」。這是**帳號模組四頁統一**的裁決（另見[規格 01-01](./01-login.mdx#已確認決議) Q1、[規格 01-03](./03-reset-password.mdx#已確認決議) Q5、[規格 01-04](./04-profile.mdx#已確認決議) Q9）。
> 落在[§欄位檢查與錯誤](#欄位檢查與錯誤)第 8 條與 §業務流程 的 E2（#183）。

### Q4. 自行註冊的姓名要不要比照 06-01 的 1–100 字？（已定案，維護者裁定 2026-11-09，**取代 Q6**）

- [x] 要，**三頁統一成 1–100 字**
- [ ] 不要，自行註冊沿用來源的「不加上限」

> 理由：[規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位)的姓名規則是「1–100 字」，而且它寫在**帳號實體的欄位表**裡、不是只管管理員新增的那條路；本頁的來源則明訂「不加長度上限」。
> 不統一的代價：同一個帳號的姓名因為建立途徑不同而有不同上限，日後在使用者管理的列表上會看到超過 100 字的姓名、**而管理員改不動它**；側欄與列表的呈現也會被撐壞。
> 三頁用同一個答案（另見[規格 01-04](./04-profile.mdx#已確認決議) Q3）。
> ⚠️ **這一條取代本頁原本的 Q6**（「不加上限，只要求去掉前後空白後非空」）。依 `spec-writing` 步驟 5 第 5 點，Q6 保留在下面、標註被這一條取代（#183）。

### Q5. 密碼的組成規則是什麼？（已定案，沿用舊來源 2026-05-06）

- [x] 至少 8 個字元，含大寫英文、小寫英文與數字
- [ ] 只限制長度

> 理由：舊來源的規格常數 `PASSWORD_RULE` 寫明「至少 8 個字元，含大寫英文、小寫英文與數字」，使用者故事 2 的驗收情境也逐字複述；`FR-007` 定長度、`FR-007A` 要求在欄位旁顯示。依搬移設計文件的 D5 以來源現況為準，prototype 的密碼提示文字與它逐字相同。
> **這條規則正是 [規格 01-01 §已確認決議](./01-login.mdx#已確認決議) Q8 在等的對照**（登入要不要檢查密碼組成）——那一題已於 2026-11-09 裁定為**登入不檢查**，而[規格 01-03 §已確認決議](./03-reset-password.mdx#已確認決議) Q3 裁定**重設時要套同一套**（#70、#183）。

### Q6. 姓名要不要長度上限？（已定案，沿用舊來源 2026-05-22；**已被 Q4 取代**）

- [x] 不加上限，只要求去掉前後空白後非空
- [ ] 加上限

> ⚠️ **這一條已被上面的 Q4 取代**（維護者裁定 2026-11-09：三頁統一成 1–100 字）。依 `spec-writing` 不刪既有決議，原文保留在這裡。
> 原本的理由：舊來源的 Clarifications 已拍板「必填加去空白後非空，**不加長度上限**」。
> 原本的註記：這和 [規格 06-01](../06-admin/01-user-management.mdx) 的「姓名 1–100 字」不一致——那個不一致正是 Q4 解掉的（#70、#183）。

### Q7. 送出中要不要防重複送出？（已定案，沿用舊來源 2026-05-22）

- [x] 送出按鈕切換為停用，直到流程結束
- [ ] 不處理

> 理由：舊來源的 Clarifications 已拍板。與 [規格 01-01](./01-login.mdx) 的送出中處理一致，只是 01-01 進一步要求全頁不可互動（那是 01-01 來源自己的條文，本頁來源沒有）（#70）。

### Q8. 卡片上方的說明要怎麼關掉？（已定案，沿用舊來源 2026-05-22）

- [x] 沒有手動關閉的按鈕；使用者重新輸入任何欄位時自動清除
- [ ] 提供關閉按鈕

> 理由：舊來源的 Clarifications 已拍板。使用者要讓說明消失的唯一理由就是去改錯誤，所以「改了就消失」比多一個關閉按鈕直接（#70）。

### Q9. 註冊的帳號是什麼系統角色？（已定案，PRD §使用者角色）

- [x] 一律是平台成員
- [ ] 可以選擇

> 理由：PRD §使用者角色 寫「平台成員：自行註冊或由系統管理員邀請加入」，而系統管理員只能由管理員指派（見 [規格 06-01](../06-admin/01-user-management.mdx)）。讓使用者自己選角色會讓任何人都能註冊成管理員（#70）。

## Q&A

:::tip{title="為什麼密碼規則寫在欄位旁邊，登入頁卻刻意不寫？" collapsible}
兩頁的使用者處境不同。註冊的人正在**設定**一個密碼，規則寫出來他第一次就設得對，不必靠送出失敗來猜。登入的人是在**回想**一個已經設好的密碼，規則對他沒有幫助，卻會讓任何打得開登入頁的人問出平台的密碼政策。
:::

:::tip{title="為什麼送出表單還不算完成註冊？" collapsible}
因為沒有這一步的話，**任何人都能用別人的 Email 註冊**——來源完全沒有驗證 Email 所有權的步驟。而且舊的做法還有一個副作用：為了告訴使用者「這個 Email 已經有人用」，註冊頁必須揭露某個 Email 註冊過沒有，而登入頁刻意不揭露同一件事。任何人在註冊頁輸入一個 Email 就能得到確答，登入頁的保護因此失效。

寄驗證信同時解掉這兩件事：所有權由「收得到那封信」證明，而送出後一律顯示同一句話，畫面上看不出那個 Email 原本的狀態。
:::

:::tip{title="為什麼註冊成功後要把欄位停用？" collapsible}
成功訊息顯示之後還有一段導向的時間。那段時間裡欄位如果還能改，使用者會以為自己還在編輯、改了有效，但帳號其實已經用剛才送出的內容建好了。停用欄位讓畫面和事實一致。
:::
