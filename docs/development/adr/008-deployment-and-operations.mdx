# ADR-008 部署與維運

這份 ADR 管系統怎麼部署與運作、出錯時看什麼、資料壞掉怎麼救、重啟時進行中的工作怎麼辦、AI 與使用者行為怎麼留下紀錄、個資怎麼匿名化，以及 CI 怎麼掃安全問題。認證與授權不在這裡，見 [ADR-004](004-auth-and-security.mdx)；資料庫與背景工作的選型見 [ADR-003](003-backend-architecture.mdx)；測試分層見 [ADR-007](007-testing-strategy.mdx)。
規則本體在 `AGENTS.md`、[security-agent-rules.mdx 的 S9](../rules/security-agent-rules.mdx#s9-稽核脫敏與保留) 與 [backend-agent-rules.mdx 的 B8](../rules/backend-agent-rules.mdx#b8-刪除軟刪除與匿名化)，落地的做法在 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)與 [§稽核與可追溯](../architecture.mdx#稽核與可追溯)，本文只寫為什麼；衝突時的優先序見 [ADR 索引](index.mdx#衝突時以誰為準)。

## D1 Compose 加 Nginx 當 runtime，Cloudflare 可選

### 背景

要決定系統在本機、CI 與正式環境用什麼方式跑起來。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：環境要可重現、彼此隔離，而且能在 CI 跑 | 每個服務要有容器化的定義 |
| 來源記錄：所有服務（資料庫、Redis 等）都有狀態 | 容器化時要處理資料的持久儲存 |
| 來源記錄：Demo Paper 要能用一個指令啟動（來源的前提，見附錄） | 啟動步驟不能比一個指令多 |
| 來源記錄：開發者只有一人、沒有 Kubernetes 經驗（來源的前提，見附錄） | 運維負擔重的方案先排除 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A Docker 加 Compose，前面放 Nginx | 來源記錄：Docker 對 FastAPI 加 Celery 加 Redis 的文件最多；Nginx 較簡單，也有最多文件，適合服務靜態檔與明確的 API 轉發 | 見後果的變困難 | 採用 |
| B Kubernetes（含 Ingress） | 來源記錄：映像檔之後仍可搬過去 | 來源記錄：運維負擔大，要管叢集、manifest、ingress 與 secrets，對「單人研究系統的 MVP 階段」過重（來源的前提，見附錄） | 不採用 |
| C Podman | 來源記錄：沒有記錄好處 | 來源記錄：預設 rootless，增加 volume 權限的複雜度，文件也不如 Docker 多 | 不採用 |
| D 裸機或單台 VM 加 systemd | 來源記錄：沒有記錄好處 | 來源記錄：PostgreSQL 與 Redis 要手動安裝、環境不可重現，失去隔離 | 不採用 |
| E Compose 加 Traefik | 來源記錄：沒有記錄好處 | 來源記錄：用不到動態服務發現；服務靜態檔與明確的 API 轉發，Nginx 較簡單 | 不採用 |
| F 只用 PaaS | 來源記錄：沒有記錄好處 | 來源記錄：降低可重現性，並綁定供應商的 buildpack 與網路 | 不採用 |

### 決定

Compose 是預設 runtime，Nginx 是唯一公開入口；有 Cloudflare 時用它當 DNS、CDN 與 TLS 邊緣，Nginx 仍要擋安全標頭、做路由並隔離內部服務；Cloudflare 到 origin 這一段用 Full (strict) TLS 模式，origin 裝 Cloudflare Origin CA 憑證。每個環境怎麼起、CI 怎麼起服務見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)，分支與映像推進見 [commit-and-release.md](../workflow/commit-and-release.md)。

### 後果

**變容易**

- 本機、CI 與正式環境都用容器定義，環境可重現、彼此隔離
- 映像檔仍可搬到別的編排工具

**變困難**

- 貢獻者要裝 Docker；來源記錄 macOS 的 volume I/O 較慢
- 資料庫 migration 要在 backend 容器內執行；多容器的 log 要合併來看
- 沒有 Kubernetes 的自我修復與自動擴展；來源記錄零停機部署的能力有限
- 有 Cloudflare 時多一道代理邊界，要確認它和 Nginx 的行為一致
- origin 要安裝 Cloudflare Origin CA 憑證；憑證怎麼放進 Nginx、怎麼更新，留到正式部署的 change 再寫

### 什麼情況要重新討論

- 要在多台主機上執行，或需要自我修復與自動擴展時
- 單人維運的前提不再成立（例如有了專職維運）時

## D2 後端與 worker 共用一個 image

### 背景

要決定 API 與 Celery worker 是各自建一個 image，還是共用。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：多出一份 image 就多一個要維護的建置產物 | 偏向共用 |
| 來源記錄：API 與 worker 要跑相同的 Python 環境 | 偏向共用 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 共用一個多階段 Dockerfile，worker 用同一個 image | 來源記錄：少一份建置產物，API 與 worker 的 Python 環境相同 | 見後果的變困難 | 採用 |
| B worker 另寫 Dockerfile（推論） | 來源沒有記錄 | 來源記錄：要多維護一份建置產物，兩邊的 Python 環境可能不同 | 不採用 |

### 決定

後端與 worker 共用同一個 image，不另寫 worker 的 Dockerfile；前端 build 完由 `nginx:alpine` 服務 `/dist` 的做法見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)。

### 後果

**變容易**

- 只維護一份後端建置產物；API 與 worker 跑同一份 Python 環境

**變困難**

- worker 用到的套件（例如 NLP 評估的套件）要宣告在後端同一份 `pyproject.toml`，見 [architecture.mdx 的 §非同步任務](../architecture.mdx#非同步任務)

### 什麼情況要重新討論

- worker 需要與 API 不同的執行環境，同一份相依套件宣告放不下時

## D3 寄信用 Resend，沒設 key 時把連結印到 log

### 背景

系統要寄設定密碼信，同時有些部署（例如 Lite 層）不會設定寄信服務。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：要有一個郵件服務，設定步驟越少越好 | 偏向只要一把 key 的服務 |
| 來源記錄：個人帳號的 SMTP 受 2FA 與供應商政策牽制 | 不用個人帳號的 SMTP |
| 規格 06-01 記錄：沒有設定寄信服務是 Lite 層的常態，不是故障 | 沒有 key 時不能讓新增帳號整個失敗，見[規格 06-01 的 Q9](../../specs/06-admin/01-user-management.mdx#已確認決議) |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A Resend | 來源記錄：有官方 SDK，免費額度每月 3,000 封、每日 100 封，設定只要一個 `RESEND_API_KEY` | 外部 SaaS 依賴；要設定 SPF 與 DKIM 才有送達率；要有 token 儲存 | 採用 |
| B Brevo、SendGrid | 來源記錄：Brevo 走 SMTP relay | 來源記錄：設定更多，在這個規模沒有明顯優勢 | 不採用 |
| C Gmail SMTP | 來源記錄：沒有記錄好處 | 來源記錄：綁個人帳號，要 2FA 加 App Password，Google 可能撤銷；有供應商政策風險 | 不採用 |
| D 不寄信，由管理員重設 | 來源記錄：沒有記錄好處 | 來源記錄：運維負擔無法接受 | 不採用 |

### 決定

用 Resend 寄信，`RESEND_API_KEY` 是可選設定；沒設 key 時，把設定密碼連結印在伺服器 log，由部署者轉給使用者，所以 Lite 層的 log 視為敏感，畫面也要讓管理員知道信沒有寄出去。降級路徑的形狀與 Google SSO 的可選整合一致（[ADR-004 的 D4](004-auth-and-security.mdx#d4-google-sso-直接走-oidc)），畫面條文見[規格 06-01 的 Q9 至 Q11](../../specs/06-admin/01-user-management.mdx#已確認決議)。信由 API 還是 worker 寄出，見 [architecture.mdx 的 §容器視圖](../architecture.mdx#容器視圖c4-第二層)；沒有 key 時自行註冊走不通，見 [architecture.mdx 的 §待決](../architecture.mdx#待決)第 2 列。

### 後果

**變容易**

- 沒有郵件服務的部署仍然能建立帳號

**變困難**

- 多一個外部 SaaS 依賴，以及 SPF、DKIM 的設定
- 要有 token 儲存
- Lite 層的 log 含可用的設定密碼連結，必須當敏感資料處理
- 沒有 key 時，連結要由部署者手動轉給使用者

### 什麼情況要重新討論

- 免費額度（每月 3,000 封、每日 100 封）不夠用時
- 部署形態改變，Lite 層的 log 不再能當敏感資料控管時（本節的重新討論條件是推論）

## D4 觀測性只做 ai_runs，監控與錯誤追蹤本期不做

### 背景

要決定出錯時用什麼工具追查：架設指標與錯誤追蹤，還是只靠 log 與 AI 稽核表。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 維護者裁定：`ai_runs` 不是運維工具，而是研究可追溯性 | 它不能拿來當監控的替代品，所以要明說監控沒做 |
| PRD 的定位是研究原型，不是生產規模服務 | 監控與告警的投入不在本期範圍 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A Prometheus 加 Grafana（自架） | 來源記錄：指標與儀表板表現佳，告警走 Alertmanager | 來源記錄：運維負擔中等 | 本期不做 |
| B Sentry（錯誤追蹤） | 來源記錄：前端、後端與 Celery 的錯誤與 source map 表現佳，運維負擔低到中等 | 來源沒有記錄代價 | 本期不做 |
| C 託管服務（Grafana Cloud、Datadog、New Relic） | 來源記錄：運維負擔低 | 來源記錄：Grafana Cloud 多一個外部帳號、網路依賴與成本保留考量；Datadog 與 New Relic 有成本與廠商鎖定 | 不採用 |
| D ELK 或 OpenSearch | 來源記錄：集中 log 有用 | 來源記錄：不能取代以指標為基礎的告警，儲存與調校負擔大 | 不採用 |
| E Sentry 的替代品（GlitchTip、Rollbar、只用 OpenTelemetry collector） | 來源記錄：GlitchTip 相容 Sentry 且可自架 | 來源記錄：Sentry 的 SDK 文件、release 工具與 source map 支援較廣；Rollbar 對現有技術棧的契合度不如 Sentry；OpenTelemetry collector 不能取代 issue 分組、release 回歸追蹤與前端 source map | 不採用 |
| F 只看 log，加 `ai_runs` | 來源記錄：運維負擔低 | 來源記錄：沒有儀表板與告警；維護者裁定記錄的代價是出錯時只能看 log | 採用 |

### 決定

觀測性只做 `ai_runs`，Prometheus、Grafana 與 Sentry 本期不做；代價是出錯時只能看 log、沒有告警。落地的寫法見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)。

### 後果

**變容易**

- 不必維運指標、儀表板或錯誤追蹤的服務

**變困難**

- 出錯時只能看 log，沒有告警
- 沒有指標與儀表板

### 什麼情況要重新討論

- 定位從研究原型變成要對外提供的服務時
- 出錯但看 log 追不到原因，已經影響到使用者時（本節的重新討論條件是推論）

## D5 AI 可追溯用只新增的 ai_runs 表

### 背景

AI 輔助流程（產生、評估、工具呼叫）的紀錄要存成什麼形狀，才能事後回溯某次結果。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：要依任務、使用者、模型、狀態與時間查詢 | 儲存要支援結構化查詢 |
| 來源記錄：要保留 prompt 與版本沿革，並給審閱者看歷史 | 不能只存 log 或指標 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 結構化稽核表加物件快照 | 來源記錄：可依任務、使用者、模型、狀態與時間查詢 | 見後果的變困難 | 採用 |
| B 只新增的 JSONL 檔 | 來源記錄：適合匯出與備份 | 來源記錄：難以依任務、使用者、模型、狀態與時間查詢，不當主儲存 | 不採用 |
| C OpenTelemetry traces | 來源記錄：之後可以加上來關聯 | 來源記錄：不足以當持久的 AI 稽核紀錄、prompt 與版本沿革，或給審閱者看的歷史 | 不採用 |
| D Prometheus labels | 來源記錄：沒有記錄好處 | 來源記錄：基數高、有隱私風險 | 不採用 |
| E console log | 來源記錄：沒有記錄好處 | 來源記錄：容易遺失、脫敏不一致、沒有產品層的歷史 | 不採用 |

### 決定

AI 輔助流程記在只新增、不更新也不刪除的 `ai_runs` 與 `ai_run_events`：`ai_runs` 只在建立時寫一次，每次狀態轉換就新增一列 `ai_run_events`（`status`、`at`）；目前狀態取最新的事件，`completed_at` 是終態事件的時間。使用者接受、編輯或拒絕一個 AI 產出記在 `ai_runs`，不另寫 `audit_events`。`ai_runs` 與 `ai_run_events` 的欄位還沒有寫進[資料表字典](../../diagrams/architecture/data-table-dictionary.mdx)，兩張表的分界見 [architecture.mdx 的 §稽核與可追溯](../architecture.mdx#稽核與可追溯)。

### 後果

**變容易**

- 回溯某次 AI 結果時，可以依任務、使用者、模型、狀態與時間查詢

**變困難**

- 表只新增，更正要寫新事件，不能改舊列
- 目前狀態與完成時間要從最新的事件推得，不能直接讀 `ai_runs` 的欄位

### 什麼情況要重新討論

- 要把追蹤傳到外部的觀測工具時（本節的重新討論條件是推論）

## D6 使用者行為記在單一只新增的 audit_events 表

### 背景

人發起的領域行為（發布、提交、裁決、投票、成員變更、匯出）要記在哪、怎麼記，才能事後稽核。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：一次 AI run 是多個事件的生命週期，使用者的一個動作是單一的原子事實 | 兩者不宜混在同一張表 |
| 來源記錄：稽核要能重建一個實體的生命週期 | 跨動作類型的查詢不能靠逐一合併的表 |
| 規格 06-02 記錄：稽核紀錄至少保留 1 個曆年 | 要有保留政策 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 擴充 `ai_runs` | 來源記錄：沒有記錄好處 | 來源記錄：一次 run 是多事件生命週期、使用者動作是單一原子事實；插入變肥大，保留與存取政策混在一起 | 不採用 |
| B 每個領域各一張稽核表 | 來源記錄：沒有記錄好處 | 來源記錄：重建生命週期要 N 路 union，每多一種動作就多一路，是寫死任務邏輯的反面例子 | 不採用 |
| C 單一只新增的表，動作由設定驅動的註冊表驗證 | 來源記錄：一張表就能重建生命週期，不必逐一 union | 見後果的變困難 | 採用 |

### 決定

用單一只新增的 `audit_events` 表：一般 service 寫入只做 insert，update 與 delete 在兩層資料庫都拒絕；由 service 層與領域異動在同一個交易內寫入（見 [backend-agent-rules.mdx 的 B4](../rules/backend-agent-rules.mdx#b4-交易的擁有層)）；`action` 與 `target_type` 由註冊表驗證；非人的行為 actor 為 null、角色為 `system`；`payload_summary` 只放去識別化的內容，脫敏規則見 [security-agent-rules.mdx 的 S9](../rules/security-agent-rules.mdx#s9-稽核脫敏與保留)。表名 `audit_events` 是單數、模組前綴命名慣例的明確例外。欄位與保存見 [architecture.mdx 的 §稽核與可追溯](../architecture.mdx#稽核與可追溯)。

### 後果

**變容易**

- 動作類型由註冊表驗證，不是每種動作各一張表
- 重建一個實體的生命週期，只查一張表

**變困難**

- update 與 delete 要在兩層資料庫都拒絕
- 每個寫入點都要登記動作並提供去識別化的 `payload_summary`
- 更正錯誤的事件要寫新事件，不能改舊列

### 什麼情況要重新討論

- 稽核事件量大到單一表的查詢無法接受時（本節的重新討論條件是推論）

## D7 稽核保留至少一個曆年，刪除請求就地匿名化同一列

### 背景

要決定使用者的刪除請求怎麼處理，而不破壞只新增的稽核與研究所需的 gold 追溯。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：多張表只新增或有 RESTRICT 保護，一般的刪除抹不掉它們 | 刪除請求不能靠一般 delete |
| 來源記錄：研究可重現需要 gold 追溯保存 | 匿名化後追溯仍要連得起來 |
| 規格 06-02 記錄：稽核紀錄至少保留 1 個曆年 | 保留期內不能刪事件 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 就地匿名化同一列 | 來源記錄：稽核行為人、session、成員身分、歷史與 gold 追溯都保持完整 | 見後果的變困難 | 採用 |
| B 把 FK 改指向共用墓碑帳號（推論） | 來源沒有記錄 | 來源的決定寫明不採用；理由沒有記錄 | 不採用 |
| C 直接刪除使用者列（推論） | 來源沒有記錄 | 來源記錄：只新增與 RESTRICT 的表使一般刪除做不到，且 gold 追溯要保存 | 不採用 |
| D 所有 entity 一律軟刪除 | 來源沒有記錄 | [backend-agent-rules.mdx 的 B8](../rules/backend-agent-rules.mdx#b8-刪除軟刪除與匿名化)記錄不把它當預設 | 不採用 |

### 決定

使用者的刪除請求就地匿名化同一列，不把 FK 指向共用墓碑帳號；稽核事件至少保留一個曆年、不自動刪除，事件列永遠不刪，過了最短保留期後只能把 PII 欄位墓碑化；帶答案的歷史 JSON 跟著它所屬的資料集版本或 run 保存。規則見 [backend-agent-rules.mdx 的 B8](../rules/backend-agent-rules.mdx#b8-刪除軟刪除與匿名化)與 [security-agent-rules.mdx 的 S9](../rules/security-agent-rules.mdx#s9-稽核脫敏與保留)。匿名化與保留的細節如下。

| 項目 | 做法 |
| :--- | :--- |
| 稽核事件的行為人 | 事件保留 `user_id`，畫面顯示成「已刪除的使用者 #短碼」，同一個人做過的事仍然串得起來；短碼怎麼產生未定 |
| 匿名化帳號的狀態 | `users` 加 `anonymized_at`（`timestamptz`，可為 null）；個資欄位清掉之後，這個帳號不能再登入 |
| 清除工作的頻率 | 每天跑一次（Celery beat），實際保留最多只會比期限多一天 |
| 版本撤回 | 只標記撤回，不刪除：版本加 `withdrawn_at` 與撤回原因；撤回後不能再指派到新任務，已經跑過的 run 與帶答案的歷史 JSON 照舊保存，撤回本身記一筆稽核 |
| 刪除請求的記錄 | 另記在一張只存 `user_id` 與時間的小表；從備份還原之後，要先把這些刪除重新套用一次，才能恢復服務（見 [D9](#d9-資料備援只做正式層備份產出到獨立-volume)） |

### 後果

**變容易**

- 匿名化之後，稽核行為人、session、成員身分、歷史與 gold 追溯仍然連得起來

**變困難**

- 匿名化後，稽核事件上的行為人只顯示成「已刪除的使用者 #短碼」，不再有身分；這在最短保留期內可以接受
- 清除工作每天一次，實際保留會比期限多最多一天
- 版本撤回不刪除，撤回後的版本與其歷史 JSON 要一直存續
- 帶答案的歷史 JSON 要跟著版本或 run 存續，不能隨使用者被刪

### 什麼情況要重新討論

- 保留期或匿名化範圍被法規或機構要求改變時（本節的重新討論條件是推論）

## D8 CI 安全掃描做相依套件掃描與 Semgrep

### 背景

要決定 CI 掃哪些安全問題、門檻多高，以及哪些先不做。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：系統是論文用的 demo，不是對網際網路開放的正式環境（來源的前提，見附錄） | DAST 與 fuzzing 現在的價值有限 |
| `AGENTS.md` 硬性規則 7、8：禁止 `allow_origins=["*"]` 與寫死的 secret | SAST 要至少蓋這兩條 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A `pip-audit`（後端相依套件掃描） | 來源記錄：沿用既有做法 | 來源記錄：沒有記錄代價 | 採用 |
| B `pnpm audit`（前端相依套件掃描） | 來源記錄：現在就接，前端出現前不會觸發 | 來源記錄：誤報較多，用 `--prod` 或逐筆 ignore 處理，不降低門檻 | 採用 |
| C Semgrep SAST | 來源記錄：可蓋專案禁令（至少兩條）加上一份註冊表規則集 | 來源記錄：原本延後到有後端程式才接，延後期間禁令只靠 agent 把關 | 採用：已建成，只蓋專案禁令 |
| D DAST | 來源記錄：沒有記錄好處 | 來源記錄：目前不做 | 不採用：系統對網際網路開放、不只本機或 demo 使用時重新討論 |
| E API fuzzing（Schemathesis） | 來源記錄：沒有記錄好處 | 來源記錄：延後 | 延後：OpenAPI schema 穩定之後 |
| F Playwright E2E | 來源記錄：不屬安全掃描 | 來源記錄：由測試策略負責 | 不在這裡決定，見 [ADR-007](007-testing-strategy.mdx) |

### 決定

CI 有兩個安全 job，DAST 與 API fuzzing 先不做。

- **相依套件掃描**（job `dependency-audit`）：後端 `uv run pip-audit`，任何已知弱點都失敗；前端 `pnpm audit --prod --audit-level high`，正式依賴有 high 以上弱點才失敗。**後端門檻比 high 嚴格**，因為 `pip-audit` 2.10.1 沒有嚴重度旗標（維護者 2026-11-22 裁定），所以不加 `--fail-on`、也不另寫嚴重度腳本。
- **Semgrep**（job `semgrep`）：用固定版本的官方映像 `semgrep/semgrep:1.186.0`，免得新版釋出就改變 PR 的判準；先跑 `semgrep --test .semgrep/` 驗規則對得上回歸樣本，再跑 `semgrep scan --error --config .semgrep/label-suite.yml backend/ frontend/ e2e/`。目前蓋兩條專案禁令：CORS 的 `allow_origins=["*"]`、寫死的 API key 與 secret（`AGENTS.md` 硬性規則 7、8），沒有註冊表規則集。

做法見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)，相依套件警示的升級邊界見 [dependency-policy.mdx](../workflow/dependency-policy.mdx)。

### 後果

**變容易**

- 相依套件的已知高風險弱點在 PR 就被擋下
- CORS 萬用來源與寫死的 secret 在 PR 就被擋下，不再只靠 agent 把關

**變困難**

- `pnpm audit` 誤報較多，只能用 `--prod` 或逐筆 ignore 處理，不能降低門檻
- 沒有修補版本的 high CVE 會讓 CI 失敗；來源記錄的出口是逐筆 ignore 並開 issue 追蹤
- 後端的相依套件掃描比 high 嚴格：任何已知弱點（含 low 與 medium）都會讓 `dependency-audit` 失敗

### 什麼情況要重新討論

- `pip-audit` 提供嚴重度旗標，後端門檻可以改回 high 時（本節的重新討論條件是推論）
- 要加 Semgrep 的註冊表規則集或新的專案禁令時（本節的重新討論條件是推論）
- 系統對網際網路開放，不只本機或 demo 使用時（DAST）
- OpenAPI schema 穩定之後（API fuzzing）

## D9 資料備援只做正式層，備份產出到獨立 volume

### 背景

要決定資料庫壞掉或遺失時怎麼救。標註結果是人工產出的，和可以重跑的評分不同，掉了補不回來，所以 [D4](#d4-觀測性只做-ai_runs監控與錯誤追蹤本期不做) 不做監控的理由不能照搬到這裡。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 標註結果是人工產出，無法由系統重建 | 不能以「研究原型」為由完全不做 |
| 資料庫分兩層（[ADR-003 的 D7](003-backend-architecture.mdx#d7-資料庫分兩層)）：Lite 層是具名 volume `label-suite-data`（掛在 `/app/data`）裡的單一 SQLite 檔，正式層是 PostgreSQL 16 | 兩層的備份手法不同，要分開決定 |
| ADR-003 的 D7 已決定 Lite 層不建議多人使用 | Lite 層保護的是單人試用的資料，價值與正式層不同 |
| 本 repo 沒有地端主機規劃（個人 repo ADR-023 的地端計畫在 [D1](#d1-compose-加-nginx-當-runtimecloudflare-可選) 已不採用） | 備份目的地不能綁在某台具名主機上 |
| 這一期不引入新的 secret 與相依套件 | 排除需要雲端憑證的方案 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 正式層用 `pg_dump` 定期備份到獨立的 backups volume，Lite 層不做 | 現在就做得出來，不需要新的 secret 或相依套件；範圍與 ADR-003 的 D7 兩層定位一致 | 主機整台損毀時備份一起沒；Lite 層的使用者要自己備份具名 volume 裡的資料 | 採用 |
| B 兩層都做：Lite 層也排一個 `VACUUM INTO` 的定期備份 | 兩層行為一致，文件不必分層解釋 | 多一個排程與一條 SQLite 專屬路徑，[B7](../rules/backend-agent-rules.mdx#b7-雙資料庫的測試要求) 要求兩種 dialect 都測；而 Lite 層本來就不建議多人使用，保護的資料價值低 | 不採用自動排程；`VACUUM INTO` 這個手法仍是 Lite 層手動備份的做法，見決定 |
| C 備份上傳 S3 相容的物件儲存 | 真的做得到災難復原 | 多一組 secret 與一個相依套件，沒設定時還要再設計一條降級路徑（像 [D3](#d3-寄信用-resend沒設-key-時把連結印到-log) 的 Resend 那樣） | 不採用，列為重新討論的條件 |
| D 直接複製 SQLite 檔或 PostgreSQL 的資料目錄 | 不需要額外工具 | 寫入進行中複製會得到壞檔；PostgreSQL 的資料目錄要先停機或改用 `pg_basebackup` 才一致 | 不採用 |
| E 本期不做備援 | 範圍最小 | 標註結果掉了補不回來，和監控不同；等於把唯一一份資料押在單一磁碟上 | 不採用 |

### 決定

正式層用 `pg_dump` 定期備份，產物寫到獨立的 backups volume；Lite 層不做自動備援，改由使用者自己來，而且文件要給安全的做法：停掉服務再用 `docker compose cp` 把 `backend` 服務的 `/app/data` 複製出來，或在服務執行中用 `sqlite3 <db> "VACUUM INTO '<path>'"` 取一份一致的副本。不能只寫「複製資料目錄」—— 寫入進行中直接複製會得到壞檔（選項 D），而 SQLite 壞檔平常看不出來，要還原時才發現。備份只放在主資料碟上不足以災難復原，異地複製是部署者的責任，文件要寫明這一點。還原演練每週自動、每季人工：每週排程把最新的備份還原到暫時的 PostgreSQL，檢查各表筆數，失敗就報警；每季由部署者依 runbook 完整走一次還原；runbook 本身留到正式部署的 change 再寫。刪除請求在備份裡有最多約七天的曝險，這一點接受，寫進隱私說明；從備份還原之後的處理見 [D7](#d7-稽核保留至少一個曆年刪除請求就地匿名化同一列)。格式、頻率與保留份數（每日一次 `pg_dump -Fc`、滾動保留 7 份，裁定見 [#490 的留言](https://github.com/label-suite/label-suite/issues/490#issuecomment-7010266013)）見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)。

### 後果

**變容易**

- 正式層的資料庫損毀有一條明確的還原路徑，不必從標註者的記憶重建
- 不引入新的 secret 與相依套件，這一期就做得出來

**變困難**

- 主機整台損毀（磁碟、電源、核心）時備份一起沒，只有部署者自行異地複製能救
- 要維護每週的還原排程與報警，並由部署者每季依 runbook 走一次還原；runbook 還沒有寫
- Lite 層與正式層的行為不同，文件要分開說，不能只寫一句「系統有備份」
- 備份檔含測試集答案與個資，存取控制要比照原資料庫；[D7](#d7-稽核保留至少一個曆年刪除請求就地匿名化同一列) 的就地匿名化不會回溯既有的備份，所以刪除請求的曝險上限就是保留期，滾動 7 份約七天；還原之後要先重新套用刪除請求的記錄才能恢復服務

### 什麼情況要重新討論

- 系統開始承載真實的標註專案，不再只是 demo 與研究原型時
- 願意引入一組物件儲存的憑證，或出現明確的異地備份要求時（選項 C）
- [D7](#d7-稽核保留至少一個曆年刪除請求就地匿名化同一列) 的刪除請求必須涵蓋備份時

## D10 worker 收到 SIGTERM 先做完手上的任務

### 背景

要決定重啟或部署時，正在跑的評分任務怎麼辦。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 單一評分最長 300 秒（[architecture.mdx 的 §非同步任務](../architecture.mdx#非同步任務)） | 收工的寬限時間要跨過這個上限才有作用 |
| Compose 的 `stop_grace_period` 預設 10 秒 | 不設定的話，超過 10 秒的評分在每次重啟都會被 SIGKILL |
| Celery 預設一領到任務就 ack | 被 SIGKILL 的任務不會回佇列，直接消失，狀態停在進行中 |
| [ADR-003 的 D8](003-backend-architecture.mdx#d8-非同步任務用-celery-加-redis) 拒絕 RabbitMQ 時寫「研究系統偶爾在重啟時掉一個 task 可以接受」 | 這句涵蓋兩種掉法，要分清楚哪一種本決定要收斂 |

那句話涵蓋的兩種掉法要分開看：Redis 本身掛掉造成佇列裡的訊息遺失，和 worker 重啟造成進行中的任務遺失。本節只收斂後者；前者仍照 ADR-003 的 D8，本 repo 接受 Redis 單實例沒有高可用。

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A warm shutdown：收到 SIGTERM 後不再領新任務，手上的跑完才退，`stop_grace_period` 設成大於 300 秒 | 重啟不會掉任務；正確性不依賴任務可以重跑；使用者不會看到停在進行中、其實已經沒人處理的任務 | 部署最差要等五分鐘才停得下來 | 採用 |
| B `task_acks_late` 加 `task_reject_on_worker_lost`：停機時未完成的任務回佇列，重啟後重跑 | 部署不必等 | 被打斷的評分整段重算，跑到 299 秒被打斷就白做、重啟後再跑 300 秒，最壞情況比 A 更久；而且「任務算到哪裡」在部署語意裡變成不確定，排查時要先分辨一筆結果是第幾次跑出來的 | 不採用 |
| C 維持現狀，接受掉任務 | 不必改任何設定 | 掉掉的任務狀態停在進行中，要另做掃描機制才會轉成失敗，等於把成本挪到別處；使用者看不出來要重新提交 | 不採用 |
| D A 加 B：寬限期內做完，超過寬限期的回佇列 | 兼顧不掉任務與部署不卡住 | 超時路徑等於 B，卻多一套設定要測；評分有 300 秒硬上限，寬限期設對之後超時路徑幾乎不會觸發 | 不採用 |

### 決定

Celery worker 維持 warm shutdown：收到 SIGTERM 後不再領新任務，把手上的跑完才退出；Compose 的 `stop_grace_period` 要設成大於單一評分上限 300 秒，不能留在預設的 10 秒。FastAPI 容器同樣要讓進行中的請求收尾後才退。兩個容器各自的數值見 [architecture.mdx 的 §部署與維運](../architecture.mdx#部署與維運)，Celery 的參數見 [§非同步任務](../architecture.mdx#非同步任務)。本決定不改變 ADR-003 的 D8 對 Redis 單實例可靠度的接受。

### 後果

**變容易**

- 重啟與部署不會掉進行中的評分，不需要為了重啟而要求任務可以安全重跑
- 不會留下停在進行中、其實沒人處理的任務，所以不必另做掃描機制

**變困難**

- 部署最差要等五分鐘，CI 的部署步驟與健康檢查的逾時都要跟著放寬
- `stop_grace_period` 和評分上限 300 秒是一組互相綁住的數字，改其中一個要一起改
- 強制停止（`docker kill`、主機斷電、OOM killer）仍然會掉任務，warm shutdown 只管收得到 SIGTERM 的情況
- 評分既有的重試三次不受本節影響，重複寫入仍要靠 [ADR-003 的 D10](003-backend-architecture.mdx#d10-背景計算的結果寫入做成冪等) 擋

### 什麼情況要重新討論

- 單一評分的上限從 300 秒往上調，寬限期跟著長到部署無法接受時
- 出現沒有時間上限的背景工作（例如大批次匯出），寬限期不可能涵蓋它時
- 改成多副本滾動部署，需要舊副本邊收工邊讓新副本接手時
