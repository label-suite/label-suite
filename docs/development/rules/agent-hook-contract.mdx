# Agent Hook 契約與平台支援矩陣

`AGENTS.md` 是規則本體；本文件只定「怎麼觸發、怎麼傳遞結果」，不是第二份規則 canon，一條新規則也沒有。規則內容在 [agent-rules.mdx](agent-rules.mdx)、[backend-agent-rules.mdx](backend-agent-rules.mdx)、[security-agent-rules.mdx](security-agent-rules.mdx)、[api-agent-rules.mdx](api-agent-rules.mdx)、[frontend-agent-rules.mdx](frontend-agent-rules.mdx)、[testing-agent-rules.mdx](testing-agent-rules.mdx)，自動 gate 的政策在 testing-agent-rules 的 T9。兩邊說法不同時以 `AGENTS.md` 為準，並回報給維護者。

## 邊界

本文件只定契約、不實作任何 gate，也不宣稱兩個平台等價。

| 邊界 | 說明 |
| :--- | :--- |
| 不實作任何 gate | [T9](testing-agent-rules.mdx) 明文禁止在規範文件裡實作 gate。檢查器與 CI job 在 `scripts/`、`.github/`，agent 事件的註冊在 `.claude/`，都由 [#111](https://github.com/label-suite/label-suite/issues/111) 實作 |
| 不是規則來源 | hook 只呼叫本 repo 的共用檢查器。檢查器要擋什麼，依六份規範文件 |
| hook 不等於權限控制 | hook 攔不住平台權限層、產品授權與 CI 要負責的事。**本機 hook 通過不能代替 CI**（T9 的禁止格） |
| 不宣稱兩邊等價 | Claude 的設定、事件名稱、exit code 與工具名稱**不會**自動在 Codex 生效。見[§平台支援矩陣](#平台支援矩陣)與[§能力缺口與承接](#能力缺口與承接) |
| `check:specs` 驗得到的只有形狀 | **本檔是 `.mdx`，`scripts/check-specs.mjs` 的 `listMdx` 一直都收**，所以它會走五個對全部頁面跑的檢查：`checkTerms`（術語 id）、`checkAnchorLinks`（連結錨點）、`checkQuestions`（Q 編號）、`checkCitedNames`（引文與節名）、`checkStaleUnwritten`（過期的「未撰寫」標記）。但規格頁專用的五個檢查（frontmatter、章節順序、Scenario、決議依據、舊編號對照）只對 `docs/specs/NN-<模組>/NN-<頁面>.mdx` 跑——`specParts()` 要求路徑第一段是 `specs`，本檔不在那裡，所以套不到。也就是說：術語、錨點、Q 編號、引文與過期標記驗得到，**事實正確性驗不到**——那仍然靠實查與獨立審查，**不得因為 `check:specs` 綠就當成這份對過了** |

## 本 repo 的 Hook 契約

七個 hook 各列九個欄位：目的、事件、適用路徑或角色、payload 欄位、共用檢查器、timeout、輸出與退出碼、阻擋或提醒、缺工具或無適用檔案時的行為。

**七個 hook 的檢查器都已存在，註冊也都落地了。** 下表的「共用檢查器」欄說的是那支腳本在不在，「事件」欄說的是它由什麼叫起；兩者仍要分開讀，因為兩件事會各自腐壞。Git 事件由 `core.hooksPath=scripts/git-hooks` 接上（`commit-msg` 跑 H5，`pre-commit` 跑排版與 H4），agent 事件由 `.claude/settings.json` 的 `hooks` key 與 `.codex/hooks.json` 兩份手寫設定接上，H1 自己會核對那兩份是否一致。**註冊存在不等於會執行**：Codex 側的 hook 在被 `/hooks` 信任前是**靜默**跳過的，而兩個平台都還可以用 `--no-verify`、`disableAllHooks` 或 `[features] hooks = false` 整批關掉——真正的 gate 在 H7 的 CI。

### H1 Session 開始：環境自我檢查

| | |
| :--- | :--- |
| **目的** | 把「這個 checkout 的 Git hook 有沒有啟用、規則入口在不在、工具版本夠不夠」在對話一開始就講清楚，而不是等到 commit 被退才發現 |
| **事件** | `SessionStart`（matcher `startup|resume|clear|compact|fork`，兩邊都支援這五種） |
| **適用路徑／角色** | 整個 repo，不分角色 |
| **payload 欄位** | `cwd`（定位 repo）、`hook_event_name`、`session_id`（只用於 log 關聯） |
| **共用檢查器** | `scripts/check-env.sh`（**已存在並註冊到 `SessionStart`**）：核對 `core.hooksPath` 是否指向 `scripts/git-hooks`、`AGENTS.md` 是否存在、`node`／`pnpm`／`uv` 版本，以及**本次的 hook 是不是真的會跑**——Claude 看 `disableAllHooks`，Codex 看 `[features] hooks` 是否被關掉、以及該 hook 有沒有被信任；另外**核對 `.claude/settings.json` 與 `.codex/hooks.json` 兩份設定指向的腳本是否都存在**——兩份設定手寫兩份、不做生成器，這道檢查是它們唯一的防漂移機制（[§能力缺口與承接](#能力缺口與承接)第 7 條的承接、[ADR-001 D3](../adr/001-agent-engineering.mdx#d3-兩個平台的-hook-設定手寫兩份不做生成器)） |
| **timeout** | **10 秒**。環境檢查不該讓對話等 |
| **輸出與退出碼** | 一律 exit `0`，訊息走 stdout。缺東西時列出「缺什麼、怎麼補」 |
| **阻擋或提醒** | **提醒**。`SessionStart` 在兩邊都擋不住，所以也不假裝它能擋 |
| **缺工具／無適用檔案** | `backend/`、`frontend/` 還不存在時標 **not applicable** 而不是失敗（不要求尚未建立的 backend/frontend 必須存在）。**不讀 `.env` 的值**，只看檔案在不在 |

### H2 工具執行前：破壞性命令與受保護目標

| | |
| :--- | :--- |
| **目的** | 在動作**發生前**擋下 `AGENTS.md` 硬性規則 2、3、10 會禁止的事：commit／push 到 `main`、`git push --force`、`rm -rf`、`git reset --hard`、`git branch -D`、用 `pip install`／`npm install` 取代 `uv add`／`pnpm add` |
| **事件** | `PreToolUse`。Claude matcher `Bash`；Codex matcher `Bash`。寫檔目標的保護另註冊一組：Claude `Edit|Write|NotebookEdit`，Codex `apply_patch` |
| **適用路徑／角色** | 命令那組不分路徑；寫檔那組只看目標路徑。清單**沿用**參考 settings 的 `permissions.deny`，加上裸檔名 `.env` 共六類：`**/.env`、`**/.env.*`、`*.pem`、`*.key`、`*id_rsa*`、`*credentials.json`。**合法例外**：`.env.example` 與其他 `*.example`、`*.pub`、`scripts/tests/fixtures/` 底下的假憑證——這些要放行，否則連範例設定檔都寫不了。`docs/specs/00-prd.mdx` **不在**受保護清單（見[決策紀錄](#決策紀錄)） |
| **payload 欄位** | `tool_name`、`tool_input`（Bash 取 `command`；寫檔取檔案路徑）、`tool_use_id`、`cwd` |
| **共用檢查器** | `scripts/check-command.sh`、`scripts/check-write-target.sh`（**兩者已存在並註冊到 `PreToolUse`**，各自吃命令類與寫檔類的工具名） |
| **timeout** | **5 秒**。這支擋在每個工具呼叫前面，不能慢 |
| **輸出與退出碼** | 擋下時 **exit `2`，原因寫 stderr**；`permissionDecision: "deny"` 加 `permissionDecisionReason` 兩邊也都收。優先用 exit `2`，理由見 [ADR-001 D5](../adr/001-agent-engineering.mdx#d5-h2-失敗時由腳本自己-exit-2) |
| **阻擋或提醒** | **阻擋**。必須在動作前拒絕；不能只在執行後提醒 |
| **缺工具／無適用檔案** | 檢查器不存在或壞掉時，**兩個平台的預設都是讓動作照做**（fail-open），所以**兩邊都靠腳本自己在無法判斷時 exit `2`**（理由見 [ADR-001 D5](../adr/001-agent-engineering.mdx#d5-h2-失敗時由腳本自己-exit-2)）：包裝腳本一律先確認檢查器存在且可執行，不存在就 exit `2`。**不得用 `|| true` 把判斷不了變成通過**，也不得假設路徑打錯會被擋下 |

**這一條的保護範圍有明確上限，寫在[§能力缺口與承接](#能力缺口與承接)第 2 條，不得當成完整安全邊界。**

### H3 編輯後：按路徑跑快速檢查

| | |
| :--- | :--- |
| **目的** | 剛改過的檔案立刻拿到可修正的診斷，而不是等 CI |
| **事件** | `PostToolUse`。Claude matcher `Edit|Write|NotebookEdit`；Codex matcher `apply_patch` |
| **適用路徑／角色** | 只對**本次受影響且已存在**的檔案，依副檔名分流：`.py` → `ruff check`（整個 `backend/`）加 `mypy --strict`（只有 `app/`，範圍照 `openspec/config.yaml`），兩者都不在 `PATH` 上（`uv sync` 裝進 `backend/.venv`），所以經 `uv run --directory <backend> --project <backend> --no-sync` 以 `backend/` 為工作目錄呼叫，檔名給相對路徑——ruff 的 `per-file-ignores` 是對工作目錄解析的；`.ts`／`.tsx` → `tsc -b`（整個專案，不帶檔案參數——單檔編譯看不到專案設定）加 `eslint`（逐檔），同樣不在 `PATH` 上（在 `frontend/node_modules/.bin`），所以經 `pnpm -C <frontend> exec` 以 `frontend/` 為工作目錄呼叫——eslint 的 flat config 也是對工作目錄解析的；`docs/` 底下的 `.mdx` **與 `.md`** → `node scripts/check-specs.mjs docs`（`.md` 自 [PR #395](https://github.com/label-suite/label-suite/pull/395) 起才在它的範圍內）。**排除** `frontend/src/api/generated/`、Alembic migration、`pnpm-lock.yaml`、`uv.lock` 與 vendor |
| **payload 欄位** | `tool_name`、`tool_input` 的檔案路徑、`cwd` |
| **共用檢查器** | `scripts/check-changed.sh`（**已存在並註冊到 `PostToolUse`**；同一支的 `--staged` 模式由 H4 的 Git hook 叫起，`--range` 由 H7 的 CI 叫起）。`docs/` 那條沿用既有的 `scripts/check-specs.mjs` |
| **timeout** | **30 秒** |
| **輸出與退出碼** | 診斷走 stderr。**一律不以 exit `2` 阻擋**——見下 |
| **阻擋或提醒** | **提醒**。`PostToolUse` 在兩邊都撤銷不了已發生的編輯，能做的只是替換 model 看到的結果；本契約**刻意不用**那個替換（理由見 [ADR-001 D4](../adr/001-agent-engineering.mdx#d4-h3-只回報診斷不自動修)）。真正的 gate 是 H4、H5 與 H7 |
| **缺工具／無適用檔案** | 本次沒有命中的檔案（例如只改了 `docs/` 以外的 `.md`）→ 標 not applicable 並 exit `0`；檔案被刪除或改名 → 不對不存在的檔案報錯；`ruff`／`mypy`／`tsc`／`eslint` 不存在且該層尚未 bootstrap → 標 not applicable。**已宣告啟用的檢查缺工具時要明確失敗**，不是靜默通過——`.py` 的「缺工具」指 `PATH` 上沒有、`backend/` 的 uv 環境也叫不動，單是不在 `PATH` 上是常態而非缺工具 |

**check-only。** H3 **只回報診斷，不改檔、不自動 `git add`**，連 formatter 都不自動套用；要修由 agent 自己依診斷修（理由見 [ADR-001 D4](../adr/001-agent-engineering.mdx#d4-h3-只回報診斷不自動修)）。

### H4 Git pre-commit：檢查 staged 快照

| | |
| :--- | :--- |
| **目的** | 在提交成形前，對**真正要進去的內容**跑檢查 |
| **事件** | Git `pre-commit`（不是 agent 事件）。由 `core.hooksPath=scripts/git-hooks` 啟用 |
| **適用路徑／角色** | `git diff --cached` 命中的檔案，分流規則同 H3 |
| **payload 欄位** | 無（Git hook 沒有 JSON payload）。輸入是 staged snapshot |
| **共用檢查器** | 兩件事，順序有意義：先由 lint-staged（`.lintstagedrc.mjs`）對 staged 的 `*.{json,md,yml,yaml,css,js,mjs}` 跑 `prettier --write` 並重新暫存，再把結果交給 `scripts/check-changed.sh --staged`（與 H3 同一支，差別只在檔案清單怎麼來）。排版會改寫並重新暫存檔案，所以檢查器必須排在後面，否則它判的是這次提交已經不會收錄的內容 |
| **timeout** | 無平台 timeout，檢查器也不自建 watchdog：上限由執行這支 hook 的環境承擔，CI 那一側以 `timeout-minutes` 表達（H7）。**不得用 shell `timeout`**（本機沒有，見[§查核方式](#查核方式)） |
| **輸出與退出碼** | 非零即擋下 commit，這是 Git 的既有語意 |
| **阻擋或提醒** | **阻擋**。但 `--no-verify` 可跳過，所以它不是最終 gate：排版的 gate 是 CI 的 `format` job（`pnpm format:check`） |
| **缺工具／無適用檔案** | 必須讀**staged 版本**（`git show :<path>`），不能拿工作區的檔案充數，否則「unstaged 的修正」會被誤當成「staged 已通過」。部分暫存與在子目錄執行都要正確——`git rev-parse --show-toplevel` 已是本 repo 既有作法。排版那一半綁在 `.lintstagedrc.mjs` 上：設定檔在而找不到 `lint-staged` 或 `prettier` 時 exit `1` 並提示 `pnpm install`，不略過；沒有設定檔的 checkout（例如測試用的臨時 repo）沒有東西要排版，直接進到檢查器那一半 |

### H5 Git commit-msg：檢查提交訊息

| | |
| :--- | :--- |
| **目的** | 擋下不符 `AGENTS.md` §Commits 的訊息（英文 Conventional Commits、subject ≤ 72 字、body 每條粗體動詞開頭） |
| **事件** | Git `commit-msg` |
| **適用路徑／角色** | 提交訊息本身 |
| **payload 欄位** | 無。輸入是 `$1`（訊息檔路徑） |
| **共用檢查器** | **`scripts/check-commit-msg.sh`（已存在）**。它是唯一只由 Git 事件叫起、沒有 agent 事件對應的檢查器 |
| **timeout** | 無 |
| **輸出與退出碼** | 非零即擋下 commit |
| **阻擋或提醒** | **阻擋**；同樣可被 `--no-verify` 跳過，所以 CI 的 `commit-messages` job 才是真正的 gate |
| **缺工具／無適用檔案** | merge commit（`$GIT_DIR/MERGE_HEAD` 存在）直接 exit `0`，這是現行行為，照留 |

**H5 不改，只記錄。** 它與 CI 的 `commit-messages` job 已經共用同一支檢查器，正是這份契約要的形狀；實作時不重建它。

### H6 工作與子任務結束：核對證據

| | |
| :--- | :--- |
| **目的** | 在 agent 宣告做完之前，核對該跑的驗證有沒有跑、evidence 齊不齊（[T11](testing-agent-rules.mdx)） |
| **事件** | `Stop` 與 `SubagentStop`（兩邊都有，且**兩邊都可阻擋**） |
| **適用路徑／角色** | 整個 repo。`SubagentStart`／`SubagentStop` **兩邊都能以 agent／subagent type 當 matcher** 分流角色。但 **Codex 的 `Stop` 不吃 matcher**（`UserPromptSubmit`、`Interrupt` 也不吃），所以 `Stop` 那一支要自己從 payload 判斷 |
| **payload 欄位** | **`stop_hook_active`**（防重入就靠它：為 `true` 代表這次結束本來就是上一個 stop hook 擋下所造成的）、`last_assistant_message`、`session_id`、`transcript_path`（只在本機用，**不外傳**）、`cwd`。`SubagentStop` 另有 `agent_type` 可供分流 |
| **共用檢查器** | `scripts/check-evidence.sh`（**已存在並註冊到 `Stop` 與 `SubagentStop`**） |
| **timeout** | **60 秒** |
| **輸出與退出碼** | 擋下時 exit `2` 或 `decision: "block"`，原因要寫「缺哪一項證據」 |
| **阻擋或提醒** | **阻擋**，但**必須防重入**：被擋下之後 agent 會再結束一次，又觸發自己。先讀 `stop_hook_active`，為 `true` 就直接放行——這是兩邊文件都提供的現成機制，不要自己另造標記檔 |
| **缺工具／無適用檔案** | 只重用與**目前 snapshot、規則版本與驗證範圍一致**的 evidence；對不上就當沒有。`backend/`、`frontend/` 不存在時標 not applicable |

**不新增停點。** [T12](testing-agent-rules.mdx) 明文只有一個人工停點；H6 是機械核對，不是要維護者確認的關卡。

### H7 CI：重跑必要檢查

| | |
| :--- | :--- |
| **目的** | 本機 hook 有**四條**被跳過的途徑——Git 的 `--no-verify`、Claude 的 `disableAllHooks`、Codex 的 `[features] hooks = false`，以及 Codex 的 hook 未被信任而 skipped——所以合併前的真正 gate 在 CI |
| **事件** | `pull_request`（`.github/workflows/ci.yml`，已存在五個 job：`commit-messages`、`docs-site`、`format`、`specs`，以及在 ubuntu 與 macOS 兩個平台跑檢查器回歸測試的 `hooks`） |
| **適用路徑／角色** | 整個 PR |
| **payload 欄位** | GitHub 事件的 `base.sha` 與 `head.sha`（現行 `commit-messages` job 已經在用） |
| **共用檢查器** | 與 H3、H4、H5 **同一組**。CI 與本機共用邏輯是防漂移的唯一辦法 |
| **timeout** | 由 workflow 設定 |
| **輸出與退出碼** | job 失敗即擋下合併（搭配 branch protection） |
| **阻擋或提醒** | **阻擋**。**本機通過不能代替 CI**（[T9](testing-agent-rules.mdx) 的禁止格） |
| **缺工具／無適用檔案** | CI 不得標 not applicable 來跳過已宣告啟用的必要檢查。branch protection 的啟用是**維護者的設定權限**，不是實作這份契約的人能改的——這兩件事要分清楚 |

## 能力缺口與承接

沒有對應能力時明列限制，以共用指令／Git／CI 承接，不宣稱等價攔截。

1. **Codex 的 hook 信任模型讓 hook 不能單獨作為必要 gate。** 非 managed 的 hook 在被信任前是 skipped，而信任綁 hash——意思是**每次改 hook，所有開發者那邊都會重新變成未信任而跳過**，而版控裡的檔案看起來是好的。
   **承接**：必要 gate 一律在 **CI（H7）** 再跑一次；hook 只負責「早一點講」。另外在 H1 的環境檢查裡回報「hook 是否實際生效」，讓跳過這件事看得見而不是靜悄悄。
2. **字串比對不是完整的命令安全邊界。** H2 讀的是 `tool_input.command` 的字串。複合命令、引號、變數展開、`eval`、`git -C <path>`、refspec 寫法、base64 之類的編碼都能繞過字串規則；反過來，Issue 本文或 commit body 裡**提到** `rm -rf` 的文字也可能被誤判成正在執行。
   **承接**：H2 擋**明顯**的情況並寫明它不是安全邊界；真正的保護靠平台權限層（Claude 的 `permissions.deny`、Codex 的 sandbox 與權限設定）與 **branch protection**。驗收要涵蓋複合命令、引號、參數變體與「文件裡提到命令」這幾類。
3. **Codex 攔不住讀取。** 沒有 `Read`／`Grep`／`Glob` 工具名，讀檔走 shell，所以「不要讀 `.env` 的值」在 Codex 上沒有 hook 層的攔截點。
   **承接**：平台權限層的宣告式機制——Codex 的 `filesystem = "deny"`、Claude 的 `permissions.deny`；`AGENTS.md` 硬性規則 8 本來就要求 secret 從環境變數來。**本 change 沒有設定權限層**，所以這個缺口目前沒有實際的承接者。**不宣稱 Codex 有等價攔截。**
4. **`PostToolUse` 在兩邊都撤銷不了編輯**，能做的只是替換 model 看到的結果，所以 H3 一律當提醒。真正的 gate 在 H4、H5、H7。
5. **hook 的預設行為是 fail-open，而目前沒有宣告式的 fail-closed 開關。** 兩邊在 hook 失敗、timeout 或輸出不合法時都讓動作照做；Claude 的 `onFailure: "block"` 要 **v2.1.295**，本機 **2.1.273** 還沒有，Codex 沒有等價欄位。
   **承接**：H2 的包裝腳本自己負責 fail-closed（檢查器不存在或無法判斷就 exit `2`）；真正不能漏的保護放 **branch protection 與 CI**。升級 Claude Code 之後可以改用 `onFailure`，屆時要把版本下限記下來。
6. **平台權限層兩側都查完了，但查完不等於設好。** Claude 的 `permissions.deny` 有見過實例（參考來源那份 settings 擋 `.env.*`、`*.pem`、`*.key`、`*id_rsa*`、`credentials.json` 的寫入）；Codex 這一半於 2026-11-17 核對官方文件（`https://learn.chatgpt.com/docs/permissions`，runtime codex-cli 0.153.0）。Codex 的 permission profile 與舊的 sandbox 設定**互斥**，不得把 `permissions`、`default_permissions`、`sandbox_mode`、`sandbox_workspace_write` 並列成四個同時生效的鍵。**本 change 沒有設定任何一邊的權限層**，第 3 與第 8 條的承接因此都還是空的。
   **承接**：列為實作 PR 的前置查核項。「平台權限控制」與「hook 攔截」要分清楚，而這一半還沒查完——**不在這份文件裡假裝查過了**。
7. **`.claude/` 與 `.codex/` 兩份設定有漂移風險。** 事件集合與工具名都不同，改一邊忘了另一邊不會有任何報錯。
   **承接**：**手寫兩份、由 H1 核對**，不做生成器。所以 H1 的環境檢查要同時核對兩份設定指向的腳本是否都存在、兩邊是否都實際生效（Claude 看 `disableAllHooks`，Codex 看 `[features] hooks` 與信任狀態）——一致性靠這道檢查，不靠結構保證。
8. **Codex 的寫檔途徑沒有 hook 層的目標保護，而 Claude 有——這一項兩平台不對等。** `apply_patch` 與 `Bash` 共用 `tool_input.command`，沒有任何路徑欄位，`command` 的內部結構官方也未記載（見[§工具名稱](#工具名稱)）。所以 H2 的寫檔那組在 Codex 上無法判斷目標是什麼：它輸出一行 `NA:` 說明這條途徑沒有保護，然後放行，**不是**因為缺欄位就擋下每一次 `apply_patch`。Claude 的 `Edit`／`Write`／`NotebookEdit` 在 `tool_input` 直接給路徑，那一側擋得住。
   **承接**：與第 3 條同為平台權限層，而**本 change 沒有設定權限層**，所以這個缺口目前也沒有實際的承接者。改為承認缺口、不解析未文件化的封包格式，是維護者 2026-11-17 的裁定。

## Repo 定位

不寫死 `/Users/...`，不以目前 shell 的另一個 checkout 代替事件 workspace。

| 情境 | 作法 |
| :--- | :--- |
| Claude，專案層 hook | `${CLAUDE_PROJECT_DIR}/scripts/<checker>`。這是平台提供的專案根佔位符 |
| Codex，專案層 hook | **沒有**對應佔位符。用 `"$(git rev-parse --show-toplevel)"/scripts/<checker>`，與 `scripts/git-hooks/commit-msg` 現行作法一致 |
| 事件 cwd | 兩邊的 hook command 都以 session 的工作目錄為 `cwd`，payload 另給 `cwd` 欄位。**以 payload 的 `cwd` 為準**，不要用腳本自己的 `$PWD`——那可能是另一個 checkout |
| 子目錄執行 | 一律先 `cd "$(git rev-parse --show-toplevel)"`，`scripts/setup.sh` 已是這個形狀 |
| worktree | `git rev-parse --show-toplevel` 在 worktree 裡回傳該 worktree 的根，正確。**不要**用 `--git-common-dir` 去找主 checkout |
| 空白與中文路徑 | 所有路徑展開一律加雙引號。本 repo 的 `scripts/` 路徑目前都是 ASCII，但 `cwd` 由使用者的目錄決定，不能假設 |

### 阻擋能力與退出碼

| 事件 | Claude Code 2.1.273 | Codex 0.153.0 |
| :--- | :--- | :--- |
| `PreToolUse` | exit `2`（stderr 當原因）或 `hookSpecificOutput.permissionDecision: "deny"` 加 `permissionDecisionReason` | exit `2`（stderr 當原因）或 `permissionDecision: "deny"`（舊式 `decision: "block"` 仍收） |
| `PostToolUse` | **撤銷不了**。`decision: "block"` 把 reason 附在工具結果旁（agent 仍看得到原輸出），`updatedToolOutput` 則**整個替換**輸出 | **撤銷不了**。`decision: "block"` 與 exit `2` 都是「記下回饋、把工具結果替換成那段回饋、讓 model 從它繼續」；`continue: false` 同樣是替換後繼續 |
| `Stop` / `SubagentStop` | exit `2` 或 `decision: "block"` | exit `2` 或 `decision: "block"`（擋下代表「帶著原因繼續這個 turn」，不是終止） |
| `SessionStart` | **擋不住**。exit `2` 只顯示 stderr | 文件未列為可阻擋事件 |
| 通用 `continue: false` | **停住整個處理**，優先於任何事件專屬的 decision 欄位 | 只「把該次 hook run 標成 stopped」；在 `PostToolUse` 是替換結果後**繼續**。`PreToolUse` 與 `PermissionRequest` **不支援**這個欄位 |
| exit `0` | 成功，套用 JSON 輸出欄位 | 同 |
| 其他非零 | **非阻擋錯誤，動作照做**，只顯示 stderr 第一行 | 文件只定義 `2` 為阻擋；其他非零視為錯誤 |
| hook 失敗或 timeout 時 | **動作照做**。文件原文：路徑打錯或腳本 crash 的 policy hook「lets everything through」 | **動作照做**。`PreToolUse` 回傳不支援的欄位（`continue`／`stopReason`／`suppressOutput`）時，Codex 把該次 hook 標為失敗並**繼續執行那個工具** |
| 失敗即阻擋的開關 | 有：handler 的 `onFailure: "block"`——但**需 Claude Code v2.1.295 以上，本機 2.1.273 還沒有** | **沒有**（本次查核未見等價欄位） |

**三個會咬人的差異**：

- **`PostToolUse` 在兩邊都撤銷不了，而它們能做的事幾乎一樣。** 兩邊都是「把 model 看到的結果換掉」而不是「把動作收回來」：Claude 用 `decision: "block"`（附在結果旁）或 `updatedToolOutput`（整個替換），Codex 用 `decision: "block"`／exit `2`／`continue: false`（替換後繼續）。工作項 2 的「PostToolUse 回報失敗不等於撤銷原編輯」在兩個平台都成立。真正不對稱的是**通用 `continue: false`**：Claude 的會停住整個處理，Codex 的只是標記該次 hook run。
- **`onFailure: "block"` 在本機還不能用。** Claude 的這個欄位**需 v2.1.295 以上**，而本機是 **2.1.273**。所以「檢查器自己壞掉時要不要擋」目前在**兩個平台**都只能由腳本自己以 exit `2` 表達。
- **預設是 fail-open，不是 fail-closed。** 兩邊在 hook 失敗、timeout 或輸出無法解析時都讓動作**照做**。Claude 的文件直說路徑打錯或 crash 的 policy hook「lets everything through」；Codex 在 `PreToolUse` 收到不支援的欄位時會標記失敗並繼續執行那個工具。**不得假設不寫就會擋。**

### 工具名稱

matcher 比對的是工具名，而**兩邊的工具名不一樣**。這是本次查核影響最大的一項。

| 用途 | Claude Code 2.1.273 | Codex 0.153.0 |
| :--- | :--- | :--- |
| 執行命令 | `Bash` | `Bash` |
| 寫檔／改檔 | `Edit`、`Write`、`NotebookEdit` | `apply_patch`（matcher 也吃 `apply_patch`、`Edit`、`Write` 這三種寫法） |
| 讀檔 | `Read` | **沒有對應工具名**（讀檔走 shell） |
| 搜尋 | `Grep`、`Glob` | **沒有對應工具名**（走 shell） |
| MCP | `mcp__<server>__<tool>` | `mcp__<server>__<tool>` |
| 本地 function tool | — | `update_plan`、`spawn_agent` 等，走同一條 hook 路徑 |
| hosted 工具 | `WebSearch` 等有 hook | `WebSearch` 等 hosted 工具**不支援 hook** |
| 寫檔工具的 payload 形狀 | `tool_input` 直接給路徑：`Edit`／`Write` 用 `file_path`、`NotebookEdit` 用 `notebook_path` | `apply_patch` 與 `Bash` **共用 `tool_input.command`，沒有任何路徑欄位**，而 `command` 的內部結構官方未記載（`https://learn.chatgpt.com/docs/hooks`，查核日 2026-11-17） |

**沒有路徑欄位不是「待確認的欄位名」，是查核過的事實。** 它的後果是 hook 層在 Codex 的 `apply_patch` 這條途徑上沒有寫檔目標保護；承接者見[§能力缺口與承接](#能力缺口與承接)第 8 條。

matcher 語法兩邊一致：`"*"`、`""` 或省略代表全部命中；`Edit|Write` 是替代列舉；含其他字元時當 regex（Claude 的文件明寫是**未定錨**的 JavaScript regex，所以 `^Bash$` 與 `Bash` 不同義）。

**既有設定的空轉警告。** 參考來源那份 `.claude/settings.json`（原始本機 repo）用 `Read|Edit|Write|Grep|Glob|NotebookEdit` 當 matcher 來擋敏感檔。搬到 Codex 時，`Read`、`Grep`、`Glob`、`NotebookEdit` **永遠不會命中**，只剩 `Edit|Write`（作為 `apply_patch` 的別名）有效——也就是「**攔截讀取**」這件事在 Codex 上整個落空。那份設定裡的 `MultiEdit` 是否仍是 Claude 的有效工具名，**本次沒有確認**（官方文件的 matcher 範例沒有列它），實作時要用 `/hooks` 與實際事件對過，不要照抄。

### 設定位置、handler、timeout、信任

Codex 的 `command` 欄位是**字串，不是陣列**——官方文件的範例是 `"command": "python3 ~/.codex/hooks/session_start.py"`（`https://learn.chatgpt.com/docs/hooks`，查核日 2026-11-17）。

:::note{title="設定對照表" collapsible}

| 項目 | Claude Code 2.1.273 | Codex 0.153.0 |
| :--- | :--- | :--- |
| 專案層設定 | `.claude/settings.json` 的 `hooks` 鍵（另有 `.claude/settings.local.json` 不進版控） | `.codex/hooks.json`，或 `.codex/config.toml` 的 `[[hooks.<Event>]]` |
| 使用者層設定 | `~/.claude/settings.json` | `~/.codex/hooks.json` 或 `~/.codex/config.toml` |
| 組織層 | managed policy settings（**最高優先、不能停用**） | managed hooks（system／MDM／cloud／`requirements.toml`，**trusted by policy 且不能停用**） |
| handler 型別 | `command`、`http`、`mcp_tool`、`prompt`、`agent` | `command`、`mcp_tool` |
| 設定結構 | `hooks.<Event>[].matcher` 加 `hooks[]`（`type`／`command`／`args`／`timeout`／`onFailure`） | `hooks.<Event>[].matcher` 加 `hooks[]`（`type`／`command`／`statusMessage`／`timeout`／`async`） |

| 非同步執行 | — | `"async": true`（預設同步） |
| 信任模型 | **沒有**。設定檔裡的 hook 直接生效 | **有**。非 managed 的 hook 要逐一審核並信任，信任綁 hook 定義的 **hash**；新加或改過的在信任前**被跳過**。`/hooks` 管理，`--dangerously-bypass-hook-trust` 可單次跳過 |
| 全部停用 | `"disableAllHooks": true` | `config.toml` 的 `[features] hooks = false`（一行就全關；`codex_hooks` 是已棄用的別名）。管理者可在 `requirements.toml` 強制關閉 |
| 停用單一個 | 從設定檔刪掉（無法保留設定又停用個別 hook） | `/hooks` 可停用個別非 managed hook |
| 專案根佔位符 | `${CLAUDE_PROJECT_DIR}`（另有 `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PLUGIN_DATA}`） | **沒有專案根佔位符**。只有 `PLUGIN_ROOT`、`PLUGIN_DATA`（與 `CLAUDE_PLUGIN_ROOT`、`CLAUDE_PLUGIN_DATA` 相容別名）。官方給的作法是 `$(git rev-parse --show-toplevel)` |

**兩份設定要分開維護。** 同一個 hook 在本 repo 會有兩個註冊點（`.claude/settings.json` 與 `.codex/hooks.json`），兩邊指向**同一支腳本**。腳本只有一份，差異收在設定裡；為什麼手寫兩份、不做生成器見 [ADR-001 D3](../adr/001-agent-engineering.mdx#d3-兩個平台的-hook-設定手寫兩份不做生成器)。

**`SessionEnd` 不放任何實際工作。** Codex 給 1 秒、上限 3 秒，Claude 的共用預算是 1.5 秒。要做事的收尾放 `Stop`（H6），不放 `SessionEnd`。

## 查核方式

查核日：2026-11-11。以下是實際跑過、看過的東西，不是憑印象；實作前要再核對當時版本的官方 hook 文件與實際 runtime。

### 四個會讓人寫錯的地方

1. **這台機器沒有 `timeout`，也沒有 `gtimeout`。** 所以 hook 腳本裡**不能**用 shell 的 `timeout` 去包檢查器——在 macOS 上那行會直接 `command not found`，而且如果寫成 `timeout 30 checker || true` 還會把「工具不存在」偽裝成通過。要用的是**平台 hook 設定自己的 `timeout` 欄位**（兩邊都有）。跨 macOS／Linux 驗證 timeout 不依賴機器剛好裝了 GNU timeout，這件事在本機就已經成立。
2. **Codex 的事件名稱是 PascalCase，不是 snake_case。** 從 `codex` binary 的 strings 讀得到 `pre_tool_use`、`post_tool_use`、`session_start`、`user_prompt_submit`，但官方文件寫的是 `PreToolUse`、`PostToolUse`、`SessionStart`、`UserPromptSubmit`。那些 snake_case 是**內部 enum 名稱**，不是設定檔的 wire format。**逆向讀 binary 不能當依據**，照它寫設定會得到一個永遠不觸發的 hook。
3. **Codex 有 hook 信任模型，Claude 沒有。** 非 managed 的 hook 要先逐一審核並信任，而**信任是綁在 hook 定義的 hash 上**：新加或改過的 hook 在被信任之前是 **skipped**。這件事對「必要 gate」是決定性的，見§能力缺口第 1 條。
4. **「這個欄位存在」不等於「這個版本有」。** Claude 的 `onFailure: "block"` 是唯一的宣告式 fail-closed 開關，但文件在三處都註明**需 v2.1.295 以上**，而本機是 **2.1.273**。查能力時要連版本下限一起看，否則會把一個還不存在的欄位當成現成的保護。
