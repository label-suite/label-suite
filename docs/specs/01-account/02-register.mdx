# 01-02 註冊

:badge[草稿]{variant="warning"} :badge[帳號]{variant="neutral"}

## 目標

- 讓還沒有帳號的人自己建立帳號成為 :ref[平台成員]{id="term.platform-member"}，不必等 :ref[系統管理員]{id="term.system-admin"} 邀請
- 在送出之前就把填錯的地方指出來，讓使用者不必送出失敗才知道哪裡要改
- 把密碼的組成規則寫在欄位旁邊，讓使用者第一次就設得出合格的密碼

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

這一頁在登入之前，沒有任何角色能從它讀到或改到既有的業務資料。

- 未登入的訪客：R（只有這一頁本身的內容）／C（建立一個自己的帳號）；讀不到任何既有資料，也不能編輯或刪除任何東西
- :ref[平台成員]{id="term.platform-member"}：自行註冊建立的帳號，:ref[系統角色]{id="term.system-role"} 一律是平台成員（PRD §使用者角色）；這一頁不能選角色
- :ref[系統管理員]{id="term.system-admin"}、:ref[Seeder 管理員]{id="term.seeder-admin"}：不從這一頁產生。管理員要替別人開帳號走 [規格 06-01 使用者管理](../06-admin/01-user-management.mdx)
- 已經登入的人直接開這一頁會怎樣，比照 [規格 01-01 §待釐清](./01-login.mdx#待釐清) Q3

- **自行註冊**
  - 觸發：沒有帳號的人想加入平台
  - 前置條件：使用者在註冊頁
  - 主流程：
    1. 使用者填姓名、Email、密碼、確認密碼 → 點「建立帳號」
    2. 系統確認四欄都通過檢查 → 停用送出按鈕，避免重複送出
    3. 系統確認這個 Email 還沒有人用 → 建立帳號、顯示成功訊息、停用所有欄位
    4. 使用者進入儀表板
  - 替代流程：無
  - 例外流程：
    - E1（第 2 步）有欄位沒填、Email 格式不對、密碼不合組成規則，或兩次密碼不一致 → 在對應欄位旁顯示說明，停在註冊頁，流程結束（見 [§規格 › 欄位檢查與錯誤](#欄位檢查與錯誤)）
    - E2（第 3 步）這個 Email 已經有人使用 → 卡片上方顯示說明，送出按鈕恢復可用，停在註冊頁，流程結束（見 [§規格 › Email 已被使用](#email-已被使用)）
  - 結果：成功的人有了一個平台成員帳號並進入儀表板；失敗的人停在註冊頁，已填的內容都還在

- **改正後重送**
  - 觸發：使用者看到錯誤要修正
  - 前置條件：畫面上至少有一個錯誤
  - 主流程：
    1. 使用者在任一欄重新輸入 → 該欄的錯誤與卡片上方的說明都清掉
    2. 使用者重新點「建立帳號」→ 回到自行註冊的第 2 步
  - 替代流程：
    - A1（第 1 步）使用者改切換語言 → 所有欄位錯誤與卡片上方的說明也一併清掉，文字換成新語言，回到第 2 步
  - 例外流程：無
  - 結果：使用者不必重填整張表單，只改要改的那一欄

## 規格

### 註冊頁的內容

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者開啟註冊頁 → 顯示頁首（品牌與語言切換）與註冊卡片
2. 卡片裡依序是：標題與副標、姓名欄、Email 欄、密碼欄（下方有組成規則的提示）、確認密碼欄、「建立帳號」按鈕
3. 卡片底部顯示「已有帳號？」與「返回登入」
4. 頁首的語言切換鈕上只顯示目前語言的代號：繁體中文顯示 `ZH`、英文顯示 `EN`

### 填寫與送出

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者填好四個欄位 → 點「建立帳號」
2. 四欄都通過檢查 → 送出按鈕停用並顯示進行中的指示，避免重複送出
3. 這個 Email 還沒有人用 → 見 [§規格 › 註冊成功](#註冊成功)
4. 已經有人用 → 見 [§規格 › Email 已被使用](#email-已被使用)

- 這一頁建立的帳號一律是平台成員，頁面上沒有選角色的地方
- 送出按鈕停用期間使用者仍可以看到自己填的內容

### 欄位檢查與錯誤

<PrototypeFrame page="account/register" caption="註冊" client:idle />

所有能在送出前就判斷的錯誤都在送出前擋下，而且顯示在出問題的那一欄旁邊。

1. 任一欄沒填 → 該欄旁顯示必填的說明
2. 姓名去掉前後空白後為空 → 視為沒填，顯示必填的說明
3. Email 的格式不合法（沒有 `@` 或沒有網域） → Email 欄旁顯示格式的說明
4. 密碼不符合組成規則 → 密碼欄旁顯示規則的說明（見 [§規格 › 密碼規則](#密碼規則)）
5. 確認密碼和密碼不一致 → 確認密碼欄旁顯示不一致的說明
6. 使用者在報錯的欄位重新輸入 → 那一欄的錯誤立刻消失

- 姓名與 Email 都在檢查前先去掉前後的空白
- 姓名沒有長度上限（來源明訂不加上限）

### 密碼規則

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者看到密碼欄 → 下方直接顯示組成規則：**至少 8 個字元，含大寫英文、小寫英文與數字**
2. 使用者填的密碼不符合 → 密碼欄旁顯示規則的說明，不送出
3. 使用者切換語言 → 規則的提示也換成另一種語言

- 規則寫在欄位旁邊而不是等送出才說，使用者第一次就設得出合格的密碼
- 這一頁顯示規則；[規格 01-01 登入](./01-login.mdx) 刻意不顯示，因為登入不是設定密碼的時機

### Email 已被使用

<PrototypeFrame page="account/register" caption="註冊" client:idle />

這是唯一要送出之後才知道的檢查。

1. 使用者送出的 Email 已經有人使用 → 卡片上方顯示說明，停在註冊頁
2. 送出按鈕恢復可用，四欄的內容都不清空，而且焦點回到 Email 欄，使用者可以直接改
3. 使用者在任一欄重新輸入 → 卡片上方的說明自動消失；沒有手動關閉的按鈕
4. 使用者切換語言 → 說明也一併消失

- 帳號 Email 的長度上限與大小寫規則見 [規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位)：不分大小寫、最多 254 字。比對前要怎麼統一寫法（正規化的做法）由 [規格 01-05 §Email 的識別規則](./05-login-state.mdx#email-的識別規則) 定義，本頁不重複定義
- 要不要在註冊時就驗證這個 Email 真的屬於填寫的人，見 [§待釐清](#待釐清) Q1
- **這條說明會揭露「某個 Email 已經在平台註冊過」**，與 [規格 01-01 §登入失敗](./01-login.mdx#登入失敗) 刻意不揭露同一件事的立場衝突——任何人在註冊頁輸入一個 Email 就能得到確答，登入頁的保護因此失效。這一題併在 [§待釐清](#待釐清) Q1，因為寄驗證信同時解掉它

### 註冊成功

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 帳號建立成功 → 卡片上方顯示「帳號建立成功！正在導向儀表板…」
2. 同時 → 四個欄位都停用，使用者不能再改
3. 接著 → 使用者進入儀表板

- 成功後是直接進入儀表板（等於直接登入）還是回到登入頁自己登入，見 [§待釐清](#待釐清) Q2
- 成功後欄位停用是為了讓使用者不會以為還能改，而送出已經完成

### 密碼的顯示與隱藏

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 密碼欄與確認密碼欄預設都遮住內容 → 各自右側有一個切換顯示的按鈕
2. 使用者點某一個 → 只有那一欄變成看得見；再點一次 → 變回遮住
3. 按鈕的說明文字隨目前狀態改變，讓只讀文字的人也知道按下去會發生什麼
4. 使用者在密碼顯示中切換語言 → 保持顯示中，只有說明文字換語言

### 導向其他頁面

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者點「返回登入」→ 前往 [規格 01-01 登入](./01-login.mdx)
2. 使用者註冊成功 → 前往儀表板（規格 02-01，未撰寫）

### 語言切換

<PrototypeFrame page="account/register" caption="註冊" client:idle />

登入後各頁的語言切換與持久化由 [規格 07-01 §語言切換](../07-shared/01-sidebar.mdx#語言切換) 擁有，本節只寫註冊頁自己的部分。

1. 使用者點語言切換 → 卡片標題、欄位標籤、密碼規則的提示、按鈕文字、錯誤說明與瀏覽器頁籤上的頁面名稱即時換成另一種語言，不必重新整理
2. 圖示型控制項（語言切換、兩個密碼顯示按鈕）的說明文字一起換
3. 切換語言時畫面上有錯誤 → **所有欄位錯誤與卡片上方的說明都清掉**
4. 系統記住這個選擇 → 使用者回到登入頁或進入儀表板時維持同一種語言

- 第一次來的訪客預設看到繁體中文（與 [規格 01-01 §已確認決議](./01-login.mdx#已確認決議) Q5 同一個依據）

### 不同螢幕寬度的呈現

<PrototypeFrame page="account/register" caption="註冊" client:idle />

1. 使用者在手機、平板或桌機開啟註冊頁 → 都看得完整、點得到每一個控制項
2. 任何寬度下都沒有文字重疊、沒有控制項被遮住、不需要左右滑動

- 具體的螢幕寬度分界、頁首高度與卡片內距以 prototype 為準，不寫進規格

### 資料欄位

| 欄位 | 型別 | 必填 | 規則 | 使用者看到 |
| :--- | :--- | :--- | :--- | :--- |
| 姓名 | 文字 | 是 | 去掉前後空白後不得為空；沒有長度上限 | 姓名欄；沒填時旁邊的必填說明 |
| Email | 文字 | 是 | 去掉前後空白後不得為空，且格式合法（有 `@` 與網域）；不分大小寫、最多 254 字（同 [規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位)）；是否已被使用要送出後才知道 | Email 欄；格式或重複的說明 |
| 密碼 | 文字 | 是 | 至少 8 個字元，含大寫英文、小寫英文與數字 | 密碼欄預設遮住，可切換顯示；欄位下方常駐顯示規則 |
| 確認密碼 | 文字 | 是 | 必須與密碼完全一致 | 確認密碼欄預設遮住，可切換顯示 |
| 系統角色 | 單選 | 是 | 一律是平台成員，不由使用者選擇 | 不出現在畫面上 |
| 語言 | 單選：繁體中文、英文 | 是 | 第一次來的訪客預設繁體中文；記住後跨頁沿用 | 頁首的語言切換鈕上的代號；整頁文字 |

- 這一頁不顯示也不編輯既有帳號的任何資料

## 卡控機制

| 條件 | 結果 |
| :--- | :--- |
| 姓名或 Email 去掉前後空白後為空 | 擋下送出，該欄旁顯示必填的說明 |
| 密碼或確認密碼未填 | 擋下送出，該欄旁顯示必填的說明；這兩欄不去空白，全是空白字元時走組成規則或不一致的檢查 |
| Email 格式不合法 | 擋下送出，Email 欄旁顯示格式的說明 |
| 密碼不符合組成規則 | 擋下送出，密碼欄旁顯示規則的說明 |
| 確認密碼與密碼不一致 | 擋下送出，確認密碼欄旁顯示不一致的說明 |
| Email 已經有人使用 | 不建立帳號，卡片上方顯示說明，四欄內容都不清空 |
| 正在送出中 | 送出按鈕停用並顯示進行中的指示，只會送出一次 |
| 註冊成功後 | 四個欄位都停用，不能再改 |
| 使用者想選自己的系統角色 | 畫面上沒有這個選項；一律是平台成員 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到什麼 |
| :--- | :--- |
| 姓名只填空白字元 | 視為沒填，顯示必填的說明 |
| Email 前後有空白 | 先去掉空白再檢查，不因為空白被判格式錯誤 |
| 密碼有 8 個字元但全是小寫 | 顯示規則的說明，不送出 |
| 兩欄密碼都填了但不一致 | 確認密碼欄顯示不一致的說明，密碼欄不報錯 |
| 多個欄位同時出錯 | 每一欄各自顯示自己的說明，不是只顯示第一個 |
| 卡片上方正顯示重複 Email 的說明時切換語言 | 說明消失，欄位錯誤也一起清掉 |
| 註冊成功後想再改欄位 | 欄位已停用，改不了 |
| 送出後平台沒有回應 | 顯示的訊息依 [§待釐清](#待釐清) Q3；四欄的內容都還在，使用者可以重試 |
| 瀏覽器不讓平台記住語言，或記住的值不是兩種語言之一 | 當成繁體中文，不出現錯誤畫面 |
| 兩個人幾乎同時用同一個 Email 送出 | 只有一個人建立成功；後送出的那位看到同一句「這個 Email 已經有人使用」 |

## 驗收標準

| Scenario | Given | When | Then |
| :--- | :--- | :--- | :--- |
| 註冊頁顯示四個欄位與返回登入 | 未登入的訪客 | 開啟註冊頁 | 顯示姓名、Email、密碼（含規則提示）、確認密碼四欄、「建立帳號」按鈕，以及底部的「已有帳號？」與「返回登入」 |
| 語言切換鈕只顯示代號 | 目前是繁體中文 | 查看頁首的語言切換鈕 | 上面只顯示 `ZH` 一個代號 |
| 任一欄沒填就送出 | 姓名空白，其餘三欄已填 | 點「建立帳號」 | 姓名欄旁顯示必填的說明，沒有建立帳號 |
| 姓名只填空白字元 | 姓名只有空白字元，其餘三欄已填妥 | 點「建立帳號」 | 姓名欄旁顯示必填的說明 |
| Email 格式不合法 | Email 填了沒有 `@` 的字串 | 點「建立帳號」 | Email 欄旁顯示格式的說明 |
| Email 前後空白不影響檢查 | Email 的前後各有一個空白，本身格式合法 | 點「建立帳號」 | 不因為空白被判格式錯誤 |

## 待釐清

### Q1. 自行註冊要不要有門檻？

- [ ] 要：送出後寄一封驗證信到那個 Email，點了連結才算完成註冊
- [ ] 要：改成只接受特定 Email 網域（例如實驗室所屬機構）
- [ ] 不要，現在這樣就好：填完就直接有帳號
- [ ] 其他（請說明）

> 建議：第一個。目前的流程**任何人都能用別人的 Email 註冊**——來源完全沒有驗證 Email 所有權的步驟，而 [規格 06-01](../06-admin/01-user-management.mdx) 由管理員邀請的帳號反而要靠一封設定密碼信才能用密碼登入，兩條路的把關強度不一致。
> PRD §假設與限制 也寫「使用者主要是實驗室成員，人數在數十人以內」，但完全開放的自行註冊和這個假設對不上。
> **還有一個跨頁的矛盾要一起解掉**：本頁的「這個 Email 已經有人使用」會揭露某個 Email 有沒有註冊過，而 [規格 01-01](./01-login.mdx) 的登入失敗訊息刻意不揭露同一件事（理由寫在它的 Q&A）。
> 註冊頁等於把登入頁想保護的資訊整批洩出。選第一個（寄驗證信）可以同時解掉這一半：送出後一律顯示「驗證信已寄出」，不透露這個 Email 原本有沒有帳號。
> 這一題同時影響本頁的業務流程（多一段等待驗證的狀態）、01-01 的安全立場與 PRD §範圍內的描述，所以要你拍板。
> 需要決定的人：維護者（可能有 PRD 連帶影響）

### Q2. 註冊成功後是直接進入儀表板，還是回登入頁自己登入？

- [ ] 直接進入儀表板，等於註冊即登入
- [ ] 回到登入頁，請使用者用剛設定的密碼登入一次
- [ ] 其他（請說明）

> 建議：第一個。prototype 的成功訊息寫「帳號建立成功！正在導向儀表板…」，來源也導向儀表板——但來源把它標成「原型行為」，沒有說這是業務決定。
> 選第二個的好處是使用者立刻驗證一次自己記得的密碼是對的；代價是多一道手續。
> 如果 Q1 選了要寄驗證信，這一題的答案會跟著變（還沒驗證就不該直接進入平台）。
> 需要決定的人：維護者

### Q3. 送出後平台沒有回應時顯示什麼？

- [ ] 顯示一句可以重試的說明，四欄內容保留
- [ ] 其他（請說明）

> 建議：第一個，和 [規格 01-01 §待釐清](./01-login.mdx#待釐清) Q1 一起決定——兩頁都需要「送出失敗」的訊息，而來源因為只做前端原型（明寫尚未串接真實註冊）都沒有定義。
> 需要決定的人：維護者

### Q4. 自行註冊的姓名要不要比照 06-01 的 1–100 字？

- [ ] 要，兩條路統一成 1–100 字
- [ ] 不要，自行註冊沿用來源的「不加上限」
- [ ] 其他（請說明）

> 建議：第一個。[規格 06-01 §資料欄位](../06-admin/01-user-management.mdx#資料欄位) 的姓名規則是「1–100 字」，而且它寫在帳號實體的欄位表裡，不是只管管理員新增的那條路；本頁的來源則明訂「不加長度上限」。
> 同一個帳號的姓名因為建立途徑不同而有不同上限，日後在使用者管理的列表上會看到超過 100 字的姓名、但管理員改不動它。
> 兩條都有自己的依據，不是誰寫錯，所以交給你決定要不要統一。
> 需要決定的人：維護者

### Q8. 卡片上方的說明要怎麼關掉？（已定案，沿用舊來源 2026-05-22）

## Q&A

### Q. 為什麼密碼規則寫在欄位旁邊，登入頁卻刻意不寫？

兩頁的使用者處境不同。註冊的人正在**設定**一個密碼，規則寫出來他第一次就設得對，不必靠送出失敗來猜。登入的人是在**回想**一個已經設好的密碼，規則對他沒有幫助，卻會讓任何打得開登入頁的人問出平台的密碼政策。

### Q. 為什麼只有「Email 已被使用」要等送出後才知道？

其他四種檢查只看使用者填的內容本身——有沒有填、格式對不對、兩次一不一致——在使用者的裝置上就判斷得出來。「這個 Email 有沒有人用過」要問平台既有的帳號，不送出就問不到。把它和其他檢查分開寫，是為了讓讀規格的人知道哪些錯誤可以即時提示、哪些做不到。

### Q. 為什麼註冊成功後要把欄位停用？

成功訊息顯示之後還有一段導向的時間。那段時間裡欄位如果還能改，使用者會以為自己還在編輯、改了有效，但帳號其實已經用剛才送出的內容建好了。停用欄位讓畫面和事實一致。
