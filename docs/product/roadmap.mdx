# 產品路線圖

這份文件說明 Label Suite 的工作**依什麼順序做、為什麼**：每個 Epic 用一句話說它要交付什麼、服務 PRD 的哪個目標、排在哪個時段。它是策略地圖，不是排程承諾，不寫日期與工時；需求內容以 [PRD](../specs/00-prd.mdx) 與 `docs/specs/` 的規格為準，兩者說法不同時以規格為準。

## 怎麼讀

時間越遠拆得越粗：下個月拆到 Feature 與 Sub-feature，接下來兩個月只到 Epic，之後只寫要達成的目標。

| 時段 | 拆到哪一層 | 用途 |
| :--- | :--- | :--- |
| 下個月 | Feature、Sub-feature | 直接開 issue 動工 |
| 接下來兩個月 | Epic | 確認先後與依賴，動工前再拆 |
| 之後 | Goal | 說明方向，條件成熟再排 |

## 目標

路線圖的目標就是 PRD 的六個目標，不另訂；完整說法與衡量方式見 [PRD 目標](../specs/00-prd.mdx#目標)，這裡只用代號 G1～G6 指稱。

## 排序依據

順序只看依賴：一個 Epic 要等它依賴的模組能用才開始，不打分數。依賴關係以 [PRD 的跨模組流程與模組依賴](../specs/00-prd.mdx) 為準。

1. **基礎建設先收尾**：前後端、契約與 CI 共用同一套檢查，之後每個模組才不必各自補。
2. **帳號與共用外殼接著做**：每個角色都要先登入，每一頁都掛在同一個外殼上。
3. **系統管理排在任務管理前**：任務管理的權限要在系統管理收窄過的角色上檢查。
4. **任務管理 → 標記作業 → 資料集**：照跨模組流程的交接順序；資料集放在這一段而不是之後，因為試標要靠 IAA 才能推進到正式標記。
5. **儀表板與通知放到之後**：它只彙整前面模組已有的資料。
6. **論文驗證在第一次完整流程之後**：五種研究示例、步驟數比較與 SUS 都要平台能跑完一次流程；SUS 依 PRD 在正式標記完成後才招募。

效益與複雜度只分高低，用來說明每個 Epic 的投入與回報，不決定順序；所以低效益的前置工作仍然排在前面。

## 更新方式

路線圖跟著實際進度改，不是寫完就定：

| 時機 | 要改什麼 |
| :--- | :--- |
| 一個 Epic 完成 | 從 `roadmap-data.ts` 把下一段的 Epic 往前移，並把新進「下個月」的 Epic 拆到 Feature |
| 規格或 PRD 改了模組範圍或依賴 | 改對應 Epic 的範圍、一句話與排序依據 |
| SUS 或試用回饋指出新的需求 | 先走規格流程，再決定排進哪個時段 |

一句話、時段、象限都只改 `roadmap-data.ts`；元件與本文不另寫一份。
