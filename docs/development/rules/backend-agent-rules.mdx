# 後端開發規範

本文說明後端的十二條開發規範，由 `AGENTS.md` 的 Agent Rules Index 指過來；`AGENTS.md` 是規則本體，兩邊說法不同時以 `AGENTS.md` 為準，並回報給維護者。
跨領域的規範（先搜尋再新增、最小變更、衝突處理等）在 [agent-rules.mdx](agent-rules.mdx)，技術選型與 ADR 效力在 [architecture.mdx](../architecture.mdx)。

**`backend/` 已存在，但只有 B1、B2、B6、B7、B11 與 B12 的一部分檢查在 CI 跑**（job 與指令寫在各條的「檢查方式」）；B12 已建置的只有寄信、Google OIDC、對外 HTTP 客戶端三項入口契約與兩條跨模組契約，其餘四項仍標「待建置」；B8 靠人工／獨立審查，其餘各條仍標「待建置」。標「待建置」就是字面意思：那些檢查還沒有寫，**不得因為這份文件存在就宣稱架構已被強制**。

每條規範的反例與檢查方式收在摺疊區塊，預設收起；適用路徑、禁止、正例與例外在表裡。

## 規範

### B1 分層與允許的 import

Router 只呼叫 service，service 才碰 repository 與 model；資料層不處理 HTTP，狀態機的轉移判斷只在 service。一個業務模組一個資料夾 `app/modules/<module>/`，裡面放自己的 router、service、repository 與 schemas，見 [architecture.mdx](../architecture.mdx)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**` |
| **禁止** | Router 直接呼叫 Repository；資料層處理 HTTP（讀 request、回 status code、丟 `HTTPException`）；狀態機的轉移判斷寫在 Router 或 Repository |
| **正例** | `router → service → repository／model`；狀態轉移只在 service，違反時丟 `InvalidTransitionError` |
| **例外** | 無。唯讀的健康檢查之類不碰業務資料的端點沒有資料層可碰，但健康檢查模組（`app/modules/health/`）仍是分層檢查對象，檢查照跑 |

完整的轉移條件以 `docs/specs/` 與 PRD §共用狀態機 為準，不以個人 repo ADR-022 的表為準——那張表帶著個人 repo 的 FR 編號；為什麼放 service 層見 [ADR-003 的 D4](../adr/003-backend-architecture.mdx#d4-任務狀態機只放在-service-層)。

:::note{title="B1 的反例與檢查方式" collapsible}
- **反例**：Router 裡 `await repo.get(...)` 然後自己組回應；Repository 裡 `raise HTTPException(404)`
- **檢查方式**：CI 的 `backend-sqlite` job 跑 `uv run lint-imports`，契約寫在 `backend/pyproject.toml`：`app.modules.*` 內依 router、service、repository、models、schemas 的 layers 契約；router 不得直接 import 同模組的 repository 或 models；`app.core` 不得 import `app.modules`；repository 與 models 不得 import `fastapi`、`starlette`。`backend/tests/unit/test_layer_boundaries.py` 另以違規範例驗證契約真的會失敗。取得入口與跨模組（業務模組互相 import、router 只由組裝點 import）的契約見 [B12](#b12-單一入口)，這裡不重複清單
- **尚未檢查**：「狀態機的轉移判斷只在 service」沒有機械檢查，靠審查
:::

### B2 docstring、型別與指令

公開介面要有型別標註與英文 docstring，後端指令一律走 `uv run`。

| | |
| :--- | :--- |
| **適用路徑** | `backend/**` |
| **禁止** | 公開介面缺型別標註；為了讓單次測試通過而放寬型別或驗證；用 `pip`／裸 `python` 跑後端指令 |
| **正例** | `uv run pytest`、`uv run alembic upgrade head`；公開函式有英文 docstring 寫明前提、副作用與例外（`Args:`／`Returns:`／`Raises:`） |
| **例外** | 私有 helper（`_` 開頭）不強制 docstring，但型別標註仍然要 |

相依一律 `uv add` 已在 `AGENTS.md` 硬性規則 3。

:::note{title="B2 的反例與檢查方式" collapsible}
- **反例**：`python -m pytest`；為了讓一個測試過而把參數型別從 `TaskId` 放寬成 `str`
- **檢查方式**：CI 的 `backend-sqlite` job 與 `pnpm run check` 跑 `uv run mypy --strict app`；`backend/pyproject.toml` 的 `[tool.mypy]` 已設 `strict = true`，所以本機 `uv run mypy app` 結果相同。型別檢查的範圍只有 `app`。`uv run ruff check .` 對整個 `backend/` 跑，選用 `E`、`F`、`I`、`UP`、`B`、`S`、`ASYNC` 與 `D`（docstring 規則，google 風格，忽略 `D107`）；文件註解規則實際上只約束 `app`，`tests/**` 與 `alembic/**` 以目錄樣式豁免 `D`，因為 B2 約束的是公開介面，測試函式與遷移腳本不是公開介面。`_` 開頭的私有 helper 不受 docstring 檢查，這是 ruff 不檢查 `_` 開頭名稱的預設，設定裡沒有為此加規則。`uv run ruff format --check .` 檢查格式。指令一律以 `uv run` 執行
- **尚未檢查**：docstring 的**有無與段落格式**已機械檢查，但內容是否寫明前提、副作用與例外，以及建構參數是否寫在類別 docstring 的 `Args:`（`__init__` 的 `D107` 已忽略），仍靠審查；`tests` 的型別與 docstring 不受檢
:::

### B3 session 的生命週期

API 一個請求一個 session、worker 一個 task 一個同步 session，用完就關，不跨請求或跨 task 共用。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**`（含模組內的 Celery 進入點）。**不寫 `backend/worker/`**：`architecture.mdx` 的 `worker` 是與 `backend` 共用同一個 image 的 container，不是一個目錄；Celery 進入點落在 `app/modules/<module>/` |
| **禁止** | 跨請求或跨 task 共用同一個可變 session；把 session 存進模組層的全域變數；在 Celery task 裡用 async engine |
| **正例** | API 用 `db: AsyncSession = Depends(get_db)`，一個請求一個 session；worker 用同步 session，一個 task 一個，結束就關 |
| **例外** | 無。例外發生時一律 rollback 並釋放連線，不讓連線留在交易中回到 pool |

理由：Celery 跑在同步執行緒裡，不能用 async engine，所以 API 與 worker 用不同的驅動（Lite 用 `sqlite+aiosqlite`／同步 URL；正式用 `postgresql+asyncpg`／`psycopg2`，見 [architecture.mdx](../architecture.mdx)）。

:::note{title="B3 的反例與檢查方式" collapsible}
- **反例**：`SESSION = async_session()` 放在 module top-level，所有請求共用；把 `AsyncSession` 當參數塞進 `task.delay(...)`
- **檢查方式**：**待建置**。整合測試可斷言「請求結束後 pool 的 checked-out 連線回到 0」；需要 `backend/` 的測試 harness
:::

### B4 交易的擁有層

交易由 service 擁有；外部呼叫與 task 派送都放在 commit 之後，且每一個都要有明確的補償路徑。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**` |
| **禁止** | Repository 自行 `commit`；在 DB 交易裡做外部網路呼叫；**在交易尚未 commit 前呼叫 `.delay()`／`.apply_async()`**；把「寄完信再 commit」當成預設做法 |
| **正例** | **交易由 service 擁有**：多步寫入在同一個交易內，業務資料與必要稽核一起 commit；外部呼叫（寄信、第三方 API）**與 task 派送**都放在 commit 之後，失敗走補償路徑 |
| **例外** | 稽核事件若規格要求「即使業務失敗也要留痕」，那一筆走獨立交易，而且要在程式註解寫明為什麼分開 |
| **失敗補償要寫明** | commit 之後的每一個外部動作（寄信、派送 task）都要有**明確的補償路徑**：寄信失敗照[寄信降級的做法](../architecture.mdx)（連結印在伺服器 log）；**派送失敗**則由該筆資料的狀態欄留在「待派送」，由排程補送或人工重送——不得靜默吞掉 |

理由：「寄完信再 commit」的順序會讓寄信失敗吃掉已成立的業務結果。

:::note{title="B4 的反例與檢查方式" collapsible}
- **反例**：`repo.create()` 裡面自己 `await session.commit()`，讓上層的交易邊界失效；在交易裡 `await smtp.send()`，把 DB 連線佔住到網路逾時；**交易內就 `score.delay(submission_id)`——worker 搶先查不到那一列**
- **檢查方式**：**待建置**。可用「Repository 層不得出現 `commit`」的靜態檢查
:::

### B5 資料存取一律走 SQLAlchemy

查詢、寫入與測試的資料準備都用 SQLAlchemy 的 model 與 select／insert 構造，不拼 SQL 字串，也不用 `text()` 繞過 ORM。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**`、`backend/tests/**` |
| **禁止** | 拼接 SQL 字串；用 `text()` 包一段手寫 SQL 來繞過 ORM |
| **正例** | 查詢、寫入與測試的資料準備都用 SQLAlchemy 的 model 與 select／insert 構造 |
| **例外** | **三種**：(1) Alembic migration 裡的 DDL；(2) schema API 表達不了的 DDL（partial index、extension、RLS 之類）；(3) **migration 內的資料遷移（DML）**。三者都要在該 migration 的 docstring 寫明為什麼只能這樣寫；第 (3) 項另外要寫明**影響的列數量級、能不能重跑、以及怎麼回復**，資料遷移需個別說明，不把 migration 變成任意 SQL 逃生門 |

:::note{title="B5 的反例與檢查方式" collapsible}
- **反例**：`session.execute(text(f"SELECT * FROM tasks WHERE id = '{task_id}'"))`
- **檢查方式**：**待建置**。可用「`app/` 底下不得 import `text`」的靜態檢查，migration 目錄排除。import-linter 只能擋整個套件，擋不了 `text` 這種名稱，所以不能用它補這一條（見 [B12](#b12-單一入口) 的尚未檢查）
:::

### B6 schema 只由 Alembic 管

任何環境的 schema 都只由 Alembic migration 建立與變更，每個 migration 都能 `up` 也能 `down`，已部署的 migration 不再改動。

| | |
| :--- | :--- |
| **適用路徑** | `backend/alembic/**`、`backend/app/**/models.py` |
| **禁止** | 任何環境（含 dev、test）用 `create_all` 或自動同步建 schema；改動已部署的 migration |
| **正例** | 每個 migration 都能 `up` 也能 `down`，`down` 精確還原 `up`；提交前在本機跑一次 `upgrade → downgrade → upgrade`；generate 之後讀過產物，確認沒有非預期的 `DROP` |
| **例外** | **不可逆的變更**（刪欄位、改型別導致資料遺失）允許 `down` 無法完全還原，但要在 migration 的 docstring 寫明不可逆的部分，並經維護者審核 |

:::note{title="B6 的反例與檢查方式" collapsible}
- **反例**：測試 fixture 裡 `Base.metadata.create_all(engine)`；直接編輯上一版已部署的 migration 檔
- **檢查方式**：`backend/tests/integration/test_migrations.py` 在所選的測試資料庫上跑 `upgrade → downgrade → upgrade`，由 CI 的 `backend-sqlite` 與 `backend-postgres` 兩個 job 各跑一次
- **尚未檢查**：禁用 `create_all`、禁改已部署 migration 都沒有機械檢查，靠審查
:::

### B7 雙資料庫的測試要求

牽涉 SQLite 與 PostgreSQL 差異的行為，兩邊都要有測試；只在 SQLite 上跑過不得宣稱 PostgreSQL 通過。

| | |
| :--- | :--- |
| **適用路徑** | `backend/tests/**` |
| **禁止** | 只在 SQLite 上跑過就宣稱 PostgreSQL 通過 |
| **正例** | 兩層都在支援範圍內，所以牽涉下列差異的行為**兩邊都要有測試**：JSON／JSONB 的查詢與索引、約束（partial unique、check、外鍵的 deferrable）、日期與時區、migration 行為、並發寫入 |
| **例外** | 不碰上述差異的純邏輯測試只跑一邊即可 |

:::note{title="B7 的反例與檢查方式" collapsible}
- **反例**：整個測試套件只跑 SQLite，PR 寫「資料層測試通過」
- **檢查方式**：CI 有兩個後端 job：`backend-sqlite` 不設 `TEST_DATABASE_URL`，標 `postgres` 的測試在這一輪 skipped；`backend-postgres` 以 `postgres:16` 服務容器與 `TEST_DATABASE_URL` 跑 `uv run pytest`，之後 `node ../scripts/check-junit-skips.mjs` 在任何測試被 skipped 時失敗，所以標 `postgres` 的測試不會悄悄停跑。哪些行為「牽涉兩層差異」仍由撰寫測試的人判斷，靠審查
:::

### B8 刪除、軟刪除與匿名化

每一種資料的刪除語意依功能規格與資料保留政策個別決定，不把「所有 entity 一律軟刪除」當預設。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**`、`backend/alembic/**` |
| **禁止** | **把「所有 entity 一律軟刪除」當成預設**；對帶答案的歷史資料做 PII 匿名化或單獨刪除 |
| **正例** | 每一種資料的刪除語意依**功能規格與資料保留政策**個別決定。稽核事件列**永遠不刪**，過了最短保留期只能把 PII 欄位墓碑化；帶答案的歷史 JSON 跟著它所屬的資料集版本或 run 存續 |
| **例外** | 規格明確要求軟刪除的那些資料照做，並在 model 的 docstring 指向該規格 |

檢查方式是**人工／獨立審查**：刪除語意是規格問題，沒有辦法機械判定，所以現在就要做。

:::note{title="B8 的反例" collapsible}
新增 entity 時順手繼承一個「含 `deleted_at` 的共用基底」並把查詢預設都加上排除條件——那是把別的專案的預設搬過來，不是本專案的規格。
:::

### B9 Celery 的界線

Celery task 只收可序列化的識別資訊，在自己的行程裡重新查權限與資料版本；重試有界、task 冪等、結果與失敗狀態落地。

| | |
| :--- | :--- |
| **適用路徑** | 模組內的 Celery task 定義（落在 `app/modules/<module>/`）與所有 `.delay()`／`.apply_async()` 的呼叫點 |
| **禁止** | 把 HTTP 物件（request、response、`UploadFile`）或 DB session 塞進 task 參數；無界重試；task 的結果與失敗狀態不落地 |
| **正例** | 只傳可序列化的識別資訊（`task_id`、`submission_id`）；task 在自己的行程裡**重新查權限與資料版本**；重試有上限、task 冪等（重跑同一個 task 不會產生第二筆結果）；結果與失敗狀態寫進資料庫 |
| **既定界線** | Celery 只用於**長時間工作**（評分、IAA 計算、匯出）走 `scoring` 佇列；雜務走 `default`（`architecture.mdx`）。「重試有界」的數字也已定：**最多重試三次、退避 60／180／540 秒、單一評分工作硬上限 300 秒、結果在 result backend 留 24 小時**，不要另訂 |

「重新查權限」與授權規範相接，授權本身見 [security-agent-rules.mdx](security-agent-rules.mdx)。

:::note{title="B9 的反例與檢查方式" collapsible}
- **反例**：`score.delay(submission=upload_file, db=session)`；`autoretry_for=(Exception,)` 不設 `max_retries`
- **檢查方式**：**待建置**。「task 參數只能是基本型別」可用靜態檢查；冪等性要靠測試（重跑同一個 task 斷言只有一筆結果）
:::

### B10 設定與 secret

設定集中在一個 Pydantic Settings 類別驗證，必要設定缺失時啟動就明確失敗；可選整合的降級要維護者確認。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/core/config*`、所有讀環境變數的地方 |
| **禁止** | 散落各處 `os.environ[...]`；必要設定缺失時用預設值悄悄啟動；**在未決的情況下自行把密碼或重設連結印出來** |
| **正例** | 設定集中在一個 Pydantic Settings 類別驗證；必要設定缺失**明確失敗**（啟動就報錯，不是第一個請求才爆） |
| **例外** | **可選整合的降級要維護者確認**。已確認的一例：沒設定 Google 時登入頁不顯示 Google 按鈕與「或」分隔線；寄信降級的做法為「連結印在伺服器 log，Lite 版的 log 視為敏感」 |

:::note{title="B10 的反例與檢查方式" collapsible}
- **反例**：`SECRET_KEY = os.getenv("SECRET_KEY", "dev-secret")`——缺設定時靜默用弱預設值
- **檢查方式**：**待建置**。「`app/` 底下除 config 模組外不得 import `os.environ`」可靜態擋
:::

### B11 函式複雜度與檔案行數上限

函式的圈複雜度、敘述數、分支數與檔案行數各有上限；這是擋極端值的護欄，不是拆分判準。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/`、`backend/tests/`、`backend/alembic/` |
| **禁止** | 函式的圈複雜度超過 10（`C901`）、敘述數超過 30（`PLR0915`）、分支數超過 10（`PLR0912`）；單一檔案超過 400 行 |
| **正例** | 逼近上限時，先依 [agent-rules.mdx](agent-rules.mdx) R4 判斷職責是否該拆；不為了壓低數字把同一個概念硬拆成兩處 |
| **例外** | （1）`alembic/versions/`（產生的 migration 腳本）不受函式與檔案兩類上限約束；`alembic/` 的其他檔案照常受限；（2）檔案行數的例外表是 `backend/tests/unit/test_size_limits.py` 的 `EXEMPTIONS`：條目即棘輪（檔案再變長就再失敗）、過期即失敗（檔案已不超標就必須移除條目），目前為空；新增條目要寫 issue 與理由。函式的三條 ruff 規則沒有例外表。**不檢查**參數數與回傳數，也不開 `RUF100` |

檔案行數的「行」以純文字逐行計算、不做語法解析：排除空白行與去掉前後空白後以 `#` 開頭的行；docstring 內以 `#` 開頭的行同樣排除，docstring 的其他行計入。這與前端 [F12](frontend-agent-rules.mdx) 的計法不同（F12 由 ESLint 排除空白行與註解），兩邊的數字不可互比。

與 R4 的關係：R4 與 [agent-rules.mdx](agent-rules.mdx) 駁回以固定行數取代職責審查，這個判斷不變。B11 的上限只擋極端值，沒超過上限不代表不需要拆，超過上限也只是必須處理而不是自動該拆成幾份；是否拆分仍依 R4 的職責判斷。

:::note{title="B11 的反例與檢查方式" collapsible}
- **反例**：在 `app/` 加一個有 31 個敘述的函式，`ruff` 報 `PLR0915`；一個檔案累計 401 行非空白、非 `#` 開頭的行，`test_size_limits.py` 失敗
- **檢查方式**：CI 的 `backend-sqlite` job 的 Lint 步驟（`uv run ruff check .`）擋三條函式規則，數值在 `backend/pyproject.toml` 的 `[tool.ruff.lint.mccabe]` 與 `[tool.ruff.lint.pylint]`；兩個後端 job（`backend-sqlite`、`backend-postgres`）的 pytest 跑 `tests/unit/test_size_limits.py`，它檢查檔案行數、守住例外表的棘輪與過期，並以探針守住 ruff 規則碼、數值與 `alembic/versions/` 以外沒有被放寬
:::

### B12 單一入口

每一種對外的整合與橫切能力，後端只准有一個入口；業務程式經由入口使用，不直接 import 底層套件。業務模組之間也不得互相 import，router 只由組裝點 `app.main` import。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**`。`backend/alembic/` 與 `backend/tests/` 不在 import 檢查的圖內，不受檢 |
| **禁止** | 單一入口清單（下表七項）中，入口以外的程式直接 import 該入口包裝的底層套件；任兩個業務模組（`app/modules/` 底下）互相 import，不分 router、service、repository、models、schemas（唯一的放行形式見「例外」）；組裝點以外的任何檔案 import router |
| **正例** | 業務模組 import 入口，入口再 import 自己的套件（間接使用不算違規）；`app/main.py` 同時 import 多個模組的 router |
| **例外** | 入口本身 import 自己的套件。今天 `backend/app/` 沒有任何入口，契約沒有 `ignore_imports`，也沒有白名單。第一個入口落地的 change 要在同一個 change 裡升級契約，二擇一：（a）入口是新的頂層套件：不動契約，把它登記進 `backend/tests/unit/import_tree.py` 的 `ENTRY_TOP_LEVEL_PACKAGES`，它因不在 `source_modules` 內而被放行；（b）入口在 `app/core/` 或 `app/modules/` 內：該契約改成 `source_modules = ["app"]` 加帶理由與來源的 `ignore_imports`。兩種都要同步 `backend/tests/unit/import_tree.py` 的 `ENTRY_THIRD_PARTY`。放行 import 的 `ignore_imports` 必須寫成多行陣列、每條各佔一行，緊接其上的註解寫明理由與來源（issue 編號或規則編號）；契約不得設定關閉「放行項已不存在」警示的選項，放行項過期時檢查就失敗。業務模組之間的例外只有一種形式：一個模組讀另一個模組的資料，只透過對方 service 公開的函式，每一處在 `Modules do not import each other` 加一條 `ignore_imports`，箭頭右邊只准是對方的 `app.modules.<module>.service`，不准是 `repository` 或 `models`，寫法同上（理由見 [ADR-003 的 D12](../adr/003-backend-architecture.mdx#d12-跨模組讀資料只透過對方-service-的公開函式)）。稽核紀錄的寫入在 `app/core/`，任何模組直接 import（見 [ADR-003 的 D13](../adr/003-backend-architecture.mdx#d13-稽核紀錄的-model-與寫入函式放在-core)）；授權第 3、4 步的檢查在 `app/core/`，權限矩陣的資料經 `app/core/` 定義的 Protocol 提供（見 [ADR-004 的 D6](../adr/004-auth-and-security.mdx#d6-權限矩陣當授權輸入)）；兩者都不需要 `ignore_imports` |

單一入口清單（本文唯一定義處，其他規則只指向這裡）：

| # | 入口 | 禁止直接 import（`forbidden_modules`） | 狀態 |
| :-: | :--- | :--- | :--- |
| 1 | 寄信 | `resend`、`smtplib`、`aiosmtplib` | 已建置：契約 `Mail only through its entry` |
| 2 | Google OIDC | `authlib` | 已建置：契約 `OIDC only through its entry` |
| 3 | 對外 HTTP 客戶端 | `httpx`、`requests`、`aiohttp`、`urllib3` | 已建置：契約 `Outbound HTTP only through its entry`。每個整合自己的包裝就是它的入口，不另設共用 HTTP 層 |
| 4 | 取得目前使用者 | — | 待建置：import-linter 只看 import 圖，看不到方法呼叫與依賴注入接線 |
| 5 | 發 session cookie 的 helper | — | 待建置：同上 |
| 6 | CSRF 驗證 middleware | — | 待建置：同上 |
| 7 | 資料庫 session 取得（`get_db`） | — | 待建置：同上 |

三條入口契約的 `source_modules` 都是 `app.core`、`app.modules`、`app.main`、`app.scripts`，並帶 `allow_indirect_imports = true`，所以入口套件不在檢查來源內時可以 import 自己的套件，業務模組經由入口間接到達該套件也不算違規。跨模組有兩條契約：`Modules do not import each other`（`independence`，涵蓋 `app.modules.*`）與 `Only the assembly point imports routers`（`protected`，router 只准 `app.main` import）。

入口也是測試替身應該放的位置，見 [testing-agent-rules.mdx](testing-agent-rules.mdx) 的 T6。

:::note{title="B12 的反例與檢查方式" collapsible}
- **反例**：某模組的 service 裡 `import resend` 自己寄信；`health` 模組的 router import 另一個模組的 service；某模組的 service import 自己的 router
- **檢查方式**：CI 的 `backend-sqlite` job 跑 `uv run lint-imports`，契約名稱與設定在 `backend/pyproject.toml`：`Mail only through its entry`、`OIDC only through its entry`、`Outbound HTTP only through its entry`、`Modules do not import each other`、`Only the assembly point imports routers`。兩個後端 job 的 pytest 另跑四個測試檔：`backend/tests/unit/test_entry_contracts.py` 以違規樣本驗證入口與跨模組契約真的會失敗，並守住「`app` 底下每個頂層套件不是列入每條入口契約的檢查來源，就是已登記的入口套件」；`backend/tests/unit/test_dependency_classification.py` 要求 `app` 實際 import 的每個第三方套件都已歸類，且入口的套件清單與契約的 `forbidden_modules` 一致；`backend/tests/unit/test_contract_exemptions.py` 守住 `ignore_imports` 的註解、多行寫法與不得關閉過期警示；`backend/tests/unit/test_layer_boundaries.py` 以契約數量與名稱集合比對 `pyproject.toml`，增、刪或改名契約而沒有同步預期名稱時失敗
- **尚未檢查**：（1）取得目前使用者、發 session cookie 的 helper、CSRF 驗證 middleware、`get_db` 四項沒有機械檢查，標「待建置」，原因見上表，不用 Semgrep；（2）標準庫的 `urllib.request` 與 `http.client` 擋不了，外部套件只認根套件，`urllib` 整包會誤擋 `urllib.parse`；不宣稱 Ruff `S310` 補得上；（3）子模組與名稱擋不了，例如 `sqlalchemy.text`（見 [B5](#b5-資料存取一律走-sqlalchemy)）；（4）入口 A import 入口 B 的套件沒有契約，入口落地時再補；（5）新的第三方套件被歸為「一般套件」就不受入口限制，歸類本身靠審查；（6）跨模組的 `ignore_imports` 只准指向對方的 `service`，這一點沒有機械檢查，靠審查
:::
