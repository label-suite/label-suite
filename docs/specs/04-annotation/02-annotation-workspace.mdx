## 目標

| 目標 | 誰受益 |
| :--- | :--- |
| 讓:ref[標記員]{id="term.annotator"}一次只面對一筆資料，題目、作答控制項與任務說明**同時在畫面上**，不必在頁面之間來回 | 標記員——減少翻頁造成的標記偏差 |
| 讓任務說明**翻筆之後還在**，而且在手機上也拿得到 | 標記員與:ref[審核員]{id="term.reviewer"}——說明一消失，標準就會各憑記憶 |
| 讓工作區**完全由任務發布時凍結的設定驅動**，不替任何任務寫死特例 | 專案負責人——改設定就能改作業方式，不必等系統改版 |
| 讓網址**一直指著畫面上的那一筆**，重新整理、加書籤、貼給別人都回到同一個地方 | 需要互相對照同一筆資料的人 |
| 讓標記員在這一頁接觸不到:ref[標準答案]{id="term.ground-truth"}，**連樣本的識別鍵都不顯示** | 整個標記品質管線——答案一旦外洩，這個任務的資料就不能用了 |

## 使用角色

| 角色 | 這一頁能做什麼 | PRD §權限矩陣的上限 |
| :--- | :--- | :--- |
| :ref[標記員]{id="term.annotator"} | R／C／E，**只限被指派給自己的資料** | 「04 標記清單與標記工作區（產出標記）」給標記員 `R/C/E (o)` |
| :ref[審核員]{id="term.reviewer"} | R／E | 「04 標記清單與標記工作區（審核與仲裁）」給審核員 `R/E` |
| :ref[專案負責人]{id="term.project-leader"} | 只處理:ref[審核員]{id="term.reviewer"}收不掉的例外（見[§最終例外池是最後一道出口](#最終例外池是最後一道出口)），**不產出標記** | 同一列給專案負責人 `R` |

- 工作區的作用角色只有標記員與審核員兩種；專案負責人進得來的是**最終例外池的處置畫面**，它共用這一頁的外殼但不是標記畫面（麵包屑第 1 層因此有第三種字面，見[§入口麵包屑的第三層](#入口麵包屑的第三層)）
- 專案負責人在這一頁的處置動作寫在[§最終例外池是最後一道出口](#最終例外池是最後一道出口)
- **這裡有一處超出 PRD 的上限，本頁不默默放寬**：PRD §權限矩陣「04 標記清單與標記工作區（審核與仲裁）」那一列給專案負責人的上限是 `R`，而最終例外池的收尾（採標記員值／採審核員值／填自訂答案／排除這筆）是**寫入動作**。PRD 另有一句「專案負責人在標記工作區只處理審核員無法收斂的例外，不產出標記」，說的是**範圍**不是權限字母。本頁依[規格 07-01](../07-shared/01-sidebar.mdx)的做法明寫這個落差，**不把那一列改成 `R/E`**；PRD 的改動由 Issue #85 處理。階段五寫處置動作時要再引一次這一條
- 這個落差與[規格 04-01 §待釐清](./01-annotation-list.mdx#待釐清) Q1 是同一個缺口的兩半：那一題問的是專案負責人進不進得了標記清單，這一條管的是他進到工作區之後做的事超不超出上限
- :ref[系統管理員]{id="term.system-admin"}沒有任務角色時進不來，和[規格 04-01](./01-annotation-list.mdx)一樣

### 進入工作區並開始作業

1. 使用者從儀表板的快速入口、[標記清單](./01-annotation-list.mdx)的某一列，或**直接貼一個深連結**進來
2. 系統解析網址帶來的任務、那一筆、角色與標記階段
3. 查任務**發布時凍結**的設定，查得到嗎？
   - 查得到 → 載入那一筆樣本、說明檔案與進度，三欄就位
   - 查不到 → 導回標記清單，**不得以任何預設的輸出類型或空白控制項呈現工作區**，流程結束
4. 這個任務要求先讀說明嗎？
   - 要求，而且目前這個:ref[指引版本]{id="term.guideline-version"}還沒被確認過 → 顯示說明彈窗，使用者按確認才開始
   - 不要求 → 直接開始（替代流程 A1）
5. 使用者在中欄作業，必要時翻到上一筆或下一筆；每次翻筆都把網址改寫成畫面上的那一筆
6. 替代流程 A1：任務沒要求先讀說明 → 跳過第 4 步的彈窗，右欄的說明仍然常駐
7. 替代流程 A2：使用者在手機上 → 說明改由底部抽屜承載，翻筆時抽屜維持原本的開合狀態
8. 例外流程 E2：網址沒帶那一筆 → 導回標記清單，流程結束
9. 例外流程 E3：網址帶的那一筆查不到 → **回退到第一筆**，並把網址改寫成實際顯示的那一筆，回到第 5 步

## 規格

本階段寫的是**外殼**：版面、挑筆、翻筆、說明與檔案、進場的說明確認、網址同步與快捷鍵。中欄裡面**實際怎麼作答**（八種輸出類型）由階段二寫，**審核卡**由階段四寫。

### 工作區的外殼：三欄與行動版

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 工作區是**單筆作業頁**：一次只處理一筆，整頁**沒有頁首**，最上面只有一條[入口麵包屑](#入口麵包屑的第三層)
2. 桌機固定三欄：

| 欄 | 承載什麼 |
| :--- | :--- |
| 左欄 | [標記清單](#左欄標記清單)與目前定位 |
| 中欄 | 上方[樣本導覽與進度](#中欄上方樣本導覽與進度)、主體[題目卡與標記卡](#中欄主體題目卡與標記卡)、下方[操作列](#中欄下方操作列) |
| 右欄 | [說明與檔案、操作紀錄](#右欄說明與檔案操作紀錄)雙頁籤 |

3. 右欄在桌機**可以收合，收合後可以再展開**
4. 手機（寬度 767 以下）只留精簡的目標列與主操作區，說明與檔案改放**底部抽屜、預設收合**
5. 手機必須**主操作優先**：抽屜是輔助資訊，**不得遮蔽核心的標記區**
6. 抽屜**只承載說明與檔案**；「操作紀錄」頁籤是桌機右欄才有的（見 [§已確認決議](#已確認決議) Q6）
7. 翻到下一筆時：桌機右欄**不收起、內容不重置**；手機抽屜**維持目前的開合狀態**
8. 中欄**不得出現任務標題卡**——任務名稱的標頭與卡內的語言切換鈕都不行，標記員與審核員都一樣
9. 任務名稱**只由右欄「任務說明」的摘要呈現**，而且要優先用這個任務實際的名稱，只有在缺任務上下文時才退回輸出類型層級的預設文案
10. 語言切換由側欄提供，和其他頁面一致（見[規格 07-01](../07-shared/01-sidebar.mdx)）
11. 要驗的螢幕寬度是 375、768、1440 三種
12. 來源要求的「固定任務目標列」在畫面上只有一部分落地，**任務目標與操作指引沒有落點**，見 [§待釐清](#待釐清) Q1

#### 這一頁讀得到什麼、不得改什麼

1. 工作區讀的是任務**發布時凍結**的那一份設定：輸出類型與它們的順序、欄位各自的用途（舉證、題目輸入、作答產出）、配對任務的兩邊標題、說明檔案清單
2. 樣本來源**鎖定在發布時凍結的那一份資料快照**，工作區**不得自己重算或覆寫切分**——:ref[試標]{id="term.dry-run"}與:ref[正式標記]{id="term.official-run"}都一樣
3. 說明檔案來自**當前回合釘住的那個:ref[指引版本]{id="term.guideline-version"}**；之後把說明另存新版，**不會改到已經開始的回合**
4. 工作區**不得為個別任務寫死邏輯**：有幾個輸出類型、是哪幾種、什麼順序，一律照設定來
5. 資料敏感度：這一頁讀得到的樣本內容是**任務資料**，可能含個資，只有被指派的人進得來；:ref[標準答案]{id="term.ground-truth"}**不屬於標記員讀得到的範圍**（階段二會把這條寫成卡控）
6. 設定本身在這一頁是**唯讀**的——要改設定得回[規格 03-03 任務詳情](../03-task-management/03-task-detail.mdx)

### 入口麵包屑的第三層

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

麵包屑的前兩層與「深連結和站內點進來要長得一樣」這條總規則寫在[規格 04-01 §入口麵包屑](./01-annotation-list.mdx#入口麵包屑)；工作區**多出第 3 層**，而且第 1 層在這一頁有第三種字面。

1. 工作區的麵包屑**有三層**，第 3 層就是目前層級：

| 層級 | 顯示 | 連到哪 |
| :--- | :--- | :--- |
| 第 1 層 作業區 | 審核員「審核作業」、標記員「標記作業」、專案負責人處理例外時「例外處置」 | **儀表板** |
| 第 2 層 任務 | 「〈任務名稱〉（〈標記階段〉）」 | 標記清單，**回帶任務、角色與標記階段** |
| 第 3 層 目前單位 | 依角色不同，見第 2 條 | **不帶連結，它就是目前層級** |

2. 第 3 層依角色分流，這是**資料公平性的硬性規則**：

| 角色 | 第 3 層顯示 |
| :--- | :--- |
| 審核員 | `審核單位 {sample} · {annotator}`——那一筆的識別碼與**受審標記員的帳號** |
| 標記員 | **只顯示佇列位置** `樣本 {i} / {n}`，**不得顯示那一筆的識別碼，也不顯示自己的帳號** |
| 專案負責人（例外處置） | `例外項目 {sample} · {annotator}` |

3. 標記員那一層**不得顯示識別碼**的理由寫在來源裡：有些資料集拿**沒有被指派用途的欄位**當記錄識別鍵，把它渲染進標記員看得到的地方就等於洩漏答案線索；標記員自己的帳號對標記員而言是零資訊，也不重複顯示（見 [§已確認決議](#已確認決議) Q7）
4. 麵包屑要**跟著換筆與換語言一起重畫**，不能只在進場時畫一次
5. 第 2 層一定要**回帶身分參數**：帶著標記員身分進來的，返回清單的網址也要帶同一個身分；**沒帶身分進來的就不得補上**（否則「缺值套用預設」這件事在兩頁之間就不再是共識）
6. 身分參數要和清單的四個檢視狀態**併存**，不能只轉發一種（見 [規格 04-01 §清單檢視狀態往返工作區](./01-annotation-list.mdx#清單檢視狀態往返工作區)）
7. 麵包屑在窄螢幕**不會被隱藏**，但標記員帳號在它的尾端，需要橫向捲動才看得到——窄螢幕下審核單位的身分就由這一層承載

### 左欄：標記清單

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 左欄的標題**固定是「標記清單」**，**不得附加回合標籤**——不能變成「試標回合 R2」「正式標記清單」之類的字面
2. 回合是靠[麵包屑第 2 層](#入口麵包屑的第三層)講的，位置在三欄主體之上，兩者不衝突
3. 標題旁的**筆數仍然要按當前回合的清單規模顯示**：試標顯示這一回合建立的筆數，正式標記顯示正式清單的筆數
4. 當前標記階段**還沒有已建立的清單筆數**時，筆數**回退顯示該任務資料集的筆數**
5. 審核員的筆數單位是**審核單位**而不是樣本（同一筆由 N 位標記員標記就是 N 個單位），算法見階段六
6. 每一列的組成：**序號徽章 + 文本摘要（必要時加摘要標籤）+ 完成狀態標籤**
7. 文本摘要和[標記清單](./01-annotation-list.mdx)用**同一套算法**，不另立一套：見 [規格 04-01 §文本摘要怎麼來](./01-annotation-list.mdx#文本摘要怎麼來)
8. **摘要標籤只有工作區左欄會顯示**，標記清單那一頁沿用前綴、不顯示標籤。摘要取自對話串形態時，摘要**旁邊**要加標籤：

| 條件 | 標籤 |
| :--- | :--- |
| 任務設定指定了對話串欄位，而且摘要就是取自對話串形態 | 「〈則數〉 則發言」（則數就是那一串的筆數） |
| 再加上任務設定指定了發言者子欄位，而且不重複的非空發言者數至少 1 位 | 再加「〈人數〉 位發言者」 |

9. 標籤要出現在**工作區左欄的三個地方**：標記員的每一列、審核員的分組表頭、例外處置的分組表頭
10. 標籤**不得依任務編號或欄位名稱寫死**、**不得讀用途是輸出的欄位**，也**不得從實體、關係或文字裡的 `@名字` 去猜**——和前綴同一套限制
11. 搜尋比對的字串**不含前綴也不含標籤**（搜尋本身在[標記清單](./01-annotation-list.mdx)那一頁）
12. 標記員視角的完成狀態標籤是**三態**，而且儲存草稿或提交之後要**即時更新**那一列：

| 標籤 | 什麼時候 |
| :--- | :--- |
| 已提交 | 這一筆已經提交 |
| 已儲存 | 存了草稿、還沒提交 |
| 待標記 | 還沒動過 |

13. 目前在看的那一列要**高亮**，而且必須是網址帶進來的那一筆，**不得固定落在預設的第一筆**
14. 點某一列就切到那一筆
15. 審核員視角的一列是**一個審核單位**、狀態標籤換成審核單位的三態，而且同一筆的多個單位要包在該筆的分組容器裡——見[§審核員視角的左欄：審核單位依樣本分組](#審核員視角的左欄審核單位依樣本分組)
16. 專案負責人的例外處置清單列的是**待處置的例外項**，不是一般樣本，見[§例外處置畫面的外殼](#例外處置畫面的外殼)

### 中欄上方：樣本導覽與進度

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 中欄頂部是導覽列：**「上一筆」按鈕 + 進度摘要（含進度條）+「下一筆」按鈕**
2. 位在**首筆或末筆**時，對應的那個按鈕**停用**
3. 進度摘要依角色分流：

| 角色 | 文字 |
| :--- | :--- |
| 標記員 | `{已提交} / {總筆數} 已提交` |
| 審核員 | `我的審核提交 {已提交} / {總筆數} 個審核單位`——分子是自己已送出審核的單位數，分母是審核單位總數 |

4. 提交之後進度要**即時更新**，不必重新整理
5. 審核員的「筆」是**審核單位**，所以導覽與分母都按審核單位算（算法見階段六）；標記員的「筆」就是樣本
6. 翻筆時右欄的說明**不收起、不重置**（見[§工作區的外殼](#工作區的外殼三欄與行動版)第 7 條）

### 中欄主體：題目卡與標記卡

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

這一段只寫**卡片怎麼切**；卡片裡面實際的作答控制項由**階段二**撰寫。

1. 題目內容與標記控制項**以獨立卡片區隔**：題目卡承載舉證內容與題目輸入，標記卡承載**依設定順序逐一排出**的各個輸出類型
2. 卡片怎麼切，**依欄位用途與輸出類型的結構決定**，**不得依任務名稱或個別輸出類型寫死分支**
3. 輸出類型自己就把原文內嵌在標記區裡時（例如要在文本上圈選的那幾種），**題目卡可以省略**
4. **卡片邊框是題目／標記區塊的唯一外框**：
   - 題目卡裡的輸入內容**直接呈現，不得再包一層內框**
   - 標記卡裡**不得殘留水平分隔線**，包含區塊分隔線與「無法判定」選項上方的虛線（那個選項在畫面上的字面是「無法判定 (Bypass)」，它本身由階段二撰寫）
   - 兩種輸出類型合併成整合標記模式時，整合預覽區塊**不得在卡片裡再包一層外框**
5. **「無法判定」選項自己的虛線外框是刻意設計，要保留**
6. 這條規則**一體適用所有輸出類型**，不得逐類型寫死

### 中欄下方：操作列

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 中欄底部是操作列：**左側是自動儲存狀態指示，右側是「儲存草稿」與提交按鈕**
2. 自動儲存的三態文字與它們**什麼時候才會變**，由**階段三**撰寫——那一條的重點是「指示必須誠實」，所以放在提交與草稿那一段一起寫
3. 提交按鈕**靠右對齊是兩種角色共同的契約**：審核員視角的自動儲存指示會隱藏，但送出按鈕**不得因為左側元素消失就掉到左邊**
4. 審核員視角**不提供「儲存草稿」**（按鈕隱藏，而且沒有綁行為）
5. 這個操作列是**唯一的提交位置**：審核員的「送出審核」、仲裁的「送出仲裁」都固定在這裡、**不隨中欄內容捲動**，卡片裡**不得再放一顆送出按鈕**
6. 那兩顆**互斥顯示**，依[審核員視角落在哪個分支](#審核員視角的六個互斥分支)決定：

| 分支 | 操作列上出現哪一顆 |
| :--- | :--- |
| 仲裁版面 | 只有「送出仲裁」，而且**只在該單位仍有未裁定的爭議項時出現** |
| 可互動的審核卡 | 只有「送出審核」 |
| 當事審核員重入、已定稿、已離冊、未指派、空單位 | **兩顆都不出現** |

### 右欄：說明與檔案、操作紀錄

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 桌機右欄是**兩個頁籤**，標記員與審核員看到的一樣，**預設停在第一個**：

| 頁籤 | 承載什麼 |
| :--- | :--- |
| 說明與檔案 | 「任務說明」摘要 + 說明檔案清單 |
| 操作紀錄 | 目前這一筆的操作時序，標記員與審核員的事件合併後依時間排 |

2. 第二個頁籤的名稱在來源與畫面不一致（來源寫「歷程」、畫面是「操作紀錄」），見 [§待釐清](#待釐清) Q2
3. 「操作紀錄」裡面放什麼、誰看得到哪些、耗時與理由怎麼呈現，見[§操作紀錄裡的每一筆事件](#操作紀錄裡的每一筆事件)（清單側已寫在 [規格 04-01 §處理狀況](./01-annotation-list.mdx#處理狀況)）
4. **說明與檔案是這個模組強制常駐的資訊**，不能只在進場的彈窗裡出現一次
5. 「任務說明」的標題**帶一個提示圖示**
6. 檔案清單每一列要顯示**對應檔案類型的小圖示**，並在檔名右側顯示**動作提示文字「預覽」**
7. 圖示與動作提示**由檔案類型驅動，不得依任務別寫死**；動作提示要**跟著語言切換即時更新**
8. 說明檔案的連結失效時，**不影響標記主流程**，但要顯示一則可追蹤的錯誤訊息

### 說明檔案的三種預覽

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 說明檔案至少支援三種類型的**頁面內預覽彈窗**，標記員與審核員共用同一套面板與行為：

| 類型 | 點下去會怎樣 |
| :--- | :--- |
| 圖片 | 置中彈窗顯示**大圖**；**不得只用右欄底部的小圖預覽頂替** |
| PDF | 置中彈窗**在頁面內嵌入顯示**；**不得開新分頁** |
| Markdown | 置中彈窗顯示**排版後的內容**；**不得用面板底部的純文字區塊頂替** |

2. 三種彈窗都要能關掉，而且**三條關閉路徑都要有**：關閉按鈕、點背景遮罩、按 `Esc`
3. 三種彈窗都要**管好鍵盤焦點**：開啟時焦點移進彈窗、`Tab` 侷限在彈窗內、關閉後焦點**還給觸發它的那個元素**
4. PDF 與 Markdown 彈窗的**標題顯示檔案名稱**
5. Markdown 的排版至少要支援：標題、段落、有序與無序清單、粗體、斜體、行內程式碼、連結、程式碼區塊、表格與圖片
6. 安全規則（使用者看得到的結果）：
   - 說明檔案裡夾帶的網頁標記**一律當文字顯示**，不照它排版；程式碼區塊裡的內容也只當文字
   - 連結與圖片的位址**只接受一般網址、信件位址、站內相對位置與同頁錨點**，其他一律降級成純文字
   - 連結**一律開新分頁**，避免把人帶離工作區
7. 排版後的每個標題都要**帶一個由標題文字推導出來的錨點**，而且：
   - 同一份沒改過的說明，**每次排版都要得到同一組錨點**
   - 同一份說明裡**兩個文字相同的標題，要得到互不相同的錨點**
   - 錨點**不得只靠標題的出現順序決定**
8. 第 7 條不是排版細節：**審核員在修正理由裡引用某個說明段落**時，引用就是跳到這個錨點，而**點它的人是標記員**——他在試標歷史回饋裡讀那則理由（清單側見 [規格 04-01 §試標歷史回饋](./01-annotation-list.mdx#試標歷史回饋)；審核員怎麼寫引用由階段四撰寫）。錨點的順序一變，舊的引用就會指錯地方
9. 進場的說明彈窗**用同一個排版器**，不另外維護一份

### 指引閘門：第一次進來先讀說明

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 任務設定可以要求**先讀說明才開始標記**（開關在[規格 03-03 任務詳情](../03-task-management/03-task-detail.mdx)）
2. **這個開關沒開，彈窗在任何情況下都不得出現**，也不受下面的確認紀錄影響（**依建議撰寫、待維護者確認**，見 [§待釐清](#待釐清) Q4）
3. 開關開著時，進場顯示說明彈窗，使用者按確認按鈕才開始；確認後**同一台裝置對同一個任務的後續進入（含重新整理）不得再顯示**（同 Q4）
4. 彈窗的內容**和右欄「說明與檔案」同一個來源**，取其中 Markdown 類型的全文顯示；沒有 Markdown 類型時**退回顯示檔名清單**——**不得為彈窗另外維護第二份說明文字**
5. 彈窗與右欄**必須是同一個:ref[指引版本]{id="term.guideline-version"}**
6. 確認紀錄**以任務為鍵各自獨立**：確認了 A 任務**不得抑制** B 任務的彈窗；換任務就要**從頭重新判定**
7. 確認紀錄還要**比對當前回合釘住的指引版本**：
   - 已經確認過**這個版本**的不再顯示
   - 第一次遇到**另一個版本**而且開關開著時，**必須重新確認**
   - 之後把說明另存新版，**不得改寫舊回合的指引，也不得讓舊版本的確認失效**
   - 歷史回合的版本**不得從任務的當前版本、最後一個試標回合或相同的回合顯示號去猜**
8. 確認紀錄要綁在**帳號**還是**裝置**上，來源明寫留待後端接上時定義，見 [§待釐清](#待釐清) Q3
9. 來源另有**三處**未被註銷的規則說「每次進入都顯示一次」，與第 2、3 條相矛盾，而來源沒有裁決句，見 [§待釐清](#待釐清) Q4

### 網址一直指向目前這一筆

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 網址必須**持續指著畫面上正在看的那一筆**：每次換筆或換受審標記員，都要把它寫回網址
2. 這樣的話，**重新整理、加書籤、把連結貼給別人，都會回到畫面上的那一筆**，而不是回到最初進來的那一筆
3. 同步的範圍：

| 參數 | 誰要同步 |
| :--- | :--- |
| 那一筆的識別碼 | **所有角色** |
| 受審標記員 | **只有審核員視角**（它是審核單位的另一半） |

4. 標記員視角翻筆時身分不會變，所以**不得在網址裡新增它原本沒有的參數**
5. 改寫要**原地取代**，**不得每翻一筆就在瀏覽器的上一頁堆一筆**——否則走過 N 筆之後要按 N 次上一頁才離得開工作區
6. 改寫必須**就地更新既有的網址參數**，**不得照已知的鍵重建一份**——重建會把這一頁不讀的參數**靜默丟掉**
7. 網址帶的那一筆**查不到而回退到第一筆**時，網址也要改寫成**實際顯示的那一筆**，讓重新整理的結果穩定不漂移

### 鍵盤快捷鍵

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 側欄快捷鍵總覽（見[規格 07-01](../07-shared/01-sidebar.mdx)）在「工作區」分類列出的四個快捷鍵**必須全部真的可用**，不能只是文案：

| 快捷鍵 | 做什麼 |
| :--- | :--- |
| `Ctrl/Cmd + S` | 儲存草稿 |
| `Ctrl/Cmd + Enter` | 提交目前這一筆 |
| `Alt + ←` | 上一筆 |
| `Alt + →` | 下一筆 |

2. 每個快捷鍵都要**走它對應的那顆按鈕本身的行為**，不得另開一條繞過按鈕既有條件的路：
   - 按鈕**隱藏或停用時，快捷鍵就無作用**——首筆按 `Alt + ←` 不得回捲到末筆，審核員按 `Ctrl/Cmd + S` 不得寫入草稿
   - 理由是按鈕上已經帶著角色配置與首末筆的停用狀態，另推一次就會出現**第二份會漂移的事實來源**
3. `Ctrl/Cmd + Enter` **依角色分流**：標記員觸發「提交」、審核員觸發「送出審核」，兩者都要**照各自既有的完整性驗證走**，不得繞過
4. 這四個都是**修飾鍵組合、不產生文字**，所以**焦點在輸入框裡時照常生效**——最需要「儲存草稿」的時機正是在長文作答途中
5. 必須**攔住瀏覽器的預設行為**（`Ctrl/Cmd + S` 會開「儲存網頁」、`Alt + ←` 在瀏覽器是上一頁），而且**要在判斷按鈕可不可用之前就攔**，否則隱藏或停用的目標會漏出瀏覽器的預設動作
6. 審核卡還有不帶修飾鍵的單鍵快捷鍵，和這四個的規則不同，由**階段四**撰寫

### 進不來的時候：導回清單

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 網址**查不到已發布的任務設定**時，**導回[標記清單](./01-annotation-list.mdx)**，並且**不得以任何預設的輸出類型或空白控制項呈現工作區**
2. 清單那一側對應的規則寫在 [規格 04-01 §路由上下文與回退](./01-annotation-list.mdx#路由上下文與回退)；這一條是**工作區這一側**的導回
3. 網址**沒帶那一筆**時，**不得載入作業區**，一樣導回標記清單
4. 角色與標記階段的缺值回退和清單一致（角色回退成標記員、標記階段回退成試標）
5. 任務設定讀到了、但**輸出類型是空的或缺必要內容**時：顯示任務設定錯誤並**阻擋提交**，**不得用任一輸出類型的預設控制項頂替**
6. 這一頁**沒有從本機記憶體還原上下文**這條路——上下文只從網址來
7. 導回時要**保留同一個任務的上下文**

### 作答區塊由任務設定驅動

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 中欄的標記區塊**完全由任務發布時凍結的那份輸出類型清單驅動**：依**清單的順序**逐一排出各輸出類型的標記區塊
2. **不得為特定輸出類型、特定組合或任務名稱寫死專屬分支**——任何合法的輸出類型組合都要能一致運作
3. 每個輸出類型**各自獨立成一個標記區塊**；任一區塊的互動**只更新該區塊**，不影響其他輸出類型的既有作答
4. 切換或儲存某一個輸出類型，**不得清除或覆寫**其他輸出類型的既有作答
5. 有幾種輸出類型就有幾個區塊，一到多個都適用；三個以上也必須都能在**同一筆的同一個畫面**內完成
6. 審核員那一側的「每種輸出類型怎麼呈現審查結果」與「逐列的直接修正入口」由**階段四**撰寫

### 題目怎麼呈現：單筆、配對與背景參考

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 單筆任務只顯示**單一「原始文本」區塊**，**不得顯示雙欄配對版面**
2. 配對任務以**雙欄**呈現兩個項目，區塊小標取任務設定的**項目對名稱**；缺值時回退顯示對應輸入欄位的原始名稱
3. 項目對名稱**只影響顯示文案**，不改變欄位的用途，也不改變資料本身
4. 「**背景參考 (Evidence)**」有兩條呈現路徑，**同一筆不得同時出現兩張**：

| 情況 | 背景參考放哪 |
| :--- | :--- |
| 這個輸出類型自己就會在它的專屬預覽裡嵌入背景參考（目前只有自由文本） | 由它自己依「背景參考 → 題目內容 → 作答框」的順序呈現 |
| 其餘七種輸出類型 | 由**通用的背景參考卡**統一呈現在**題目卡最上方**，位置早於題目內容卡與所有作答控制項 |

5. 沒有指定背景參考欄位時，**不得顯示空的背景區塊**
6. 背景參考卡**只供閱讀**：不得包含任何可編輯的輸入或選取控制項
7. 當有多個輸出類型自己就把原文內嵌在它的預覽裡時（例如序列標記、實體辨識、關係識別、自由文本），**通用的輸入文字區塊不得重複顯示**，輸入內容改由那個輸出類型的專屬或整合預覽完整呈現
8. 工作區**不得為特定輸出類型另外寫死顯示順序的例外**

### 八種輸出類型的作答控制項

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

每一種的控制項都由該輸出類型的設定動態決定。下面逐一寫規則；**畫面上的四個區塊標題目前是英文**，見 [§待釐清](#待釐清) Q9。

#### 單選標籤

1. 以**互斥的單選標籤鈕**呈現設定裡的選項
2. 記下**選了哪一個**

#### 多選階層標籤

1. 以**可搜尋的階層多選器**呈現選項，分支節點與葉節點都可以勾
2. 已選的標籤鈕**只顯示節點名稱**（不顯示整條路徑）
3. 選取之後**選擇器保持開啟**，直到使用者明確關閉
4. 選擇器展開時**必須是該區塊的最上層不透明覆蓋層**，**完整遮蓋它後方的內容（包含「無法判定」勾選項）**，**不得有任何後方元素穿透顯示在選擇器之上**
5. 被遮蓋的控制項要**先關閉選擇器才能操作**；關閉途徑有四種：關閉鈕、`Esc`、再次點觸發器、點選擇器範圍外任意處
6. 設定了選取數上限（非 0）而超過時：**阻擋新增選取並提示上限**
7. 上限提示的文字要**沿用工作區既有欄位提示的字級與顏色**，**不得用瀏覽器預設樣式**呈現
8. 記下的是**從根到被選節點的完整路徑**，不是只有節點名稱

#### 單一維度評分

1. 以**單一可拖曳滑桿**呈現，右側另有數字輸入框顯示相同的值
2. 滑桿、當前值標籤與數字輸入框**三者雙向同步**（調整後 **100 毫秒內**同步完成），而且在**任何時刻顯示同一個數值**
3. 當前值標籤**即時跟隨滑塊顯示在它正上方**
4. 當前值標籤**不得用佔位符號取代數字**——**唯一例外**是勾了「無法判定」，此時顯示未評分的佔位符號
5. 還沒作答、也沒有預填時，滑桿與當前值標籤**可以停在範圍中點當起始位置**，但那個起始值**不計為已作答、不得當成有效值提交**
6. 數字輸入框**可以直接鍵入範圍內的非級距小數，而且不得被吸附**到級距上；**超出範圍時自動校正**回範圍內
7. 預填或匯入進來的值不落在設定的範圍與級距時，顯示驗證錯誤並阻擋提交
8. 記下**那個數值**

#### 多維度評分

1. 設定裡的**每一個維度各自**有獨立的滑桿與數字輸入框
2. 調整任一維度**只更新該維度**
3. 依維度順序配**不同的輔助色**，但**同時保留文字標籤**（不能只靠顏色區分）
4. **每一個維度**的當前值標籤在任何時刻都要與該維度的滑桿、數字輸入框顯示同一個數值——**包含還沒調整過的維度**（有預填就顯示預填的實際值，沒有就顯示範圍中點的起始位置）
5. 一樣**不得用佔位符號取代數字**，唯勾了「無法判定」時**全部維度**顯示未評分佔位符號
6. 任一**未評分維度的起始值不計為已作答**，不得當成有效值提交
7. 記下**每個維度各自的數值**

#### 序列標記

1. 顯示帶「原始文本」標題的、**未經任何切分**的原始文本，當成單一的圈選面
2. 使用者**拖曳圈出一段文字，再點選標籤類型**完成標記
3. 記下**起點、終點與標籤**；起點與終點是**相對於原始文本的字元位置**，而且**終點那個字元本身不算在範圍內**
4. 已標記的範圍要以**對應標籤顏色的底線**呈現
5. 另有已標記清單，每一列含**類型徽章、文字、字元位置與刪除按鈕**
6. **範圍不得相交**：落在既有範圍上時要給**即時可見的拒絕回饋**且**不建立**那一筆
7. **相鄰但不相交**（前一筆的終點正好等於新一筆的起點）**必須被允許**
8. 吸附單位由任務設定決定：不吸附，或把起訖各自**吸附到最近的詞界**
9. **吸附只影響滑鼠放開時的落點，不影響存下來的值**——兩種設定產出的資料形狀完全相同
10. 執行環境做不到詞界判定時，**那一位標記員退回「不吸附」**，並在標記卡顯示一行提示；**不得因此改寫任務的設定值**
11. 第 10 條的提示**只能定位為操作手感說明，不得呈現為資料品質警告**
12. **吸附能力的差異不影響資料可比性**：同一個任務的不同標記員可能在能力不同的環境作業，而吸附不進入資料，所以降級那一位產出的範圍與其他人**完全相容**——系統**必須照常把他的答案納入一致性、共識與差異比對**，**不得標記為可疑、降權或排除**，也**不得事後對他的邊界做任何「對齊詞界」的修正**
13. 畫面上**不存在**把原始文本預先切成一格一格、讓人逐格點選的版面，**不存在**任何帶 `B-`／`I-`／`E-`／`S-` 前綴的標籤鈕，也**不存在**「標記方案」相關的呈現
14. 提交前要驗證每一筆範圍：**起點大於等於終點**、**起點小於 0**、**終點超出原始文本長度**都是錯誤，要**阻擋提交並顯示可定位的錯誤**
15. **沒有標任何範圍又沒宣告「無法判定」時阻擋提交**；建立任一筆之後這個阻擋就解除

#### 實體辨識

1. 顯示原始文本圈選區、**依設定動態產生的實體類型按鈕列**，以及已標記實體列表
2. 列表每一列含**類型徽章、文字、字元位置與刪除按鈕**；已標範圍以對應顏色底線呈現在原始文本上
3. **兩種順序都要支援**：先選類型再圈選，或先圈選再選類型
4. **沒有先圈選文字就點實體類型按鈕**時：顯示錯誤提示，**不得建立實體**
5. 記下**文字、類型、起點與終點**（終點那個字元本身不算在範圍內）

#### 關係識別

1. **只有關係識別、沒有實體辨識**時（純模式）：既有實體以**資料集提供的唯讀高亮**呈現，**不得顯示**實體類型選擇器、實體列表或建立／刪除實體的控制項
2. 三元組用**循序建構器**建立：在原始文本反白選取文字，依序按 `E1/Arg1` → `Relation` → `E2/Arg2` 把選取填進對應的草稿格，最後按「新增」寫入列表
3. 建構器要顯示**三個草稿狀態格與當前選取的內容**
4. `E1`／`E2` 兩步**只接受與既有實體相符的選取**（不符或沒先選取時顯示錯誤、不填入）；`Relation` 這一步**接受任意選取範圍**當關係觸發詞
5. 各步驟**依草稿進度循序啟用**：前一格沒填時後續步驟停用
6. 三格**沒全部填妥前「新增」停用**——**不存在只填一部分就能新增三元組的路徑**
7. 「退回」作用在**草稿格**上，依 `E2/Arg2` → `Relation` → `E1/Arg1` 撤回最後填入的那一格；草稿全空時停用
8. 「退回」**不移除已經入列的三元組**，純模式下**也不移除既有的唯讀實體**
9. 已入列的三元組由**每一列自己的刪除按鈕**個別移除
10. 設定的關係類型清單**非空**時，每一列另外提供類型選單，供事後指定或變更那一筆的語意類型；已指定的在該列顯示類型徽章
11. 類型是**選填**的：沒指定就是空的；清單**為空**時**不顯示類型選單，也不得輸出寫死的類型**
12. 這個循序建構器**必須和新增任務的標記預覽、任務詳情的標記設定是同一個互動控制**；工作區**不得另外提供不同型態的關係建構介面**（例如下拉選單）
13. 記下**每一筆三元組的主體、客體與選填的關係類型**
14. 主體與客體的**位置**（在原始文本上的起訖）**只能來自本來就帶位置的兩種來源**：工作區建構器的互動標記（位置來自既有實體的命中），或資料集匯入時本來就帶位置的三元組
15. **來源沒帶位置時就是「沒有」**——**不得用答案字串回原始文本做比對去回推位置**。同一個詞在文本裡出現多次時比對會選到錯的那一次，而且**不會產生任何錯誤訊號**，等於把「資料缺失」靜默換成「錯誤資料」。這一條是硬規則，**不得以「多數情況正確」為由放寬**

#### 自由文本

1. 依**這個順序**呈現：背景參考（選填）→ 輸入說明 → 題目內容卡 → 輸出說明 → 作答框 → 字數計數
2. 兩段說明文字要顯示**設定裡的文案**
3. 另有**字元計數**，形式是「目前字元數 / 上限」
4. **超過上限時阻擋繼續輸入**，而且**阻擋提交**（上限算的是**字元數**）
5. 有「用途是輸出」的欄位時，作答框要**以該欄位的值預填**；沒有時作答框是**空的**
6. 記下**那段文字**

### 實體辨識與關係識別的整合模式

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 任務**同時選了實體辨識與關係識別**時，兩者以**整合模式**呈現
2. 兩者**共用同一份文本**，實體列表與三元組列表**合併顯示在同一個區塊**
3. 實體辨識保留它的**兩種建立順序**
4. 關係識別保留它的**循序建構器**，但 `E1`／`E2` 的來源改成**整合模式提供的可編輯實體**（不再是唯讀的資料集實體）
5. 兩者**仍各自輸出獨立的作答**——一份是實體辨識的、一份是關係識別的
6. 這個關聯**只在任務同時選了這兩種時成立**；工作區**不得自動加入或移除**這個關聯
7. 關係識別**可以單獨使用**，那時候就是純模式
8. 整合預覽區塊**不得在卡片裡再包一層外框**（見[§中欄主體：題目卡與標記卡](#中欄主體題目卡與標記卡)）

### 對話串資料的整合預覽

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

輸入欄位是**一筆一筆的物件陣列**時（例如對話逐則發言），整合預覽有一套專屬的呈現與記錄規則。這一段的規則**不得依任務編號或欄位名稱寫死**。

1. 任務設定了**對話串欄位**時，整合預覽**一則發言一列**
2. 每一列分**三個部分**：

| 部分 | 內容 |
| :--- | :--- |
| 頭像 | 圓形，取**發言者文字的第一個字元**；沒有發言者欄位、或該則的發言者是空的，就**不顯示頭像** |
| 標頭行 | 依序顯示**發言者**與 `#` 加**發言編號** |
| 發言文字 | **另起一行**，而且**保留換行** |

3. 頭像底色**由發言者文字決定**（同一位發言者永遠同一個顏色），**不得依發言者名稱寫死顏色**
4. **所有發言都可以標記，不得截斷**
5. 發言編號取設定指向的那個子欄位的值；**沒設定就用該則的位置編號**（從 1 起算）
6. 在對話串裡標的實體，記下**它屬於哪一則發言**，以及**在那一則發言文字裡的起訖**（同樣是終點本身不算在內）
7. 三元組除了主體與客體的起訖，還要記下**主體與客體各自屬於哪一則發言**
8. **反白跨到兩則發言要被拒絕**：顯示提示，且**不新增實體也不新增關係選取**。跨發言的關聯**要用關係識別表達**
9. 回覆縮排：任務設定了**回覆欄位**，而且該則的值**等於同一筆資料裡另一則發言的編號**時，該則**縮排**並顯示「跨發言 · 回應 #〈編號〉」標記
10. 下列情況**不縮排也不顯示標記**：沒設定回覆欄位、該則的值缺漏或為空、值找不到對應的發言、值等於**它自己**的編號
11. **不得由實體、關係或文字裡的 `@名字` 去推測回覆關係**
12. 對話串上方有**兩個顯示切換按鈕**，預設停在第一個：

| 按鈕 | 效果 |
| :--- | :--- |
| 顯示已標實體 | 發言文字上繪製實體標示與關係選取標示（預設） |
| 純文字 | **不繪製**那些標示；**已記錄的實體資料不變**，而且**反白標記仍然可以進行** |

13. 實體的定位規則：

| 情況 | 怎麼定位 |
| :--- | :--- |
| 實體已經帶著所屬發言與起訖 | **照座標定位** |
| 沒帶座標，而它的文字在整份對話的發言裡**恰好出現一次** | 定位到那個位置 |
| 沒帶座標，而文字**出現多次或找不到** | **不得猜**（**不得取第一次出現的位置**）；那個實體**不標示**，並顯示「無法定位」的提示與**數量** |

14. **重疊的實體不得默默略過**：同一則發言裡區間重疊的實體，後面那個**不標示**，但**儲存的內容不變**，而且畫面要**顯示因重疊而未標示的數量**
15. **反白歧義**：反白的位置與發言文字對不上，而且那段選取文字在該則發言裡出現多次或找不到時，**不得取第一次出現的位置**，要顯示**專屬的歧義提示**；只有在該則發言裡恰好出現一次時才以那個唯一位置記錄
16. 第 15 條的提示**不得顯示沒被替換掉的佔位符號**
17. 輸入是物件陣列但**沒有設定對話串欄位**時：整合預覽要以**可摺疊、等寬字**呈現該欄位的原始內容，**不得出現 `[object Object]`**。那個摺疊區塊的標題目前把技術名詞露給使用者看，見 [§待釐清](#待釐清) Q10
18. 對話串與原始內容的呈現**只渲染用途是輸入的欄位**；用途是**輸出或背景參考**的欄位**不得因為這條路徑外露**
19. 輸入是物件陣列時，整合預覽**不得用「用途是輸出」的欄位內容預填實體或三元組**
20. 輸入**不是**物件陣列的任務，既有的「由輸出欄位解析預填」行為**不變**
21. 預填的來源**只能從任務設定明文宣告的預填欄位讀取**，**不得依固定的欄位名稱去讀**；設定沒宣告、或對應的那一項缺漏時，那一類就**不載入**。宣告的欄位**載入前還要通過一道角色守門**，規則見[§整合預覽的宣告預填欄位有另一道守門，方向相反](#整合預覽的宣告預填欄位有另一道守門方向相反)

### 「無法判定」

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 某個輸出類型的設定**允許**時，在**該區塊底部**提供獨立的「無法判定 (Bypass)」勾選項
2. 勾選後要**清空並停用該區塊內其他的互動控制項**，而且**只影響該區塊**，不影響其他輸出類型
3. 取消勾選後要**恢復可操作**，並依預填規則**重新初始化**
4. 每個輸出類型各自記下**是否被標為無法判定**；標了之後**其餘作答內容須為空**
5. 設定**不允許**無法判定的輸出類型：標記員做不出來時**只能依一般的驗證規則被擋下**，**不得提供「無法判定」當繞過手段**
6. 勾了無法判定**必須填理由**。沒填就送出時：**阻擋送出**、理由欄位下方出現**行內錯誤訊息**，並顯示**指名缺理由的那個輸出類型**的警告訊息
7. 被擋下時**不得產生任何提交紀錄**，既有內容**維持原狀**
8. 多個輸出類型**各自獨立判定**：兩個都勾了無法判定而只有一個填了理由時，送出被擋，而且警告**只指名留白的那一個**，已填的那個不受影響
9. 理由填好之後送得出去，而且**那段理由會連同它屬於哪個輸出類型一起寫進操作紀錄**（寫進去之後誰看得到，見[§歷程的分層遮蔽](#歷程的分層遮蔽)）
10. 整合模式下兩者**各自有獨立的「無法判定」**，但效果不對稱：

| 勾哪一個 | 效果 |
| :--- | :--- |
| 實體辨識 | **整合區塊一併清空停用**（含關係建構器）——因為關係識別依賴它的實體來源 |
| 關係識別 | **只**清空停用關係建構器與三元組列表，**實體標記不受影響** |

### 預填：兩道方向相反的守門

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

這一段是這一頁的**測試集保護**所在。

1. 初始化每一筆時，**所有輸出類型的控制項都必須是空白／未選取**——**除非**下面兩種情況之一：
   - 這一筆**已經有儲存過的作答**（存過草稿且有有效值，或已提交）
   - 這個輸出類型有**「用途是輸出」的欄位**可以預填（見第 3 條）
2. 兩種情況都不成立時，**不得預填任何合成的預設值**，**包含數值的中間點**。滑桿即使因為控制項本身需要一個視覺位置，也要**用未評分狀態區分**，而且**在使用者操作前不得被當成有效值提交**
3. 有「用途是輸出」的欄位時，用**那個欄位的實際值**初始化對應的控制項，呈現為**標記員看得見、可編修、可以直接提交**的預填：

| 輸出類型 | 怎麼預填 |
| :--- | :--- |
| 單選標籤 | 預選符合的那個標籤 |
| 多選階層標籤 | 以正規化後的路徑預選 |
| 單一維度評分 | 滑桿設在實際的分數值 |
| 多維度評分 | 各維度的滑桿設在對應維度的值 |
| 序列標記 | 以可見的預標記範圍初始化 |
| 實體辨識 | 以實際的實體列表初始化 |
| 關係識別 | 以實際的三元組初始化 |
| 自由文本 | 預填實際的答案文字 |

4. 沒有對應的「輸出」用途欄位時，那個輸出類型**維持空白／未選取**
5. **逐輸出類型的預填，來源只限被明文標記為「輸出」用途的欄位。** 沒有標任何用途的、標成「輸入」或「背景參考」的欄位，**不得作為這條路徑的預填來源**
6. **隱藏的測試集標準答案，不得透過這條路徑或任何其他路徑，下發到標記員接觸得到的任何地方**——包含畫面、預覽與任何中間狀態
7. 第 5、6 條是**不可協商**的
8. 預填**不是**標準答案：它是任務建立者明確指定要讓標記員看見的起始內容，所以可以編修、也可以直接送出

:::note{title="第 5 條只管預填這條路徑，不是「這些欄位不給標記員看」"}
來源那一句若單獨照字面讀，會連**題目內容**與**背景參考**都一起剝掉；但同一份來源另有三處明文要求把它們顯示出來——`FR-024N`（背景參考卡要呈現該欄位的**實際內容**）、`FR-107` 第 5 點（對話串**只渲染**用途是輸入的欄位，也就是說輸入欄位本來就要渲染）、`AC-2.49`（宣告的預填欄位用途是輸入或背景參考時，內容**照常載入**）。所以它限定的是**預填的來源**，而它真正要擋的是那一句自己的結尾：**隱藏的標準答案不得以任何形式下發**。
:::

#### 整合預覽的宣告預填欄位有另一道守門，方向相反

1. 整合預覽的預填實體與預填三元組，**只能從任務設定明文宣告的預填欄位讀取**，**不得依固定的欄位名稱去讀**
2. 設定沒宣告、或對應的那一項缺漏時，**那一類預填就不發生**
3. 宣告的欄位**載入之前還要查它的欄位用途**，而且這道守門**從嚴**（查不出來就不給）：

| 宣告欄位的用途 | 載不載入 |
| :--- | :--- |
| 已知、而且**不是**「輸出」（例如輸入、背景參考） | **載入** |
| 是「輸出」 | **一律不預填** |
| **沒有指派、是空的，或查不出來** | **一律不預填** |

4. 這道守門**不分輸入是字串或物件陣列、不分實體或三元組**，一律適用
5. 關係類型清單由預填三元組自動帶入時，候選**同樣只能來自通過這道守門的欄位**
6. 這一段只管**資料自帶欄位**的載入路徑；輸入不是物件陣列時「由輸出用途欄位解析預填」的既有路徑**不在這一段範圍內**（見[§對話串資料的整合預覽](#對話串資料的整合預覽)第 19、20 條）
7. 兩道守門**方向相反，但不矛盾**——它們看的是**不同的設定**：

| 哪一條路徑 | 看哪個設定 | 守門方向 |
| :--- | :--- | :--- |
| 逐輸出類型的預填 | 欄位的**用途**標記 | 來源**必須是**「輸出」用途的欄位 |
| 整合預覽的預填實體與三元組 | 任務設定裡**宣告的預填欄位** | 宣告的欄位**不得是**「輸出」用途，用途不明也不給 |

8. 之所以相反：第一條路徑的「輸出」用途是任務建立者**刻意指定要讓標記員看見**的；第二條路徑的宣告欄位可能指到標準答案，所以**查不出來就不給**

### 作答被鎖住的兩種情況

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 有兩種情況會把標記員的作答**鎖住**。兩種的共同效果是：畫面渲染**鎖定提示**，而且「儲存草稿」與「提交」兩顆按鈕**都停用**——但**兩顆都仍然留在畫面上**，不是消失

| 鎖 | 什麼時候 | 標題 | 說明 | 自動儲存列 | 色調 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 已定稿 | 這一筆的審核單位已經定稿（前提是這位標記員**確實有真實的已儲存提交**） | `此標記結果已定稿` | `作答內容已鎖定，無法再修改或提交。如需異動請聯絡審核員。` | `已定稿，不再自動儲存` | **資訊色** |
| 審核中 | 審核員**第一次把審核結果送出**之後，而這一筆的審核單位**還沒定稿** | `此標記已進入審核` | `審核員已開始處理這筆作答，內容已鎖定，無法再修改或提交。` | `審核中，不再自動儲存` | **提醒色**＋鎖頭圖示 |

2. 色調**不得互換**：已定稿**必須用資訊色**，**不得用錯誤色，也不得用提醒色**——**定稿是終態，不是錯誤也不是提醒**
3. **兩個鎖同時成立時以「已定稿」為準**：正式標記的單位已定稿時，顯示定稿的文案與呈現，**不得顯示審核中的文案**
4. **鎖定提示與自動儲存列不得外洩審核狀態**：那兩處**不得出現「爭議中」「等待仲裁」「例外池」字樣**，也**不得呈現審核員的決策類型、理由或身分**。（這一條只約束這兩處；「操作紀錄」頁籤看得到什麼見[§歷程的分層遮蔽](#歷程的分層遮蔽)）
5. **定稿當下已經選定的作答必須維持可辨識**：**不得讓已選與未選的選項套用相同的視覺結果**（例如整排轉灰，導致看不出當初選了什麼）
6. **沒有解鎖入口**：這一頁**不提供任何解鎖操作**；要重新開放修改的流程目前還沒有定義
7. 兩種鎖的**適用階段不同**：

| 鎖 | 試標 | 正式標記 |
| :--- | :--- | :--- |
| 已定稿 | **不適用**——試標的後續回合不受影響 | 適用 |
| 審核中 | 適用 | 適用 |

8. **快捷鍵也不得繞過**：鎖定時按儲存或提交的快捷鍵，**都不得改變這一筆的內容或狀態**
9. 鎖定期間，這一筆的審核單位狀態**不得因為任何嘗試而翻回「爭議中」或「待審」**
10. **不得誤觸**：只由示範資料遞補、而**標記員本人還沒有任何真實已儲存提交**的審核單位，**不得顯示鎖定提示**，兩顆按鈕也**不得停用**；他的**第一次提交必須正常送出**
11. 標記員自己**促成這個單位變成已定稿的那一筆提交**，因為送出時還沒定稿，**必須正常寫入、不得被擋下**
12. **鎖只鎖這一個單位**：另一個試標回合裡同一位標記員的作答，**不得因為這個單位的審核中鎖而顯示提示或被擋下**
13. 審核員與仲裁者的寫入**不受這兩個鎖約束**（他們那一側由階段四、五撰寫）

### 作答完整性與提交阻擋

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

這一段只寫**什麼情況下送不出去**；送出之後往哪、草稿與自動儲存的規則在**階段三**。

1. 提交前，**每一個輸出類型都要已經作答，或已經勾了「無法判定」**
2. 任一個還沒完成時：**阻擋提交並提示對應的那個區塊**
3. 被擋下時，**其餘已完成區塊的作答不受影響**
4. 各輸出類型自己的驗證錯誤（評分超出範圍、字數超過上限、範圍起訖不合法、配對任務缺了一邊的內容）也各自阻擋提交，並顯示**可定位的**錯誤
5. 勾了「無法判定」但沒填理由的，依[§「無法判定」](#無法判定)第 6 到 8 條阻擋

### 儲存草稿與提交

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 標記員有兩個寫入動作：**儲存草稿**與**提交**
2. 「儲存草稿」存下**所有已作答輸出類型的暫存值**，並更新這一筆的完成狀態
3. 「提交」要先通過[§作答完整性與提交阻擋](#作答完整性與提交阻擋)——每個輸出類型都已作答或已勾「無法判定」，而且勾了的都填了理由
4. 這兩個動作是**這一頁唯一會產生實際寫入的事件**；下面的狀態指示只由它們驅動
5. :ref[IAA]{id="term.iaa"} 閘門的語意、α 的計算範圍與呈現規則**不由這一頁定義**——這一頁只負責**供應它需要的輸入**；正典在規格 05-02 資料集分析詳情（未撰寫）
6. 審核員**沒有對稱的「儲存草稿」**：他的逐列決策草稿走另一條寫入路徑（由階段四撰寫），所以這一段的規則不套用到他身上
7. 作答被鎖住時這兩個動作都停用，見[§作答被鎖住的兩種情況](#作答被鎖住的兩種情況)

### 自動儲存狀態只能說三句誠實的話

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. **沒有被鎖住**時，中欄底部左側的狀態指示**只有三種狀態**，而且**用語不得暗示沒有真正發生的儲存**（被鎖住時另有兩句專屬文案，見第 10 條）：

| 狀態 | 文案 | 什麼時候 |
| :--- | :--- | :--- |
| 尚未儲存 | `尚未儲存` | 這一筆**沒有任何已寫入的內容**，而且載入之後也還沒編輯過 |
| 有未儲存的變更 | `尚未儲存的變更` | 這一筆**有還沒寫入的編輯** |
| 已儲存 | `上次儲存於 〈時間〉` | 這一筆**有真實寫入的紀錄**，而且那次寫入之後沒有新的編輯；時間的格式是「月/日 時:分」 |

2. 除了這三句，指示器**不得出現任何字面或視覺上暗示「已自動儲存」「儲存中」的語意**——那些是沒有發生真實寫入就成立的說法
3. 狀態**只能由那兩個真實寫入事件改變**：**沒有背景計時器**，也**不得由切換樣本觸發**
4. 狀態要**逐筆各自推導**：切到另一筆之後，依**那一筆自己的寫入狀態**重新判斷是「尚未儲存」還是「已儲存」，**不得沿用切換前那一筆的狀態**
5. 切換樣本**本身不構成寫入**，所以**不得讓任何一筆因為被切過就顯示已儲存的語意**
6. 重新整理整頁之後，只要那一筆仍然是已儲存或已提交，指示器要**維持顯示同一個寫入時間**，**不得因為畫面重載就退回「尚未儲存」**
7. 這一筆的狀態如果回到「待標記」，指示器要顯示**「尚未儲存」而不是舊的時間戳**——「待標記」的意思就是**沒有任何反映當前狀態的寫入可以陳述**
8. 這個逐筆的指示器，與**頁籤層級的「有未儲存變更」**是**兩件各自獨立的事，不得互相取代**：後者管的是頁籤不被自動淘汰與關閉前的確認，見[規格 07-02 §未儲存保護](../07-shared/02-workspace-tabs.mdx#未儲存保護)
9. **審核員視角整個指示器隱藏**（不渲染）。理由是他沒有對稱的「儲存草稿」入口，而他的決策草稿走另一條寫入路徑；沿用同一個指示器會給他一個**沒有定義過的儲存語意**
10. 作答被鎖住時，指示器**改顯示鎖定的那一句**（「已定稿，不再自動儲存」或「審核中，不再自動儲存」），而且**不得沿用上面那三句**，見[§作答被鎖住的兩種情況](#作答被鎖住的兩種情況)

:::note{title="第 7 條目前沒有可達的觸發路徑"}
來源寫這一條時，讓一筆已提交的樣本退回「待標記」的是**審核退回**；而退回機制已在來源 v5.0.0 整組移除（審核的決策集合裡沒有「退回」）。這一條的**原則**仍然成立並且寫在這裡——狀態指示陳述的是「有沒有反映當前狀態的寫入」，不是「歷史上曾經寫過什麼」；只是目前沒有任何操作走得到它。
:::

### 版本衝突

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 寫入標記結果時**必須做版本檢查**
2. 版本衝突時**阻擋覆寫**，並要求**手動合併**
3. 典型情境是同一個人**在兩個分頁開著同一筆**同一個任務的資料
4. 仲裁的寫入**沿用同一套規則**，不另立機制（仲裁本身見[§仲裁版面](#仲裁版面仲裁者選邊不重新標記)）

### 提交之後往哪

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 標記員提交成功後的**預設行為是載入下一筆**，停留在工作區
2. 任務裡**所有樣本都已提交**時，系統**自動導回[標記清單](./01-annotation-list.mdx)**，而且清單上那一筆的完成狀態顯示為**已提交**
3. 第 2 條那條返回路徑**必須沿用同一個網址組裝點**，因此會**保留清單的檢視狀態四鍵與身分參數**，**不得另立第二個**
4. 三條返回路徑**都要保住那些狀態，但靠的方式不同**：

| 返回路徑 | 怎麼保住 |
| :--- | :--- |
| 側欄的「標記作業」連結、查不到任務時的轉址 | **逐字沿用原本的網址參數**，所以自動成立 |
| 麵包屑第 2 層、以及第 2 條那條全部完成後的返回 | **自己重組網址**，所以**必須另外把那四個檢視狀態鍵與身分參數轉發過去**；這兩者是**同一個組裝點** |
5. 清單側對應的規則寫在 [規格 04-01 §清單檢視狀態往返工作區](./01-annotation-list.mdx#清單檢視狀態往返工作區)；這一條是**工作區這一側**
6. 被阻擋而**沒有真正寫入**的提交，**不得前進到下一筆、也不得導頁**——畫面要留在原地，讓阻擋的原因看得到

### 審核員送出被擋時，要指名是哪一個輸出類型擋住

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

三向決策本身由**階段四**撰寫；這一段只寫**送出的驗證與阻擋提示**。

1. 審核員送出的驗證是：**每個輸出類型都要有一筆決策**，而且**選了「修正」的，修正後的答案不能是空的**
2. 被擋下時，提示**必須指名全部擋住送出的輸出類型**（多筆用「、」串接）——不能只給一句泛用的話
3. 有兩種阻擋，文案不同：

| 阻擋原因 | 文案 |
| :--- | :--- |
| 有輸出類型**還沒決策** | `請完成以下輸出類型的審核決策：{list}` |
| 全部已決策，但有**選了「修正」而修正後答案是空的** | `以下輸出類型選了「修正」但修正後答案為空，請填寫答案：{list}` |

4. **只要存在任一個還沒決策的**，就用第一種文案
5. 這份清單**必須重用送出驗證本身的那一份逐輸出類型判定**，**不得另建第二份計算**——否則提示指的和實際擋住的會不一致
6. 送出按鈕在被擋期間**不得真的停用**：真的停用會把點擊吞掉，提示就永遠指不出是哪一個輸出類型。（來源 v13.0.0 把「缺理由」這個阻擋整項移除之後，連那個停用外觀的標記也一併退場，現在兩類阻擋都**沒有**停用外觀）
7. **理由不再是阻擋原因**：來源 v13.0.0 把「修正」與「無法裁決」的理由改為**選填**，所以缺理由不再擋送出
8. **審核員的第三向決策叫「無法裁決」，不是「無法判定」**。來源 v6.8.0 刻意把同一個詞拆成兩套語彙，而且明寫**兩者不得互相取代**：

| 哪一個 | 字面 | 出現在哪 |
| :--- | :--- | :--- |
| **答案值**——標記員宣告自己無法作答 | `無法判定 (Bypass)` | 作答與修正面板、任務設定、清單 |
| **決策值**——審核員宣告自己無法裁決這一項 | `無法裁決` | 決策按鈕、操作紀錄徽章、快捷鍵總覽、仲裁的 B 選項、定稿卡 |

9. 標記員那一側的「無法判定」**理由仍然必填**，見[§「無法判定」](#無法判定)——那是**答案值**，與第 7 條說的決策理由是兩回事

### 審核員送出之後往哪

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 一次**成功寫入**的送出之後，去向看**這次送出有沒有讓這個審核單位定稿**：

| 這次送出 | 去向 |
| :--- | :--- |
| **沒有**讓單位定稿 | **自動前進到下一個可處理的審核單位** |
| **讓單位定稿了** | **停在原單位**，就地重新渲染成唯讀的定稿卡 |
| **沒有成功寫入**（被阻擋） | **留在原地**，不前進也不導頁 |

2. 第 1 條適用兩條送出路徑：審核決策的送出，與爭議仲裁的送出（兩者本身由階段四、五撰寫）
3. 前進的方式是**在同一頁內切換到那個單位**，**不得導向一個新的網址**；切換時要**一併帶上目標單位的受審標記員**，否則會因為身分缺值回退成預設標記員而顯示到別的單位
4. 切換之後的網址同步由[§網址一直指向目前這一筆](#網址一直指向目前這一筆)承擔，**不得新增第二個網址寫入點**
5. 目標**必須由同一套「哪些單位可處理」的判定取得**，**不得另立第二套**，也**不得沿用標記員那一側的「下一個待處理」**——後者的「待處理」只是「這一筆還沒提交」這個二元事實，**不含優先序、也不含仲裁資格與利益迴避**，拿它當審核端的目標會把審核員送進他無權處理的唯讀單位
6. 前進的**方向刻意和標記員那一側不同**：取的是**全體可處理單位裡優先序最高的那一個**（**同順位時取列舉順序最前面的那一個**），不是從目前這一筆往後繞。所以送出後**可能前進到排序在目前這一筆之前的單位**，這是刻意的
7. 第 6 條**不得為了讓兩側「看起來一致」而加上繞行限制**——那會讓一個更該優先處理的單位，只因為排序在前面就被跳過
8. **不得另加「排除目前這一個單位」的特例**：目標會不會是它，由可處理的判定自然決定。加特例會在狀態推導日後變動時與判定各說各話，並掩蓋判定本身的缺陷。（兩條送出路徑套用同一個判定之後**結果刻意不同**——仲裁送出含「兩者皆非」時，那個單位仍可能是合法的前進目標，見[§最終例外池是最後一道出口](#最終例外池是最後一道出口)）
9. **沒有任何可處理的單位時**，導向[標記清單](./01-annotation-list.mdx)**且不帶那一筆**，而且下面兩件事**必須同時成立**：

| 要做的事 | 不做會怎樣 |
| :--- | :--- |
| 網址經**同一個組裝點**產生，因此保留清單的檢視狀態四鍵與身分參數 | 只給空狀態說明，會落在沒有篩選的第 1 頁 |
| 網址帶上「**已無可處理單位**」的提示參數，觸發清單那一側既有的空狀態說明 | 只保留篩選條件，審核員會面對一整頁已定稿的列而**沒有任何訊號** |

10. 第 9 條的情況**不得回退為開啟任何一個已定稿的唯讀單位**
11. **讓單位定稿的那一次送出，必須停在原單位**：不前進、不導頁，就地重新渲染成唯讀的定稿卡。理由是**定稿卡是那次送出唯一的結果回饋**——逕行前進的話，審核員無從當場確認自己剛剛定稿了什麼，也無從察覺誤觸
12. 審核員離開已定稿單位的路徑是**既有的返回清單入口**，不由這一條接管
13. 前進的目標**只能由審核單位的狀態與登入者的身分推導**，**不得對任何特定任務分流**

### 定稿卡上的剩餘可處理量與歸零去向

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

定稿卡本身（唯讀、純文字）由**階段四**撰寫；這一段只寫卡上那一段**剩餘量敘述**。

1. 渲染唯讀定稿卡時，卡上**必須有一段剩餘量敘述**，位置在唯讀說明**之後**、第一個輸出類型的定稿值**之前**
2. **只要會渲染那張卡就要有**，不限於剛送出之後——開啟一個已經定稿的單位、定稿後的就地重新渲染、語言切換後的重繪，三種都算
3. 剩餘量的定義：**這個任務、這個標記階段裡，對目前登入的這位審核員判為可處理的審核單位數**
4. 這個判定**必須和前進目標共用同一份逐單位判定**，使兩者**不可能給出不同答案**——恆有「**剩餘量為 0 等價於沒有下一個可處理單位**」
5. **不得另立第二套計數公式**，**不得把這個數字另外存成一個欄位或暫存起來**（每次都現算），也**不得從上方的「我的審核提交 〈已提交〉 / 〈總數〉」相減或換算**——那個進度計的是**本人提交數**，和可處理量不是同一個量
6. 目前正在看的這個已定稿單位，本來就不算可處理，**不得用任何特例額外排除或納入**
7. 剩餘量**大於 0** 時：敘述要**寫出數字**，而且**不得渲染任何連結或其他行動點**——回清單的既有路徑是[麵包屑第 2 層](#入口麵包屑的第三層)，這裡不重複
8. 剩餘量**等於 0** 時：敘述由**一個標題與一段說明**組成，兩者的文字**必須與[標記清單](./01-annotation-list.mdx#沒有可處理的審核單位)那一側的空狀態說明逐字相同**（中英文皆然）
9. 第 8 條**不得為定稿卡另寫一套措辭**，也**不得依角色或依剩餘單位的類型分流措辭**；那一組措辭**只能有一份定義**，由兩個地方共讀，使兩處不可能因為只改一邊而分歧
10. 第 8 條要的那組文案**目前在來源與畫面都查不到**，見 [規格 04-01 §待釐清](./01-annotation-list.mdx#待釐清) Q13——那一題沒定案之前，這一段只能寫出「必須逐字相同」這個約束，寫不出文字本身
11. 剩餘量等於 0 時，敘述還要**另含一個回清單的連結**，它的網址**和[§審核員送出之後往哪](#審核員送出之後往哪)第 9 條那個「沒有可處理單位」的出口完全相同**（同一個組裝點、保留檢視狀態與身分、帶那個提示參數、**不帶那一筆**）
12. 那個連結**必須是導覽用的連結**，不得做成按鈕、表單控件，也不得用攔截點擊再導頁的方式；卡片內的按鈕數量**不得因為這一段而增加**
13. 這張卡的**出口恰為 1 個**，而且只在剩餘量為 0 時出現。**不得**在定稿卡上提供「下一個可處理單位」或「返回儀表板」的出口——那是一個**已經撤銷的設計**（它的三個出口都與既有導覽重複），**不得復活**
14. 剩餘量等於 0 **不改變**「讓單位定稿的送出要停在原單位」這件事：那個連結**只在審核員主動點它的時候才導頁**
15. 剩餘量的推導**不得對任何特定任務分流**

### 送出前的後果提示

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核員的送出按鈕旁邊**必須有一行恆常可見的純文字**，說明**這次送出會造成什麼結果**
2. 它不是要停留才看得到的提示泡泡——**不需要任何操作就讀得到**
3. 三種分支**互斥，同一時刻恰好成立一句**：

| 情況 | 文案 |
| :--- | :--- |
| 任一**已決策**的輸出類型符合下面兩種條件之一 | `送出後進入爭議池，待仲裁定案` |
| **全部**輸出類型都已決策、而且**全部都是「通過」** | `送出後即定稿，成為最終答案`（試標階段在同一句後面加註 `（試標不產生最終答案，僅計入一致性統計）`） |
| 其餘（還沒決策完，而且已選的裡面沒有上面那種） | `尚未選擇決策` |

4. 第一種分支的兩個條件是**「或」**：

| 條件 | 說明 |
| :--- | :--- |
| (a) 決策是「修正」或「無法裁決」 | 這兩個對單位狀態的效果相同，所以**必須顯示同一句文字**，不得為兩者編不同的措辭 |
| (b) 決策是「通過」，但審核員目前的草稿答案**與標記員原本的答案不同** | 「通過」不代表沒改過——改了答案再按通過，送出後仍然會被判為爭議 |

5. **兩個條件必須都實作**：只做 (a) 會讓「先改答案、再選通過」的情況誤報成「送出後即定稿」，而實際送出會因為答案不同被判爭議——來源把這件事記成一次審查發現
6. **還沒決策的輸出類型不參與**第一種分支的判定：那種情況送出本來就會被全數擋下
7. 第一種分支**優先於**另外兩種：**即使其他輸出類型還沒決策**，只要已經有一個符合 (a) 或 (b)，就顯示爭議池那一句
8. 這個單位**沒有真實的標記員提交**時（只有示範資料遞補），條件 (b) 的前提不成立，**不視為爭議**
9. 審核員**一改變任何一個決策**（點決策按鈕、用快捷鍵，或因為改答案而使決策被清空），這一行**必須立刻重算並更新**，**不得需要重新整理或重新開啟才會變**
10. 這一行的**顯示與隱藏，必須和它旁邊那顆送出按鈕完全一致**
11. 這一行的判定**必須重用既有的那一套規則**（判斷一個已送出的審核會讓單位變成爭議中還是定稿的同一套），**不得另立第二套**；答案有沒有變動也**必須重用既有的答案比較方式**，**不得自建第三套比較邏輯**
12. 中英文兩份文案**必須表達相同語意**，不得只修其中一種語言
13. 這一行是**預覽**：**不得寫入任何地方**，也**不得影響實際送出時的任何判定**

### 審核卡：兩個標記階段同一套版面

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核卡對**試標與正式標記渲染同一套版面**，**不得有任何依標記階段分流的呈現分支**
2. 一個審核單位就是**一位標記員對一筆資料的標記**，所以**一張卡只審一位標記員**
3. **每個輸出類型一列**（實體辨識與關係識別合併為一列，見[§實體辨識與關係識別合併成一列](#實體辨識與關係識別合併成一列)）
4. 一列的內容收斂成**單一作答面板 ＋ 單一決策列**：

| 位置 | 放什麼 |
| :--- | :--- |
| 列內 | **只有**作答／修正控件（它本身就完整呈現受審的內容） |
| 其後 | **獨立的決策列**，上面是一組「通過／修正／無法裁決」按鈕 |

5. **不得渲染輸出類型的標題**——那一列除了作答面板別無他物，面板本身已經呈現受審內容，再標一次只是噪音
6. 決策按鈕**必須掛在作答面板（含它的「無法判定」列）之後的專屬決策列上**，**不得與答案值的「無法判定 (Bypass)」勾選項共處同一個容器**——兩者是獨立的語彙，版面要明確分區
7. 這樣所有輸出類型的卡片都**以同一條決策列收尾**
8. 決策列的版面是**橫跨決策列可用寬度的分段控制**，而且它的視覺重量有下限：
   - 決策按鈕的**觸控目標不得小於 44 像素**
   - 三顆按鈕**各自面積的總和，不得小於同一張卡上答案值標籤（含「無法判定 (Bypass)」標籤）的可視面積**
   - 量測要**逐顆加總**，**不得拿按鈕群組容器本身的面積替代**——那個面積含按鈕之間的間距，會虛高
9. 每一列另外呈現**受審標記員的原答案**（標題 `標記員原答案：`，每個輸出類型各一列）與**審核員修正後的答案**（`審核員修正後答案：`），讓兩者在同一畫面並存
10. 原答案是「無法判定 (Bypass)」時，**那個標籤旁邊必須顯示標記員填的理由**——審核員要判斷這一項，得先看得到對方為什麼判不出來
11. 舊資料沒有理由欄位時：標籤**照常顯示**，理由區塊**不渲染任何文字**，**不得顯示空字串或內部值、不得報錯**，也**不得為它補寫推估的理由**

#### 審核卡上刻意完全不渲染的六樣東西

1. 下面六樣**一律完全不渲染**，而且**不得留下空殼**：

| 不渲染的東西 | 為什麼 |
| :--- | :--- |
| 標記分布統計盒 | 一張卡只審一位標記員，**跨標記員的分布沒有比對對象** |
| 一致／分歧徽章 | 同上，單人情境下沒有「一致」可言 |
| 「套用多數決至全部分歧項」 | 多數決需要多個人，單人接力下沒有可批次的對象 |
| 標記員清單 | 一張卡只有一位標記員，清單退化為單列 |
| 「設為底稿」 | 隨共識模型一併失效 |
| 中欄最上方的「原始文本」卡 | 它的資訊價值來自**跨標記員的標記聯集高亮**；只有一位標記員時，它退化成**與作答面板內原始文本完全相同的第二份副本**，只增加捲動距離與「哪一份可互動」的認知負擔 |

2. 第 1 條那張表的最後一列在**兩個標記階段都不渲染**
3. 批次的「全部通過」「全部退回」快捷鍵也**一併廢止**：審核單位收斂成單一標記員之後，沒有可批次的對象

#### 兩種情況下整張審核卡換成別的東西

1. 下面兩種情況，**決策按鈕、直接修正控件與送出按鈕一律不出現**（送出按鈕隱藏，因此它的快捷鍵同步失效）：

| 情況 | 改渲染什麼 |
| :--- | :--- |
| **空的審核單位**——受審標記員沒有儲存的提交，**而且**這一筆連示範資料的遞補列都沒有 | 空狀態卡：標題 `暫無可審核內容`、說明 `此標記員尚未提交此樣本，暫無可審核的內容。` |
| **已定稿的審核單位** | 唯讀的[定稿結果卡](#定稿結果卡) |

2. 「空」的判定**必須與脈絡橫幅顯示「尚無標記提交」的判定同源**，**不得另外維護第二份判定**
3. 標記員實際提交之後，**下一次載入就恢復完整的審核卡**
4. 已定稿的鎖定**在進入時判定**，所以**促成定稿的那一筆送出本身不受影響**——它照常寫入，寫完就地重新渲染成定稿卡
5. 已定稿單位**全面唯讀**：無決策、無直接修正、無送出，而且**這一頁不發明任何解鎖入口**
6. **中間狀態（待審、爭議中）不受這個鎖定影響**
7. 另有兩種「看得到但不能送出」的情況，文案如下（指派與名冊的規則由**階段六**撰寫）：

| 情況 | 標題與說明 |
| :--- | :--- |
| 已不在這個任務的審核員名冊中 | `無法提交審核決策` ／ `你已不在本任務的審核員名冊中，可檢視自己審核過的內容與歷程，但無法再提交審核決策。` |
| 這個審核單位沒有指派給你 | `無法提交審核決策` ／ `這個審核單位未指派給你，可檢視內容但無法提交審核決策。` |

### 三向決策

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 每個輸出類型的決策是**三向**，字面與效果如下：

| 決策 | 字面 | 效果 |
| :--- | :--- | :--- |
| 通過 | `通過` | 該項**直接定稿**；正式標記階段那個值就成為最終答案 |
| 修正 | `修正` | 審核員直接改寫該項答案，但**修正不會立即生效**——該項**進入爭議池待仲裁**，修正值成為仲裁的 B 選項 |
| 無法裁決 | `無法裁決` | 審核員表示自己無法裁決該項，該項**同樣進入爭議池**；仲裁者採 B 即定案為「無法判定」 |

2. 這三個在**兩個標記階段完全一致**，**不得依標記階段分流**
3. 決策按鈕支援**選取與取消的切換**：再次點目前選取中的那一顆，視為**取消該筆決策**並回到未選取
4. **「退回重標」不在集合內**：兩個標記階段都**不得出現**退回的控件、退回的決策值或退回的歷程產生點——標記員不再因為審核而被要求重標。畫面上留一顆沒有效果的按鈕比沒有更糟
5. 審核員對有疑慮的答案，改用**修正**（直接改，進爭議池）或**無法裁決**（進爭議池）；仲裁解決不了的進最終例外池由專案負責人收尾（見[§最終例外池是最後一道出口](#最終例外池是最後一道出口)）
6. 決策值的字面**必須讀自同一個來源**，**不得另行手寫**——它與標記員的答案值是兩套語彙，見[§審核員送出被擋時，要指名是哪一個輸出類型擋住](#審核員送出被擋時要指名是哪一個輸出類型擋住)第 8 條

#### 修正與無法裁決要附理由

1. 選**修正**或**無法裁決**時，在**同一列、作答面板之後**展開一個理由欄
2. 選**通過**或**取消決策**時，理由欄**不出現**
3. 理由是**選填**的：**理由空白不得阻擋送出**
4. 合併成一列的那兩個輸出類型，**各自有一個理由欄**
5. 理由跟著決策一起存，也跟著[決策草稿](#決策草稿)一起還原
6. 兩個標記階段**都要渲染理由欄**
7. 理由的用途是讓**仲裁者**理解分歧的成因，以及讓主持人據以修訂指引；但**要不要寫由審核員自己判斷**

### 逐輸出類型的直接修正入口

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. **八種輸出類型全部都有**逐列的直接修正入口（可新增、刪除、修改）
2. 修正用的控制項**必須重用該輸出類型在標記端的那一套作答控制項**，**不得為任何一種輸出類型另外開發專屬的修正介面**：

| 輸出類型 | 修正用的控制項 |
| :--- | :--- |
| 單選標籤 | 互斥的單選標籤鈕 |
| 多選階層標籤 | 階層多選器 |
| 單一維度／多維度評分 | 滑桿 ＋ 數字輸入框 |
| 序列標記 | **原始文本上的拖曳圈選面**（見下方說明） |
| 實體辨識 | 實體建構器 |
| 關係識別 | 關係建構器 |
| 自由文本 | 文字輸入框 |

3. 控制項的**初始值是那一筆受審標記員提交的答案**
4. 修正區的標題是 `直接修正（審核員修正後答案）`

:::warning{title="來源在這裡列了一個已經不存在的控制項"}
來源在列舉修正控制項時，序列標記那一項寫的是「Token 網格」。但**把文本預先切成一格一格、逐格點選**的那一套座標系，已經在來源 v6.0.0 **整組移除**（見[§八種輸出類型的作答控制項](#八種輸出類型的作答控制項)的序列標記第 13 條：畫面上不得出現那種版面）。依「修正控制項必須重用標記端的控制項」這條**上位規則**，序列標記的修正就是**現行的拖曳圈選面**。這裡**不照抄那個括號**。
:::

5. 修正之後，系統必須**同時保留三份東西**供品質追溯：**標記員的原始提交**、**審核員修正後的結果**，以及**兩者的差異**
6. 差異要依輸出類型呈現對應的形式：分類型是選值的差異、評分型是數值的差異、序列／實體／關係型是結構化的差異、文字型是文字的差異

#### 修正控制項的初始值要從哪裡來

1. 每個輸出類型**各自**初始化它自己的狀態；每次初始化**只能重設該輸出類型自己擁有的那一份**，**不得動到別的輸出類型剛初始化好的內容**
2. 第 1 條不是潔癖：實體辨識與關係識別**共用同一份狀態**，而合併列會依序初始化這兩個，任務再多一種輸出類型時那一列又排在後面——無差別清空會**抹掉前一個剛初始化完的清單**，修正面板就會顯示成空的
3. 關係識別的實體來源**依任務有沒有選實體辨識而不同**：

| 任務的輸出類型 | 修正控制項的實體來源 |
| :--- | :--- |
| **只有**關係識別 | 用**資料紀錄裡的實體欄位**當初始值（那些實體只是背景支架，標記員從來不標也不提交） |
| **含**實體辨識 | **一律不得**用資料紀錄的欄位回填——那時候實體**本身就是受審的答案**，回填等於把標準答案當成「沒人作答」呈現出來 |

4. 第 3 條第一列的理由：純關係任務的實體是支架，如果只用標記員的提交當初始值，實體清單必定是空的，關係建構器就會拒絕每一次文本選取（「這個選取不是資料裡的既有實體」），審核員**完全沒辦法修正關係**
5. 第 3 條兩列**在兩個標記階段都適用**
6. 初始值裡的實體**可能沒有位置**，而建構器只對帶位置的實體在原始文本上高亮；所以初始化時要**從輸入文本解析位置**：取**第一個還沒被其他實體占用的出現位置**，重疊的略過
7. 位置**一律不得取自資料紀錄的實體欄位**
8. 文本裡已經不存在的實體**維持沒有位置**，**只列在清單裡、不高亮**

#### 改了修正值之後，決策會不會被重置，看的是哪一個決策

1. 決策**綁定的是它當下所判定的那個答案值**。答案改了之後要不要重置，**依決策種類分流**：

| 原本的決策 | 改動修正值之後 |
| :--- | :--- |
| **通過**、**無法裁決** | **決策被重置**，要重新確認再送出；畫面提示 `直接修正的值已變更，對應的審核決策已重置，請重新確認後再送出` |
| **修正** | **不重置決策，也不清空理由欄，而且不出現提示**；只把它綁定的答案值**重新錨定到新值** |

2. 第 1 條第二列是**刻意的**：**把答案改成正確值，本來就是「修正」這個決策所指的動作本身**，不是對已決策答案的意外二次變更。重置它等於懲罰審核員完成了正確的操作順序
3. 第 1 條第一列的理由相反：選「通過」或「無法裁決」時，審核員判定的是**他看到的那個答案**；答案一變，原本的判定就不再成立
4. 重新整理頁面會讓**修正控制項裡還沒送出的文字或數值編輯遺失**（那部分不在決策草稿的範圍內，見[§決策草稿](#決策草稿)第 6 條）。此時：
   - **曾經改過修正值的那幾列**，決策**不還原**，並提示 `偵測到直接修正的內容因重新整理而遺失，對應的審核決策已重置，請重新確認後再送出`
   - **沒有動過修正值的列**，決策**照常還原**
5. 這些都是**呈現層的正確性守衛**，不改變送出之後的狀態轉換規則

:::note{title="這條規則的依據在哪"}
原本定義它的 `FR-077` 與 `AC-3.42` 都在 v4.55.0 **整組撤銷**，但撤銷說明的第 2 點**就是這條規則的書面落點**，而且它在 **v6.26.0 被修訂過**——正是那次修訂把重置範圍收斂成「決策不是『修正』時才成立」。所以依據是**現行正典**，不是舊轉述。

值得記一筆的是：來源的 `AC-3.59` 在它的 Given 裡引用了這條規則，而它引的是 **v6.26.0 之前**的版本（「答案須於決策之前清空，否則決策會被重置」）。只讀那一句會把「修正」的行為寫反。
:::

### 實體辨識與關係識別合併成一列

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 任務**同時含**實體辨識與關係識別時，審核卡**必須把兩者合併為單一審查列**，**不得各自渲染一列**
2. 合併的理由：兩者是**同一個標記動作的兩個階段**，共用的作答面板（關係建構器）本身就包含原始文本、實體類型選擇器與兩個「無法判定」開關；逐型別各掛一份會在同一畫面**重複渲染同一份樣本文本**，而且外觀上**無從區辨**
3. 合併列裡**只渲染一個**直接修正控制項——由**關係識別**掛載，因為它的面板是實體辨識面板的**超集**
4. 合併列的決策列上**並列兩組**決策按鈕，**各自前置型別標籤**
5. 兩者仍各自輸出獨立的決策與理由

### 差異比對：審核員到底改了什麼

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 標記員與審核員答案的差異**逐輸出類型定義**，而且比對結果要**同時提供「是否相同」與「差異項清單」**
2. 各輸出類型的比對方式：

| 輸出類型 | 怎麼比 |
| :--- | :--- |
| 多選階層標籤、序列標記、實體辨識、關係識別 | 用**合併鍵**做**順序無關的集合比對**；只存在於單邊的列為差異項 |
| 多維度評分 | **逐維度**比對 |
| 單選標籤、單一維度評分、自由文本 | **單值**比對 |

3. **評分型一律採嚴格相等，不套用任何容差**。理由值得寫出來：容差回答的是「**兩位標記員算不算有共識**」，而審核單位問的是「**審核員有沒有更動這個答案**」——**任何幅度的更動都是差異**
4. 序列標記用**集合比對**而不是逐位置比對，合併鍵是**起點＋終點＋標籤**。三個理由：
   - 範圍模型下**不存在**可以逐位比對的格子陣列
   - 逐位比對會把「一個 n 字實體被改了型別」算成 **n 個**差異項；集合比對算成「原項移除 ＋ 新項新增」共 **2 項**，與實體辨識對同一種更動的算法**一致**
   - 標籤的值不再帶 `B-`／`I-`／`E-`／`S-` 前綴
5. 差異項裡的文字是**呈現用**的，它**必須等於原始文本從起點到終點那一段**；**位置才是權威**：兩者不一致時以位置為準，**不得用文字反過來修正位置**
6. 保留那個文字欄位的理由是：審核清單與審核卡的既有呈現直接讀它來顯示標記文字，而它們的資料列未必帶著原始文本

### 決策草稿

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核員每一次變更逐列決策，**都要即時寫進一個與提交紀錄分離的草稿區**
2. 這個草稿**不得寫進提交紀錄**，也**不得產生任何操作紀錄事件**
3. 目的是**角色對稱**：標記員有「儲存草稿」，審核員在送出之前重新整理頁面時，**尚未送出的逐列決策也要還原得回來**
4. 草稿**以審核單位加上審核員本人為鍵**：一位審核員的草稿**不得外溢**到另一位審核員，也不得外溢到另一位受審標記員
5. 送出審核成功之後，該單位的草稿**必須清除**，**不得殘留舊決策讓下次進入時誤還原**
6. 草稿涵蓋**逐列的三向決策與它的取消狀態**，**不涵蓋**直接修正控制項裡還沒送出的文字或數值編輯——那部分重新整理就會遺失（見[§改了修正值之後，決策會不會被重置](#改了修正值之後決策會不會被重置看的是哪一個決策)第 2 條）
7. 草稿本身**不得構成盲審污染**：**不得以任何形式讓其他審核員看見**，連「這個人已經有動作」這個事實都不行（完整規則見[§盲審隔離](#盲審隔離還沒送出的判斷只有本人看得到)）

### 審核單位脈絡橫幅

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核卡、仲裁版面或定稿結果卡的**上方**，要渲染一個**審核單位脈絡橫幅**，**每個審核單位恰好渲染一次**
2. 橫幅的項目**依這個順序**：

| 順序 | 項目 | 內容 |
| :--- | :--- | :--- |
| 1 | 標記階段徽章 | 試標顯示 `試標 R〈回合〉`、正式標記顯示 `正式標記`；任務沒有回合值時當作**第 1 回** |
| 2 | 狀態 pill | 審核單位的狀態，見第 3 條 |
| 3 | 流程抽屜觸發鈕 | 點開一個隨選抽屜（標題 `流程與目前狀態`），**狀態軌渲染在抽屜裡、不在橫幅裡** |
| 4 | 審核決策說明 | 橫幅的**末項**；內容見[§審核決策說明](#審核決策說明) |

3. 狀態 pill 寫的是審核單位的**三態**；標記員還沒提交時，它**整個被另一句取代**：

| 狀態 | 文字 | 色系 |
| :--- | :--- | :--- |
| 待審 | `待審` | 中性 |
| 爭議中 | `爭議中 · 未定稿，待仲裁` | 錯誤色 |
| 已定稿 | `已定稿 · 已鎖定` | 成功色 |
| （三態都不成立）標記員還沒提交 | `尚無標記提交`——**取代**上面那三種，不是第四個狀態 | — |

4. **終態與未定稿一定要用文字標示，不得只靠顏色**——這就是第 3 條中間兩列各帶一個後綴的原因
5. pill 的可見文字就是**裸狀態詞加那個後綴**，**不得加 `目前：` 之類的前綴**（那個前綴是[狀態軌](#審核狀態軌)目前節點才有的）
6. 有示範資料的遞補列時**視為已經有標記員答案**，pill 要顯示 `待審`，**不得落到 `尚無標記提交`**
7. 第 6 條**只管那個 pill**。**沒有真實提交的單位**（包含只有遞補列的那種）：
   - **不渲染流程抽屜觸發鈕**，也**不渲染狀態軌**——它們描述的是「一筆真實提交走過哪條車道」，而那條歷程**確實不存在**
   - 橫幅因此只剩**標記階段徽章與 pill**，而[審核決策說明](#審核決策說明)**直接成為橫幅的末項**
8. 第 6 條的判定**必須與[空的審核單位](#兩種情況下整張審核卡換成別的東西)的判定同源**，也**必須與左欄清單的審核單位狀態標籤共用同一份推導**，**不得各自維護**
9. 橫幅的資訊**一律從既有的資料層讀取**，**不得另外維護一份狀態**
10. 橫幅的主題是「**這個單位處於哪個狀態、經由哪條車道到達**」；**身分不屬於它的主題**（受審標記員的身分由[麵包屑第 3 層](#入口麵包屑的第三層)承載）
11. 曾經有一個「定稿門檻 〈x〉 / 〈n〉 位審核員」的標籤，已經**整項移除、不得以任何形式留存**——一個單位恰好指派一位審核員，分母恆為 1，寫出「1 / 1 位審核員」只是雜訊

#### 審核狀態軌

1. 狀態軌**恰好三個節點**：`待審`、`爭議中`、`已定稿`
2. 它**刻意不是**一條線性的步驟指示器——`待審` 之後分成**兩條互斥的車道**：

| 車道 | 條件 | 走法 |
| :--- | :--- | :--- |
| 直通 | 審核員逐項**全部通過** | 直達 `已定稿`，**不經過** `爭議中` |
| 繞行 | 任一項是**修正**或**無法裁決** | 經 `爭議中`，再由仲裁或例外池定稿 |

3. 車道的條件寫在連接線上的**分支標籤**：`審核通過`、`修正或無法裁決`、`仲裁後`
4. 分支標籤是**唯一**寫出車道條件的文字，所以**不得對輔助技術隱藏**，也**不得被算成狀態軌的節點**（只有純裝飾的分岔線才隱藏）
5. 目前節點**恰好一個**，而且要用文字前綴 `目前：` 標示，**不得只靠顏色**
6. 已經走過的節點與分支要標成「走過」，而那個標記的語意是「**路線曾行經**」而不是「曾停留」：
   - 經仲裁定稿的單位，`爭議中` 節點與「修正或無法裁決」「仲裁後」兩個分支**都算走過**
   - 直通定稿的單位，`爭議中` 節點與「修正或無法裁決」分支**都不算走過**
7. 狀態軌曾經有五個節點，兩個中繼節點已隨審核單位狀態的收斂一併移除；**所有任務一律三節點**

### 審核決策說明

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核說明是一個**預設隱藏、由真實按鈕觸發**的提示泡泡，**不得用瀏覽器原生的提示屬性**
2. 它渲染在**脈絡橫幅之內**、緊接流程抽屜觸發鈕之後，位於**審核單位層級**——在審核卡堆疊之上、**不在任何一張審核卡之內**；那個單位**沒有觸發鈕時，它就是橫幅的末項**
3. 它在**整個審核單位內恰好渲染一次**，而且這個次數**不隨輸出類型數量或審核卡張數改變**：三個輸出類型的任務是 1，合併列的任務是 1，單一輸出類型的任務也是 1
4. 第 3 條**不得用「把說明拿掉」的方式**達成
5. 它在**畫面與朗讀順序上必須排在第一張審核卡之前**，維持「**先說明、後決策**」的閱讀順序
6. 它**只適用可互動的審核單位**：仲裁版面、已定稿唯讀卡與空的審核單位**都不渲染**
7. 說明的內容**必須逐字對應三向決策的真實效果**，**不得描述任何已經不存在的機制**：

| 說明要寫 |
| :--- |
| 通過 → 該項直接定稿（正式標記階段即成為最終答案） |
| 修正 → 修正**不會立即生效**，該項進入爭議池待仲裁 |
| 無法裁決 → 同樣進入爭議池，仲裁者採 B 即定案為無法判定 |
| 兩個標記階段**都不退回重標** |
| 試標的定稿**不產生最終答案**，只彙總一致性與被修改率 |

8. 說明裡**不得出現**「退回」「退回理由」「重新標記」「定稿門檻」「多數決」這些字樣
9. 兩份語言的文案**必須表達相同語意**，不得只修一種

### 決策快捷鍵

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核員有兩個決策快捷鍵：`A` ＝ 通過、`B` ＝ 無法裁決
2. 它們的作用對象是**當前審核單位的全部輸出類型**——一次按鍵就完成這個單位的決策
3. 第 2 條的理由：介面**不提供「目前聚焦的輸出類型」這個概念**，所以**不得只決定其中一個**
4. 重複按同一鍵**取消回未決策**（與決策按鈕的切換語意一致）
5. **「修正」刻意不綁快捷鍵**——修正需要鍵入替代值，沒辦法用單一按鍵完成
6. `R` **不得有任何作用、不得產生任何決策**（它曾經是「退回」）
7. 下列情況**一律不觸發**：

| 情況 | 為什麼 |
| :--- | :--- |
| 焦點在輸入框、文字區、下拉或可編輯區域 | 自由文本的修正本身就是輸入行為 |
| 按鍵帶 `Shift`／`Ctrl`／`Cmd`／`Alt` | 那是別的組合鍵 |
| 角色是標記員 | 這兩個鍵是審核用的 |

8. 批次的 `Shift+A`（全部通過）／`Shift+R`（全部退回）**已廢止並從側欄的快捷鍵總覽移除**
9. 側欄總覽裡 `B` 那一列的說明文字**必須讀自與決策按鈕相同的來源**，不得另行手寫

### 定稿結果卡

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核單位定稿後，審核卡**改渲染唯讀的定稿結果卡**，而且它的內容**必須是純文字**
2. 卡上**不得渲染**任何決策控件、修正控件或送出按鈕，**也不得渲染可互動的作答面板**
3. 卡片內容：

| 內容 | 說明 |
| :--- | :--- |
| 標題與唯讀說明 | `審核已定稿` ／ `此審核單位已定稿，結果為唯讀。` |
| 每個輸出類型的定稿值 | 來源只要求「每個輸出類型的定稿值」；畫面實際逐輸出類型分成三段，字面是 `標記員原答案`、`最終結果` 與 `定稿依據`（**這三段是畫面現況，不是來源寫出的內容契約**） |
| **微型衝突歷程** | **每個曾發生衝突的項目一列**，以單行文字寫出該項的責任鏈 |
| 剩餘可處理量 | 見[§定稿卡上的剩餘可處理量與歸零去向](#定稿卡上的剩餘可處理量與歸零去向) |

4. 微型衝突歷程的形式是一行責任鏈，例如「標記 A ➔ 審核 B（修正）➔ 仲裁 B」；**停留或聚焦時展開完整帳號與時間**
5. 那份責任鏈的資料**沿用既有的那一份，不另存第二份**（責任鏈本身見[§責任鏈與它誠實的那一句](#責任鏈與它誠實的那一句)）
6. **沒有衝突的項目不渲染歷程列**
7. 這張卡**取代**了曾經的「逐位審核員投票明細」：單人接力下每個項目恆只有一位審核員，逐位投票表恆為單列、**沒有資訊價值**；**責任鏈才是定稿後真正需要回答的問題**
8. 定稿的四種路徑**一體適用**這張卡：逐項全數通過、仲裁定案、最終例外池收尾、該單位全部項目遭排除（後三種見[§最終例外池是最後一道出口](#最終例外池是最後一道出口)與[§仲裁版面](#仲裁版面仲裁者選邊不重新標記)）

### 工作區不得有存不了的備註欄

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 中欄**不得渲染任何「看起來會被保存、實際上不接任何儲存路徑」的自由文字輸入控件**
2. 審核意見、審核理由與修正說明**一律走既有的、有持久化的路徑**：三向決策、[修正與無法裁決的理由](#修正與無法裁決要附理由)、操作紀錄事件
3. 凡是**需要被別人看見或事後追溯**的文字，**必須落在上述任一條路徑上，而且帶得出是誰、什麼時候**
4. **唯讀一致性**：已定稿單位的畫面**不得一邊宣稱唯讀、一邊保留語意不明的可編輯欄位**。任何可編輯控件的存在**就構成對唯讀狀態的否定**，不管它會不會真的寫入
5. 判定原則是**看它有沒有持久化路徑**，而不是看它在哪個角色或哪個狀態分支下
6. 要新增任何文字輸入控件之前，**必須先指明三件事**：它存在哪裡、誰看得到、會不會影響定稿結果。**三者有一個指不出來就不得渲染**
7. 有持久化的作答控制項與理由輸入**不在這條限制範圍內**

### 審核員視角的六個互斥分支

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核員開啟一個審核單位時，畫面落在**下面六個分支的其中一個**，而且**同一時刻恰好成立一個，不得混合渲染**。判定**依這個順序**：

| 順序 | 分支 | 成立條件 | 畫面 |
| :--- | :--- | :--- | :--- |
| 1 | **仲裁** | 單位是**爭議中**，而且這位審核員**具仲裁資格** | [仲裁版面](#仲裁版面仲裁者選邊不重新標記) |
| 2 | **當事審核員重入** | 單位是**爭議中**、這位審核員**不具**仲裁資格（他就是當事人），但他**在這個單位已經有自己的提交** | [唯讀摘要與改判入口](#當事審核員重入爭議單位) |
| 3 | **已定稿** | 單位已定稿 | [定稿結果卡](#定稿結果卡) |
| 4 | **已離冊** | 他已不在這個任務的審核員名冊中 | 唯讀，附說明（文案見[§兩種情況下整張審核卡換成別的東西](#兩種情況下整張審核卡換成別的東西)第 7 條） |
| 5 | **未指派** | 這個單位沒有指派給他 | 同上 |
| 6 | **空單位** | 標記員沒有提交，而且連遞補列都沒有 | [空狀態卡](#兩種情況下整張審核卡換成別的東西) |

2. 六個都不成立時，就是[可互動的審核卡](#審核卡兩個標記階段同一套版面)
3. 判定的**順序不得改變**，各分支的渲染行為也不得互相滲透
4. 仲裁資格的兩個條件寫在 [規格 04-01 §每列的動作：編輯或仲裁](./01-annotation-list.mdx#每列的動作編輯或仲裁)第 27 條，這一頁**不重寫一份**
5. 已離冊與未指派的指派規則由**階段六**撰寫

### 審核員視角的左欄：審核單位依樣本分組

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

左欄的外殼寫在[§左欄：標記清單](#左欄標記清單)，那一節第 15 條把這一段交給本階段。

1. 審核員視角的左欄**一列一個審核單位**；**同一筆資料的 N 個審核單位，必須包在一個以那筆資料為範圍的分組容器裡**
2. 每一筆資料**恰渲染一個分組容器**，而且它**不只是視覺線索**——分組要讓輔助科技也感知得到，容器的可存取名稱**必須同時包含那一筆的識別碼與它的標記員人數**
3. 第 2 條是這一頁與[標記清單](./01-annotation-list.mdx)的差別：清單那一頁受表格的列結構所限，只能用邊框與弱化樣式表達分組
4. **分組表頭承載共用的資訊**：那一筆的識別碼、標記員人數，以及那一筆的文本摘要
5. **文本摘要每個分組恰渲染一次**。理由值得寫出來：同一筆資料的所有審核單位**共用同一段原文**，逐列重複渲染會讓**最無鑑別度的內容占據最大的視覺權重**
6. 摘要旁的標籤依[§左欄：標記清單](#左欄標記清單)第 8 到 10 條，掛在**分組表頭**上
7. **群組內的項目只承載「差異」資訊**：標記員帳號與審核狀態標籤
8. 項目內**不再渲染那一筆的識別碼**。理由：同一個識別碼在三位標記員的分組內會重複出現四次（表頭一次、每列各一次），而在固定寬度的左欄裡它恆被截斷成同一串、**沒有辨識價值**
9. 項目脫離群組脈絡時的自我描述，由第 11 條的可存取名稱承載
10. **被截斷的值要還原得回來**：左欄寬度固定，項目裡的標記員帳號與表頭的識別碼都可能被截斷，所以兩者都要能**在停留時顯示完整值**
11. 每個審核單位項目的**可存取名稱必須同時包含那一筆的識別碼、標記員帳號與該單位的審核狀態**；項目本身維持原生按鈕（焦點樣式與鍵盤啟用不變）
12. **選取狀態要同時標示在兩個層級**：項目要帶得出審核單位身分的兩半（那一筆與那位標記員），而**目前選取項目所屬的分組容器也要另加標記**，使選取位置**在群組層級也辨識得出來**
13. 這一條**不改變**審核單位的資料模型、左欄項目總數、上一筆／下一筆與進度分母的粒度，也不改變網址同步的契約——**不合併任何審核紀錄**
14. **標記員視角不適用這一條**：他每一筆資料本來就只有一個項目、沒有重複的原文，所以維持逐項目顯示文本摘要
15. 響應式：寬度小於 768 時左欄整欄收合，這一條的分組不改變那個行為；該寬度下審核單位的身分改由[麵包屑第 3 層](#入口麵包屑的第三層)承載
16. 寬度 768 以上的各種寬度下，那一筆的識別碼、標記員帳號與審核狀態**都要看得到**，而且**左欄不得產生水平溢出**

### 爭議項是推導出來的，不是存起來的

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 爭議項**每次讀取時都由[差異比對](#差異比對審核員到底改了什麼)重新推導**，**不實體化儲存**
2. 這和審核單位狀態是**同一個哲學**：推導使爭議池在結構上**不可能與狀態機漂移**
3. **唯一會被寫下來的狀態是仲裁的票與定案值**
4. 推導的輸入是：那個審核單位裡**標記員已提交的答案**，與**所有審核員已提交的決策**
5. 標記員還沒提交、或還沒有任何審核員提交時，**爭議項清單是空的**
6. 爭議項的識別是**輸出類型 ＋ 合併鍵**；同一個識別跨審核員**合併成單一爭議項**
7. 排序是**穩定的**：先依任務設定的輸出類型順序，再依差異項出現的順序
8. A／B 值：

| 值 | 取法 |
| :--- | :--- |
| A（標記員側） | 差異項的標記員側值；**只存在於審核員側的，A 是空值** |
| B（審核員側） | 逐審核員保存他有差異的那一側值 |

9. **與標記員一致的審核員不得出現在 B 裡**——**沒有差異就沒有立場**。所以**完全一致的審核單位，推導結果是空清單**
10. 拆解的粒度**沿用差異比對**：

| 輸出類型 | 一個爭議項是什麼 |
| :--- | :--- |
| 多選階層標籤、實體辨識、關係識別 | 逐合併鍵各一項——**實體改型別就拆成兩項**（舊鍵移除、新鍵新增） |
| 序列標記 | 逐「起點＋終點＋標籤」各一項；**同文字不同位置不合併**；改標籤同樣形成兩項 |
| 多維度評分 | **逐維度**，只有有差異的維度成項 |
| 單選標籤、單一維度評分、自由文本 | 整個輸出類型**至多一項** |

11. 凡是呈現仲裁進度的計數，**都以爭議項為聚合單位**：每個爭議項計 1，**不得以審核單位或輸出類型把同一個單位裡的多個爭議項合併成一筆**
12. 第 11 條的分母是查詢範圍內的爭議項總數，分子是其中已裁定的數目

### 仲裁版面：仲裁者選邊，不重新標記

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 仲裁版面呈現**標記員答案的唯讀摘要**（提供一致項的脈絡）與**逐爭議項的 A／B 選擇**
2. **修正控件與三向決策控件一律不渲染**——**仲裁的產出是「採哪一側」，不是第三份新答案**
3. 仲裁**不得觸發任何形式的重新標記**
4. B 的呈現**依它的決策來源動態決定**：

| 審核員當時的決策 | B 顯示成 | 採 B 的結果 |
| :--- | :--- | :--- |
| 修正 | `B · 審核員修正值`，並附他的理由 | **以那個修正值定案** |
| 無法裁決 | `B · 審核員：無法裁決` | **定案為「無法判定」**，而且**不得回填標記員的原答案** |

5. 第 4 條第二列的冒號後面是**決策值**的文案，**不得含「Bypass」字樣**——舊標籤把答案值與決策值兩個概念的名字疊在同一個標籤裡
6. 一個審核單位恰有一位審核員，所以**每個爭議項恰有一個 B**；不存在多個 B 或需要合併相同值的情形
7. 第三個出口是**兩者皆非**：仲裁者判定 A 與 B 都不可採時選它，並提供**選填**的裁定理由
8. 選了兩者皆非之後，那個爭議項**落入[最終例外池](#最終例外池是最後一道出口)**，而那個單位**維持爭議中，直到例外池收尾**
9. **所有爭議項都裁定過（採 A／採 B／兩者皆非）才送得出去**；沒完成時**阻擋，而且不得寫入任何狀態**
10. 送出是**整個單位一次原子寫入**：當前單位的全部爭議項同一批次，**每個爭議項至多一張票，而且那張票不可變**
11. **不會因為「還有其他項沒解決」而允許改票**
12. 仲裁狀態**以審核單位定址**，**不得寫進任何審核員自己的紀錄**——**爭議屬於單位本身**，所以任何仲裁者的定案**必須對這個單位的所有檢視者可見**
13. 版面上**必須載明仲裁的效果**：逐爭議項選定定稿值、不重新標記
14. **爭議中不是終態**：這個單位所有爭議項都解決了（仲裁定案或例外池收尾）就推導為**已定稿**；還有未解決的就維持爭議中
15. 送出仲裁的按鈕位置與互斥規則見[§中欄下方：操作列](#中欄下方操作列)第 5、6 條

### 當事審核員重入爭議單位

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 這是[六個分支](#審核員視角的六個互斥分支)的第 2 個：單位爭議中、這位審核員**不具仲裁資格**（他就是當事人），但他**已經有自己的提交**
2. 畫面是**唯讀摘要**，逐輸出類型呈現：

| 內容 | 來源 |
| :--- | :--- |
| 標記員的原答案 | 標記員的提交 |
| **他自己**的決策（通過／修正／無法裁決） | **他自己的提交** |
| 修正值（決策是修正時） | 同上 |
| 裁定理由（修正或無法裁決時） | 同上 |

3. 第 2 條那三樣**必須與他自己提交的內容逐字一致**，**不得從目前還沒提交的草稿取值**
4. 裁定理由**不得拼接在決策文字的尾端**，必須**另起一組「標籤／內容」列**，與決策列用同一套對齊
5. **送出按鈕與[送出前的後果提示](#送出前的後果提示)必須隱藏**，而且**不能只是視覺上藏起來**——否則送出的快捷鍵還是打得到它
6. 版面底部有一顆次要按鈕 **「修改我的審核」**
7. 按下它之後切換成**可互動的審核卡**，而且**以他自己的提交**（不是標記員的原答案）帶出三樣東西：修正面板的初始可編輯值、決策按鈕的初始選取、裁定理由
8. 但**畫面上「標記員原答案：」那一份比對資料，來源仍然是標記員的原答案**——**兩者用途不同，不得混用同一份資料**
9. 另有一顆 **「取消，維持原決策」**，按下退回唯讀摘要，而且**不得寫入任何變更**
10. **寫入側必須有護欄**，光把送出控件藏起來不夠：

| 不設護欄會怎樣 |
| :--- |
| 當事審核員經殘留的路徑重新送出「通過」，會**抹掉他自己原本造成爭議的那個修正或無法裁決**，使一個**仍待仲裁的單位被當事人單方面消解出爭議池** |

11. 護欄的條件是三者同時成立就拒絕寫入、不追加任何歷程事件：單位是**爭議中**、這位審核員**在這個單位已有自己的提交**、而且畫面**不在**按下「修改我的審核」之後的編輯態
12. **有票就凍結**：原審核員只有在單位**仍是爭議中**、而且**整個單位還沒有任何仲裁票**時才能改判
13. 第一張仲裁票出現之後，改判入口**只顯示唯讀的原因**；直接呼叫也必須被拒絕，而且**不能用刪票來解鎖**
14. 單位已定稿時一律依[定稿結果卡](#定稿結果卡)唯讀

### 盲審隔離：還沒送出的判斷只有本人看得到

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 審核員對某個審核單位**還沒送出**的判斷——草稿決策、修正內容、「無法裁決」的標記，以及它們的草稿歷程事件——**必須只有他本人看得到**
2. **不得對任何其他角色可見**：其他審核員、具仲裁資格的審核員、專案負責人，都不行
3. 涵蓋的呈現路徑是**全部**：

| 路徑 |
| :--- |
| 右欄「操作紀錄」的合併時序清單 |
| 審核卡 |
| [仲裁版面](#仲裁版面仲裁者選邊不重新標記) |
| [標記清單](./01-annotation-list.mdx) |
| [最終例外池的收尾畫面](#最終例外池是最後一道出口) |
| [定稿結果卡](#定稿結果卡) |
| [責任鏈](#責任鏈與它誠實的那一句) |

4. **「這個人已經有動作」這個事實本身就構成污染**，**不得以摘要或去內容化的形式呈現**
5. **已送出**的判斷照既有規則走：逐審核員獨立保存、可依序讀出，以真實操作者身分併入時序清單，而仲裁的定案對所有檢視者可見
6. 標記員自己的儲存與提交事件**是受審內容的一部分**，不受這一條影響
7. 這一條保護的對象是**裁定者**：**仲裁者與專案負責人在下判斷之前，只應該看到已經正式提交的兩側主張**
8. 它與[歷程的分層遮蔽](#歷程的分層遮蔽)是**疊加關係**——一筆事件要**同時通過兩者**才呈現得出它的快照與理由

### 最終例外池是最後一道出口

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 仲裁者對某個爭議項裁定**兩者皆非**時，那一項落入**最終例外池**，由:ref[專案負責人]{id="term.project-leader"}**逐筆收尾**
2. 四個收尾動作：

| 動作 | 效果 | 限制 |
| :--- | :--- | :--- |
| 採用標記員答案 | 以標記員原答案定案 | — |
| 採用審核員答案 | 以審核員的修正值、或「無法判定」定案 | — |
| 自訂答案 | 填入自訂答案定案 | **只適用正式標記**——試標不產出最終答案，自訂答案沒有落點 |
| 排除於資料集 | 那一筆自資料集排除 | **不產生最終答案** |

3. 第 2 條第三列是**這份規格裡合法的標記階段分流**（其餘地方一律不得依階段分流）
4. **例外池是爭議池之後的最後一道出口，不得再有第四層轉送**
5. 收尾**必須記錄理由欄位的輸入與歷程事件**；理由是**選填**的，所以那個欄位允許是空字串，但**欄位本身必須隨每筆收尾紀錄寫入，不得省略**
6. 那個單位在**所有例外項都收尾之前維持爭議中**，全數收尾後推導為**已定稿**
7. 一筆收尾要算「已收尾」，**必須真的持有定案值**；自訂答案另外要求那個值**不得是空的**——負責人沒在作答控件選任何答案時的落空值，**不算已定稿**
8. 但「採用審核員答案」承接的是**無法裁決**時，定案值**本身就是空的**——那是設計上既有的「無法判定」定案語意，**不是缺陷**，仍然算已定稿，而且**不得回填標記員的原答案**

#### 例外處置畫面的外殼

1. 專案負責人的最終例外處置畫面**必須用例外池專屬的外殼**，**不得沿用標記員工作區的樣本導覽外殼**：

| 規則 | 內容 |
| :--- | :--- |
| 佇列就是左側清單 | 列出這個任務、這個標記階段的**全部待處置例外項**（一列一項），而且**與任務詳情頁的例外池計數同源**，兩處不得對「還有幾項」產生分歧 |
| 佇列**依資料分組** | 左側清單的項目**必須依那一筆資料分組**：分組表頭顯示那一筆的識別碼、**該筆待處置例外項的數目**與文本摘要（**每個分組只呈現一次**；摘要取不到時**必須省略**，**不得用其他欄位或標準答案頂替**） |
| 分組內的項目 | 每個待處置例外項**仍各自是一個原生按鈕**，**不得把不同標記員或不同輸出類型的項目合併成一列** |
| 兩種計數不混用 | **分組數（資料筆數）與整欄列項數（例外項數）是兩個不同的計數** |
| 每一項的次要資訊 | **必須用人類可讀的輸出類型名稱**，**不得顯示原始的鍵名**（原始值只留在內部識別） |
| 每一項的狀態標示 | 必須有「待處置」的**文字**標示（中英文皆然），**不得只靠顏色區辨**，而且要與一般標記進度的文案（待標記／已儲存／已提交）**明確區隔** |
| 不列一般樣本 | 清單**不得列出一般標記樣本**，也**不得對它的列套用標記進度狀態**（待標記／已儲存／已提交） |
| 計數單位是例外項 | 畫面進度**以待處置例外項為單位**，**不得用「已提交 / 總筆數」那套文案**——負責人在這個畫面不做標記提交 |
| 沒有自動儲存狀態 | 自動儲存狀態列**不得出現在這個畫面**，而且**儲存與送出入口本身也必須隱藏**：負責人在這裡沒有草稿儲存路徑，那個狀態永遠不會前進，**呈現出來就是誤導** |
| 仲裁理由就地可見 | 每一個待處置項都要呈現**使它落入例外池的仲裁理由與裁定者身分**，讓處置決定**不需要離開這個畫面就能查證** |
| 排除動作要有危險樣式 | 「排除於資料集」在視覺上**要與其餘三個採用型處置可區辨**；它不產生定案答案，而且**在這個畫面不可復原** |

2. 第 1 條那條禁止**也涵蓋畫面頂部的麵包屑**：它的第 3 層**不得沿用標記員那一套資料集樣本序號的語意**，必須與左側清單、中欄計數同源，改以**待處置例外項**識別當前項（字面見[§入口麵包屑的第三層](#入口麵包屑的第三層)第 2 條）
3. 處置的互動是**先選取、後確認**兩個獨立步驟：

| 步驟 | 規則 |
| :--- | :--- |
| 選取 | 點任一處置動作（含自訂答案展開的作答控件裡的選取）**只標記成目前選取**，**不觸發任何寫入、不產生歷程事件** |
| 切換選取 | 可以自由換，**切換前已填的理由文字不因此清空** |
| 彙整 | 畫面要有彙整區塊：沒選時顯示 `尚未選擇最終處置`；選了之後顯示所選處置的名稱，而「採用標記員答案」「採用審核員答案」與**已選到合法值**的「自訂答案」還要**額外顯示定案值**；「排除於資料集」不顯示定案值 |
| 確認 | **「確認處置」是這個畫面唯一的寫入入口**；點了才依已選的處置與已填理由執行寫入 |

4. 四個處置動作**都提供理由欄位**，而且**都是選填**
5. 「確認處置」的停用條件**只取決於有沒有選取處置**——**不得再以理由是否為空當停用條件**
6. **權限上限**：這個畫面的四個收尾動作都是**寫入**，而 PRD §權限矩陣給專案負責人的上限是 `R`。本頁**不默默放寬**，落差與處理方式見[§使用角色](#使用角色)

### 責任鏈與它誠實的那一句

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

1. 每一筆歷程事件都要能回答四個問題：**誰**、**在哪個環節**、**做了什麼決定**、**為什麼**
2. 所以事件必須攜帶：真實的操作者身分與他當下的角色（標記員／審核員／仲裁者／專案負責人）、他的動作、受影響的輸出類型，以及該動作所附的理由
3. 同一個審核單位的事件**依時序串起來就是那個單位的責任鏈**
4. **但「為什麼」這一問已經沒有保證**：

| 四問 | 保證程度 |
| :--- | :--- |
| 誰、在哪個環節、做了什麼決定 | **由資料結構本身保證可答** |
| **為什麼** | **取決於操作者是否自願填寫**——審核側的修正、無法裁決、兩者皆非與例外池收尾，理由都已改為選填 |

5. 第 4 條是**維護者明示接受的取捨**，**不得被讀成實作缺陷**；理由為空時畫面顯示 `未填寫理由`，**不得留白、不得顯示內部值**
6. `reason` 這個欄位**仍然必須隨每筆事件寫入**，空值以空字串表示，**不得用「沒有這個欄位」來表示空**
7. [定稿結果卡的微型衝突歷程](#定稿結果卡)與仲裁版面的脈絡，**都必須由這一份責任鏈推導**，**不得另存第二份**
8. [盲審隔離](#盲審隔離還沒送出的判斷只有本人看得到)**優先於**這一條：還沒送出的判斷**不得出現在別人看得到的責任鏈裡**
9. 歷程事件**永不刪除**，而且一般的寫入路徑**只能追加**，**不得更新或刪除既有事件**

### 操作紀錄裡的每一筆事件

<PrototypeFrame page="annotation/annotation-workspace" caption="標記工作區" client:idle />

右欄那個頁籤的外殼寫在[§右欄：說明與檔案、操作紀錄](#右欄說明與檔案操作紀錄)；這一段寫**裡面放什麼**。清單側的呈現已寫在 [規格 04-01 §處理狀況](./01-annotation-list.mdx#處理狀況)，**這一頁不重寫那一半**。

1. 同一筆資料的標記員事件與審核員事件**合併成單一時序清單，最新的在前**；沒有紀錄時顯示空狀態文案
2. 每一筆事件呈現：操作者的角色與身分、時間、動作徽章、對應輸出類型的作答摘要
3. 動作的集合是**固定的八種**，**不得是自由字串**：

| 動作 | 什麼時候產生 |
| :--- | :--- |
| 已存草稿 | **只有標記員**存草稿會產生；**審核員的草稿不產生這個事件** |
| 已提交 | 標記員提交 |
| 審核修正 | 審核員直接修正答案 |
| 審核通過 | 審核員通過 |
| 無法裁決 | 審核員的決策是無法裁決 |
| 仲裁定案 | 仲裁者定案 |
| 例外收尾 | 專案負責人在最終例外池收尾 |
| 已排除 | 那一筆經例外池排除於資料集之外 |

4. 每個動作值**必須有對應的產生點**，而且**每一個都要對到唯一的徽章語意色**，那個對應**由單一來源驅動**，**不得在渲染端逐值寫死分支**
5. 動作徽章的**可見文字是中文標籤**，**不得直接把動作的內部值當畫面文案**；中文標籤的對照表寫在 [規格 04-01 §處理狀況](./01-annotation-list.mdx#處理狀況)第 54 條
6. 第 5 條的禁止**只適用集合內的動作**。既有事件出現**集合以外**的動作值時：**可見文字原樣顯示來源的英文動作值**，**不得替它臆測一個中文譯名**；徽章用**中性**樣式，而且**不得中斷渲染**
7. 第 6 條有兩個例外與一個不是例外的，規則逐字寫在 [規格 04-01 §處理狀況](./01-annotation-list.mdx#處理狀況)第 55 到 57 條，**這一頁不重寫**
8. 舊事件缺少後來才加的欄位時：**缺哪一個就不渲染對應的區塊**，系統**不得為舊事件補寫推估的快照、耗時或理由**

#### 答案改了什麼：結果快照與差異

1. 每一筆**會改變答案內容**的事件（提交、審核修正、仲裁定案）都要保存**當下的結果快照**
2. 快照是那一筆的完整作答結果，而且**必須排除原始文本與資料集欄位**——**快照的用途是回答「答案改了什麼」，不是複製受標記的資料**
3. 歷程面板上的差異，由**同一操作者維度下相鄰兩筆事件的快照在呈現時計算**，**不得另存一份差異結果**
4. 差異的呈現**由輸出類型驅動**，不得逐任務寫死：

| 類型 | 怎麼呈現差異 |
| :--- | :--- |
| 純值類型（單選、多選、單一維度、多維度、自由文本） | 比對值本身 |
| 具位置資訊的類型（實體辨識、關係識別、序列標記） | **逐實體列出新增、刪除與邊界變更三類**；**實體數量相同而邊界不同時也必須列出** |

5. 同一操作者維度下**沒有前一筆事件時**（首次提交），該事件呈現為**全新內容而不是差異**
6. 關係識別**依來源形狀分流**：來源本身帶位置的逐實體列出；**來源本身不帶位置的，維持純值比對遞補**
7. 第 6 條**不是例外開口**，而是「**來源資料本身沒有位置時不得偽造位置**」的落實
8. 審核修正事件的相鄰快照比對**產生至少一筆可見差異時，那個結構化差異就是畫面上唯一的答案變更摘要**；只有在沒產生差異時才退回顯示原始摘要

#### 耗時

1. 每一次作業都要記下**起算時間**與**耗時**
2. 耗時的口徑是**頁面可見時間的累計**：分頁切到背景或視窗失焦時**暫停計時**，回到前景**續計**
3. **不得用「事件時間相減」的掛鐘時間充當耗時**
4. **耗時不得出現在標記員視角的任何地方**。理由寫在來源裡：**讓標記員看見秒數會改變他的作答行為，污染用耗時分析標記難度的研究資料**
5. 審核員視角與任務層級的統計**看得到**
6. **一次作業只記一份耗時**：審核員一次送出會寫入多筆決策事件時，**只有第一筆帶這兩個欄位**，其餘不得重複帶
7. 這裡的耗時**不等於工時**——工時由任務詳情那一側的工時紀錄計算（見[規格 03-03](../03-task-management/03-task-detail.mdx)）

#### 歷程的分層遮蔽

1. 歷程的呈現**分兩層**：

| 層 | 內容 | 誰看得到 |
| :--- | :--- | :--- |
| 事件列 | 操作者角色與身分、時間、動作 | **所有能檢視這一筆的人** |
| 快照與理由 | 答案內容與理由文字 | **依角色遮蔽**，見第 2 條 |

2. 快照與理由的可見範圍：

| 角色 | 看得到什麼 |
| :--- | :--- |
| 標記員 | **只有自己**那些事件的快照與理由 |
| 審核員 | **自己審核單位範圍內**全部事件的快照與理由 |
| 具仲裁資格的審核員，在爭議單位上 | 該筆資料**全部標記員**的快照與理由 |

3. 標記員這一層**比遮蔽更嚴**：**別的標記員的事件不得進入他的歷程輸出，連事件列都不行**
4. 第 3 條的理由：事件列本身承載「對應輸出類型的作答摘要」，而**那個摘要就是答案內容**；只遮蔽快照與理由，仍然會經由摘要外洩
5. 第 3 條是這一條**新確立**的規則，依據是資料公平性這條不可協商的原則
6. 試標階段還有一道**揭露時點的閘門**：標記員在**該回合還沒揭露之前**，歷程輸出**只含他本人的事件**——審核員、仲裁、例外池的事件都不得進來，**事件列、快照與理由皆然**。揭露的時點寫在 [規格 04-01 §什麼時候才能揭露](./01-annotation-list.mdx#什麼時候才能揭露)
7. **遮蔽必須在供給資料的那一層完成，不得只用樣式隱藏**——被遮蔽的內容**不得存在於那個檢視者取得的呈現輸出裡**

## 卡控機制

階段一到五的卡控都列在這裡；階段六會往下加。

| 條件 | 結果 |
| :--- | :--- |
| 網址查不到已發布的任務設定 | 導回標記清單，**不得以預設輸出類型或空白控制項呈現工作區** |
| 網址沒帶要處理的那一筆 | **不得載入作業區**，導回標記清單 |
| 網址帶的那一筆查不到 | 回退到第一筆，並把網址改寫成實際顯示的那一筆 |
| 任務設定的輸出類型是空的或缺必要內容 | 顯示任務設定錯誤並**阻擋提交**，不得用預設控制項頂替 |
| 角色缺值或是不認得的值 | 回退成標記員 |
| 標記階段缺值或是不認得的值 | 回退成試標 |
| 左欄標題 | **固定「標記清單」**，不得附加任何回合標籤 |
| 麵包屑第 3 層、角色是標記員 | **不得顯示那一筆的識別碼，也不顯示自己的帳號**；只顯示佇列位置 |
| 麵包屑第 2 層、進來時帶了身分參數 | 返回網址要**帶回同一個身分**，並與清單的四個檢視狀態併存 |
| 麵包屑第 2 層、進來時沒帶身分參數 | 返回網址**不得**補上身分參數 |
| 翻筆 | 網址**原地取代**，不得在瀏覽器的上一頁堆疊；其餘參數**就地保留** |
| 翻筆、角色是標記員 | **不得**在網址新增它原本沒有的受審標記員參數 |
| 位在首筆或末筆 | 對應的導覽按鈕停用；該方向的快捷鍵**無作用**，不得回捲到另一端 |
| 按鈕隱藏或停用 | 對應快捷鍵無作用，但**瀏覽器預設行為仍須被攔住** |
| 角色是審核員（儲存草稿） | **不提供「儲存草稿」**；`Ctrl/Cmd + S` 不得寫入草稿 |
| 任務沒開「先讀說明」 | 說明彈窗**在任何情況下都不得出現**（待 Q4 確認） |
| 任務開了「先讀說明」、這個指引版本沒確認過 | 進場顯示彈窗，按確認才開始 |
| 任務開了「先讀說明」、這個指引版本已確認過 | **不得重複顯示**（含重新整理）（待 Q4 確認） |
| 確認過 A 任務後進入 B 任務 | B 任務**從頭重新判定**，不得被 A 的確認抑制 |
| 遇到另一個指引版本 | **必須重新確認**；舊版本的確認**不得失效** |
| 說明彈窗的內容來源 | **必須與右欄同一來源與同一指引版本**，不得另維護第二份文字 |
| 說明檔案沒有 Markdown 類型 | 彈窗退回顯示檔名清單 |
| 點說明檔案（PDF） | **頁面內嵌入預覽，不得開新分頁** |
| 點說明檔案（圖片） | 置中彈窗顯示大圖，不得只用底部小圖頂替 |
| 點說明檔案（Markdown） | 彈窗顯示排版後內容，不得用純文字區塊頂替 |
| 任一預覽彈窗 | 關閉按鈕、點遮罩、`Esc` **三條路都要能關**；焦點進得去、出得來 |
| 說明檔案裡夾帶網頁標記 | **一律當文字顯示** |
| 說明檔案的連結位址不是一般網址、信件位址、相對位置或錨點 | **降級成純文字** |
| 說明檔案的連結 | 一律開新分頁 |
| 同一份說明重複排版 | **錨點必須相同**；同名標題的錨點必須互不相同 |
| 翻到下一筆（桌機） | 右欄**不收起、內容不重置** |
| 翻到下一筆（手機） | 抽屜**維持原本的開合狀態** |
| 手機版 | 抽屜**不得遮蔽核心標記區**；抽屜**不含操作紀錄頁籤** |
| 中欄 | **不得渲染任務標題卡**（含卡內語言切換鈕），兩種角色都一樣 |
| 卡片內 | 題目卡**不得再包內框**；標記卡**不得殘留水平分隔線**；整合預覽**不得再包外框**；「無法判定」自身的虛線框**要保留** |
| 送出按鈕的位置 | 固定在底部操作列右側、不隨內容捲動；卡片內**不得再放一顆** |
| 工作區讀到的樣本切分 | **不得重算或覆寫**，只能用發布時凍結的那一份 |
| 說明另存新版 | **不得改寫已開始回合的指引** |
| 任務設定的輸出類型清單 | 區塊**依清單順序**逐一排出；**不得依輸出類型、組合或任務名稱寫死分支** |
| 在某一個輸出類型作答 | **只更新該區塊**；不得清除或覆寫其他輸出類型的既有作答 |
| 單筆任務 | **不得顯示雙欄配對版面** |
| 配對任務缺了任一邊的輸入內容 | **不得顯示空白配對區塊**；顯示資料欄位錯誤並阻擋提交 |
| 沒有指定背景參考欄位 | **不得顯示空的背景區塊** |
| 輸出類型自己已呈現背景參考 | **不得再顯示第二張**背景參考卡 |
| 多個輸出類型自己內嵌原文 | 通用輸入文字區塊**不得重複顯示** |
| 背景參考卡 | **只供閱讀**，不得有任何可編輯輸入或選取控制項 |
| 多選階層標籤的選擇器展開 | **必須是最上層不透明覆蓋層**，完整遮蓋後方內容（含「無法判定」），**不得穿透** |
| 多選階層標籤超過選取上限（非 0） | **阻擋新增選取**並提示上限；提示沿用工作區既有欄位提示的字級與顏色，不得用瀏覽器預設樣式 |
| 評分的當前值標籤 | 任何時刻都要顯示數值、與數字輸入框一致，**不得用佔位符號取代數字**——唯勾了「無法判定」例外 |
| 評分未作答、也沒有預填 | 範圍中點**只是起始位置**，不計為已作答、**不得當成有效值提交** |
| **預填或匯入**的評分值不落在設定的範圍與級距 | 顯示驗證錯誤並阻擋提交 |
| 標記員**手動鍵入**的評分值 | 只依**範圍**校正：範圍內的非級距小數**必須接受、不得吸附**；超出範圍的**自動校正**回範圍內，不是驗證錯誤 |
| 序列標記圈選範圍與既有範圍相交 | **即時可見的拒絕回饋**且**不建立**那一筆 |
| 序列標記圈選範圍與既有範圍相鄰但不相交 | **必須允許** |
| 序列標記的吸附單位 | **只影響滑鼠落點，不影響存下來的值** |
| 執行環境做不到詞界判定 | 那一位標記員退回「不吸附」並顯示一行提示；**不得改寫任務設定值**，提示**不得呈現為資料品質警告** |
| 標記員的吸附能力與他人不同 | 答案**必須照常納入**一致性、共識與差異比對；**不得標記為可疑、降權或排除**，**不得事後對齊詞界** |
| 序列標記的畫面 | **不得出現**預先切格的逐格點選版面、`B-`／`I-`／`E-`／`S-` 前綴的標籤鈕或「標記方案」呈現 |
| 序列標記的範圍起點大於等於終點、起點小於 0、終點超出文本長度 | **阻擋提交**並顯示可定位的錯誤 |
| 序列標記沒有任何範圍且沒宣告「無法判定」 | 阻擋提交；建立任一筆後解除 |
| 沒先圈選文字就點實體類型按鈕 | 顯示錯誤提示，**不得建立實體** |
| 關係識別純模式 | **不得顯示**實體類型選擇器、實體列表或建立／刪除實體的控制項 |
| 關係識別的 `E1`／`E2` 選取不符既有實體，或沒先選取 | 顯示錯誤，**該草稿格不填入** |
| 關係識別三個草稿格沒全部填妥 | 「新增」停用——**不存在只填一部分就新增三元組的路徑** |
| 關係識別草稿全空 | 「退回」停用；**不移除**已入列的三元組，純模式**也不移除**既有唯讀實體 |
| 關係類型清單為空 | **不顯示類型選單**，**不得輸出寫死的類型** |
| 關係識別的建構介面 | **必須與新增任務的標記預覽是同一個互動控制**，不得另提供下拉選單之類的替代型態 |
| 三元組的來源沒帶位置資訊 | 位置就是**沒有**；**不得用答案字串回原始文本比對回推**（硬規則，不得以「多數情況正確」放寬） |
| 自由文本超過字數上限 | **阻擋繼續輸入**並**阻擋提交** |
| 自由文本沒有「用途是輸出」的欄位 | 作答框是**空的** |
| 同時選了實體辨識與關係識別 | 以**整合模式**呈現；工作區**不得自動加入或移除**這個關聯 |
| 反白跨到兩則發言 | **拒絕**並顯示提示，不新增實體也不新增關係選取 |
| 實體沒帶座標、文字在對話裡出現多次或找不到 | **不得猜**、不得取第一次出現；該實體不標示並顯示「無法定位」提示與數量 |
| 同一則發言內實體區間重疊 | 後者**不得默默略過**；儲存內容不變，畫面顯示因重疊而未標示的數量 |
| 反白位置與發言文字對不上且該文字出現多次 | **不得取第一次出現**；顯示專屬歧義提示，而且提示**不得顯示未替換的佔位符號** |
| 回覆欄位的值缺漏、為空、找不到對應發言，或等於自己 | **不縮排也不顯示**回應標記；**不得由實體、關係或 `@名字` 推測回覆關係** |
| 輸入是物件陣列但沒設定對話串欄位 | 以可摺疊、等寬字呈現原始內容，**不得出現 `[object Object]`** |
| 對話串與原始內容的呈現 | **只渲染用途是輸入的欄位**；輸出與背景參考**不得因此外露** |
| 輸入是物件陣列 | **不得用「用途是輸出」的欄位預填**實體或三元組 |
| 整合預覽的預填來源 | **只能從任務設定明文宣告的預填欄位讀取**，不得依固定欄位名稱去讀 |
| 宣告的預填欄位用途是「輸出」 | **一律不預填** |
| 宣告的預填欄位**沒有指派用途、是空的，或查不出來** | **一律不預填**（守門從嚴）；**不分輸入是字串或物件陣列、不分實體或三元組** |
| 關係類型清單由預填三元組帶入 | 候選**只能來自通過角色守門的欄位** |
| 勾了「無法判定」 | **清空並停用該區塊**其他控制項；**只影響該區塊** |
| 取消「無法判定」 | 恢復可操作並依預填規則**重新初始化** |
| 設定不允許「無法判定」的輸出類型 | 只能依一般驗證規則阻擋提交，**不得提供「無法判定」當繞過手段** |
| 勾了「無法判定」卻沒填理由 | **阻擋送出**、行內錯誤、警告訊息**指名**缺理由的輸出類型；**不得產生提交紀錄** |
| 整合模式勾了實體辨識的「無法判定」 | 整合區塊**一併**清空停用（含關係建構器） |

| 寬度 768 以上 | 識別碼、標記員帳號與審核狀態**都要看得到**，而且**左欄不得水平溢出** |
| 爭議項 | **每次讀取時重新推導**，**不得實體化儲存**；唯一會寫下來的是**仲裁的票與定案值** |
| 與標記員一致的審核員 | **不得出現在爭議項的 B 裡**——沒有差異就沒有立場；完全一致的單位推導為**空清單** |
| 仲裁進度的計數 | **以爭議項為聚合單位**；**不得把同一單位裡的多個爭議項合併成一筆** |
| 仲裁版面 | **不渲染**修正控件與三向決策控件；**不得觸發任何形式的重新標記** |
| 採 B 而該決策是「無法裁決」 | **定案為「無法判定」**，**不得回填標記員的原答案** |
| B 的字面 | 冒號後是**決策值**文案，**不得含「Bypass」字樣** |
| 仲裁送出 | **全部爭議項都裁定過才送得出去**；未完成時阻擋且**不得寫入任何狀態** |
| 仲裁的寫入 | **整個單位一次原子寫入**，每個爭議項**至多一張不可變票**；**不因還有未解決項而允許改票** |
| 仲裁狀態的定址 | **以審核單位定址**，**不得寫進審核員自己的紀錄**；任何仲裁定案**必須對該單位所有檢視者可見** |
| 兩者皆非 | 該項落入**最終例外池**，單位**維持爭議中**直到收尾 |
| 當事審核員重入 | 唯讀摘要的三樣內容**必須與他自己的提交逐字一致**，**不得取自未提交的草稿** |
| 裁定理由的呈現 | **不得拼接在決策文字尾端**，必須另起「標籤／內容」列 |
| 當事審核員重入時的送出控件 | **必須隱藏**，而且**不能只是視覺遮蔽**——否則送出快捷鍵還打得到 |
| 「修改我的審核」的初始值 | 以**他自己的提交**帶出修正值、決策與理由；但「標記員原答案」那一份比對資料**仍取自標記員**，**不得混用** |
| 「取消，維持原決策」 | 退回唯讀摘要，**不得寫入任何變更** |
| 單位爭議中、他已有自己的提交、且不在編輯態 | **拒絕寫入**、不追加任何歷程事件——否則當事人會**單方面把仍待仲裁的單位消解出爭議池** |
| 整個單位已有仲裁票 | 改判入口**只顯示唯讀原因**；直接呼叫也拒絕，**不得刪票解鎖** |
| 還沒送出的審核判斷 | **只有本人看得到**；**不得對任何其他角色可見**（含仲裁者與專案負責人） |
| 「已有動作」這個事實 | **本身就構成盲審污染**，**不得以摘要或去內容化形式呈現** |
| 一筆事件要呈現快照與理由 | **必須同時通過盲審隔離與分層遮蔽** |
| 自訂答案 | **只適用正式標記**——試標不產出最終答案 |
| 排除於資料集 | **不產生最終答案**；視覺上要與其餘三個採用型處置**可區辨**，而且**在該畫面不可復原** |
| 例外池 | **是最後一道出口**，**不得再有第四層轉送** |
| 收尾紀錄 | 理由**選填**但欄位**必須隨每筆寫入、不得省略**；要算已收尾**必須真的持有定案值** |
| 自訂答案的定案值為空 | **不算已定稿** |
| 「採用審核員答案」承接「無法裁決」 | 定案值為空**是設計語意、不是缺陷**，仍算已定稿且**不得回填標記員原答案** |
| 例外處置畫面 | **不得沿用標記員工作區的樣本導覽外殼**（含頂部麵包屑）；**不得有自動儲存狀態列** |
| 例外處置畫面的左側清單 | 只列待處置例外項，**與任務詳情頁的計數同源**；**不得列一般樣本**、不得套用標記進度狀態 |
| 例外處置的選取 | **不觸發任何寫入、不產生歷程事件**；切換選取**不清空已填理由** |
| 「確認處置」 | **是該畫面唯一的寫入入口**；停用條件**只取決於有沒有選取處置**，**不得以理由是否為空當條件** |
| 例外池的四個收尾動作 | 都是**寫入**，而 PRD 的上限是 `R`——**不得默默放寬**，見[§使用角色](#使用角色) |
| 歷程事件 | **永不刪除**；一般寫入路徑**只能追加**，不得更新或刪除既有事件 |
| 動作值 | 取自**固定的八種**，**不得是自由字串**；每個值**必須有產生點**，徽章語意色**由單一來源驅動** |
| 集合以外的動作值 | **可見文字原樣顯示英文原值**、**不得臆測中文譯名**；中性徽章、**不得中斷渲染**（兩個例外見 規格 04-01） |
| 動作徽章的可見文字 | **必須是中文標籤**，不得直接用內部值當文案 |
| 舊事件缺少後來才加的欄位 | **缺哪一個就不渲染對應區塊**；**不得補寫推估的快照、耗時或理由** |
| 結果快照 | **必須排除原始文本與資料集欄位**——快照要回答「答案改了什麼」，不是複製受標記資料 |
| 歷程面板的差異 | 由相鄰兩筆快照**在呈現時計算**，**不得另存一份差異結果** |
| 具位置資訊的類型的差異 | **逐實體列出新增、刪除與邊界變更**；**數量相同而邊界不同也必須列出** |
| 來源資料本身沒有位置 | **維持純值比對遞補**；**不得偽造位置** |
| 耗時的口徑 | **頁面可見時間累計**，切到背景暫停；**不得用事件時間相減的掛鐘時間** |
| 耗時對標記員 | **不得出現在標記員視角的任何地方** |
| 一次作業的耗時 | **只記一份**；審核員一次送出寫多筆事件時只有第一筆帶，其餘不得重複 |
| 標記員的歷程輸出 | **別的標記員的事件不得進入，連事件列都不行** |
| 試標回合揭露之前、標記員檢視 | 歷程輸出**只含他本人的事件**；事件列、快照與理由皆然 |
| 遮蔽的實作位置 | **必須在供給資料的那一層完成**，**不得只用樣式隱藏**——被遮蔽的內容不得存在於該檢視者取得的輸出裡 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到什麼 |
| :--- | :--- |
| 網址什麼參數都沒帶 | 導回標記清單（清單那一側會顯示「未指定任務」，見[規格 04-01](./01-annotation-list.mdx#空的與找不到)） |
| 網址帶了不存在的任務 | 導回標記清單，**不會看到半套的工作區** |
| 網址帶了不存在的那一筆 | 停在第一筆，網址同步成第一筆——重新整理不會再跳一次 |
| 任務設定的輸出類型是空的 | 任務設定錯誤的訊息，提交被擋住 |
| 這個任務只有一筆 | 「上一筆」與「下一筆」兩顆都停用 |
| 停在第一筆按 `Alt + ←` | 沒有任何反應，**不會跳到最後一筆**，也不會觸發瀏覽器的上一頁 |
| 說明檔案清單是空的 | 右欄只有「任務說明」摘要，沒有檔案列；標記主流程不受影響 |
| 說明檔案的連結失效 | 一則可追蹤的錯誤訊息，標記主流程**照樣能走** |
| 說明沒有 Markdown 類型、但任務要求先讀 | 彈窗顯示檔名清單（不是空白彈窗） |
| 說明檔案裡有兩個文字一樣的標題 | 兩個標題各自跳得到，不會互相搶 |
| 作業中途換語言 | 麵包屑、頁籤名稱與動作提示文字即時跟著換；作答內容不受影響 |
| 在手機上翻筆 | 抽屜維持原本的開合，不會自己彈開也不會自己收起 |
| 把右欄收起後翻筆 | 翻筆**不會自行改變收合狀態**；收起後要展開得自己點（來源只禁止「自動收起或清空」，沒有定義手動收起之後的保存，見 [§待釐清](#待釐清) Q8） |
| 從深連結直接進來（沒經過站內導覽） | 麵包屑三層都在，和站內點進來一模一樣 |
| 任務在試標第 2 回合 | 左欄標題還是「標記清單」，回合由麵包屑第 2 層講 |
| 回合換了指引版本 | 再次進場要重新確認一次說明 |
| 同一個人在兩個分頁開同一筆 | 以版本號檢查為準：衝突時阻擋覆寫並提示手動合併（細節見階段三） |
| 任務的輸出類型只有一種 | 就一個標記區塊；規則與多種時完全相同 |
| 任務有三種以上輸出類型 | 全部都在同一筆的同一個畫面裡完成，不分頁 |
| 多選階層標籤的選擇器正蓋著「無法判定」 | 要先關掉選擇器才點得到它；四種關閉途徑任一種都行 |
| 評分滑桿停在中點、使用者沒動過 | 提交被擋（那不算作答）；畫面也看得出是未評分狀態 |
| 圈選的範圍剛好接在前一個範圍的結尾 | 正常建立——相鄰不算相交 |
| 預標記的範圍超出原始文本長度 | 那幾筆被拒絕並列在錯誤清單，其餘正常載入 |
| 關係識別純模式、反白的文字不是既有實體 | `E1`／`E2` 那一格不填入並顯示錯誤；`Relation` 那一格照樣接受 |
| 三元組來自純字串形狀、完全不帶位置 | 位置四個值都是「沒有」；差異比對**回退為純值比對，照常呈現，不得變成空差異** |
| 對話串的某則沒有發言者 | 那一則不顯示頭像，其餘照常 |
| 對話串沒有設定發言編號欄位 | 用位置編號，從 1 起算 |
| 對話串某則的回覆值指向自己 | 不縮排、不顯示回應標記 |
| 切到「純文字」模式 | 標示不畫了，但**已記錄的實體資料不變**，而且**還是可以反白標記** |
| 同一筆裡同時有定位不到與重疊未標示的實體 | 兩種數量各自顯示，不混在一起 |
| 正式標記的單位已定稿、標記員又進來 | 看到已定稿提示；兩顆按鈕在但停用；按快捷鍵沒有反應 |
| 試標的單位已定稿、標記員又進來 | **不受定稿鎖影響**，後續回合照常 |
| 審核員剛開始處理、標記員同時還開著這一筆 | 下一次渲染就看到審核中提示並鎖住；已輸入但沒存的內容不會被寫入 |
| 剛載入一筆、什麼都沒動 | 指示器是「尚未儲存」 |
| 編輯了但還沒存就切到別筆再切回來 | 切回來時依**這一筆自己**的寫入狀態顯示；切換本身不會讓它變成已儲存 |
| 存過草稿之後重新整理 | 仍然顯示同一個「上次儲存於」時間 |
| 在兩個分頁對同一筆同時編輯並儲存 | 後存的那次被擋下並提示手動合併，不會靜默覆寫 |
| 任務只剩最後一筆未提交 | 提交後直接導回清單，而且篩選、搜尋、頁碼與身分都還在 |
| 審核員三個輸出類型只決策了兩個 | 送出被擋，提示指名**那一個**還沒決策的 |
| 審核員全部決策完，但其中一個選了「修正」而答案留空 | 送出被擋，提示指名**那一個**答案為空的 |
| 審核員改了某個輸出類型的答案再選「通過」 | 後果提示顯示**爭議池**那一句，不是「送出後即定稿」 |
| 審核員在試標階段全部選「通過」 | 後果提示是「送出後即定稿，成為最終答案」再加上試標的加註 |
| 審核員送出後這個任務已經沒有可處理的單位 | 導回清單，篩選與身分都在，而且看得到「已無可處理單位」的說明 |
| 審核員送出後讓這個單位定稿、而且已經沒有其他可處理單位 | 停在原單位的定稿卡上，卡上的剩餘量是 0 並附一個回清單連結；**不會自動跳走** |
| 下一個可處理單位的排序在目前這一筆之前 | 照樣前進到它——方向是優先序，不是往後繞 |
| 審核單位的標記員完全沒提交、也沒有遞補列 | 看到「暫無可審核內容」，沒有任何決策或送出控件；按 `A`／`B` 也沒有反應 |
| 標記員之後補提交了 | 下一次載入就看到完整的審核卡 |
| 審核員按 `A` 而任務有三個輸出類型 | 三個**全部**變成「通過」，不是只決定其中一個 |
| 連按兩次 `A` | 第二次把整個單位的決策**取消**回未決策 |
| 焦點在修正用的文字框時按 `A` | 輸入一個字母 `A`，**不觸發**決策 |
| 按 `R` | 完全沒有反應 |
| 選了「通過」之後又改了修正值 | 那個輸出類型的決策被重置，要重新確認；畫面有提示 |
| 選了「修正」之後又改了修正值 | 決策與理由**都還在**，**沒有**提示——改答案就是「修正」這個決策本身的動作 |
| 改過修正值之後重新整理 | 那一列的編輯遺失、決策不還原並提示；**其他沒動過的列決策照常還原** |
| 任務同時有實體辨識與關係識別 | 審核卡上**只有一列**，列內只有一個修正控制項，決策列上並列兩組按鈕 |
| 純關係識別任務 | 修正控制項裡看得到資料裡的既有實體，選得到它們來建關係 |
| 任務含實體辨識 | 修正控制項**不會**冒出資料紀錄裡的實體——那是受審答案本身 |
| 審核員把某個評分從 3 改成 3.1 | 算差異（嚴格相等，沒有容差） |
| 審核員把一個 5 字實體的型別改掉 | 算 2 個差異項（原項移除 ＋ 新項新增），不是 5 個 |
| 直通定稿的單位 | 狀態軌上 `爭議中` 節點與「修正或無法裁決」分支**都不算走過** |
| 經仲裁定稿的單位 | 狀態軌上 `爭議中` 節點與「修正或無法裁決」「仲裁後」分支**都算走過** |
| 三個輸出類型的任務 | 審核決策說明仍然**只有一份**，不是三份 |
| 已不在審核員名冊中的人開啟單位 | 看得到自己審過的內容與歷程，但沒有送出入口 |
| 審核員完全沒改任何答案、全部選「通過」 | 爭議項推導為**空清單**，單位直接定稿、不經爭議中 |
| 一筆資料由三位標記員標過 | 左欄是**一個分組容器內三列**；摘要只在表頭出現一次 |
| 標記員帳號太長被截斷 | 停留時看得到完整帳號 |
| 以標記員身分看左欄 | **沒有分組**，每一筆一列並各自顯示摘要 |
| 標記員還沒提交、但已有審核員決策 | 爭議項清單是**空的**（推導的輸入缺一半） |
| 仲裁者把某一項裁為「兩者皆非」、其餘採 A | 該單位**維持爭議中**，只有那一項落入例外池 |
| 仲裁者只裁定了一部分爭議項 | 送不出去；而且**沒有任何狀態被寫入** |
| 仲裁送出後又想改票 | 改不了——每項至多一張不可變票 |
| 當事審核員在仲裁票出現後點「修改我的審核」 | 只看到唯讀的原因，進不了編輯態 |
| 當事審核員進了編輯態又按「取消，維持原決策」 | 退回唯讀摘要，原本的決策與理由都沒變 |
| 另一位審核員存了草稿還沒送出 | 仲裁者在仲裁版面上**看不到那件事存在**——連「已有動作」都看不到 |
| 專案負責人在例外處置畫面找自動儲存狀態 | 沒有——他在這個畫面沒有草稿儲存路徑 |
| 專案負責人選了「排除於資料集」並確認 | 那一筆排除、不產生最終答案，而且**在這個畫面無法復原** |
| 專案負責人選了處置但沒填理由 | 「確認處置」仍然可用——理由是選填 |
| 專案負責人在兩個處置之間切換 | 已填的理由文字**不會被清掉** |
| 某個爭議項的理由全部沒人填 | 責任鏈的前三問照樣答得出來，第四問顯示「未填寫理由」 |
| 標記員在試標回合揭露前看操作紀錄 | 只看得到自己的事件；審核員與仲裁的動作一筆都看不到 |
| 標記員想看另一位標記員在同一筆上的事件 | 看不到，**連事件列都不出現** |
| 某事件是舊資料、沒有耗時欄位 | 那一塊不渲染，**不會顯示推估值** |
| 審核員一次送出三個輸出類型的決策 | 寫入三筆決策事件，但**只有第一筆帶起算時間與耗時** |

## 待釐清

階段一開了 5 題（Q1 到 Q4 與 Q8），階段二再開 2 題（Q9、Q10），階段五再開 1 題（Q12）。**Q11 在階段四開過、同一階段內撤回**（它的前提查錯了，詳見[§變更紀錄](#變更紀錄)），那個號碼**不再重用**；之後的階段從 Q13 接下去；一題在待釐清與已確認決議之間搬動時**保留原本的題號**。

### Q1. 來源要求的「固定任務目標列」，任務目標與操作指引要放哪？

- **來源怎麼寫的**：桌機介面必須提供三欄工作區與**固定任務目標列**，該列的必要元素是任務目標、操作指引、已標記數量、總量、當前階段、微型進度視覺
- **畫面上實際有什麼**：最上面只有一條麵包屑；已標記數量、總量與進度條在**中欄上方的導覽列**，當前階段在**麵包屑第 2 層**。**任務目標與操作指引沒有任何落點**——右欄「任務說明」的摘要位置放的是**任務名稱**，而且來源的行為規則還明文禁止中欄渲染任務標題卡
- **我的建議**：把「任務目標」與「操作指引」收進右欄「說明與檔案」的任務說明區，不要在頂部另立一列。工作區的垂直空間是標記效率的主要瓶頸，而這兩段內容在整個作業期間都不變，常駐在右欄比固定在頂部划算；且麵包屑已經承擔了「我在哪個任務、哪個階段」
- **影響**：[§工作區的外殼](#工作區的外殼三欄與行動版)第 12 條、[§右欄：說明與檔案、操作紀錄](#右欄說明與檔案操作紀錄)第 5 條
- **誰決定**：維護者（這是畫面與來源不一致，依 `spec-migration.md` 列入待釐清）

### Q2. 右欄第二個頁籤叫「歷程」還是「操作紀錄」？

- **來源怎麼寫的**：右欄是「說明與檔案」／**「歷程」**雙頁籤，而且來源通篇用「歷程事件」「歷程可追溯」描述這個概念
- **畫面上實際是什麼**：頁籤的字面是**「操作紀錄」**
- **我的建議**：頁籤字面用畫面的「操作紀錄」（對使用者更直白），但**概念名稱**在規格與術語表裡統一用「歷程」，因為[§責任鏈與它誠實的那一句](#責任鏈與它誠實的那一句)通篇要講「歷程事件」。兩者如果都要統一，建議統一成「操作紀錄」並同步改掉來源的概念名稱
- **影響**：[§右欄：說明與檔案、操作紀錄](#右欄說明與檔案操作紀錄)第 1、2 條；[§操作紀錄裡的每一筆事件](#操作紀錄裡的每一筆事件)；未來可能要加的術語表條目
- **誰決定**：維護者

### Q3. 「已經讀過說明」這件事要記在帳號上還是裝置上？

- **來源怎麼寫的**：確認紀錄必須**以任務為鍵**獨立記錄，但**「確認紀錄的儲存實體（使用者帳號綁定或裝置綁定）留待後端接上時定義」**——來源自己把這一題留著，只鎖定「逐任務可獨立追蹤」這個契約
- **差別在哪**：綁帳號的話，換一台電腦不必重讀；綁裝置的話，同一個人換瀏覽器就要再讀一次，而共用電腦的兩個人會互相抑制彼此的彈窗
- **我的建議**：綁**帳號**。這個閘門的目的是「確定這個人讀過說明」，那是人的屬性不是機器的屬性；共用電腦的情境下綁裝置會讓第二個人直接跳過說明，正好違背設定這個開關的目的
- **影響**：[§指引閘門](#指引閘門第一次進來先讀說明)第 3、6、8 條
- **誰決定**：維護者

### Q4. 說明彈窗到底是每次進入都顯示，還是每個任務確認一次？來源有五處規則、分成兩派、沒有裁決句

- **互相矛盾的五處**（全部都**沒有被劃掉**，前兩列是一派、後三列是另一派）：

| 來源位置 | 說的是 |
| :--- | :--- |
| `FR-066` 第 1 點（v4.16.0） | 任務沒開「先讀說明」時，彈窗**在任何情況下都不得渲染** |
| `FR-066` 第 3 點（v4.16.0） | 確認過之後的後續進入（含重新整理）**不得重複顯示** |
| `FR-021` | 原型頁**每次進入都必須顯示一次**說明彈窗 |
| 規格常數 `GUIDELINE_MODAL_BEHAVIOR` | 值就是「每次進入顯示一次」 |
| 使用者故事 2 的行為規則（未編號散文） | 「原型入場時**固定顯示**說明 modal 一次」 |

- **為什麼不能自己結案**：`FR-066` 第 1 點的「於任何情況下」看起來像裁決句，但它後面緊接的限定詞是「**不受第 2、3 點之確認狀態影響**」——指名的是 `FR-066` 自己的第 2、3 點，處理的是這一條內部的優先順序（閘門開關壓過確認紀錄），**沒有觸及 `FR-021`**。而且 v4.16.0 的變更紀錄自述第 1 到 3 點只是「既有原型行為之正式化…**不改變任何既有版面呈現**」，這句話正好否認它推翻了既有規則
- **我的建議**：照 `FR-066`——它版本最新，而且任務設定那一側（`force_guideline` 開關）已經定義了觸發行為，沒有開關卻強制每個人每次進來都讀一次說明，與那個開關的存在意義衝突
- **影響**：[§指引閘門](#指引閘門第一次進來先讀說明)第 2、3、9 條與[§卡控機制](#卡控機制)裡的四條閘門規則；若改採「每次都顯示」，`FR-066` 的整套確認紀錄（含逐任務、逐指引版本）就沒有消費端
- **誰決定**：維護者

### Q8. 使用者**手動**把右欄收起之後再翻筆，要維持收起還是回到展開？

- **來源怎麼寫的**：只有三處沾到，而且三處講的都是**不得自動收起**，沒有一處定義手動收起之後的狀態保存——`FR-019`「面板必須於翻筆後持續可見，不可自動收起或清空」、`AC-5.1`「右欄說明不收起且內容不重置」、`SC-005`「翻筆後內容維持，Desktop 可收合／展開」
- **為什麼需要決定**：`FR-019` 的「持續可見」和「維持使用者收起的狀態」字面上互相拉扯——照字面讀，手動收起後翻筆應該要自己展開回來，但那會讓收合鈕在翻筆流程裡形同無效
- **我的建議**：**維持使用者收起的狀態**。收合鈕的用途就是把中欄的空間讓出來，如果翻一筆就彈回來，這顆鈕在實際作業中沒有價值；`FR-019` 的本意是禁止系統自己收起，不是禁止使用者收起
- **影響**：[§工作區的外殼](#工作區的外殼三欄與行動版)第 3、7 條、[§邊界情況](#邊界情況edge-case)那一列
- **誰決定**：維護者

### Q9. 中文介面裡有四個區塊標題是英文，要不要改成中文？

- **畫面上實際是什麼**：實體辨識與關係識別的四個區塊標題，在**中文介面**顯示的是英文——`Entity Type`、`Entity List`、`Relation Type`、`Triple List`。這四個字面由共用的設定引擎提供，所以[新增任務](../03-task-management/02-task-new.mdx)的標記預覽、任務詳情的標記設定與這一頁**會一起變**
- **來源怎麼寫的**：來源只給英文識別名（`Entity Type` 按鈕列、已標記實體列表、triple 清單），**沒有指定中文字面**
- **我的建議**：改成中文（例如「實體類型」「已標記實體」「關係類型」「已建立的三元組」）。整個介面其餘部分都是中文，四個英文標題會讓標記員在作業中斷一下；而且這四個詞沒有「必須保留原文」的理由（不像 `IAA` 或 `Bypass` 是被當成術語在用）
- **影響**：[§八種輸出類型的作答控制項](#八種輸出類型的作答控制項)的實體辨識與關係識別兩段、[§畫面上的字面](#畫面上的字面)；改了會同時動到 03-02 與 03-03 兩頁描述的同一組字面
- **誰決定**：維護者（這是畫面文案，不是規則）

### Q10. 摺疊區塊的標題把技術名詞露給使用者，要不要改？

- **畫面上實際是什麼**：輸入是物件陣列、但任務還沒設定對話串欄位時，整合預覽會出現一個摺疊區塊，標題逐字是 `原始 JSON（尚未設定對話串欄位）`
- **為什麼是問題**：那是技術名詞。（這個詞在這一份規格裡只以「引用畫面字面」的形式出現，不是規格自己的用語。）標記員是這個畫面的使用者，而他不需要知道資料的儲存格式叫什麼；這個專案的規格撰寫規則本身也要求用使用者語言
- **我的建議**：改成不帶技術名詞的說法，例如「原始資料（尚未設定對話串欄位）」。這個區塊的用途是「讓人看到這筆資料長什麼樣」，換掉名詞不影響它的功能
- **影響**：[§對話串資料的整合預覽](#對話串資料的整合預覽)第 17 條、[§畫面上的字面](#畫面上的字面)
- **誰決定**：維護者（同 Q9，這是畫面文案）

### Q12. 例外池那顆確認按鈕的字面是「確認處置」還是「確認」？

- **來源怎麼寫的**：來源通篇把它稱作**「確認處置」**控件——包括「它是這個畫面唯一的寫入入口」與「停用條件只取決於有沒有選取處置」兩條規則都用這個名字
- **畫面上實際是什麼**：按鈕的字面是**「確認」**
- **為什麼要問**：這顆按鈕是**整個例外處置畫面唯一會寫入資料的入口**，而它旁邊同時有四個處置動作可以切換。只寫「確認」在上下文裡還讀得懂，但它是**不可在本畫面復原**的動作（尤其「排除於資料集」），字面愈具體愈好
- **我的建議**：字面改成「確認處置」，與來源一致，也讓這顆按鈕在四個動作旁邊更明確
- **影響**：[§例外處置畫面的外殼](#例外處置畫面的外殼)第 3 條那張表的最後一列與第 5 條
- **誰決定**：維護者（這是畫面文案）

### Q5. 左欄標題可不可以帶回合標籤？（已定案，沿用舊來源）

- **結論**：**不行**。標題固定「標記清單」，回合由[麵包屑第 2 層](#入口麵包屑的第三層)承載；但**筆數仍然要按當前回合的清單規模顯示**
- **依據**：來源使用者故事 1 的行為規則明文禁止在左欄標題附加回合標籤，並同時要求筆數照回合顯示；`FR-080` 第 5 點又特別聲明麵包屑不改變這條約束，兩者位置不同、不衝突
- **為什麼**：同一個畫面上把「這是哪個回合」講兩次，是資訊重複；而回合放在三欄主體之上，讀者第一眼就看得到
- **影響**：[§左欄：標記清單](#左欄標記清單)第 1 到 4 條

### Q6. 手機版有沒有「操作紀錄」？（已定案，沿用舊來源）

- **結論**：**沒有**。手機的底部抽屜只承載「說明與檔案」，操作紀錄是桌機右欄才有的
- **依據**：來源的規格常數明寫「Mobile 底部抽屜僅承載『說明與檔案』，不含歷程頁籤」，使用者故事 2 的介面定義也寫「`歷程` 頁籤為 Desktop 右欄功能」
- **為什麼**：手機要主操作優先，抽屜不得遮蔽核心標記區；操作紀錄是回顧用的資訊，不是作答必需
- **影響**：[§工作區的外殼](#工作區的外殼三欄與行動版)第 6 條

### Q7. 標記員看不看得到那一筆的識別碼？（已定案，沿用舊來源，來源標為不可協商）

- **結論**：**看不到**。麵包屑第 3 層對標記員**只顯示佇列位置**，不顯示那一筆的識別碼，也不顯示標記員自己的帳號
- **依據**：來源 `FR-080` 第 3 點標為 **NON-NEGOTIABLE**，理由是有些資料集用**沒有被指派用途的欄位**當記錄識別鍵，把它渲染進標記員看得到的地方就會違反來源的兩條資料公平性條文（標記員可見之處不得出現答案；用途是輸出的欄位不得被當成可讀內容）
- **為什麼**：識別碼本身可能就是答案線索；而標記員自己的帳號對標記員是零資訊
- **影響**：[§入口麵包屑的第三層](#入口麵包屑的第三層)第 2、3 條、[§卡控機制](#卡控機制)

## Q&A

### Q. 為什麼左欄標題不准帶回合標籤，這不是多此一舉嗎？

因為工作區是一個會停留很久的畫面，而「我在哪個回合」這件事只需要一個地方講。來源把它放在三欄主體**之上**的麵包屑，而不是左欄標題裡，理由是視線進入畫面時第一個落點在上方；標題如果也講一次，讀者就得確認兩處是不是同一件事。真正不能省的是**筆數**——它會因回合而不同，所以標題固定、筆數照回合變。

### Q. 為什麼標記員的麵包屑連那一筆的識別碼都不給看？

因為識別碼不一定只是流水號。來源點出有些資料集拿**沒有被指派用途的欄位**當記錄的識別鍵，那個欄位可能本身就帶著答案線索；一旦渲染進標記員看得到的地方，測試集保護就破了。這條在來源被標成不可協商，而且它換來的成本很低——標記員需要知道的是「我做到第幾筆、還剩幾筆」，那個識別碼對他本來就是零資訊。

### Q. 為什麼翻筆要把網址改寫成「原地取代」，不是正常地新增一筆瀏覽紀錄？

因為工作區的「下一筆」是作業動作，不是導覽動作。一個 5 筆樣本 × 3 位標記員的任務有 15 個審核單位，若每翻一筆都堆一筆瀏覽紀錄，審核員看完全部之後要按 15 次上一頁才離得開這一頁。原地取代同時保住了另一件事：重新整理、加書籤、把連結貼給別人，拿到的都是**畫面上的那一筆**，而不是最初進來的那一筆。

### Q. 為什麼說明彈窗的內容一定要和右欄同一份？

因為這個閘門的目的是「確定這個人讀過這一版說明」。如果彈窗另有一份文字，使用者確認的就不是他後續會對照的那一份，閘門只剩下儀式。同一個理由延伸到版本：彈窗與右欄必須是同一個指引版本，而換了版本就要重新確認——否則「已讀」這個紀錄會指向一份已經不適用的說明。
