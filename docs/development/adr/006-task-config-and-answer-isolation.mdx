# ADR-006 任務設定與答案隔離

這份 ADR 管任務類型怎麼定義、設定長什麼樣、序列標記存成什麼，以及測試集答案怎麼對標記員隔離。授權與認證不在這裡，見 [ADR-004](004-auth-and-security.mdx)；資料庫與背景工作的選型見 [ADR-003](003-backend-architecture.mdx)。
規則本體在 `AGENTS.md` 的硬性規則 5、6 與 [security-agent-rules.mdx](../security-agent-rules.mdx)，落地的做法在 [architecture.mdx 的 §任務設定](../architecture.mdx#任務設定input_type-加-outputs)與 [§測試集答案不外露](../architecture.mdx#測試集答案不外露)，本文只寫為什麼；衝突時的優先序見 [ADR 索引](index.mdx#衝突時以誰為準)。

## D1 任務類型由設定決定，核心不寫任務專屬邏輯

### 背景

要決定任務的行為（標籤、指標、介面）寫在程式裡，還是由設定定義。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：平台要支援分類、迴歸、span 標記等多種任務類型，而不必為每一種新任務寫程式 | 新增任務類型不能需要改核心程式 |
| 來源記錄：寫死任務邏輯，其他研究團隊不改程式就不能重用 | 設定要能由使用者提供 |
| 來源記錄：平台主張最少的設定步驟 | 寫死的做法與這個主張矛盾 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 寫死任務類型：每種任務各一條程式路徑（例如 `if task_type == "ner"`） | 來源沒有記錄好處 | 每新增一種任務就要改程式並重新部署；不改程式其他團隊不能重用；與最少設定的主張矛盾 | 不採用 |
| B 設定驅動：行為完全由設定檔定義，平台在建立任務時讀取並調整 | 新任務不必改程式 | 見後果的變困難 | 採用 |
| C 外掛系統：任務類型寫成執行時載入的 Python 外掛 | 彈性最大 | 需要穩定的外掛 API、版本與文件，對研究原型階段過重 | 不採用 |

### 決定

任務類型完全由設定決定，平台核心不得出現任務專屬邏輯；設定在建立任務時用 schema 驗證，不合法的設定在存檔前就被拒絕，評分指標登記在指標 registry，新指標加進 registry、不寫進評分邏輯。既有 output type 的新組合只改設定，全新的 output 能力仍要寫設定片段的 schema、registry 的 renderer、驗證與指標登記。規則本體見 `AGENTS.md` 硬性規則 5 與 [security-agent-rules.mdx 的 S7](../security-agent-rules.mdx#s7-設定驅動的界線)、[S8](../security-agent-rules.mdx#s8-設定的驗證與-span-的表示)。

### 後果

**變容易**

- 研究團隊寫一份設定檔就能部署新的標記任務，不必寫程式
- 設定在建立時驗證，標記員遇到之前就能擋下設定錯誤
- 指標登記在 registry，同一個指標可以被不同任務重用

**變困難**

- 設定 schema 要在一開始就夠寬，涵蓋計畫中的任務類型；部署後改 schema，要遷移已存的設定（JSONB）
- 追查「這個任務為什麼表現不同」要去讀設定，不是讀程式
- registry 要隨新指標維護，沒有登記的指標不能在設定裡引用
- 設定的彈性可能掩蓋效能問題（例如在大資料集上要求十個指標），平台要驗證資源限制

### 什麼情況要重新討論

- 反覆出現無法用既有 output type 組合表達的任務，每次都要改核心程式

## D2 任務設定用 input_type 加 outputs 組合

### 背景

要決定設定怎麼表示任務類型；固定的 task type enum 沒辦法表達「同一份資料要做好幾件事」的任務。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：三份研究資料集需要的輸出不同：NLI 要單選標籤、MRC 要自由文字、ABSA 要實體辨識加關係辨識 | 一個任務要能同時有多個輸出 |
| 來源記錄：ABSA 的實體辨識與關係辨識要一起運作，關係辨識吃實體辨識的結果 | 輸出之間要能宣告依賴 |
| 來源記錄：固定 enum 下，組合型任務只能新增 enum 值，或在同一資料集上拆成兩個任務 | 新增 enum 值違反 [D1](#d1-任務類型由設定決定核心不寫任務專屬邏輯)；拆成兩個任務會打斷標記員的流程 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 沿用 enum，為每種組合加一個值 | 來源沒有記錄好處 | 組合爆炸：八種 output type 兩兩組合要 36 個 enum 值，每個要自己的 schema；這是 `if task_type ==` 在 schema 層的翻版 | 不採用 |
| B 組合模型：設定是 `input_type` 加 `outputs[]`，每個 output type 貢獻一段設定片段 | 組合不必新增程式或 enum 值；新增 output type 只需要片段 schema、標記元件與指標登記；符合研究社群「依標記員產出什麼」分類的方式 | 見後果的變困難 | 採用 |
| C 外掛系統：每個 output type 是一個可載入的外掛，自帶渲染、驗證與評分 | 彈性最大 | 對論文階段過重 | 延後：來源記錄組合模型之後可以演進成外掛系統而不破壞 schema，沒有記錄觸發條件 |

### 決定

設定由 `input_type`（`single_item` 或 `item_pair`）加 `outputs[]` 組成，取代固定的 `task.type` enum；每個 output type 自帶設定片段、標記 UI 與評分指標，output 之間的依賴用 `source_output` 宣告且不得循環。驗證分兩段：片段各自驗，再驗跨 output 的規則；多 output 的任務產生分數向量，IAA 逐 output type 獨立計算。output type 目錄、組合規則與 v1 限制見 [architecture.mdx 的 §任務設定](../architecture.mdx#任務設定input_type-加-outputs)。

### 後果

**變容易**

- 任何組合型任務不必新增程式或 enum 值就能設定
- 目錄可以自然擴充：新增 output type 只需要新的片段 schema、標記元件與指標登記

**變困難**

- 多 output 的標記介面更複雜，每個 output type 都要有可組合的元件
- 設定驗證有兩層（片段加組合），邏輯變多
- 評分要處理分數向量，不是單一分數
- 標記員的認知負擔隨 output 數量增加，可能需要介面上的防護
- 範本不能為每種組合預先做好
- v1 限制：同一種 output type 每個任務最多一次，要靠設定內部的區分（例如 `entity_recognition` 的 `entities[]` 對 `polarity_options[]`）涵蓋多用途的情形

### 什麼情況要重新討論

- 出現具體的研究需求，要在同一個任務放兩個同類型的 output；來源記錄 v1 限制可在這時重新檢討

## D3 序列標記用半開字元 offset span

### 背景

要決定 `sequence_tagging` 的標記存成什麼：對齊 token 的標籤，還是字元 offset 的區間。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：標記存成與 token 序列索引對齊的陣列，所以 tokenizer 決定標記資料的座標系，分詞方式一改，所有已存的標籤全部位移 | 回頭的成本隨標記數量增加 |
| 來源記錄：瀏覽器的 `Intl.Segmenter` 分詞結果因瀏覽器與 ICU 版本而不同 | 兩位標記員可能對同一句得到不同的 token 邊界 |
| 來源記錄：單位（字元或詞）與標記方案（BIO 等）原本是兩個獨立可組合的設定維度 | 不能把組合寫死成單一 enum，見 [D1](#d1-任務類型由設定決定核心不寫任務專屬邏輯) |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A token 對齊的標籤，前端 `Intl.Segmenter` 當正式 tokenizer | 來源沒有記錄好處 | 結果不確定，違反決定性的要求 | 不採用 |
| B token 對齊的標籤，後端在每個任務建立時算一次 token 並凍結引擎與詞典版本 | 資料集可重現；引擎升級不會悄悄破壞既有標記 | 後端要先提供分詞能力；舊任務保留舊的分詞行為；詞模式卡在引擎選型 | 不採用：被選項 C 取代 |
| C 半開區間的字元 offset span `{ start, end, label }` | 沒有儲存的座標系需要凍結 | 來源原本拒絕它，理由是它改變任務語意（`sequence_tagging` 以 token 級標記與 token 級指標定義）；該理由被 span 級指標取代 | 採用 |

### 決定

`sequence_tagging` 的標記存成半開區間的字元 offset span `{ start, end, label }`，不存對齊 token 的標籤；設定是 `entities[]` 與 `snap_unit`，不再有 `tagging_scheme` 與 `tokenization`，評分用 span 級指標、不用 `token_f1` 與 `token_accuracy`。`snap_unit` 只影響拖曳落點，不改變既有 span 的意義。改採 span 的原因，來源只記錄它的結果，採用的理由沒有記錄。落地細節見 [architecture.mdx 的 §任務設定](../architecture.mdx#任務設定input_type-加-outputs)，規則本體見 [security-agent-rules.mdx 的 S8](../security-agent-rules.mdx#s8-設定的驗證與-span-的表示)。

### 後果

**變容易**

- 沒有 tokenizer 版本要凍結：換 `snap_unit` 只改變拖曳落在哪裡，不改變既有 span 的意義

**變困難**

- 標記文本不得被改寫：offset 是標記的基礎，例如把 `<` 換成 `&lt;` 存回資料庫會讓 offset 位移（XSS 靠輸出轉義處理，見 [security-agent-rules.mdx 的 S9](../security-agent-rules.mdx#s9-稽核脫敏與保留)）
- 指標從 token 級改成 span 級：來源記錄 `token_f1` 與 `token_accuracy` 不再是現行指標

### 什麼情況要重新討論

- 出現需要 token 級指標的研究需求
- 標記文本在標記之後仍然需要被改寫

## D4 答案隔離涵蓋標記員能到達的每個出口

### 背景

要決定測試集答案放哪裡、誰能讀、哪些出口要守；答案一旦外露，測試集就失去意義，所以這是硬性規則 6。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 來源記錄：答案存放與讀取的決定都以資料公平原則為依據，沒有展開 | 答案要和一般標記資料分開 |
| 標準答案的讀取不屬於任何使用者角色，儲存之後只有經授權的計分程序讀得到（見 [規格 05-03](../../specs/05-dataset/03-ingestion-lineage.mdx)） | 讀答案的只能是計分程序 |
| 來源記錄：帶答案的歷史 JSON 要跟著它所屬的資料集版本或 run 存續 | 不能對它做 PII 匿名化或單獨刪除 |

### 考慮過的選項

下面三個被否決的選項是從 [security-agent-rules.mdx 的 S6](../security-agent-rules.mdx#s6-受控答案表與-worker-的讀取邊界)的禁止欄推論出來的，來源沒有把它們寫成選項。

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 答案與一般標記資料放同一張表（推論） | 來源沒有記錄好處 | 來源只記錄它被列為禁止，理由沒有記錄 | 不採用 |
| B 在 API 行程裡讀答案（推論） | 來源沒有記錄好處 | 答案會經過 API 層；來源要求答案只在 worker 裡讀、不經過 API 層 | 不採用 |
| C 瀏覽器下載答案再算分（推論） | 來源沒有記錄好處 | 答案一旦進 bundle 就等於公開 | 不採用 |
| D 四道隔離：獨立答案表、worker 內讀取、授權第四步、保留政策；覆蓋面是標記員能到達的每個出口 | 計分與 IAA 在後端算完才回結果，答案不離開 worker | 見後果的變困難 | 採用 |

### 決定

標記員能到達的每個出口都不得出現標準答案或測試集辨識資訊，覆蓋面包括 API 回應、列表與詳情、下載與匯出、輪詢結果、快取、瀏覽器 bundle 與 source map、公開 fixture 與 mock handler、錯誤訊息與 log。架構分四道：答案存在獨立、受存取控制的資料表（[ADR-003 的 D7](003-backend-architecture.mdx#d7-資料庫分兩層)）；`load_answers()` 只在 worker 行程內讀答案（[ADR-003 的 D8](003-backend-architecture.mdx#d8-非同步任務用-celery-加-redis)）；答案隔離是授權第四步的附加條件，權限矩陣 cell 為 true 也不能蓋過（[ADR-004 的 D6](004-auth-and-security.mdx#d6-權限矩陣當授權輸入)）；帶答案的歷史 JSON 跟著所屬的資料集版本或 run 存續（[backend-agent-rules.mdx 的 B8](../backend-agent-rules.mdx#b8-刪除軟刪除與匿名化)）。規則本體見 `AGENTS.md` 硬性規則 6 與 [security-agent-rules.mdx 的 S5](../security-agent-rules.mdx#s5-答案隔離的覆蓋面)、[S6](../security-agent-rules.mdx#s6-受控答案表與-worker-的讀取邊界)，四道的表見 [architecture.mdx 的 §測試集答案不外露](../architecture.mdx#測試集答案不外露)。

### 後果

**變容易**

- 每個出口都能以標記員身分逐一斷言 payload 裡沒有答案
- 計分與 IAA 在後端算完才回結果，前端與 API 層不需要碰答案

**變困難**

- 覆蓋面包括 bundle、source map、fixture、mock handler、錯誤訊息與 log，所以 mock 不能複製含答案的真實回應，錯誤訊息不能回「期望值是 X」
- 帶答案的歷史不能匿名化或單獨刪除，只能隨所屬版本或 run 一起處理
- 目前這些檢查都待建置，覆蓋面只靠審查與驗收清單守住

### 什麼情況要重新討論

- 出現標記員以外、需要看到答案的使用者角色
- 自動檢查建好之後，審查或驗收仍反覆發現遺漏的出口
