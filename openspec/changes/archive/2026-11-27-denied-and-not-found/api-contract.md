## 前端依賴的既有錯誤契約

### 錯誤外層

`403` 和 `404` 都使用同一個錯誤外層（`api-envelope`「錯誤回應使用同一個錯誤外層」），頂層恰好七個欄位：

| 欄位        | 型別                    | nullable | 在 `403 PERMISSION_DENIED`／`404 NOT_FOUND` 時的值                             |
| :---------- | :---------------------- | :------- | :----------------------------------------------------------------------------- |
| `success`   | boolean                 | 否       | `false`                                                                        |
| `code`      | string                  | 否       | `"PERMISSION_DENIED"` 或 `"NOT_FOUND"`；符合 `^[A-Z][A-Z0-9_]*$`，不帶模組前綴 |
| `message`   | string                  | 否       | 依 `Accept-Language` 在地化的一句固定通用訊息（見下表）；沒有參數              |
| `data`      | null                    | 是       | `null`                                                                         |
| `timestamp` | string（ISO 8601 UTC）  | 否       | 回應時間                                                                       |
| `traceId`   | string                  | 否       | 與 `X-Correlation-ID` 回應標頭相同                                             |
| `errors`    | `ErrorDetail[]` 或 null | 是       | `null`（只有 `422` 才會有值）                                                  |

範例（`zh-TW`）：

```json
{
  "success": false,
  "code": "NOT_FOUND",
  "message": "找不到指定的資源",
  "data": null,
  "timestamp": "2026-11-27T08:00:00.000Z",
  "traceId": "3f2b9c1e-0000-4000-8000-000000000000",
  "errors": null
}
```

### 兩種拒絕與觸發條件

| HTTP  | `code`              | 訊息鍵                     | `zh-TW`／`en` 訊息                                                                 | 觸發條件（授權步驟）                                                                                                                                                                                                                                                | 前端對到的畫面 |
| :---- | :------------------ | :------------------------- | :--------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | :------------- |
| `404` | `NOT_FOUND`         | `common.not_found`         | 「找不到指定的資源」／"The requested resource was not found."                      | 第 2b 步：任務不存在、不是成員、成員身分已停用或仍在邀請中、作用角色不是他的生效角色；路徑上的任務識別碼不是 UUID（回 `404`，**不是** `422`）；第 4 步：附加條件碰到看不到的資源，以及讀標準答案（`GroundTruthBarrier` 對任何人都回它）；`/api/v1` 底下不存在的路徑 | 找不到         |
| `403` | `PERMISSION_DENIED` | `common.permission_denied` | 「你沒有執行這個操作的權限」／"You do not have permission to perform this action." | 第 3 步：權限鍵不在白名單或尚未啟用、鍵的層級和操作不符、矩陣版本列不存在、生效角色的格缺列或全為關。任務層的鍵只有在第 2b 步確認他是生效成員之後，才會走到這一步                                                                                                   | 無權限         |

- 所有「看不到」的情況都回 `404`，**而且和「不存在」逐字相同**（`traceId`、`timestamp` 除外），不會用 `403` 透露那一筆存在。這跟規格 07-03 §兩種畫面的分工 第 3 條、Q2（本來就不該知道它存在 → 找不到）同一個方向
- 第 2b 步不通過就停下，不再查矩陣。所以「不存在」和「沒有權限」同時成立時，一定得到 `404`（07-03 §邊界情況「兩種條件同時成立」）

### 為什麼要看 `code`，不能只看 status

`403` 不是只有 `PERMISSION_DENIED` 一種：

| HTTP  | `code`              | 來源                                               | 什麼時候出現                                                                     | 是不是無權限                                                                                              |
| :---- | :------------------ | :------------------------------------------------- | :------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------- |
| `403` | `PERMISSION_DENIED` | `app/core/authz.py`（`PermissionDeniedError`）     | 授權第 3 步                                                                      | 是                                                                                                        |
| `403` | `CSRF_FAILED`       | `app/core/csrf.py`（`CsrfMiddleware`，在路由之前） | 帶 access cookie、不在放行清單的 `POST`／`PUT`／`PATCH`／`DELETE`，CSRF 值驗不過 | 否，是請求本身有問題                                                                                      |
| `401` | `AUTH_REQUIRED`     | `app/core/auth.py`                                 | 沒登入、登入過期或失效                                                           | 否，由 `apiFetch` 既有的延續與重送流程處理（`frontend-api-client`「`AUTH_REQUIRED` 時延續並重送原請求」） |

所以前端判斷時必須同時看 `ApiError.kind === "http"`、`status` 和 `code`；只看 `status === 403` 會把 CSRF 失敗也畫成無權限。`ui-design.md` §拒絕回應怎麼對到畫面 的 B 案就是這樣判斷，跟本份一致。其他情況，包括 `500`、`503`、`network`、`timeout`、`aborted`、`invalidResponse`，都不算這兩種畫面，屬於載入失敗（07-03 §不在本頁範圍 第 3 條）。

另外，同一個 `403 PERMISSION_DENIED` 在不同頁面、不同角色下，畫面上的處理可能不一樣。例如規格 03-03 §誰進得來 第 1 條：標記員開任務詳情時，是「帶回任務列表並顯示提示」，不是整頁顯示無權限。所以「這個 code 要不要畫成整頁」不在 API 契約裡決定；依 clarification Q4，由擁有那一頁的模組決定。

### 不回顯識別碼

- `403` 和授權產生的 `404` **都不帶**識別碼、權限鍵、角色、任務識別碼、矩陣版本，也不說擋在哪一步，也不設定或清除任何 cookie（`permission-authorization`「授權拒絕的回應不外露內部資訊」）
- 路徑參數不是 UUID 時回 `404`，`message` 是固定的通用句，不回顯送出的值
- 所以畫面上要顯示的「那一筆的識別碼」，**只能由前端從自己的路由參數取**，再當成純文字畫出（07-03 §資料欄位；AGENTS.md Hard Rule 9）。後端沒有、也不會新增帶回識別碼的欄位
- 畫面的標題、說明和返回操作的字面由前端的語言檔決定，不使用外層的 `message`（07-03 §畫面的組成 第一則註；`ui-design.md` §文案鍵）

### 在請求到達後端之前就被 nginx 擋下：`414`／`400`

正式建置時，`/api/v1/` 先經過 `frontend/nginx.conf` 的 `location /api/v1/` 再轉給後端。請求行或標頭超過 nginx 的緩衝上限時（例如網址上的識別碼非常長），nginx 會自己回 `414 Request-URI Too Large` 或 `400`，**body 不是錯誤外層**，也不保證有 `X-Correlation-ID`：

- 前端的 `apiFetch` 會把它轉成 `ApiError`，`kind` 是 `"invalidResponse"`、`status` 是 `414` 或 `400`、`code` 是 `null`（`frontend-api-client`「非外層回應轉成 invalidResponse 錯誤」）
- 依上一節，它**不會**被判成這兩種畫面，只會落到載入失敗
- 依 clarification Q6，送出請求前的格式檢查由擁有那一筆的模組做（任務編號：#763），本單不做

### 測試集答案隔離

| 回應                    | 風險                                                                                                                                                                                        |
| :---------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `404 NOT_FOUND`         | 無：讀標準答案的操作對任何人都回 `404`，和不存在相同；`data` 是 `null`，序列化後不含答案值、`answer`、`groundTruth`、`isTestItem`（`permission-authorization`「標準答案不經任何角色放行」） |
| `403 PERMISSION_DENIED` | 無：`data` 是 `null`，訊息是固定句；格為關的標記員讀標準答案得到的 `403` 同樣不含答案                                                                                                       |
| 兩種畫面                | 無：畫面不讀業務資料，只顯示網址上的識別碼本身                                                                                                                                              |

### 角色

這兩種回應不分角色，平台成員、系統管理員、Seeder 管理員拿到的外層形狀都一樣。系統管理員和 Seeder 管理員沒有隱含任何任務角色，對沒有成員身分的任務同樣得到 `404`。未登入的人得到的是 `401 AUTH_REQUIRED`，前端守門會把他帶回登入頁，他看不到這兩種畫面。權限沒有超出 PRD §權限矩陣：兩種畫面只用到「07 共用介面」的 `R`。
