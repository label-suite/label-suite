## 待釐清項目（Q）

以下全部依維護者 2026-11-25「接下來有需要決策的都依照你的建議就好」的授權，採用主 session 的建議決定（日期 2026-11-26）；選項、命中與實測取自 system-analysis §待決問題與 system-design（以 system-design 的實測更正為準）。維護者看到後可推翻任一題，推翻時依 Q 編號回修。

| #   | 題目                          | 決議                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | 理由                                                                                                                                                                |
| :-- | :---------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Q1  | 信任放在哪裡                  | **A：uvicorn 內建處理**，以原生環境變數 `FORWARDED_ALLOW_IPS` 設定；`backend/Dockerfile` 的 `CMD` 不加任何代理旗標                                                                                                                                                                                                                                                                                                                                                         | 預設已開 `--proxy-headers`；旗標會覆蓋環境變數，寫進 `CMD` 會讓編排檔給的值被靜默蓋掉（實測 D2）；不寫應用程式碼                                                    |
| Q2  | 受信任位址怎麼表達            | **A1：只信任 Nginx 的單一固定位址**。兩份編排檔各宣告預設網路的 `ipam`（`subnet` 加只供動態配位的 `ip_range`），固定 `frontend` 服務的 `ipv4_address`；後端 `FORWARDED_ALLOW_IPS` 預設為該位址。兩層同一組常數                                                                                                                                                                                                                                                             | 實測：信任整段子網路讓同網路其他容器可偽造（E2）；預設私有區段有可重現的偽造漏洞（D12）；uvicorn 不解析容器名稱（C 不可行）                                         |
| Q3  | 測試放哪一層                  | **真實 uvicorn 子行程的 integration 測試**（比照 `test_access_log.py` 起子行程），三輪：不受信任來源帶偽造標頭被忽略、受信任來源取到轉發位址、多段鏈取右到左第一個不受信任位址。編排層做 **P1 加 P2**：P1 在 CI `compose` job 對 `docker compose config` 的 JSON 做靜態斷言（兩層的值不是 `*`、涵蓋 `frontend` 的固定位址，`nginx.conf` 仍附加 `X-Forwarded-For`）；P2 用只給 CI 的 override 檔在 Lite 層實際送一般與偽造請求，斷言回報的位址不是 Nginx 位址、也不是偽造值 | 既有 `client` fixture 走 httpx 直連 ASGI，不經 uvicorn 的代理處理；issue 第 1 條「經 Nginx 拿到原始位址」只有 P2 能在執行期證明；原始位址依平台不同，只能做否定斷言 |
| Q4  | 讀取來源 IP 要不要單一入口    | **不新增**，`backend-code-boundaries` 不動                                                                                                                                                                                                                                                                                                                                                                                                                                 | 目前零個消費者；第一個讀 IP 的 change 再依 B12 決定                                                                                                                 |
| Q5  | `X-Forwarded-Proto`           | **不另外處理**：同一份信任清單同時管 XFF 與 XFP，「只信 XFF」做不到；後端看到的 scheme 是 Nginx 的 `$scheme`，在這個部署恆為 `http`，與今天相同，沒有退步。TLS 邊緣後面 scheme 的正確性寫進 `architecture.mdx` §部署與維運 的已知限制，歸到 ADR-008 尚未決定的 Cloudflare TLS 模式，**不另開 issue**                                                                                                                                                                       | 依維護者「短期非必要不開新 issue」的方針；這件事的前提（TLS 模式）本來就在 ADR-008 待決                                                                             |

## 明確問題（P）

### P1. system-analysis 與實測不符的三處

- **位置**：system-analysis §待決問題 的 Q1（預設清單）、Q5 選項 A、Q7（Nginx 需改成覆寫）
- **修正**：派 `sa` 依 system-design 更正：預設清單是 `127.0.0.1,::1`；同一份清單同時管 XFF 與 XFP，Q5-A 做不到；附加寫法搭配 uvicorn 右到左規則已能擋偽造鏈，不需覆寫。十二題的「狀態」改成決議並指回 clarification

### P2. proposal 的待決表、Capabilities 與 Impact

- **位置**：proposal §What Changes、§待決問題、§Capabilities、§Impact、§不在範圍
- **修正**：派 `planner` 依上表改寫：候選改成定案；待決表改成決議摘要；Capabilities 定為新增 `trusted-proxy-client-ip`（經 Nginx 取得原始位址、直連的偽造標頭不被採信、多段鏈的取值）、MODIFIED `runtime-config`（啟動檢查）、MODIFIED `container-runtime`（固定網段與 Nginx 位址、列出 `FORWARDED_ALLOW_IPS`）；Impact 寫明會動的檔案與 `Dockerfile` 不動

### P3. system-design 的選項比較改成定案

- **位置**：system-design §選項與建議、§技術待決問題、§常駐文件異動、三張 Sequence Diagram 的名稱
- **修正**：派 `sd` 標明採用的選項（Q1 A、Q2 A1、Q3 子行程測試加 P1、P2、Q7 A、Q12 做、T1、T2），其餘保留為「考慮過的選項」；Sequence Diagram 名稱留給 `planner` 對齊 specs
