# 產品路線圖

這份文件說明 Label Suite 的工作**依什麼順序做、為什麼**：每個 Epic 用一句話說它要交付什麼、服務 PRD 的哪個目標、排在哪個時段。它是策略地圖，不是排程承諾，不寫日期與工時；需求內容以 [PRD](../specs/00-prd.mdx) 與 `docs/specs/` 的規格為準，兩者說法不同時以規格為準。每個 Epic 底下有哪些使用者 story，見 [使用者故事地圖](story-map.mdx)。

## 怎麼讀

路線圖只列產品工作：有規格頁的模組，加上它們依賴的基礎建設收尾；論文驗證與發版不在這裡。兩個時段都拆到 Feature 與 Sub-feature，Feature 是規格頁（基礎建設收尾沒有規格頁，取自它的 issue）；時段只決定這份拆法離動工多近。

| 時段 | 用途 |
| :--- | :--- |
| 下個月 | 直接開 issue 動工 |
| 接下來兩個月 | 確認先後與依賴，動工前再對一次規格 |

## 目標

路線圖的目標就是 PRD 的六個目標，不另訂；完整說法與衡量方式見 [PRD 目標](../specs/00-prd.mdx#目標)，這裡只用代號 G1～G6 指稱。G6 靠論文驗證與發版達成，所以目前沒有 Epic 掛在它底下。

## 排序依據

順序只看依賴：一個 Epic 要等它依賴的模組能用才開始，不打分數。依賴關係以 [PRD 的跨模組流程與模組依賴](../specs/00-prd.mdx) 為準。

1. **基礎建設先收尾**：前後端、契約與 CI 共用同一套檢查，之後每個模組才不必各自補。
2. **帳號與共用外殼交錯做**：登入（01-01）先做，接著是側欄（07-01）、無權限與找不到（07-03）和儀表板外殼（02-01 的第一段），再回頭做註冊、設定密碼、工作頁籤、登入狀態與安全、個人設定；因為 01-01 登入後要導向儀表板，07-01 側欄的第一個選單是儀表板，被擋下時也回儀表板。
3. **系統管理排在任務管理前**：任務管理的權限要在系統管理收窄過的角色上檢查。
4. **任務管理 → 標記作業 → 資料集**：照跨模組流程的交接順序；資料集不往後排，因為試標要靠 IAA 才能推進到正式標記。
5. **儀表板跟著資料分段做**：02-01 拆成四段，外殼隨 E2、任務區塊隨 E4、標記與審核區塊隨 E5、「等待 IAA 確認」卡片與最近提醒隨 E7 收尾。
6. **資料集內部先匯入**：05-03 資料匯入與版本 → 05-01 分析列表 → 05-02 分析詳情。

效益與複雜度只分高低，用來說明每個 Epic 的投入與回報，不決定順序；所以低效益的前置工作仍然排在前面。

## 更新方式

路線圖跟著實際進度改，不是寫完就定：

| 時機 | 要改什麼 |
| :--- | :--- |
| 一個 Epic 完成 | 從 `roadmap-data.ts` 把下一段的 Epic 往前移，並對照規格確認它的 Feature 還是最新的 |
| 規格或 PRD 改了模組範圍或依賴 | 改對應 Epic 的範圍、一句話與排序依據 |
| 試用回饋指出新的需求 | 先走規格流程，再決定排進哪個時段 |

一句話、時段、象限都只改 `roadmap-data.ts`；元件與本文不另寫一份。
