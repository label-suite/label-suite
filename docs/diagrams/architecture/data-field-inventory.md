# 資料欄位盤點總帳與追溯矩陣

> **它不是資料表設計。** 候選表字典與關聯限制歸 [#235](https://github.com/label-suite/label-suite/issues/235)，ER 外掛呈現歸 [#236](https://github.com/label-suite/label-suite/issues/236)。

## 盤點方法

兩個方向同時走，這是原始總帳 §2 記下的作法，本專案沿用：

1. **由欄位出發**：18 頁規格的「資料欄位」章節逐列擷取，共 **320 列**（33 張表，其中一張是 04-02 的敏感度等級說明表，不是欄位表）。

   :::note{title="這個數字第一次算錯了，記在這裡"}
   第一次擷取得到的是 277 列／29 張表，**少了 43 列**。原因是 [04-02 標記工作區](../../specs/04-annotation/02-annotation-workspace.mdx#資料欄位)的「資料欄位」底下還有四個 `####` 子章節（上下文與身分、標記員的作答、審核與仲裁的決策、歷程事件），而擷取腳本遇到第一個子標題就停了，只抓到那張敏感度等級說明表。
   本專案的判例是「下『來源沒有定義 X』的結論前，先讀來源指向的所有文件」——**同一條在同一頁的子章節上也成立**。章節標題的層級不要當成章節的結束。
   :::
2. **由流程反查**：建立、修改、發布、標記、審核、仲裁、匯出、封存、稽核九條流程逐一走過，找出「畫面上沒有欄位、但流程非存不可」的資料。見§九條流程的反查。

兩個方向以外，另外讀過 PRD、七份模組 `index.mdx`、`glossary.mdx` 與 `open-questions.mdx`；**「資料欄位」以外的已確認決議與卡控也會定出持久化需求**，那些併入對應頁的總帳並在「來源」欄標明不是來自「資料欄位」那一節。

### 分類的六種

| 代碼 | 意思 | 判準 |
| :--- | :--- | :--- |
| **持久** | 獨立持久化 | 跨請求、跨裝置都要留著，而且是這個欄位自己的權威值 |
| **內嵌** | JSON 內嵌 | 要留著，但結構隨任務型別而變、不獨立查詢；塞在擁有者那一筆的 JSON 裡 |
| **推導** | 推導或查詢投影 | 可由別的持久值算出來。**存了就會有兩個真相**，所以不存 |
| **暫時** | 暫時輸入 | 只在這一次送出時存在，送完即棄（密碼確認、未儲存的草稿輸入） |
| **瀏覽器** | 瀏覽器偏好 | 只記在這一台瀏覽器，不跨裝置 |
| **待決** | 待裁決 | 規格沒有定到足以決定上面五種的程度。編號見§待裁決 |

### 其他欄位的寫法

- **讀寫者**：用 PRD §權限矩陣 的角色。`R` 只讀、`W` 可寫、`S` 系統寫（使用者不能直接改）。
- **生命週期**：這筆值從什麼時候開始存在、什麼時候不再變、什麼時候可以清掉。
- **敏感**：**高**＝外洩直接造成傷害（密碼、權杖、標準答案、原始資料項目內容）；**中**＝個資或可識別個人的操作紀錄；**低**＝其餘。
- **擁有**：這個欄位的**權威來源模組**。同一個欄位在多頁顯示時只有一個擁有者，其他頁標「讀自 NN-NN」。
- **原始對應**：原始規劃 40 張候選表裡的對應位置，格式 `表名.欄名`。`—` 表示原始規劃沒有對應，要在 [#235](https://github.com/label-suite/label-suite/issues/235) 新增。

#### [01-05 登入狀態](../../specs/01-account/05-login-state.mdx#資料欄位)

這一頁是帳號層欄位的**權威來源**。規格自己寫明「上表是其他頁共用的規則依據」「表中沒有任何一欄是使用者可以直接編輯的」。

| 欄位 | 型別 | 必填 | 分類 | 讀寫者 | 生命週期 | 敏感 | 擁有 | 原始對應 | 驗證 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |

### 02 儀表板

#### [02-01 儀表板](../../specs/02-dashboard/01-dashboard.mdx#資料欄位)

這一頁有五處直接定出資料設計的限制，列在這裡供 [#235](https://github.com/label-suite/label-suite/issues/235) 接手：

1. **「上線時長」與「工作時長」是兩個不同的數**，而且「只採信可信的紀錄」——所以原始區間要存可信度，不能只存時長。
2. **「成員的任務角色」加入時決定、之後唯讀，而同一個人可以各有一列**——多角色 membership 不是一個人一列。
3. **「回合編號」同一輪裡唯一、退回草稿後從 1 重新算**——唯一性的範圍是「週期」而不是「任務」。
4. **「排除紀錄」終局、不可刪除也不可撤回、一個工作位子最多一筆**——這同時是唯一限制與不可變限制。
5. **「條件快照」經驗證且不可變，而「匯出範圍」另外存不放進快照**——規格刻意把兩者分開，合併會讓快照失去審計意義。

這張表有三處直接否掉一種設計：

1. **「審核單位的狀態」與「爭議項」都明寫不實體化儲存**，而且判定式「恰五句」。存成欄位會與那五句產生第二個真相。
2. **「決策草稿」要存，但必須與提交紀錄分離、且送出成功後清除**——它是獨立一張表的理由，不是提交紀錄上的可為空欄位。
3. **「空值以空字串寫入、不得缺鍵」**：理由選填不等於欄位可省。這是序列化層的限制，不是欄位可空性的限制。
