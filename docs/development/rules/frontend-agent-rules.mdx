# 前端開發規範

本文說明前端的十二條開發規範，由 `AGENTS.md` 的 Agent Rules Index 指過來；`AGENTS.md` 是規則本體，兩邊說法不同時以 `AGENTS.md` 為準，並回報給維護者。
跨領域的規範在 [agent-rules.mdx](agent-rules.mdx)、後端在 [backend-agent-rules.mdx](backend-agent-rules.mdx)、授權與答案隔離在 [security-agent-rules.mdx](security-agent-rules.mdx)、API 契約與單一 HTTP 邊界在 [api-agent-rules.mdx](api-agent-rules.mdx)，這裡不重複。

**`frontend/` 已存在，但在 CI 跑的只有 F1、F2、F3 與 F12 的檢查，以及 F5、F10 的一部分**（job 與指令寫在各條的「檢查方式」）；F4、F6 至 F9 與 F11 仍標「待建置」。標「待建置」就是字面意思：那些檢查還沒有寫，**不得因為這份文件存在就宣稱規則已被強制**。

每條規範的反例與檢查方式收在摺疊區塊，預設收起；適用路徑、禁止、正例與例外在表裡。

## 前提

開工前的技術前提都已選定，下表是現行結果；為什麼這樣選見 [ADR-005](../adr/005-frontend-architecture.mdx)。

| 前提 | 內容 |
| :--- | :--- |
| 版本與框架 | **React 19** 加 Vite 加 TypeScript strict；路由 React Router v6、伺服器狀態 TanStack Query |
| 目錄分層 | **`pages/` 加 `features/`**，見 [F1](#f1-分層與允許的-import) |
| 元件庫 | **shadcn/ui**，元件以原始碼形式放進 `components/ui/`。**不用 Storybook**，改用元件展示頁（[architecture.mdx](../architecture.mdx) §前端） |
| API client 與型別 | **Orval**，產物在 `src/api/generated/`；規則在 [api-agent-rules.mdx](api-agent-rules.mdx) |
| design token 的映射 | **寫一層對照，語意色仍只來自 `design/prototype/assets/tokens.css`；資料色 `--data-*` 另來自 `data-palette.css`，不進對照層**，見 [F6](#f6-視覺基準與-design-token-的映射) |
| 深色模式 | **要做**：側欄一鍵切換、立即生效、跨頁保持（規格 07-01 §外觀切換）；「跟隨系統」**跟著作業系統的設定變**（規格 01-04 §偏好設定 第 4 條、規格 07-01 §已確認決議 Q14） |

## 規範

### F1 分層與允許的 import

下層不得 import 上層，`features/` 之間不互相 import；跨 feature 要共用時，往下搬到 `components/ui/` 或 `lib/`。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` |
| **禁止** | 下層 import 上層；`features/` 之間互相 import；`components/ui/` 認識業務（讀 query hook、知道角色、import `features/`）；多層 `index.ts` barrel；一個無所不包的 `shared/` 桶；`pages/` 直接呼叫 `api/generated/` 以外的資料來源 |
| **正例** | 見下方的分層表與最小模組範例。跨 feature 要共用時，**往下搬到 `components/ui/` 或 `lib/`**，不是互相 import |
| **例外** | `src/api/generated/`（Orval 產物）是**唯一**可以同時被 `pages/` 與 `features/` 直接 import 的「有業務語意」的目錄；它是契約的投影，不是業務邏輯。`app/` 可以 import 全部，因為 router 與 provider 必須組裝所有層 |

| 層 | 位置 | 放什麼 | 可以 import |
| :--- | :--- | :--- | :--- |
| app | `src/app/` | router、provider、全站 layout | 全部 |
| pages | `src/pages/<page>/` | 路由頁：讀路由與 query string、組合 features | features、components、api、lib |
| features | `src/features/<feature>/` | 業務元件與 hooks（呼叫 Orval 產生的 hooks） | components、api、lib |
| components | `src/components/ui/` | shadcn 元件與純 UI 元件，**不知道業務** | lib |
| api | `src/api/` | Orval 的設定與產物（`generated/`）、mutator | lib |
| lib | `src/lib/` | 不含業務的工具（`cn()`、日期格式化入口、型別 guard） | 無（只靠第三方） |
| styles | `src/styles/` | Tailwind 入口與 token 對照層（F6） | 無 |

`features/<feature>/index.ts` 是那個 feature 的**公開邊界**：`pages/` 只從它匯入。feature 內部的檔案互相 import 不受限，但不得被外面直接 import。

:::note{title="F1 的最小模組範例" collapsible}
```text
src/
├─ pages/task-list/
│  ├─ task-list-page.tsx         讀 query string、組合下面兩個 feature 元件
│  └─ index.ts                   只 re-export 這一頁的入口，不是 barrel
├─ features/task-management/
│  ├─ components/task-table.tsx  讀 useListTasks()、處理四種畫面狀態
│  ├─ hooks/use-task-filters.ts  把篩選與分頁讀寫到 query string
│  └─ index.ts                   公開邊界：只匯出 page 用得到的東西
├─ components/ui/data-table.tsx  不知道「任務」是什麼，只收 columns 與 rows
└─ lib/date.ts                   日期格式化的單一入口（F10）
```
:::

:::note{title="F1 的反例與檢查方式" collapsible}
- **反例**：`features/annotation/` import `features/task-management/hooks/useTaskRole`（改成把它搬到 `lib/` 或由 `pages/` 傳進去）；`components/ui/data-table.tsx` 裡 `useListTasks()`；`src/shared/index.ts` 一次 re-export 四十個東西
- **檢查方式**：CI 的 `frontend` job 跑 `pnpm --filter frontend lint`（`eslint . --max-warnings 0`，有任何警告即失敗）。`frontend/eslint.config.js` 以 `eslint-plugin-boundaries` 把上面的分層表寫成 `boundaries/dependencies` 規則（預設禁止、逐層允許，`pages/` 只能經 `features/<feature>/index.ts` 使用 feature），`boundaries/no-unknown-files` 讓不屬於任何一層的檔案也被回報；`no-restricted-imports` 另擋 `axios`、日期套件、測試替身等
- **尚未檢查**：循環 import（沒有設定 `import/no-cycle`）、多層 `index.ts` barrel 與 `shared/` 桶沒有機械檢查，靠審查
:::

### F2 型別安全

TypeScript 不用 `any`，不用 `as` 或 `!` 掩蓋缺值，外部資料先當 `unknown` 再收窄。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/**/*.ts`、`frontend/**/*.tsx` |
| **禁止** | `any`（含隱含 `any`：沒標註的參數、`catch (e)` 當 `any` 用）；用 `as` 或 `!` 掩蓋可能的缺值；手寫 API 型別（見 [api-agent-rules.mdx](api-agent-rules.mdx) A6）；關掉 `strict` 底下任何一項 |
| **正例** | `tsconfig` 開 `strict`；外部資料先當 `unknown`，再用 runtime schema 或 type guard 收窄；`catch (error: unknown)` 後用 helper 轉成已知型別；要擴充 API 型別時從產物衍生（`Pick<TaskDto, 'id' \| 'name'>`） |
| **例外** | （1）`as const`；（2）`src/api/generated/`：產物由工具產生，不受本條約束也不得手改；（3）第三方套件的型別缺口：允許一處 `as`，但要在**同一行**寫註解指出是哪個套件的哪個缺口；（4）框架要求 `export default` 的檔案（Vite／Vitest／Playwright／Orval 的設定檔），見 F11 |

「外部資料」指的是契約以外的來源。API 回應經 Orval 產物已經有型別，而且契約有 CI 把關（見 [api-agent-rules.mdx](api-agent-rules.mdx) A5），所以不必再寫一層 runtime schema。要先當 `unknown` 的是：query string 與路由參數、`localStorage`／`sessionStorage`、使用者上傳的檔案內容、第三方 SDK 的回呼參數、`postMessage`；這幾種都是 `AGENTS.md` 硬性規則 9 所說的「使用者輸入」。

:::note{title="F2 的反例與檢查方式" collapsible}
- **反例**：`const task = list.find(t => t.id === id)!`（找不到就是 `undefined`，`!` 只是把問題延後到執行期）；`JSON.parse(raw) as TaskDraft`（`raw` 來自 `localStorage`，沒有任何驗證）；`function onChange(e)`（隱含 `any`）
- **檢查方式**：CI 的 `frontend` job 跑 `pnpm --filter frontend typecheck`（`tsc -b`；`tsconfig.json` 開 `strict` 與 `noUncheckedIndexedAccess`）與 `pnpm --filter frontend lint`。lint 套用 `typescript-eslint` 的 `strictTypeChecked`（含 `no-unsafe-*` 系列），並明列 `@typescript-eslint/no-explicit-any` 與 `@typescript-eslint/no-non-null-assertion` 為 `error`
- **尚未檢查**：「外部資料要先驗證」只能靠審查
:::

### F3 Hooks 的呼叫順序、依賴與清理

hook 一律在元件最上層無條件呼叫，伺服器資料一律用 Orval 產生的 query hook，不用 `useEffect` 重建資料層。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**/*.tsx`、`frontend/src/**/use-*.ts` |
| **禁止** | 在條件、迴圈或 early return 之後呼叫 hook；用註解關掉依賴檢查而不說明；訂閱、計時器、`AbortController` 沒有 cleanup；把 server 資料抄進 `useState`；用 `useEffect` 加 `fetch` 自己重建一層資料層 |
| **正例** | hook 一律在元件最上層無條件呼叫；衍生值**直接從 query data 算**（必要時 `useMemo`）；取伺服器資料一律用 Orval 產生的 query hook；訂閱與計時器在 `useEffect` 的 return 裡清掉 |
| **例外** | `useEffect` 本身**不是禁止事項**。合法用途：訂閱外部事件（`window` 的 resize、`matchMedia`）、與瀏覽器 API 同步（`document.title`、焦點、捲動位置）、非 React 的第三方實例生命週期、以及把狀態寫回網址以外的宿主環境。這幾類都要有 cleanup |

:::note{title="F3 的反例與檢查方式" collapsible}
- **反例**：`if (!taskId) return null;` 之後才 `useQuery(...)`；`const [rows, setRows] = useState([]); useEffect(() => { fetch('/api/v1/tasks').then(r => setRows(r.items)); }, [])`（兩個錯：自己 fetch 繞過單一 HTTP 邊界，又把 server 狀態複製一份）；`useEffect(() => setFullName(first + ' ' + last), [first, last])`（直接算就好）
- **檢查方式**：CI 的 `frontend` job 跑 `pnpm --filter frontend lint`，`eslint-plugin-react-hooks` 的 `rules-of-hooks` 與 `exhaustive-deps` 都設為 `error`，擋前兩項；`no-restricted-globals` 與 `no-restricted-properties` 擋直接用 `fetch`（server 資料要走 Orval 產生的 client）
- **尚未檢查**：「不要用 effect 重建資料層」、cleanup 是否齊全要靠審查
:::

### F4 狀態的三個去處

狀態只有三個去處：伺服器狀態走 TanStack Query，可分享的狀態走網址，純局部 UI 狀態走 `useState`；不預先裝全域 store。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` |
| **禁止** | 把可分享的篩選或分頁只放在元件 state；為了「以後可能需要」先裝一個全域 store；把 token 或角色放進前端 store 當授權依據。（「不得把 API 回應複製進全域 store」在 [api-agent-rules.mdx](api-agent-rules.mdx) A9，這裡不重複，只標出它是三分法的第一格） |
| **正例** | 三分法：**伺服器狀態走 TanStack Query**（細節見 [api-agent-rules.mdx](api-agent-rules.mdx) A9）、**可分享的狀態走網址的 query string**（關鍵字、篩選、每頁筆數、頁次、目前分頁）、**純局部 UI 狀態走 `useState`**（下拉開合、游標位置、未送出的表單草稿） |
| **例外** | 需要全域 store 時**要在該 change 的 `design.md` 寫出理由**（跨路由共用、而且不是 server 狀態、也不適合放網址），經規劃審閱同意才引入。本條不預先禁止所有全域狀態。另有**第四個去處是規格定的**：外觀偏好（淺色／深色／跟隨系統）**只記在使用者這台瀏覽器**，換一台裝置要重新選一次（規格 01-04 §偏好設定），所以它既不是 server 狀態也不進網址 |

網址那一格在規格已定：規格 03-01 §查詢條件保留在網址、規格 03-03 §網址與畫面狀態同步。

:::note{title="F4 的反例與檢查方式" collapsible}
- **反例**：篩選條件只存在 `useState`——重新整理就掉了，而規格要求「重新整理還原查詢條件」；把 `listTasks` 的結果再存一份進 Zustand；用全域 store 存「目前使用者的角色」並以它決定能不能取得資料（角色只供顯示，見 [security-agent-rules.mdx](security-agent-rules.mdx) S3）
- **檢查方式**：**待建置**。可用 lint 擋住 `features/` 直接 import 任何 store 套件（在它被引入之前，那條規則等於「不得引入」）；網址同步的行為由規格的 Scenario 驗（E2E）。外觀偏好另有一條規格 Scenario 要驗：「重新整理後仍然是深色，**載入時不先閃一下淺色**」（規格 01-04）
:::

### F5 重用與不過度抽象

新寫 component、hook 或 util 之前先搜尋既有的；只有確實是同一個概念的兩處才抽，不以出現次數或行數為門檻。

**共用元件**是用到它的產品畫面分屬一個以上 feature 的設計系統元件，只能放 `components/`；只有一個 feature 的產品畫面用到的，留在那個 feature。用到它的畫面看 `design/system/screen-inventory.md` 的「元件 → 畫面」表；原型的元件展示頁（`components-showcase`）與原型索引（`index`）不是產品畫面，不算使用方；規格標「單頁專屬」或「原型鷹架」的一律不算共用。

畫面歸哪個 feature 依一條對應慣例：產品畫面歸它的原型模組（畫面 ID 的第一段），一個原型模組對到一個 feature，例如原型的 `account` 對到 `features/auth`；`shared/app-shell` 是登入後的外殼，自成一個。對照寫在 `scripts/check-component-reuse.mjs` 的 `SCREEN_FEATURE`，出現對照沒有的畫面 ID 時檢查會失敗，不會猜。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` |
| **禁止** | 新寫一個 component／hook／util 之前沒有先搜尋既有的；每一頁各自重造 Button、Dialog、Table、Skeleton；把共用元件建在 `features/` 或 `pages/`；把還只有一處用到的程式先抽成共用元件；無差別地 `memo`／`useMemo`／`useCallback` 包一層 |
| **正例** | 先查 `design/system/components/<元件>.md` 的「程式實作」、再 grep 既有的名稱與相近語意，然後才決定新增；shadcn 已有的元件優先用 `components/ui/`，不夠用時先擴充它的 props；**兩處確實是同一個概念時**才抽（判準見 [agent-rules.mdx](agent-rules.mdx) R4），不以出現次數為門檻；`memo` 只在有量測到的重繪問題時加，並在註解寫出原因；一個檔案一個主要元件 |
| **例外** | 無。設計上需要一次抽象（例如同一個 change 內同時建立三個同構頁面）時，在該 change 的 `design.md` 寫明 |

:::note{title="F5 的反例與檢查方式" collapsible}
- **反例**：`features/annotation/components/my-button.tsx` 自己寫一顆按鈕；把只有一處用到的 `formatTaskName` 放進 `lib/`；整個 feature 的每個元件都包 `React.memo`
- **檢查方式**：CI 的 `specs` job 與 `scripts/check-changed.sh` 的 `.ts`／`.tsx` 路由跑 `node scripts/check-component-reuse.mjs`：`features/` 或 `pages/` 底下的元件檔名對到共用元件（和規格名或它在 `components/` 的實作檔名同名、或最後一個字相同，例如 `*-toggle`、`*-banner`、`*-alert`）卻沒有 import 它在 `components/` 的實作、共用元件的「程式實作」指向 `features/` 或 `pages/`、「程式實作」的路徑不存在、或清冊的「程式實作」欄和規格不一致時失敗；現有的違規列在腳本的允許清單，每列寫明由哪張單（`#N`）搬走與觸發的元件，搬完那一列不刪也會失敗
- **尚未檢查**：hook、util 的重複與「是不是同一個概念」沒有機械檢查，由 `code-reviewer` 依職責判斷。這一條**不以行數作為拆分判準；另有 [F12](#f12-檔案函式長度與複雜度上限) 的 CI 上限擋極端值**，F12 不是 F5 的檢查
:::

### F6 視覺基準與 design token 的映射

語意色的色值只存在 `tokens.css` 一處，shadcn 的語意變數透過 `src/styles/` 的一層對照指過去，元件只用語意 class。資料色（`--data-*`，角色色、圖表色）另外來自 `design/prototype/assets/data-palette.css`，不進對照層，`components/ui/` 的原語不讀。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/styles/**`、`frontend/src/components/ui/**`，以及任何寫樣式的地方 |
| **禁止** | 在元件寫死色碼（class、`style`、SVG 屬性都算）；用 Tailwind 原色 class（`bg-blue-500`、`text-gray-600`）；寫 `p-[13px]` 這類**字面數值**的任意值去對齊品牌刻度（**引用變數的任意值不在此限**，見摺疊區塊第 3 點）；把 scaffold 的 `neutral.css`／`trendlink.css` 主題搬進來；在元件裡依主題做條件判斷；**改寫 `components/ui/` 的 shadcn 元件去讀別的變數名** |
| **正例** | **對照層在 `src/styles/`**：shadcn 的語意變數指向 `tokens.css` 的值（`--background: var(--color-surface)`、`--foreground: var(--color-ink)`…），語意色的色值**只存在 `tokens.css` 一處**；資料色另來自 `data-palette.css`，不進對照層，由用到的 feature 以引用變數的任意值使用（例如 `bg-[var(--data-role-violet-bg)]`）；元件只用語意 class（`bg-background`、`text-muted-foreground`）；深色模式由 `html[data-theme="dark"]` 驅動，shadcn 的 dark variant 設成吃那個屬性 |
| **例外** | `tokens.css` 與 `data-palette.css` 自己是色值的所在地，不受「不得寫色碼」限制。`design/prototype/` 的 HTML 另有自己的用法，不受本條約束（而且**本文件這一類工作不得改 `design/prototype/`**） |

視覺基準是 `tokens.css`（103 個不重複的變數名）與 `label-suite-design` skill。映射前要逐一確認三件事，不是改個名字就好，見下方摺疊區塊。

:::note{title="F6 映射前要確認的三件事" collapsible}
三件都是落地時已知、已經有人踩過的坑。第 1 點的落點已經裁定過（見[§決策紀錄](#決策紀錄)）；第 2、3 點是本文件的要求，不是維護者選定的內容（選定的只有「寫一層對照」與「語意色只來自 `tokens.css`、資料色另有來源檔」兩件）。

1. **shadcn 沒有對應語意的 token，在對照層新增語意變數。** `tokens.css` 有 `--color-cta`（確認、完成類的主要按鈕）、`--color-ink-muted`、`--workspace-tab-min-width` 這些 shadcn 沒有的語意。對照層只能處理「兩邊都有」的部分；剩下的新增 shadcn 風格的語意變數（`--cta`、`--success`、`--warning`、`--info`），對照層與元件都用它。**原語不直接用 `tokens.css` 的變數名**——那是上面禁止格的「去讀別的變數名」，不是可選的另一條路。
2. **`--radius-*` 與 `--font-sans` 和 Tailwind v4 的 theme namespace 同名。** scaffold 自己的 `design-tokens.md` 就記著「主題檔的 `@theme` 不得重複定義 `globals.css` 的 `@theme inline` 已有的**變數**（`--font-sans`、`--radius-*`、`--color-*`）」。而 `tokens.css` 有 `--radius-sm/md/lg`（4／8／12px）與 `--font-sans`。把它們接進 Tailwind 的 `@theme` 會**改掉 `rounded-*` 這些既有 utility 的語意**，所以映射時要逐一確認會動到哪些 utility，並在 PR 寫出來。
3. **映射數字 spacing key 會讓尺寸靜默放大。** duty-mate 的 `tailwind-theme.md` 記了一次事故：`@theme` 定義了具名的 `--spacing-10` 之後，`w-10` 從 40px 變成 80px，開關元件的圓鈕位移比例全錯。本 repo 的間距 token 是 t-shirt 命名（`--space-xs/sm/md/lg/xl/2xl/3xl`），不會逐字重演那個案例，但**同類的 namespace 覆蓋要一樣小心**；需要 token 間距時用任意值引用變數（`p-[var(--space-lg)]`），不要去覆蓋 Tailwind 的數字刻度。
:::

:::note{title="F6 的反例與檢查方式" collapsible}
- **反例**：`<div className="bg-[#6366F1]">`；`<path stroke="#e5e7eb" />`（改成 `currentColor` 或 `var(--color-border)`）；在 `src/styles/themes/neutral.css` 貼一份 shadcn 預設色值——那會變成第二個色值來源
- **檢查方式**：**待建置**。可用 stylelint 或自寫腳本掃 `#[0-9a-f]{3,6}`、`rgb(`、Tailwind 原色 class 與任意值 class；對照層是否齊全要靠審查
:::

### F7 圖示與 SVG

圖示一律用 `lucide-react`，缺圖示時回報、不自己畫；但品牌標記、資料視覺化等四類 SVG 不在此限。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` |
| **禁止** | 加入 Lucide 以外的圖示庫（Heroicons、react-icons、Font Awesome…）；用 emoji 當圖示；為了一個圖示自己手畫 inline SVG；圖示寫死顏色或用 HTML 的 `width`／`height` 屬性 |
| **正例** | 一律 `lucide-react`；尺寸與顏色由呼叫端用語意 class 傳入（`className="w-4 h-4 text-muted-foreground"`）；Lucide 缺某個圖示時**回報**，不自己畫 |
| **例外** | 四類，各自有來源：（1）**品牌與 logo 標記**（彩色 logo、banner、Google SSO 的 G）——[architecture.mdx](../architecture.mdx) §前端 明文；（2）**資料視覺化的 SVG**——長條圖、趨勢圖、分佈圖是畫資料不是畫圖示（規格 05-02 統計總覽分頁的各型統計區塊（§單一標籤的統計、§多標籤的統計、§實體辨識的統計、§多維度的統計）的橫向長條、軸標籤與圖例），顏色仍只能用 token；（3）**`design/prototype/` 的 inline SVG**——設計層沒有 npm，architecture.mdx 已明文允許，條件是每個字形都複製自真實的 Lucide 圖示；（4）**文件生成的 `.notecraft/components/*.tsx`**——NoteCraft 的視覺化元件自己畫圖，不是產品碼 |

理由：集中用 Lucide 才能保證 `stroke-width`、`viewBox` 與端點風格一致。

:::note{title="F7 的反例與檢查方式" collapsible}
- **反例**：`import { FiUser } from 'react-icons/fi'`；`<span>✅</span>` 當狀態圖示；`<svg viewBox="0 0 24 24"><path d="M5 13l4 4L19 7"/></svg>` 自己畫一個勾
- **檢查方式**：**待建置**。可用 lint 擋住 `lucide-react` 以外的圖示套件 import，並掃產品碼裡的 `<svg`（例外要逐一標註）；prototype 的 Lucide 一致性目前只有人工
:::

### F8 四種畫面狀態與表單

每個取資料的區塊都要處理 loading、error、empty、無權限四種狀態，表單要處理驗證、送出期間與可預期錯誤。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/pages/**`、`frontend/src/features/**` |
| **禁止** | 取資料的區塊少處理任何一種狀態；把 `403` 當成一般錯誤顯示重試；用「沒有資料」當成載入失敗的呈現；表單在送出期間還能再按一次；前端自己猜某個角色看不到什麼而把欄位藏起來 |
| **正例** | 每個資料區塊四種狀態齊備：**loading** 用 skeleton、維持版面不跳動；**error**（非 `403`）顯示訊息與重試；**empty** 顯示說明，有權限時附新增入口；**無權限**（`403`）顯示無權限說明、**不給重試**。表單要處理驗證訊息、送出期間 disabled、以及可預期錯誤（`409`、`400`）顯示在對應欄位 |
| **例外** | 不取資料的靜態區塊沒有這四種狀態。樂觀更新允許，但要在該 change 的 `design.md` 寫出回滾方式。**逐頁的規格可以比這四種更嚴**：規格 05-01 §四種互斥的頁面狀態 與規格 05-02 §兩個分頁各有一組自己的狀態（統計四種、品質六種，明文「不得互相代用」）就是更嚴的版本，那兩頁以規格為準 |

:::note{title="F8 的反例與檢查方式" collapsible}
- **反例**：`if (isLoading) return null`（版面跳動）；`403` 顯示「載入失敗，請重試」（重試永遠不會成功）；後端已經把欄位遮成固定值，前端又依角色再判斷一次要不要顯示
- **檢查方式**：**待建置**。四種狀態與遮蔽欄位的呈現由該 change 的 `ui-design.md` 逐區塊寫出，`design-reviewer` 與 `code-reviewer` 的 checklist 已各有一條；E2E 由規格的 Scenario 驗——但要注意**規格 03-01 §空狀態與載入失敗 只涵蓋三種**（完全沒有任務、篩選後沒有符合、載入失敗），**沒有 `403`**；無權限那一種的 Scenario 在各頁的權限條文裡（例如規格 03-01 的「沒有權限時停在列表」）
:::

### F9 無障礙的最低要求

互動元素用語意元素、欄位有標籤、圖示按鈕有可存取名稱、狀態不只靠顏色，並尊重「減少動態效果」。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**/*.tsx` |
| **禁止** | 用 `div onClick` 代替 `button`；表單欄位沒有關聯的標籤；只有圖示的按鈕沒有可存取名稱；把 shadcn Dialog 的焦點處理拆掉；只用顏色表達狀態；忽略使用者「減少動態效果」的偏好 |
| **正例** | 互動元素用語意元素（`button`、`a`、`label`）；每個欄位有 `<Label htmlFor>`；錯誤訊息用 `aria-describedby` 關聯到欄位；只有圖示的按鈕加 `aria-label`，裝飾性圖示加 `aria-hidden`；Tab 順序合理、Dialog 開關時焦點正確；狀態同時用文字或圖示表達，不只靠顏色；**`prefers-reduced-motion` 時過場動畫降到最低，操作本身照常可用** |
| **例外** | 無。裝飾性元素不需要可存取名稱，但要明確標成裝飾（`aria-hidden`） |

:::note{title="F9 的反例與檢查方式" collapsible}
- **反例**：`<div className="cursor-pointer" onClick={...}>送出</div>`；只用紅色的框表示驗證失敗而沒有訊息；側欄收合動畫在使用者關閉動態效果後照播
- **檢查方式**：**待建置**。`eslint-plugin-jsx-a11y` 可以擋語意元素與 `aria-label` 的缺漏；對比度與鍵盤流程要靠 Playwright 的 a11y 檢查與人工。**`tokens.css` 已經把對比度當成議題處理過**（多個 token 的註解寫著 WCAG AA 的修正與接受的取捨），所以色票本身不需要再驗一次，要驗的是元件有沒有用對 token
:::

### F10 日期、時區與可測的時鐘

所有日期的格式化與比較走 `src/lib/date.ts` 單一入口，並分清時間點、只有日期、顯示、報表區間四種概念。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**`（日期的讀寫、比較與格式化） |
| **禁止** | 在元件各自 `new Date()`／`Date.now()` 做邏輯；把只有日期的欄位當成時間點處理；把顯示用的時區寫死成某個固定時區；在元件裡自己拼日期格式字串；測試依賴真實時間 |
| **正例** | 四種概念分開：**時間點**在傳輸與儲存一律 UTC 的 ISO 8601 字串（`2026-11-10T02:30:00.000Z`）；**只有日期**的欄位用 `YYYY-MM-DD` 字串傳輸，不轉成時間點；**顯示**依瀏覽者裝置的時區；**報表的日期區間**固定以台北時區計算。所有格式化與比較走 `src/lib/date.ts` 單一入口，入口裡可以注入時鐘讓測試固定「現在」 |
| **例外** | 第三方套件要求原生 `Date` 時，在呼叫處轉換；測試用的假時鐘（`vi.setSystemTime`）屬框架機制。**本條不全面禁止原生 `Date`**：要求的是「邏輯走單一入口」，不是「某個 API 一律不准出現」 |

顯示時區依瀏覽者裝置在規格已定（規格 06-01 Q2，它的 Scenario 寫明東京時區的裝置看到的是當地時間；規格 03-01 §任務列的欄位 比照規格 06-01 §資料欄位）；報表固定台北時區見規格 03-03 §工時紀錄 第 10 條（跨日的部分在查詢時以當地午夜切開）。

日期套件用 day.js，搭配 utc 與 timezone 外掛，只在 `src/lib/date.ts` 裡 import。

:::note{title="F10 的反例與檢查方式" collapsible}
- **反例**：`new Date(task.createdAt).toLocaleString()` 散在十個元件裡（格式與時區各自分歧）；把 `YYYY-MM-DD` 的生效日當成午夜時間點再轉時區（日期會跳一天）；把顯示時區寫成 `Asia/Taipei`——**本 repo 的顯示時區是裝置時區**
- **檢查方式**：CI 的 `frontend` job 跑 `pnpm --filter frontend lint`，`frontend/eslint.config.js` 以 `no-restricted-imports` 擋住 `src/lib/date.ts` 以外的地方 import `dayjs` 與 `dayjs/*`；「只有日期的欄位不轉時間點」沒有機械檢查，要靠審查與規格的 Scenario
:::

### F11 註解與 JSDoc

註解與 JSDoc 用英文，只寫名稱看不出來的資訊；元件 props 宣告成具名 `interface`。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` |
| **禁止** | 用註解複述名稱（「取得任務列表」）；寫中文註解在產品碼裡；在 JSDoc 重寫 TypeScript 已有的型別；寫其他專案的需求編號（`FR-001`、`T013`）；元件 props 寫成參數上的 inline 型別；改了行為不改註解 |
| **正例** | **英文**（`AGENTS.md` §Language Rules：程式與註解只用英文）；描述寫名稱看不出來的事——契約、前提、副作用、特殊值（`null` 與空陣列各代表什麼）；元件 props 宣告成具名 `interface XxxProps`，每個欄位一行說明；公開的 hook 與工具函式標明回傳型別與會拋出的錯誤 |
| **例外** | （1）匿名 callback 不寫；（2）測試檔不強制；（3）`src/api/generated/`：產物不寫、也不手改；（4）**`.notecraft/components/*.tsx` 的 `export default` 是 NoteCraft 的契約**——本 repo 現有 22 個這樣的檔案，產品碼的 named-export 慣例**不得**套用到它們；（5）框架要求 `export default` 的設定檔（Vite／Vitest／Playwright／Orval） |

:::note{title="F11 的反例與檢查方式" collapsible}
- **反例**：`/** 任務表格 */ export function TaskTable(...)`（沒說出任何名稱以外的資訊）；`/** @param {string} id 任務 ID */`（型別重複、而且是中文）；`export function TaskTable({ items }: { items: TaskDto[] })`（inline props，欄位無法逐一說明）
- **檢查方式**：**待建置**。`eslint-plugin-jsdoc` 可以檢查「有沒有、格式對不對」，描述與行為是否一致由 `code-reviewer` 審。**本條不要求每個具名單位都有 JSDoc**，所以覆蓋率沒有門檻
:::

### F12 檔案、函式長度與複雜度上限

檔案不超過 300 行、函式不超過 80 行、函式的圈複雜度不超過 15；這是擋極端值的護欄，不是拆分判準。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/` 底下符合 `src/**/*.{ts,tsx}` 或 `build/**/*.ts` 的檔案 |
| **禁止** | 單一檔案超過 300 行（`max-lines`）；單一函式（含 React 元件本體與箭頭函式）超過 80 行（`max-lines-per-function`）；單一函式的圈複雜度超過 15（`complexity`）。三條都是 `error`，lint 失敗 |
| **正例** | 檔案或函式逼近上限時，先依 F5 與 [agent-rules.mdx](agent-rules.mdx) R4 判斷職責是否該拆；為了壓低行數把同一個概念硬拆成兩處，或把不相干的東西湊在一起，都不是這條要的 |
| **例外** | （1）測試檔（`*.test.ts`、`*.test.tsx`、`src/test/**`）只豁免檔案與函式兩條長度上限，複雜度上限照樣適用；（2）不符合上述路徑樣式的檔案不在範圍，例如套件根目錄的 `eslint.config.js`、`vite.config.ts`、`vitest.config.ts`、`orval.config.ts`；（3）`src/api/generated/` 由全域 ignore 排除；（4）具名豁免集中在 `frontend/eslint.config.js` 的 `NAMED_EXEMPTIONS`，每筆有 issue 與理由，上限即棘輪（檔案再變長就再失敗），豁免過期由測試擋下。目前只有一筆：`src/pages/dev-gallery/dev-gallery-page.tsx` 的函式行數上限放寬到 180（[#561](https://github.com/label-suite/label-suite/issues/561)） |

這裡的「行」排除空白行與註解行，與後端 [B11](backend-agent-rules.mdx) 的計法不同（B11 只排除空白行與以 `#` 開頭的行），兩邊的數字不可互比。

與 F5 的關係：F5 與 R4 駁回以固定行數取代職責審查，這個判斷不變。F12 的上限只擋極端值，檔案或函式沒超過上限不代表不需要拆，超過上限也只是必須處理而不是自動該拆成幾份；是否拆分仍依 F5 與 R4 的職責判斷。

:::note{title="F12 的反例與檢查方式" collapsible}
- **反例**：在 `src/components/` 加一個 81 行的元件函式或有 16 條獨立 `if` 的函式，lint 失敗；為了不超過 80 行，把同一個元件的 JSX 隨意切成兩個互相依賴的檔案
- **檢查方式**：CI 的 `frontend` job 的 Lint 步驟（`pnpm --filter frontend lint`）；`frontend/build/size-limits-config.test.ts` 守住三個數值、`error` 等級、測試檔與設定檔的例外範圍，以及 `NAMED_EXEMPTIONS` 是否過期
:::
