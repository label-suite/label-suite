# 02-01 儀表板

:badge[草稿]{variant="warning"} :badge[儀表板]{variant="neutral"} :badge[109 條舊編號全數對應]{variant="success"}

> 來源：舊 repo `specs/dashboard/012-dashboard/spec.md`（**109 條**），釘在 `singyichen/label-suite@faf83356`
> 參考畫面：`design/prototype/pages/dashboard/dashboard.html`
> 相關規格：[規格 03-01 任務列表](../03-task-management/01-task-list.mdx)、[規格 04-01 標記清單](../04-annotation/01-annotation-list.mdx)、[規格 04-02 標記工作區](../04-annotation/02-annotation-workspace.mdx)、[規格 06-02 角色設定](../06-admin/02-role-settings.mdx)、[規格 07-01 側欄導覽](../07-shared/01-sidebar.mdx)

:::info{title="這一頁是讀的，不是做事的"}
PRD §權限矩陣 給儀表板的只有 `R`：:ref[平台成員]{id="term.platform-member"}是 `R (o)`、:ref[系統管理員]{id="term.system-admin"}是 `R`。**這一頁不新增、不修改、不刪除任何東西**，它做兩件事：

1. **依使用者在各任務的角色，決定他看到哪一種版面**
2. **把他送回真正做事的地方**——標記清單、標記工作區或任務列表

所以這一頁的規則幾乎都是「誰看得到什麼」與「這個入口會把人帶到哪裡、帶著什麼」。

**109 條舊編號全數對應**，見[§附錄：舊編號對照](#附錄舊編號對照)；`pnpm check:specs` 會驗證零缺漏。

:::warning{title="這一頁有一整個區塊，來源要求、但畫面上不存在"}
來源的 `FR-007C`／`FR-007D`／`FR-007E`／`FR-007F` 與 `SC-004A` 定義了一個「**三條最短成功路徑**」區塊，連標題、副標、三條路徑的名稱與每條 5 個步驟的文字都寫好了，並註明「需與原型一致」。

但 `最短成功路徑` 這五個字在整個舊 repo 裡**只出現在這一份 `spec.md`**——prototype 沒有這個區塊，沒有那些文案，連 i18n 字典裡都沒有對應的鍵。畫面上只有三張行動入口卡，每張卡 **3 步**（不是 5 步）。

依本專案的搬移規則，**畫面沒有的東西不寫成規則**，所以這一整組需求我寫進[§待釐清](#待釐清) Q1，把來源的文案原樣保留在那裡，不在 §規格 寫成「系統必須顯示」。這一題定案前，這一頁描述的**一般使用者版面是不完整的**。
:::

**這一頁仍是草稿**：狀態要等[§待釐清](#待釐清)的 11 題定案（由本模組 Epic 的第二輪 child 負責）才會改成已定案。已定案的 6 條來自來源自己的**釘了日期的釐清紀錄**（2026-05-22 與 2026-07-29 兩次），見[§已確認決議](#已確認決議)。

## 目標

| 目標 | 誰受益 |
| :--- | :--- |
| 讓使用者登入後**不必自己找路**：系統依他在各任務的角色，直接給他那個角色該看的版面 | 所有使用者，特別是同時身兼多個任務角色的人 |
| 讓還沒有任何任務角色的人**知道下一步可以做什麼**，而不是看到一個空頁面 | 第一次登入的新使用者 |
| 讓:ref[標記員]{id="term.annotator"}與:ref[審核員]{id="term.reviewer"}**一鍵回到自己真正該處理的那一筆**，不必自己翻清單 | 每天要處理大量資料的標記員與審核員 |
| 讓:ref[系統管理員]{id="term.system-admin"}與:ref[專案負責人]{id="term.project-leader"}**一眼看出哪些任務卡住了**，並從卡住的那個數字直接點進去 | 要推進任務的人 |
| 讓同一個任務的數字**在儀表板與標記清單上一致**，不會兩個畫面講不同的話 | 看數字做判斷的審核員與專案負責人 |
| 讓這一頁**碰不到**:ref[標準答案]{id="term.ground-truth"}與測試集 | 資料品質——儀表板是標記員每天進入的第一頁 |

## 使用角色

**依系統角色**

| 角色 | 權限 | 說明 |
| :--- | :--- | :--- |
| :ref[平台成員]{id="term.platform-member"} | R (o) | 進得了這一頁；只看得到**自己有參與**的任務 |
| :ref[系統管理員]{id="term.system-admin"} | R | 進得了這一頁；看得到**全平台**的統計與任務列表 |

**依任務角色**（只決定看到哪一種版面）

| 角色 | 權限 | 說明 |
| :--- | :--- | :--- |
| :ref[專案負責人]{id="term.project-leader"} | 無權限 | 任務角色**不會**讓他在這一頁多看到任何東西；它只決定他看到的是專案負責人版面 |
| :ref[審核員]{id="term.reviewer"} | 無權限 | 同上；決定他看到審核員版面（含「快速審核」） |
| :ref[標記員]{id="term.annotator"} | 無權限 | 同上；決定他看到標記員版面（含「快速繼續」） |

- **進得了這一頁只看系統角色**。PRD §權限矩陣 的**依任務角色**那張表**沒有「02 儀表板」這一列**，所以任務角色在這一頁不得被寫成一格權限——寫法與[規格 03-01 §使用角色](../03-task-management/01-task-list.mdx#使用角色)一致
- 任務角色持有者本身就是平台成員，已經有 `R (o)`，所以他**看得到的範圍沒有因為任務角色而變大**；變的只有版面
- 這一頁沒有 C／E／D：PRD §權限矩陣 的「02 儀表板」兩欄都只有 `R`
- 對應的權限名詞是 :ref[檢視儀表板]{id="term.perm-dashboard-view"}，**兩種系統角色的這一格固定開啟**（見[規格 06-02 §固定格不能改](../06-admin/02-role-settings.mdx#固定格不能改)）
- 系統管理員的**全平台統計**另有一個權限名詞 :ref[檢視全平台統計]{id="term.perm-platform-overview-view"}，它的狀態是「已登錄、待啟用」；依[規格 06-02 §五個已登錄、待啟用的鍵](../06-admin/02-role-settings.mdx#五個已登錄待啟用的鍵)第 9 條，系統管理員的全平台統計**依它自己的固定格與系統管理員硬邊界判斷，不經過那個待啟用的鍵**，所以這個能力不會因為那個鍵還沒啟用而消失
- 系統管理員**看得到所有任務的列表**，但沒有任務角色時進不了那個任務的詳情、標記與分析（PRD §權限矩陣 的附註）

### 進入儀表板拿到自己的版面

- 觸發：使用者登入成功後進入儀表板
- 前置條件：使用者已登入（見[規格 01-05 登入狀態與安全](../01-account/05-login-state.mdx)）
- 主流程：
  1. 系統讀取使用者的**系統角色** → 角色有效
  2. 系統判斷他是不是系統管理員 → 是 → 顯示全平台的四個區塊
  3. 不是系統管理員 → 系統讀取他在各任務的角色；讀取還沒回來的這段時間，畫面顯示骨架佔位（見[§還在載入與載入失敗](#還在載入與載入失敗)）
  4. 讀到的任務角色有一種以上 → 依**專案負責人 > 審核員 > 標記員**的優先序，顯示其中**一種**版面
- 替代流程：
  - A1（第 4 步）使用者**沒有任何任務角色** → 顯示三張行動入口卡（見[§還沒有任務角色的人看到什麼](#還沒有任務角色的人看到什麼)），流程結束
- 例外流程：
  - E1（第 1 步）系統角色無效 → 導向登入頁，流程結束（見[§卡控機制](#卡控機制)）
  - E2（第 3 步）讀取任務角色失敗 → 結束骨架，顯示錯誤說明與重試入口；**不改用一般使用者版面、不清掉登入狀態、不導向登入頁**，流程結束（見[§卡控機制](#卡控機制)）
- 結果：使用者看到**唯一一種**對應他身分的版面，頁首與導覽在每一種版面上都一樣

### 從儀表板回到標記工作

- 觸發：標記員要繼續標記
- 前置條件：使用者在標記員版面，任務列上有至少一個任務
- 主流程：
  1. 標記員在某個任務列按「快速繼續」
  2. 系統找這個任務**第一筆還沒提交**的資料（可能是已儲存的，也可能是還沒開始的）
  3. 找到了 → 帶著**這一個**任務、那一筆資料與他的標記員身分進入標記工作區（規格 04-02）
- 替代流程：
  - A1（第 3 步）這個任務的資料**全部都已提交** → 改帶他到**這個任務的**標記清單，不指定某一筆；「快速繼續」照樣可見可按，流程結束（見[§已確認決議](#已確認決議) Q13）
  - A2（第 1 步）標記員按的是任務列上「快速繼續」**以外**的地方 → 帶他到這個任務的標記清單，流程結束
- 結果：標記員從儀表板一步回到工作，而且回到的是**他按的那一個任務**

### 從儀表板回到審核工作

- 觸發：審核員要繼續審核
- 前置條件：使用者在審核員版面，任務列上有至少一個任務
- 主流程：
  1. 審核員在某個任務列按「快速審核」
  2. 系統依**審核單位的狀態**與**他本人的身分**推導下一個可處理的單位（規則在[規格 04-01 §沒有可處理的審核單位](../04-annotation/01-annotation-list.mdx#沒有可處理的審核單位)）
  3. 推導得出一個單位 → 帶著任務、樣本、標記員身分、審核員身分與標記階段**五項**進入標記工作區（規格 04-02）
- 替代流程：
  - A1（第 3 步）推導結果是**空的** → 改帶他到這個任務的標記清單，不指定某一筆，並說明目前沒有可處理項目；**不開任務的第一筆，也不開任何已定稿的唯讀單位**，流程結束
  - A2（第 1 步）審核員按的是任務列上「快速審核」**以外**的地方 → 帶他到這個任務的標記清單，流程結束
- 結果：審核員進到的是**他真的能處理**的那一筆，不是這個任務的第一筆

## 規格

### 這一頁顯示哪一種版面

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

使用者進到這一頁時不選版面，**系統替他決定一種**，而且只有一種。

1. 系統先讀**系統角色**：是:ref[系統管理員]{id="term.system-admin"} → 顯示**全平台版面**，不再去讀任務角色
2. 是:ref[平台成員]{id="term.platform-member"} → 系統讀他在各任務的角色，依下表決定版面：

| 他擁有的任務角色 | 顯示哪一種版面 |
| :--- | :--- |
| 一個都沒有（沒建立過任務，也沒被指派） | 還沒有任務角色的版面（三張行動入口卡） |
| 有:ref[專案負責人]{id="term.project-leader"} | 專案負責人版面 |
| 沒有專案負責人、有:ref[審核員]{id="term.reviewer"} | 審核員版面 |
| 只有:ref[標記員]{id="term.annotator"} | 標記員版面 |

3. 同時擁有多種任務角色時，優先序是 **專案負責人 > 審核員 > 標記員**，而且**只顯示那一種**，不是把幾種拼在一起（見[§已確認決議](#已確認決議) Q9）
4. 系統角色不在允許清單裡（不存在、是空的、或是別的值）→ **導向登入頁**
5. 不論哪一種版面，**頁首與側欄導覽都一樣**，不會因為換版面而消失

- 第 3 條的代價要說清楚：一個同時是專案負責人和標記員的人，在儀表板上**看不到自己的標記待辦**。他要標記得從側欄進入標記作業
- 這一頁刻意用「還沒有任務角色」來描述第一種版面，而不用來源與畫面上的「一般使用者」——那個詞不是平台上任何一個角色的名字，歸屬見[§待釐清](#待釐清) Q8
- 畫面上另有一排「場景模式」的切換鈕（一般使用者／系統管理員／專案負責人／標記員／審核員）。那是 **prototype 用來假扮不同身分的走查工具**，不是產品功能；正式系統的版面只由第 1 到第 3 條決定，使用者切不了

1. 頁面最上方固定顯示主標題 `儀表板` 與副標題 `掌握任務進度與團隊協作狀態`

### 還在載入與載入失敗

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

平台成員的版面要先知道他在哪些任務裡是什麼角色才能決定，所以這一段的等待是必然的。

1. 讀取任務角色還沒回來時 → 顯示**骨架佔位**：頁面結構看得見，資料的位置是灰色的佔位塊
2. 骨架用的是**指標卡加任務列表**的佈局，也就是「有任務角色」那幾種版面的樣子（最常見的情況）
3. 讀完之後確認是「還沒有任務角色」的版面 → **直接切成那個佈局**；骨架與最終版面長得不一樣是**可以接受的**
4. 讀完之後 → **無縫換成實際內容**，不出現空白頁閃動
5. 讀取失敗（伺服器錯誤或逾時）→ **結束骨架**，顯示錯誤說明與**重試**入口
6. 第 5 條的三個禁止，一個都不能少：
   1. **不得**改成顯示「還沒有任務角色」的版面
   2. **不得**清掉使用者的登入狀態
   3. **不得**把人導向登入頁
7. 畫面上的文字是標題 `儀表板載入失敗`、說明 `無法載入任務成員資格資料，請稍後再試。`、按鈕 `重試`

- 第 6 條之所以寫成禁止清單：這三件事都是「看起來合理的善後」，但每一件都會讓使用者以為自己的任務不見了，或是以為自己被登出了。真正的狀況只是一次讀取失敗
- 骨架**顯示多久**不寫進規格：prototype 沒有後端，它的延遲是為了讓骨架看得見而設的，不是產品規格

1. 區塊標題是 `開始你的第一個工作流程`，副標是 `從三個行動入口開始，快速達成第一個可交付成果`
2. 底下有**三張行動入口卡**，每張卡包含標題、說明、**3 個步驟**與一個行動按鈕：

| :--- | :--- | :--- | :--- | :--- |

5. 三張卡的步驟各有自己的一句說明文字。**這九句話本頁來源沒有**——來源只列出三步的箭頭標籤（「建立任務 → 上傳資料 → 指派人員」），`FR-007A` 也只要求「標題、說明文字、3 步流程圖示、CTA」。以下是**畫面現況**，是不是正式需求見[§待釐清](#待釐清) Q16：

| 卡 | 第 1 步 | 第 2 步 | 第 3 步 |
| :--- | :--- | :--- | :--- |
| A | `設定任務目標與標籤規則` | `上傳第一批資料，確認可被系統讀取` | `指派至少 1 位標記員與 1 位審核員` |
| B | `進入標記工作區，查看待辦任務` | `依照標籤規則，完成標記工作` | `自我檢查標記一致性，提交標記結果` |
| C | `檢查標記內容，檢視標記與依據` | `通過、修正或無法裁決；歧異交付仲裁與例外池` | `確認審核列表，標記任務完成` |

- 來源另外要求一個「三條最短成功路徑」區塊（每條 5 步），但**畫面上沒有那個區塊**。那一整組需求在[§待釐清](#待釐清) Q1，本節不寫
- 第 5 條那九句裡最需要注意的是 `指派至少 1 位標記員與 1 位審核員`：它讀起來是一條**建立任務的業務卡控**（最少各一人），而本頁來源完全沒有這條規則，建立任務的規則也不在這一頁（[規格 03-02](../03-task-management/02-task-new.mdx)）。所以它在這裡只能當畫面文案看，不能當成卡控
- 卡 B 與卡 C 的按鈕對一個**還沒有任務角色**的人來說會走到哪裡，來源沒有交代：他沒有任何任務可標、可審。這一題在[§待釐清](#待釐清) Q2

### 「等待 IAA 確認」這張卡是一個入口

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

系統管理員與專案負責人兩種版面上，**各自只有這一張卡的數字可以點**；其餘的指標卡都只是數字。

1. 這張卡的**數值**是一個可操作的入口：可以用滑鼠點，也可以用鍵盤（移到它上面按 Enter 或空白鍵）
2. 觸發後 → 前往[任務列表](../03-task-management/01-task-list.mdx)，並**已經套用「等待 IAA 確認」的狀態篩選**
3. 這張卡上的數字，必須和前往任務列表後篩出來的**筆數一致**；數字和清單對不上帳是不允許的
4. 兩種版面的可見範圍不同，所以同一個時間點兩邊的數字**可以不一樣**：系統管理員數的是全平台，專案負責人數的是自己參與的任務

- 第 1 條特別寫出鍵盤：一個「看起來只是數字」的東西被做成按鈕時，只用滑鼠的人看得出來，只用鍵盤的人不一定找得到
- 第 3 條是這張卡唯一的正確性要求，也是它最容易壞的地方——數字和清單是兩條不同的計算路徑

### 「查看全部」去哪裡、看得到誰的任務

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. 系統管理員與專案負責人的任務列表區塊，右上角有一個主操作按鈕 `查看全部`；按鈕文字可切換語言
2. 按下去 → 前往[任務列表](../03-task-management/01-task-list.mdx)
3. 到了任務列表之後看得到誰的任務，**依登入者自己的身分決定**：

| 誰按的 | 任務列表顯示 |
| :--- | :--- |
| 系統管理員 | **全平台**的任務 |
| 平台成員（專案負責人版面） | **只有他自己有參與**的任務，不切換成全平台視角 |

4. 第 3 條的「全平台」**只能來自伺服器端認定的當前身分**：他現在真的是系統管理員，而且他在權限矩陣上**檢視任務列表**那一格是開的
5. 第 4 條的反面要寫死：**網址上的參數、瀏覽器裡存的東西、任何前端狀態，都不能用來取得全平台範圍**
6. 當前身分**不是**系統管理員的人，即使網址上帶了看起來像管理員的參數 → **只拿到他自己有參與的任務**
7. 任務的可見範圍**不看任務名稱、也不看輸出類型**；只看他在那個任務裡有沒有有效的成員身分

- 第 5、6 條來自來源 v2.14.0 的修訂：畫面上那個參數原本只是 prototype 用來切換檢視的，而它看起來很像一個可以要求全平台範圍的開關。這兩條把它釘成「只是檢視上下文」
- 這一節和[規格 03-01 §誰看得到哪些任務](../03-task-management/01-task-list.mdx#誰看得到哪些任務)講的是同一件事，兩邊必須一致：平台成員只看得到自己參與的，系統管理員預設看得到全部，而且**沒有**「我的任務／全平台任務」切換
- 但第 4 到第 6 條那組「範圍只能來自伺服器端認定的當前身分」的硬化規則，**目前只寫在這一頁**；規格 03-01 §誰看得到哪些任務 只有四條，沒有這一組。它們留在這裡是因為來源把它們掛在 `FR-008E`／`FR-008F`——也就是掛在**這個入口**交出去的範圍上，而不是任務列表那一頁。任務列表那一側要不要也寫一份，由 Issue #140 追蹤；在那之前**不要**因為「那是別頁的事」把這三條刪掉

### 審核員任務列的摘要數字從哪裡來

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

這一節是整頁最嚴的一段，因為同一組數字在兩個畫面上都看得到。

1. 審核員任務列的**審查摘要與進度條**，一律由**審核單位的狀態即時推導**
2. **不得取用任何預先組好的顯示字串**；任務的種子資料也不得再帶摘要字串
3. 推導的公式**只有一份來源**，就是[規格 04-01 §審核員的任務摘要](../04-annotation/01-annotation-list.mdx#審核員的任務摘要)；**這一頁不自己重算，也不維護第二套**
4. 顯示的文字也只有一份來源，就是[規格 04-01 §每個數字都要寫出計數主體與分母](../04-annotation/01-annotation-list.mdx#每個數字都要寫出計數主體與分母)：寫成「任務覆蓋 〈已離開待審的單位數〉 / 〈總單位數〉 個審核單位」，其後依序附加「待審 N 個」、「爭議中 N 個」（**各自只在大於 0 時顯示**）與一致性指標
5. 這一頁的任務卡與標記清單的任務資訊卡**顯示同一個字串**，不是兩套相似的寫法
6. **不得**用不帶分母的「審核覆蓋率 N%」或沒有主體的「進度 N%」當**摘要文字**——百分比把分母藏起來，那正是讓「100%」看起來像任務已完成的成因。這條禁止**只及於摘要那一行**，不含進度條自己的覆蓋率標題（畫面文字 `審核覆蓋` 加百分比）：那一行是進度條的標籤，和帶分母的摘要並存，**不要因為第 6 條把它刪掉**
7. 進度條的長度取**審核覆蓋率**；排序也用同一個數值（見[§任務列的排序](#任務列的排序)）
8. **審核覆蓋率不等於完成率**：它衡量「已經離開待審的單位比例」，到 100% 不代表任務完成
9. 覆蓋率已經 100% 而仍有未定稿或爭議單位時 → 摘要**必須把那件事揭露出來**，不得只呈現「待審 0」與「100%」讓人讀成任務已完結
    1. 揭露的方式就是第 4 條那個字串裡的「待審 N 個」與「爭議中 N 個」（各自只在大於 0 時顯示），**字串裡不另外並列一個「未定稿 N 個」**——依[規格 04-01 §每個數字都要寫出計數主體與分母](../04-annotation/01-annotation-list.mdx#每個數字都要寫出計數主體與分母)第 50 條，在它的三狀態模型下「未定稿」恆等於「待審加爭議中」，並列會誘導讀者把它們相加
    2. 但本頁來源的 `FR-011E` 原本要求的是「審核覆蓋率 100% · 未定稿 N 筆 · 爭議 N 筆」，而且它的狀態模型**不只三種**。兩邊對不上，見[§待釐清](#待釐清) Q15；在那一題定案前，本頁照上一小條（也就是共用那個字串的現況）
10. **全部**審核員任務列都照這幾條走，**不得用任務名單分流**
11. 「這個任務還沒有任何人審核過」**不是例外**：它的推導結果是「全部待審、覆蓋 0%」，那本身就是一個講得清楚的真實狀態
12. 審核員在工作區改了某個審核單位的狀態後回到這一頁 → 摘要與進度條**立刻反映新狀態**，重新整理後也一致
13. 摘要最後那一項是 :ref[IAA]{id="term.iaa"}；[規格 04-01](../04-annotation/01-annotation-list.mdx#每個數字都要寫出計數主體與分母)在摘要的語境裡稱它「一致性指標」，本頁沿用同一個說法。它分**三種狀態**，不得互相取代：

| 狀況 | 顯示 |
| :--- | :--- |
| 算得出係數 | 以**兩位小數**呈現 |
| 這個任務的輸出類型算得出這個指標，但資料還不足（例如還沒有提交）| `IAA 無法計算` |
| 這個任務的輸出類型**本來就不適用**這個指標 | 摘要**完全不提**這個指標 |

14. 第 13 條中間那一列**不得用 `0.00` 代替**：`0.00` 的意思是「一致程度等同隨機」，不是「量不出來」
15. 第 13 條最後一列**不得顯示「無法計算」**：那句話等於宣稱曾經試著量，而這種任務根本沒有這項量測
16. 一致性指標依據哪一個輸出類型來量，取自**那個任務自己的輸出類型**，不得逐筆任務個別指定

- 第 5 條是這一節存在的理由：使用者會在儀表板看一個數字、點進標記清單再看一次，兩邊不同就等於兩邊都不可信
- 第 6 條與第 8 條是同一件事的兩面——先把百分比的語意講清楚（第 8 條），再禁止只用百分比呈現（第 6 條）

### 「快速審核」要開哪一個審核單位

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. `快速審核` 的目標必須是**這個審核員下一個可處理的審核單位**
2. **不得**取用任務種子裡預先指定的固定樣本
3. 選哪一個的規則與優先序**只有一份來源**，就是[規格 04-01 §沒有可處理的審核單位](../04-annotation/01-annotation-list.mdx#沒有可處理的審核單位)；這一頁不自己重算
4. 候選的列舉範圍與[§審核員任務列的摘要數字從哪裡來](#審核員任務列的摘要數字從哪裡來)的計數**用同一份**，所以按鈕開出來的東西不會和它旁邊的「待審 N 個」互相矛盾
5. 前往工作區時要**完整帶出五項**：任務、樣本、標記員身分、審核員身分與標記階段
6. 第 5 條的「標記員身分」是必要項，因為審核單位的粒度**含標記員**——同一筆樣本的不同標記員是不同的審核單位
7. 推導結果是**空的**時候 → 前往那個任務的標記清單，**不指定某一筆**，並顯示明確的空狀態說明
8. 第 7 條**不得**退回去開任務的第一筆，**也不得**開任何已定稿的唯讀單位
9. 推導不出來時按鈕**照樣可見可按**，不是把按鈕關掉
10. **全部**審核員任務列都照這幾條走，**不得用任務名單分流**

- 第 8 條是來源 v2.7.0 的修訂重點：這個按鈕原本固定開任務的第一筆，結果在大多數任務上開到的是一個已定稿、只能看不能動的單位，審核員還要自己去找真正的待辦
- 第 9 條和第 7 條合起來的意思是：按鈕不會「看起來壞掉」，它會把人帶到清單並說明為什麼沒事可做

### 審核概況那三張卡是示範值

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. 審核員版面**上方**那三張總覽指標卡（`待審總數`／`今日已審核`／`IAA 摘要`）是**示範用的靜態值**，**不**由審核單位狀態推導，也不隨審核動作更新
2. 畫面上必須用**看得見的文字**明示這件事，而且這行字要和那三張卡在同一個區塊裡
3. 畫面上的那行字是 `示範用靜態值：這三張指標卡不由審核單位狀態推導，不會隨審核動作更新。`
4. 只把這件事放在滑過才看得到的提示或輔助技術的屬性裡**不算數**——會誤讀的是**一般用眼睛看的人**
5. 這行字要**隨語言切換**
6. 這個標示**只出現在審核員版面**；系統管理員與專案負責人的指標卡**不得**被標成示範值
7. 這一條**不改動**那三張卡的標籤文字與數值本身
8. 同一個畫面上，**下方**的任務列摘要一律推導（見[§審核員任務列的摘要數字從哪裡來](#審核員任務列的摘要數字從哪裡來)），**上方**三張卡不推導——這個差異是**刻意的**，不是漏掉

- 第 8 條是這一節的全部理由：一個畫面上有兩種來源的數字，下面的會動、上面的不會動，而讀者沒有辦法分辨。來源的處理方式不是硬把上面三張也推導出來（那需要先定義「待審總數」的分母、「今日」依據哪個時間、跨任務的一致性指標怎麼合成，這三件都還沒定），而是**先誠實標示現況**
- 系統管理員與專案負責人的指標卡也是寫死的值，但來源明寫它們「不在本條範圍，其資料來源另行處理」——也就是沒有定。這一題在[§待釐清](#待釐清) Q4

### 任務列的排序

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. 標記員與審核員的任務列表**上方都有一個排序選單**
2. 選單至少提供三個選項：**預設順序**、**由高到低**、**由低到高**
3. 選了之後清單**立刻**依所選的值重新排序；選回「預設順序」會還原原本的清單順序
4. 排序**不影響**任務列的任何欄位、按鈕與導頁行為——排完之後點哪一列，還是進那一列的任務
5. 排序依據的數值是：

| 版面 | 排的是什麼 |
| :--- | :--- |
| 標記員 | 完成率 |
| 審核員 | **審核覆蓋率**（見[§審核員任務列的摘要數字從哪裡來](#審核員任務列的摘要數字從哪裡來)第 7 條） |

6. 切換語言時，排序選單的標籤與每個選項的文字**立刻一起換**
7. 目前**只有這一種排序鍵**。來源寫明理由：資料模型沒有提供「最後提交時間」或「待審筆數」這類獨立的數值欄位，為了不發明沒有授權的資料欄位，這一版只做依進度排序

- 第 7 條值得留著：它是一個「刻意只做一半」的決定，而且理由不是技術困難，是不想憑空生出資料欄位
- 畫面上標記員那邊的選單文字是 `排序`／`預設順序`／`進度：高到低`／`進度：低到高`，審核員那邊是 `依審核覆蓋率排序`／`預設順序`／`審核覆蓋率：高到低`／`審核覆蓋率：低到高`。來源兩邊都寫「進度」，所以**審核員那邊的文字兩邊不一致**。這一題在[§待釐清](#待釐清) Q3

### 輸出類型標籤

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

四種有任務角色的版面，任務列上都有這組標籤。

1. 依任務設定的**原始順序**，每一種 :ref[輸出類型]{id="term.output-type"} 各顯示**一個唯讀標籤**；一個任務有幾種就顯示幾個
2. 複合的任務**不得只顯示第一種**，也**不得**合成一個自訂的任務類型名稱
3. 標籤的合法值就是平台的**八種**輸出類型：:ref[單一標籤]{id="term.single-label"}、:ref[多標籤]{id="term.multi-label"}、:ref[單維度]{id="term.single-dim"}、:ref[多維度]{id="term.multi-dim"}、:ref[序列標註]{id="term.sequence-tagging"}、:ref[實體辨識]{id="term.entity-recognition"}、:ref[關係識別]{id="term.relation-identification"}、:ref[自由文字]{id="term.free-text"}
4. 這八個名字**不是這一頁定的**：定名頁是[規格 03-02 新增任務](../03-task-management/02-task-new.mdx)，這一頁只引用術語表
5. 整組標籤要能被當成**一份完整的清單**讀出來（例如「輸出類型：實體辨識、關係識別」），讓不看畫面的人也知道這個任務有幾種、是哪幾種
6. 標籤用**看得見的文字**表達型別，**不得只靠顏色**傳達
7. 切換語言時，**每一個**標籤的文字都要換，標籤的輔助說明也要換

- 第 1 條和[規格 03-01 §任務列的欄位](../03-task-management/01-task-list.mdx#任務列的欄位)第 2 條是同一條規則，兩頁必須一致
- 這個名詞原本規格寫「輸出型別」、畫面寫「輸出類型」兩種並存；維護者 2026-11-06 裁定一律用**輸出類型**（Issue #131），所以本頁與畫面、術語表三邊現在同一個名字

### 示例資料只是驗收基線，不是白名單

1. prototype 裡的那組示例任務**只是走查用的驗收基線**

3. 在示例之外再加入**任何一個合法的輸出類型組合**，並給使用者對應的成員身分 → 相應的版面**必須直接呈現得出來，不需要為它新增分支**

5. 正式系統**仍然只呈現**登入者成員身分範圍內的任務摘要（見[§「查看全部」去哪裡、看得到誰的任務](#查看全部去哪裡看得到誰的任務)）

- 所以這一頁刻意**不列出**那 16 筆的任務名稱與編號。它們是走查資料，不是需求（見[§已確認決議](#已確認決議) Q14）

### 這一頁看不到標準答案

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

儀表板是標記員每天登入後的第一頁，所以它的資料邊界要寫死。

1. 這一頁**只能用**任務名稱、輸出類型、標記階段、任務狀態、角色摘要與進度這類**安全的概要資訊**
2. 這一頁**不得**讀取、顯示、留存或送出:ref[標準答案]{id="term.ground-truth"}、參考答案、測試集或任何等價的答案內容
3. 第 2 條涵蓋**標記員在這一頁能接觸到的任何地方**——畫面上看得到的、頁面背後帶著的、以及這一頁交給下一頁的東西
4. 任務摘要裡的任何數字都**不得**由答案內容推導出來

- 這是 `AGENTS.md` 的硬性規則之一（測試集答案不得外洩），也是 PRD §權限矩陣 的附註之一
- 系統端**怎麼**做到不寫在這裡，留給後續的技術規劃

### 任務列表沒有任務時

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. 標記員或審核員的任務列表**一個任務都沒有**時 → 顯示一句說明文字，畫面上是 `目前沒有進行中的任務`
2. 這種情況**不是錯誤**，不顯示錯誤樣式，也不提供重試

- 這一節**來源沒有寫**：來源只定了「最近提醒為空」與「審核員沒有可處理項目」兩種空狀態。任務列表為空這一種是**畫面上有、來源沒有**，所以照畫面記下來，並在[§待釐清](#待釐清) Q6 問它是不是正式需求
- 它和「沒有任何任務角色」不是同一件事：沒有任務角色的人看到的是三張行動入口卡，根本不會有任務列表區塊

### 導覽、語言與登出不在這一頁

1. 側欄導覽、使用者資訊區塊（頭像、名稱、角色標示）與**登出**，規則都在[規格 07-01 側欄導覽](../07-shared/01-sidebar.mdx)，這一頁只是**使用**它
2. **語言切換**也在規格 07-01：切換不需重新載入頁面，而且會**記住**——使用者離開到別的頁面再回來，語言保持不變
3. 這一頁要負責的只有一件事：**自己的內容也要跟著換語言**，不能只換側欄（見規格 07-01 [§語言切換](../07-shared/01-sidebar.mdx#語言切換)第 2 條）
4. 窄螢幕上導覽從側欄變成「上方品牌列＋下方主導覽」，品牌列上的語言切換與登出也在規格 07-01；這一頁只要確保**自己的內容不被導覽遮住**
5. 某個文字缺少目前語言的翻譯時 → 保留原本看得到的文字，**不中斷頁面互動**

- 把這些集中寫在 07-01 是刻意的：它們在每一頁都一樣，寫在每一頁就會開始各自漂移
- 第 5 條的「不中斷互動」是這一頁自己要守的：缺一個字不該讓整個版面壞掉

### 在窄螢幕上的呈現

<PrototypeFrame page="dashboard/dashboard" caption="儀表板" client:idle />

1. 這一頁在手機、平板與桌機上都要能用，任何寬度下**都不需要左右滑動**
2. 螢幕較窄時，系統管理員的 `平台使用者統計` 與 `任務概況`、專案負責人的 `任務概況` 的指標卡 → **優先排成兩欄**，不得退化成一張一張直向堆疊

7. 每個控制項都能用鍵盤操作，使用者看得出目前焦點在哪裡

- 具體的螢幕寬度分界、尺寸與間距**以 prototype 為準，不寫進規格**（同[規格 07-01 §不同螢幕寬度的呈現](../07-shared/01-sidebar.mdx#不同螢幕寬度的呈現)的做法）
- 第 2 條和第 6 條看起來都在講指標卡，但問的是相反的事：第 2 條防「太窄的時候排得太鬆」，第 6 條防「空間夠的時候排得太擠」

## 卡控機制

| 條件 | 結果 |
| :--- | :--- |
| 系統角色不在允許清單裡（不存在、是空的、或是別的值） | 導向登入頁 |
| 使用者沒有登入 | 依[規格 01-05](../01-account/05-login-state.mdx)導向登入頁 |
| 平台成員進入這一頁 | 只拿到**自己有參與**的任務；沒有參與的任務連名稱都看不到 |
| 系統管理員進入這一頁 | 拿到全平台的統計與任務列表；**不讀**任務角色、也不顯示任務角色的版面 |
| 讀取任務角色還沒回來 | 顯示骨架佔位；**不得**出現空白頁或沒有樣式的裸畫面 |
| 讀取任務角色失敗（伺服器錯誤或逾時） | 結束骨架，顯示錯誤說明與重試入口 |
| 讀取任務角色失敗 | **不得**改成顯示「還沒有任務角色」的版面 |
| 讀取任務角色失敗 | **不得**清掉登入狀態 |
| 讀取任務角色失敗 | **不得**導向登入頁 |
| 使用者同時有多種任務角色 | 只顯示一種版面，依專案負責人 > 審核員 > 標記員的優先序 |
| 系統管理員按 `查看全部` | 任務列表顯示全平台任務 |
| 平台成員按 `查看全部` | 任務列表只顯示他有參與的任務，**不得**切換成全平台視角 |
| 當前身分不是系統管理員，但網址上帶了看起來像管理員的參數 | **只**依他自己的有效成員身分回應，**不得**因為那個參數放大範圍 |
| 要取得全平台範圍 | **只能**依伺服器端認定的當前身分加權限矩陣那一格；**不得**來自網址參數、瀏覽器存的值或任何前端狀態 |
| 任務的可見範圍 | **不得**依任務名稱或輸出類型決定 |
| `最近提醒` 一筆都沒有 | 顯示佔位文字，**不得**只留一塊空白 |
| 標記員或審核員的任務列表一個任務都沒有 | 顯示說明文字，不顯示錯誤樣式 |
| 標記員按 `快速繼續`，任務還有沒提交的資料 | 進工作區，帶任務、標記員身分與**第一筆沒提交**的資料 |
| 標記員按 `快速繼續`，任務的資料全部已提交 | 改進那個任務的標記清單，**不指定某一筆**；按鈕**仍然可見可按** |
| 審核員按 `快速審核` | 目標由審核單位狀態與他本人身分推導；**不得**取用預先指定的固定樣本 |
| 審核員按 `快速審核`，推導結果是空的 | 改進標記清單（不指定某一筆）並顯示空狀態；按鈕**仍然可見可按** |
| 審核員按 `快速審核`，推導結果是空的 | **不得**開任務的第一筆，**不得**開任何已定稿的唯讀單位 |
| 點任務列上快速按鈕以外的地方 | 進**那一列**任務的標記清單，帶任務、他的角色、標記階段與清單樣式資訊 |
| 帶給下一頁的「清單樣式資訊」 | **不得**由輸出類型推導，**不得**取輸出類型的第一項 |
| 兩個任務的輸出類型相同或清單樣式相同 | **不得**把它們的導頁上下文合在一起 |
| 任務有多種輸出類型 | 每一種各一個標籤，依原始順序；**不得**只顯示第一種或合成一個名字 |
| 欄寬不夠放完所有標籤 | **換行**；不得截斷、重疊或讓頁面需要左右滑動 |
| 審核員任務列要顯示摘要 | 一律由審核單位狀態即時推導；**不得**取用預先組好的字串 |
| 審核員任務列的摘要文字 | 必須帶分母；**不得**用不帶分母的「審核覆蓋率 N%」或「進度 N%」 |
| 審核覆蓋率 100% 但仍有未定稿或爭議單位 | 必須揭露爭議中的筆數，且那個任務**不得**顯示成已完成；字串裡不另列「未定稿 N 個」 |
| 一致性指標算不出係數但這個型別算得出 | 顯示「無法計算」，**不得**用 `0.00` 代替 |
| 一致性指標對這個型別本來就不適用 | 摘要**完全不提**它，**不得**顯示「無法計算」 |
| 審核員版面上方那三張總覽卡 | 必須有**看得見的文字**標示它們是示範值；只放在輔助屬性裡不算 |
| 系統管理員或專案負責人的指標卡 | **不得**被標成示範值 |
| 這一頁要用的資料 | 只能是安全的概要資訊；**不得**讀取、顯示、留存或送出標準答案與測試集 |
| 排序之後 | 任務列的欄位、按鈕與導頁行為**都不改變** |
| 某個文字缺少目前語言的翻譯 | 保留原本看得到的文字，**不中斷**頁面互動 |
| 示例之外新增一個合法的輸出類型組合並給了成員身分 | 相應版面**必須直接呈現得出來**，不得為它新增分支 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到 |
| :--- | :--- |
| 系統角色是空的或是未知的值 | 被帶到登入頁 |
| 平台成員一個任務角色都沒有 | 三張行動入口卡，而不是一個空的任務列表 |
| 平台成員同時是專案負責人與標記員 | 只有專案負責人版面；他的標記待辦**不在這一頁**，要從側欄進標記作業 |
| 平台成員同時是審核員與標記員 | 只有審核員版面 |
| 讀取任務角色很慢 | 骨架佔位；頁面結構看得見，資料位置是灰色塊 |
| 讀取任務角色失敗 | `儀表板載入失敗`、`無法載入任務成員資格資料，請稍後再試。` 與 `重試`；**仍然是登入狀態** |
| 讀取失敗後按重試又失敗 | 同一個錯誤畫面，重試入口還在 |
| 骨架用的佈局和最後的版面不一樣（例如最後是行動入口卡） | 直接換成正確的佈局；中間的視覺差異是可接受的 |
| 系統管理員的 `最近提醒` 一筆都沒有 | 一句佔位文字（來源指定 `目前沒有提醒`，畫面未實作），不是一塊空白 |
| 標記員的任務列表一個任務都沒有 | 一句 `目前沒有進行中的任務`；不是錯誤畫面 |
| 審核員的任務列表一個任務都沒有 | 同上一列 |
| 標記員的某個任務資料全部已提交 | `快速繼續` 還在、還能按；按下去到那個任務的標記清單，讓他自己看狀態 |
| 審核員的某個任務對他沒有任何可處理的單位 | `快速審核` 還在、還能按；按下去到標記清單並說明目前沒有可處理項目 |
| 審核員的某個任務還沒有任何人審核過 | 摘要照樣推導：全部待審、覆蓋 0%；**不是**空狀態，也不退回示範值 |
| 審核員的某個任務覆蓋率 100%，但還有未定稿與爭議單位 | 摘要寫出「爭議中 N 個」，那個任務不顯示成已完成；摘要裡沒有另一項「未定稿 N 個」 |
| 審核員的某個任務算不出一致性指標（還沒有提交） | 摘要寫 `IAA 無法計算` |
| 審核員的某個任務的輸出類型不適用一致性指標 | 摘要**完全不提**一致性指標 |
| 任務有兩種以上輸出類型 | 每一種各一個標籤，依原始順序排；不會被合併成一個名字 |
| 兩個任務的輸出類型組合完全一樣 | 兩列各自獨立；點哪一列就進哪一個任務 |
| 示例之外新增一個合法的輸出類型組合 | 相應版面直接呈現得出來，不需要為它改畫面 |
| 任務列的標籤多到放不下 | 在卡片裡換行；不截斷、不重疊、不需要左右滑動 |
| 使用者在窄螢幕看系統管理員版面 | 指標卡兩欄排列；任務列上下堆疊 |
| 使用者在寬螢幕把側欄收起來 | 指標卡維持可讀寬度；`等待 IAA 確認` 這種長標籤不被壓成窄欄 |
| 使用者切換語言 | 頁首、區塊標題、指標標籤、任務摘要、按鈕、徽章與排序選單一起換；不需要重新載入 |
| 使用者切換語言後去別的頁面再回來 | 語言保持不變（規則在規格 07-01） |
| 某個文字缺少目前語言的翻譯 | 那一處保留原本的字，其餘照常切換，頁面照常可用 |
| 使用者只用鍵盤操作 `等待 IAA 確認` 那張卡 | 可以移到它上面並按 Enter 或空白鍵觸發 |
| 系統管理員的 `等待 IAA 確認` 顯示 0 | 卡片照樣是入口；點進去是一個套了篩選、結果為空的任務列表 |
| 專案負責人與系統管理員同時看 `總任務` | 兩個數**可以不一樣**：一個數自己參與的，一個數全平台 |

| :--- | :--- | :--- | :--- |

| 頁首在每一種版面都顯示 | 任一登入者 | 依序切換到各種版面 | 每一種版面最上方都有 `儀表板` 與 `掌握任務進度與團隊協作狀態` |
| 讀取任務角色時顯示骨架 | 平台成員剛進入儀表板，任務角色還沒讀完 | 查看畫面 | 頁面結構看得見，資料位置是灰色佔位塊；沒有空白頁，也沒有沒有樣式的裸畫面 |
| 讀完無縫換成實際內容 | 骨架正在顯示 | 任務角色讀取完成 | 直接換成對應版面的實際內容，中間沒有空白閃動 |

| 讀取失敗顯示錯誤與重試 | 平台成員進入儀表板，讀取任務角色逾時或回傳伺服器錯誤 | 查看畫面 | 骨架結束，顯示 `儀表板載入失敗`、`無法載入任務成員資格資料，請稍後再試。` 與 `重試` |

| 讀取失敗不清掉登入狀態 | 同上 | 查看畫面並重新整理 | 仍然是登入狀態，沒有被帶到登入頁 |
| 重試後再失敗仍留在錯誤畫面 | 錯誤畫面已顯示 | 按 `重試` 而後端仍失敗 | 仍是同一個錯誤畫面，`重試` 還在 |
| 行動入口卡文案與步驟 | 位於三張行動入口卡的版面 | 檢視三張卡 | 卡片依序是 `建立標記專案`、`進行資料標記`、`進行標記審核`，按鈕依序是 `開始建立任務`、`開始標記`、`開始審核` |
| 行動入口卡切換語言 | 位於三張行動入口卡的版面 | 切換語言 | 區塊標題與副標、三張卡的標題／說明／按鈕與每一步的說明文字一起換 |

### Q15. 審核單位有幾種狀態？「未定稿」要不要寫進摘要字串？

- [ ] 照共用字串的現況：三種狀態（待審／爭議中／已定稿），摘要不另列「未定稿 N 個」
- [ ] 照本頁來源 `FR-011E`：狀態不只三種，摘要要並列「未定稿 N 筆」
- [ ] 其他（請說明）

> 建議：**不選邊**，因為兩邊不只是用字不同，是**狀態模型不同**。
>
> [規格 04-01](../04-annotation/01-annotation-list.mdx#每個數字都要寫出計數主體與分母)的模型只有**三種**狀態，它的第 50 條因此說「未定稿」恆等於「待審加爭議中」、並列會誘導讀者相加，第 55 條也寫「三個狀態裡只有已定稿是終態」。在那個模型裡不列「未定稿」是對的，因為它沒有新資訊。
>
> 但本頁來源的 `FR-011E` 舉的例子是 `finalized 2／approved 1／modified 1／disputed 1`，並據此寫出「未定稿 3、爭議 1」——**那是五種狀態**，而且在那個模型裡「未定稿」(3) **不等於**「待審(0) 加爭議(1)」。也就是說：如果狀態真的有五種，那麼只寫「爭議中 1 個」就**漏掉了 approved 與 modified 那兩個還沒定稿的單位**，而這正是 `FR-011E` 原本要防的誤讀。
>
> 另一個相關事實：來源 `FR-022` 的 **v2.11.1 修訂**（issue #627 第 7 項）把摘要裡的「未達定稿門檻 N 個」一項刪掉了，理由是它的唯一來源在對應版本刪了那一點。所以來源自己的兩條在不同時間往不同方向走。
>
> **這一題要先定狀態模型，文案才定得出來。** 它牽動[規格 04-01](../04-annotation/01-annotation-list.mdx) 與 04-02，不是這一頁單獨能決定的。

> 需要決定的人：維護者（與 04-01、04-02 一併決定）

## Q&A

### Q. 為什麼同時是專案負責人和標記員的人，在儀表板上看不到自己的標記待辦？

因為來源把它定成「**一種**主視圖」，不是「把有的角色都拼上去」（見[§已確認決議](#已確認決議) Q9）。

這個選擇的好處是每種版面都講一件事，使用者不必在一頁裡分辨哪個區塊是給哪個身分看的；代價就是兼任的人在這一頁只看到優先序最高的那一種。他要標記得從側欄進標記作業。

值不值得是個產品判斷，而來源已經判斷過了，所以這一頁照它寫。

### Q. 為什麼帶給下一頁的「清單樣式資訊」不能由輸出類型推導？

因為它們是兩件不同的事，只是現在剛好常常對得上。

輸出類型講的是「這個任務要產出什麼」，一個任務可以有好幾種。清單樣式資訊講的是「標記清單那一頁要用哪一種排版」，一個任務只有一個。來源把後者稱為「過渡性的相容欄位」——它存在是因為標記作業那兩頁還沒改成讀輸出類型。

如果儀表板自己從輸出類型去猜它，一個有兩種輸出類型的任務就會猜錯，而且錯的方式很隱蔽：使用者點進去看到的是一個可以用、但不完整的清單。所以來源把它寫成禁止，而不是「建議」。

### Q. 為什麼「審核覆蓋率 100%」不等於任務做完了？

因為覆蓋率數的是「**離開待審**的單位比例」，而離開待審有好幾種去處：已定稿、已通過、已修正、爭議中。只有「已定稿」是終點。

所以一個任務可以每一個單位都被審過一次（覆蓋率 100%），卻還有三個停在未定稿、其中一個還在爭議中。這種時候只顯示「待審 0」和「100%」，讀的人會以為可以收工了。

這就是來源為什麼先規定覆蓋率滿百時必須把那件事揭露出來（[§審核員任務列的摘要數字從哪裡來](#審核員任務列的摘要數字從哪裡來)第 9 條），然後更進一步禁止用不帶分母的百分比當摘要（同節第 6 條）。

揭露的**方式**則是另一回事：共用的那個字串靠「爭議中 N 個」把它講出來，不另外並列一個「未定稿 N 個」（第 9 條的第 1 小條）。本頁來源原本要求並列，兩邊的狀態模型對不上，所以那一點留在[§待釐清](#待釐清) Q15。

### Q. 為什麼審核員上方三張卡是示範值，下方任務列的數字卻是真的？

因為下方的算得出來，上方的還不知道怎麼算。

下方每一列是**一個任務**的數字，審核單位列舉得出來，公式就定得出來。上方三張是**跨任務**的彙總，而彙總需要先回答三個還沒答案的問題：`待審總數` 的分母是什麼、「今日」從哪一刻起算、不同任務的一致性指標要怎麼合成一個數。

來源的處理方式不是硬湊一個公式，也不是把那三張卡拿掉，而是**先誠實標示現況**——並且特別要求那行字要**看得見**，不能只放在滑過才出現的提示裡，因為會誤讀的是用眼睛看的人。

這是這一頁最值得學的一條：在「假裝有」和「拿掉」之間，還有「標示清楚它現在是什麼」。
