# 業務流程圖寫法

規格書的業務流程圖是**泳道圖＋逐步走查**，目的是讓相關人員在動工前看懂「這件事從誰開始、經過誰、在哪裡分岔、結束在哪」。
它不是系統流程圖：不畫系統內部怎麼處理，只畫角色做了什麼、系統回應了什麼（使用者看得到的部分）。

每份流程圖都從同一份骨架開始，**外殼、圖形與走查機制固定，只換流程資料**，不同規格的流程圖看起來是同一套。
樣式另依 `.claude/rules/notecraft-visualize.md`（改到 `docs/**` 時自動載入）。章節文字的寫法見 [writing-guide.md](writing-guide.md) 的「業務流程」。

## 放在哪

- 「業務流程」章節的開頭放**一張流程圖**，一份規格一張
- 章節裡的每段業務流程是圖上的一個「流程」tab，不另外拆圖
- 章節寫「不適用」時不放流程圖

## 骨架

參考實作：[flow-skeleton.tsx](flow-skeleton.tsx)（範例內容是規格 01-01 客戶聯絡紀錄）。

1. 整份複製到 `.notecraft/components/spec-<模組編號>-<頁面編號>-<主題>-flow.tsx`
2. **【骨架】一字不改**：色票、幾何、圖形、連線路由、外殼、走查卡片、圖例
3. **【流程】整段換掉**：`FLOWS` 與 default export 的名稱
4. 骨架少了這份規格需要的圖形或機制時，先停下來問使用者，同意後改骨架參考檔，再複製；不要只在單一流程圖裡加

生成元件不能互相 import，所以用複製，不抽共用元件。

### 外殼（固定）

| 區域 | 內容 |
| :--- | :--- |
| 控制列（上方，依序） | 流程 tab（每段業務流程一個）、「逐步走查」 |
| 觸發與結果 | 一行小字，取自章節的「觸發」「結果」 |
| 泳道圖 | 左側泳道名稱，由上而下是角色、系統；窄螢幕時只有圖在框內橫向捲動，頁面不捲動 |
| 走查卡片（圖下方） | 規格步驟代號、標題、說明、「對應：」Scenario、進度點、「上一步」「下一步／完成」 |
| 圖例（下方） | 角色操作、系統回應、判斷、例外／替代流程、結束 |

- 沒有走查時全部節點正常顯示，卡片顯示操作提示
- 走查時，這一步的節點與連線亮起（藍框、線加粗），其餘變淡
- 點擊節點跳到第一個亮起它的步驟；切換流程 tab 會結束走查

### 圖形詞彙

流程圖只用以下圖形，不用其他 BPMN 符號（訊息事件、計時器、平行閘道等）。

| 圖形 | `kind`／欄位 | 用途 | 文字 |
| :--- | :--- | :--- | :--- |
| 實心小圓 | `start` | 流程起點，一段流程一個，畫在觸發者的泳道 | 無 |
| 藍色圓角框 | `action` | 角色的操作 | 動詞開頭，例：「點「儲存」」「填寫日期」 |
| 白色圓角框 | `system` | 系統的回應（使用者看得到的） | 結果，例：「顯示確認視窗」「已新增」 |
| 菱形 | `decision` | 判斷：卡控、角色的選擇、資料狀態 | 問句，以「？」結尾 |
| 粗框 | `end: true` | 流程在這裡結束；每條路徑都要走到一個結束節點，或接回主流程 | — |
| 黃色框 | `exception: true` | 只有例外或替代流程會走到的節點 | — |
| 灰色實線 | 一般連線 | 主流程 | 判斷出口寫「是」「否」 |
| 黃色虛線 | `exception: true` | 例外或替代流程，包含「回到第 N 步」的回頭線 | 判斷出口寫「是」「否」 |

**文字長度**：操作與回應最多兩行、每行 6 個字以內；判斷最多兩行、每行 4 個字以內。放不下就縮短，細節寫在走查卡片。

### 泳道

- 一個角色一條泳道，名稱與「使用角色」章節一致；系統回應放在「系統」泳道
- 兩個角色做同一件事時可以共用一條泳道，名稱寫「角色 A或角色 B」；超過 5 個字時骨架會自動換行（優先在「或」「、」「／」之後斷開）
- 2–4 條；只有一個角色＋系統時是 2 條
- 由上而下：觸發流程的角色 → 系統 → 其他角色（接手、收到結果的人）
- 「系統」只寫使用者看得到的回應（顯示、通知、儲存成功），不寫系統內部怎麼處理

### 版面

- 節點用 `lane`（泳道）×`col`（欄）指定位置，主流程由左而右，一個步驟一欄
- 每段流程**最多 8 個節點**（不含開始點）、最多 7 欄；超過時拆成兩段流程（例：「送審」「審核」），或把細節留在規格大項
- 開始點的 `col` 寫 `0`，骨架會畫在第 0 欄左側
- 判斷的「是」通常往右（繼續主流程），「否」往上、往下或往回

### 連線

骨架依兩個節點的位置自動決定出口與入口：

| 位置 | 自動路線 |
| :--- | :--- |
| 同一泳道、往右 | 右出、左進，直線 |
| 同一欄、不同泳道 | 下出上進（或上出下進），直線 |
| 不同泳道、不同欄 | 右出，進到目標的上緣（目標在下方）或下緣（目標在上方） |
| 同一泳道、往左（回頭線） | 下出下進；通常要自己指定 |

自動路線會穿過其他節點、或和其他連線重疊時，用三個欄位調整：

- `exit`／`enter`：指定出口與入口側（`left`、`right`、`top`、`bottom`）
- `via`：折線經過的座標。兩端都水平進出時是轉折的 x，兩端都垂直進出時是轉折的 y；用骨架的 `laneTop(n)`、`laneBottom(n)`、`colX(n)` 計算，例：`via: laneTop(0) + 12` 走第一條泳道的上緣

常見寫法（見範例）：

- 例外回到同一泳道前面的步驟：`exit: "top", enter: "top", via: laneTop(泳道) + 12`，從上緣繞回
- 判斷的「否」回到上一條泳道的步驟：`exit: "left", enter: "bottom"`
- 兩個結束節點在同一泳道：`exit: "bottom", enter: "bottom", via: laneBottom(泳道) - 8`，從下緣繞過去

## 逐步走查

### 涵蓋規則

- **每段業務流程一個流程 tab**，`label` 與章節的粗體標題完全一致
- 走查步驟依序涵蓋：
  - 主流程的每一步
  - 每個替代流程（A1、A2…）與例外流程（E1、E2…）各至少一步
  - 最後一步是「結果」：流程結束時誰看到什麼
- 每段 4–10 步

### 每一步的寫法

| 欄位 | 寫法 |
| :--- | :--- |
| `title` | 這一步發生什麼；替代與例外用「替代：」「例外：」開頭 |
| `body` | 誰做了什麼、系統怎麼回應；文案用規格裡的實際文字 |
| `scenarios` | 對應的驗收 Scenario，**必須與規格「驗收標準」的 Scenario 欄完全一致**；純操作說明可以留空 |
| `ref` | 對應章節的步驟代號：`主流程 2`、`A1`、`E1`、`結果` |
| `highlight` | 這一步要亮起的節點與連線 id；包含走到這個節點的連線 |

- 例外步驟亮起「判斷節點＋例外連線＋回到的節點」，讓讀者看到從哪裡分出去、回到哪裡
- 每個節點都至少出現在一步的 `highlight`，不然點擊它沒有反應

## 樣式

- 只用骨架的色票：藍色標角色操作與亮起的步驟，黃色只標例外與替代流程
- 不畫 logo、圖示、插圖；節點裡只有文字
- **不出現技術資訊**：不寫 API、資料表、元件或框架名稱，系統節點只寫使用者看得到的結果

## 標記範本

```mdx
{/* @ai-visualize
id: spec-02-03-customer-approval-flow
type: motion
prompt: |
  骨架：.claude/skills/spec-writing/references/flow-skeleton.tsx（複製後只改【流程】）。
  核心洞察：{這個流程最重要的一件事，例：主管退回後業務要重新送審，不是重開一張}
  泳道：{角色 A、系統、角色 B}
  流程：
    {流程 1}：觸發 {…}；主流程 {步驟 → 步驟 → …}；A1 {…}；E1 {…}；結果 {…}
    {流程 2}：{…}
  走查對應：{每一步對應的 Scenario 名稱，依驗收標準}
caption: 切換流程看不同情境；選「逐步走查」依序看主流程、替代與例外流程
status: pending
*/}
```

- `id`：`spec-<模組編號>-<頁面編號>-<主題>-flow`，全站唯一，也是元件檔名
- `type` 一律 `motion`

## 自我檢查

- [ ] 【骨架】與參考檔一致（沒有改色票、幾何、圖形、路由、外殼）
- [ ] 每段業務流程都有一個流程 tab，`label` 與章節粗體標題一致
- [ ] 泳道名稱與「使用角色」一致，2–4 條；每段流程最多 8 個節點
- [ ] 每條路徑都走到結束節點，或用黃色虛線接回主流程；每個判斷都有「是」「否」兩個出口
- [ ] 主流程、每個替代與例外流程都出現在走查；`ref` 與章節的步驟代號一致
- [ ] 每一步的 `scenarios` 都能在驗收表找到完全相同的名稱
- [ ] 每個節點都至少在一步的 `highlight` 裡
- [ ] 連線沒有穿過其他節點，判斷出口的文字沒有壓到線或節點
- [ ] 窄螢幕（375px）頁面沒有橫向捲動（只有泳道圖在框內捲動）

## 生成之後

- `content-visualize` 會把標記改成 `status: generated`，並在下方寫入 `GeneratedFrame` 與 import
- 規格的業務流程有修改時，把標記改回 `status: pending` 並更新 prompt，再請 Claude「處理 `docs/specs/xx/yy.mdx` 的視覺化標記」
- 驗證：開 `pnpm docs:serve`（http://127.0.0.1:4330/） 實際切過每個流程 tab、走完每段走查；只改元件時 `pnpm exec notecraftapp build docs` 不會重新編譯，要靠預覽驗證
