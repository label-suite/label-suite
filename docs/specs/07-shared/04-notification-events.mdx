## 目標

- 讓「哪些事會通知人」只有一份清單，而不是側欄一份、儀表板一份——這正是 [02-01 Q5](../02-dashboard/01-dashboard.mdx#已確認決議) 與 [07-01 Q4](./01-sidebar.mdx#已確認決議) 各自把這件事推出去之後留下的缺口
- 讓 :ref[平台成員]{id="term.platform-member"}知道自己會因為什麼事被通知，而[規格 01-04 §通知設定](../01-account/04-profile.mdx#通知設定)讓他逐事件決定要不要收
- 讓 :ref[系統管理員]{id="term.system-admin"}在儀表板的「最近提醒」只看到與**全平台**有關的那些，不是每個人的個人事務

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

通知是系統產生的，沒有人能新增或編輯一則通知；使用者能做的是讀自己的、把自己的標為已讀，以及在[規格 01-04](../01-account/04-profile.mdx#通知設定)決定要不要收。

| 角色 | 這一頁能做什麼 | PRD §權限矩陣的上限 |
| :--- | :--- | :--- |
| :ref[平台成員]{id="term.platform-member"} | R (o)／E (o)（只有「標為已讀」這一種編輯） | 「07 共用介面」給平台成員 `R/E (o)` |
| :ref[系統管理員]{id="term.system-admin"} | R (o)／E (o) | 同一列給系統管理員 `R/E (o)` |
| :ref[Seeder 管理員]{id="term.seeder-admin"} | 與系統管理員相同 | 矩陣**沒有這一欄**；PRD §使用者角色 寫明他「權限同系統管理員」 |
| 未登入的訪客 | **無權限** | **對不到任何一列**：PRD §使用者角色 沒有「訪客」，§權限矩陣 的兩張表也沒有這一欄 |

- 系統管理員另外在儀表板看得到**全平台**那一組（[規格 02-01](../02-dashboard/01-dashboard.mdx)）。那不是 `(o)`，所以它騎的不是「07 共用介面」那一格，而是 PRD §權限矩陣「02 儀表板」給系統管理員的 `R`

PRD §權限矩陣 給「07 共用介面」的上限是 `R／E (o)`；這裡的 E (o) 只作用在使用者自己的已讀狀態，不碰任何業務資料。這就是[規格 07-01 §已確認決議](./01-sidebar.mdx#已確認決議) Q1 要的那個上限。

## 業務流程

**不適用**：這一頁定義的是一份清單與它的歸屬，不是一段操作流程。使用者怎麼看通知寫在[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)，怎麼調偏好寫在[規格 01-04 §規格 › 通知設定](../01-account/04-profile.mdx#通知設定)。

## 規格

### 這一頁定什麼、不定什麼

1. 這一頁定**平台層的通知事件清單**：有哪些事件、各自什麼時候發生、誰收得到，以及它出現在哪一個消費端
2. 這一頁**不定畫面**：側欄通知入口與清單的行為（未讀數量、`9+`、全部標為已讀、每一則顯示什麼）全部由[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)定義，本頁不重複也不覆寫
3. 這一頁**不定儀表板的區塊行為**：「最近提醒」每筆有標題與內容由[規格 02-01](../02-dashboard/01-dashboard.mdx) §規格 定義（來源 `FR-008C`），為空時顯示佔位文字由該頁[§已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q11 定義
4. 這一頁**不定使用者偏好**：哪些事件可以逐一開關、用站內還是電子郵件、預設值，由[規格 01-04 §規格 › 通知設定](../01-account/04-profile.mdx#通知設定)定義

### 查出哪些事會通知誰、出現在哪裡

同一份平台層的通知事件清單供兩個消費端使用：每個事件寫明什麼時候發生、出現在側欄的通知清單或儀表板的「最近提醒」（或兩邊）、誰收得到，以及每一則通知必備的資訊。

#### 兩個消費端

同一份清單有兩個去處，它們的讀者與範圍不同。

| 消費端 | 誰看得到 | 範圍 | 行為定義在 |
| :--- | :--- | :--- | :--- |
| 側欄的通知清單 | 每一個登入後的使用者，只看得到與自己有關的 | 與這個人有關的事件 | [規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知) |
| 儀表板的「最近提醒」 | 只有系統管理員版面有這個區塊 | **只取與全平台有關的那些**（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q5） | [規格 02-01](../02-dashboard/01-dashboard.mdx) |

- 同一個事件可以同時出現在兩邊，也可以只出現在一邊。**第 1 到 7 列只進側欄**（它們都是某一個人或某一個任務的事），**第 8 列兩邊都進**：側欄給該任務的專案負責人、儀表板給系統管理員（[§已確認決議](#已確認決議) Q2）
- <mark>**標題與內容只定形狀、不定字面**（Q8，維護者 2026-11-16）：標題就是[§規格 › 事件清單](#事件清單)那一欄的事件名稱，內容要說得出**是哪一筆**、以及**（有操作者時）是誰做的**；再往下的逐字文案由實作決定，本頁不發明</mark><sup>[#188](https://github.com/label-suite/label-suite/issues/188)</sup>
- 側欄那一則要顯示「發生了什麼事、相關的任務、是誰做的，以及多久以前發生」（[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)第 6 條），所以清單上每一個事件都要說得出這四件事——**例外**：系統自己產生、沒有操作者的事件（第 7、8 列）沒有「是誰做的」（[§已確認決議](#已確認決議) Q5）

#### 事件清單

這八個事件由維護者 2026-11-15 裁定全部收進清單（[§已確認決議](#已確認決議) Q1）。每一列都附出處，**沒有一列是本頁自己想出來的**。
<mark>「誰收得到」第 7、8 列出自 Q2 的裁定文字，第 1 到 6 列由 Q7 裁定（2026-11-16）</mark><sup>[#188](https://github.com/label-suite/label-suite/issues/188)</sup>：前四列是「有人完成了什麼」，通知擁有那個任務的專案負責人；第 5、6 列的事件名本身就寫著「**你**被分配…」，所以通知被指派的那個人。

- 第 8 列是這八列裡唯一**已經有既有消費路徑**的：02-01 的「最近提醒」寫死示例之一就是它（`IAA 已達 0.81，待確認後啟動`），而 05-02 已定案的條文把「從那個提醒點進來」寫成一個合法入口
- **這一列不替 IAA 加任何閘門語意**：[規格 05-02 §規格 › IAA 閘門的語意：顧問性，不阻擋](../05-dataset/02-analysis-detail.mdx#iaa-閘門的語意顧問性不阻擋)是「整個平台對 IAA 閘門語意的唯一權威來源」，它定的是「顧問性、軟性警告、不得阻擋」；[規格 03-03](../03-task-management/03-task-detail.mdx#試標完成條件)也明寫那五條完成條件「和 IAA 達標與否、算完沒算完都無關」。所以**提醒在轉入「等待 IAA 確認」時發出，不論 IAA 有沒有達標**——IAA 沒達標的任務反而更需要人去決定
- 02-01 畫面上另一筆寫死示例（`2 位標記員低於標準速度`）**沒有列進這份清單**：規格裡與它最接近的是[規格 03-03 §規格 › 工時紀錄](../03-task-management/03-task-detail.mdx#工時紀錄)的「異常提醒」區塊，而那是任務詳情頁裡的一個區塊、不是通知；兩者同名不同物

### 不在本頁範圍

1. **寄給使用者的信**不是這裡的通知事件：驗證信（[規格 01-02](../01-account/02-register.mdx)）、重設密碼信（[規格 01-03](../01-account/03-reset-password.mdx)）、設定密碼信（[規格 06-01](../06-admin/01-user-management.mdx)）各自由那些頁定義，它們是帳號流程的一步，不進通知清單
2. **頁面內的操作回饋**不是通知事件：例如[規格 06-02 §規格](../06-admin/02-role-settings.mdx#規格)那種儲存成功或失敗、幾秒後自動消失的提示，它屬於那一頁自己的回饋
3. **頁面裡的提醒區塊**不是通知事件：例如 03-03 的「異常提醒」、IAA 條件清單上的「提醒」圖示，它們是那一頁的內容
4. **通知怎麼送達**（站內、電子郵件、兩者）屬 [規格 01-04](../01-account/04-profile.mdx#通知設定) 的偏好設定與實作，本頁只定「有哪些事件」

## 卡控機制

- 同一個事件**不因為同時出現在兩個消費端**，就對同一個收件者產生兩則（[§已確認決議](#已確認決議) Q5）
- 使用者在[規格 01-04](../01-account/04-profile.mdx#通知設定)關掉某個事件的站內通知 → 那個事件不再進他的側欄通知清單（可以關的只有第 1 到 6 列）
- **事件發生時**與某個任務有關、而某個人在那個任務上沒有:ref[任務角色]{id="term.task-role"} → **那個事件不進他的側欄通知清單**；通知不得成為繞過任務成員身分的旁路。這一條**只管側欄那一邊**：儀表板「最近提醒」取的是與全平台有關的事件，而系統角色與任務角色是兩層、互不推導（術語表），系統管理員本來就不必在那個任務上有任務角色（[§已確認決議](#已確認決議) Q5）
- 儀表板的「最近提醒」 → 只取與全平台有關的事件（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q5），不把每個人的個人事務放上去

## 邊界情況（Edge Case）

- **沒有事件**
  - 使用者一則通知都沒有 → 側欄不顯示未讀數量（[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)第 3 條，本頁不重複定義）
  - 系統管理員的「最近提醒」一筆都沒有 → 顯示佔位文字（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q11，本頁不重複定義）
- **收件者的狀態變了**
  - 事件發生後，收件者在那個任務上的角色被移除 → 那一則通知**留在他的清單上**，不回收；點進去之後的畫面由[規格 07-03 無權限與找不到](./03-denied-and-not-found.mdx)定義（[§已確認決議](#已確認決議) Q3）
  - 事件相關的任務被刪掉 → 同上，點進去之後的畫面由 07-03 定義
- **同一件事通知很多人**
  - 一個事件有多個收件者 → 每個人各自一份已讀狀態，一個人標為已讀不影響其他人

| Scenario | Given | When | Then |
| :--- | :--- | :--- | :--- |
| 正向：清單只有一份 | 某個事件同時出現在側欄與儀表板 | 比對兩邊的敘述 | 兩邊講的是同一個事件，不是兩套說法 |
| 正向：關掉的事件不再進清單 | 使用者在個人設定關掉某個事件的站內通知 | 那個事件再次發生 | 他的側欄通知清單沒有新增那一則 |
| 反向：通知不得成為權限旁路 | 某事件與某任務有關，而這個人在那個任務上沒有任務角色 | 那個事件發生 | 他的**側欄通知清單**沒有那一則 |
| 反向：儀表板不收個人事務 | 某事件只與某一個人有關 | 系統管理員查看「最近提醒」 | 那一則不出現在「最近提醒」裡 |
| 邊界：多個收件者各自已讀 | 一個事件通知了兩個人，其中一人把它標為已讀 | 另一個人查看自己的通知 | 他那一則仍然是未讀 |
| 邊界：同一件事不重複 | 某事件同時符合兩個消費端的條件，而同一個人兩邊都看得到 | 那個事件發生 | 他只收到一則，不是兩則 |
| 正向：第 8 列兩邊都出現 | 某任務的試標自動轉入「等待 IAA 確認」 | 專案負責人看自己的側欄、系統管理員看儀表板 | 兩邊都看得到那一件事，而第 1 到 7 列的事件不出現在儀表板 |
| 正向：第 7、8 列關不掉 | 使用者在個人設定查看通知設定 | 查看那張表 | 表上只有六列，匯出完成與 IAA 待確認不在上面，也沒有關掉它們的開關 |
| 邊界：失去角色後通知留著 | 某人收過一則與某任務有關的通知，之後他在那個任務上的角色被移除 | 查看自己的通知清單 | 那一則還在清單上；點進去之後由[規格 07-03](./03-denied-and-not-found.mdx)的畫面處理 |

### Q5. 本頁提出的三條規則怎麼定？（已定案，維護者裁定 2026-11-15）

三條分別是：

## Q&A

:::tip{title="為什麼事件清單不乾脆寫在側欄那一頁？" collapsible}
因為事件來自任務管理、標記作業與資料集三個模組，而側欄只是其中一個顯示的地方。[規格 07-01 §已確認決議](./01-sidebar.mdx#已確認決議) Q4 的理由就是這個：來源自己把事件模型劃在範圍外，而清單會牽動三個模組，不該由側欄那一頁決定。儀表板那一邊（[02-01 Q5](../02-dashboard/01-dashboard.mdx#已確認決議)）同日也做了相同的判斷。
:::

:::tip{title="畫面上那兩筆提醒示例算不算需求？" collapsible}
不算。[規格 02-01](../02-dashboard/01-dashboard.mdx#已確認決議) Q5 寫得很明白：`FR-008C` 只要求「以清單呈現、每項含提醒標題與提醒內容、為空時顯示佔位文字」，**沒有列出任何一種提醒**，畫面上那兩筆是走查資料。本頁把其中一筆（IAA 待確認）列為候選，依據**不是那筆示例**，而是[規格 05-02](../05-dataset/02-analysis-detail.mdx#兩個合法入口)已定案的條文把「從那個提醒點進來」寫成合法入口。
:::
