# 相依套件政策

dependabot 目前的警示接受風險、不升：它們全在 `development` scope，CI 的 `--prod` 閘門本來就不涵蓋，而且被 `notecraftapp` 鎖住升不上去（逐筆論證見 [PR #320](https://github.com/label-suite/label-suite/pull/320)）。
**這個取捨只在沒有部署、沒有產品相依時成立**：`backend/` 或 `frontend/` 一出現，[技術架構 §部署與維運](architecture.mdx#部署與維運) 的兩道 CI 安全掃描就有東西可掃，要重新評估。

## 被擋住的套件

基準是 18 筆 open alerts（1 critical／5 high／7 medium／5 low），manifest 全是 `pnpm-lock.yaml`；這只證明 CI 閘門沒漏掉什麼，不證明沒有風險。

| 套件 | 筆數 | 修正版落在 | 誰擋住 |
| :--- | ---: | :--- | :--- |
| `astro` | 13 | astro 6 與 7 | `notecraftapp` 1.15.0（最新版）宣告 `astro ^5.0.5` |
| `sharp` | 3（全是 high） | 0.35.x | astro 的 optional 相依；要升到 astro 7 才跨得過去 |
| `katex` | 1 | 0.18.x | `notecraftapp` 自己宣告 `katex ^0.16.47`，升 astro 修不到 |
| `esbuild` | 1 | 0.28.x | 經 astro 帶進來；astro 7 之後改走 vite 8 |

本文刻意不列 CVE 編號與利用路徑（`AGENTS.md` §Issue types and titles 的「Security findings」）；明細在 repo 的 dependabot 頁面，只有維護者看得到。

## 怎麼升

- **不要用 `pnpm.overrides` 繞**：`notecraftapp build docs`（CI 的 `docs-site` job）是目前唯一的端到端驗證路徑，強推它沒測過的大版本會弄壞它。`check:specs`、`check:flows`、`check:er` 只用 Node 內建模組，不受影響
- **解除條件**：`notecraftapp` 發布支援新版 `astro` 的版本時，照相依套件 PR 的形狀另開一張升（判例 #147、#245，見 [`spec-migration.mdx` §PR 的變更範圍](spec-migration.mdx#pr-的變更範圍)；純升版不必照 #245 的「先合併」順序），升完照 [§建置閘門要重跑確認](spec-migration.mdx#建置閘門要重跑確認) 重測 build 閘門
- `katex` 那一筆要等上游把它的 range 往前推，見 [§待決](#待決)
