# 錯誤碼

這份記 `main` 上的後端現在會回的每一個錯誤碼：HTTP 狀態、訊息鍵、在哪一層產生、哪些端點會回；**只寫已合併的程式有的東西**。
錯誤碼的格式與通用碼的定義在 [`api-envelope` spec](https://github.com/label-suite/label-suite/blob/main/openspec/specs/api-envelope/spec.md)，本文不重抄；端點的路徑、request 與 response 以 `backend/openapi.json` 為準，本文只用 `operationId` 對過去。
本文與程式不一致時，是本文錯了：以程式為準，並回頭改本文。

各節的收合區塊是實作或規劃時才要查的細節，預設收起。

## 誰改、什麼時候改

規劃時先改本文，change 的 `api-contract.md` 只寫本文的路徑與異動摘要，不重抄本文的內容。

| 時機 | 誰 | 做什麼 |
| :--- | :--- | :--- |
| 規劃（寫 `api-contract.md`） | `sd` | 新的錯誤碼加進 [§模組專屬碼](#模組專屬碼)；既有的碼多了會回它的端點，改那一列的端點欄。`api-contract.md` 的「常駐文件異動」節寫出本文路徑與異動摘要 |
| 規劃審閱 | `design-reviewer` | 核對本文與這次的 `api-contract.md` 一致 |
| 實作後 | `backend-developer` | 實作出來的錯誤碼、HTTP 狀態、訊息鍵或會回它的端點和設計不同時，依程式校正本文 |
| 程式審查 | `code-reviewer` | 再核對一次本文與實作一致；不一致時列為審查意見 |

四份文件各管一件事：

| 文件 | 管什麼 |
| :--- | :--- |
| `api-envelope` spec | 錯誤外層的形狀、錯誤碼的格式、通用碼與 HTTP 狀態的對應 |
| 本文 | 合併之後全系統的錯誤碼：每個碼的狀態、訊息鍵、產生的位置與會回它的端點 |
| change 的 `api-contract.md` | 這次每個端點在什麼條件下回哪個碼 |
| `backend/openapi.json` | 每個操作在 API 文件裡宣告哪些 HTTP 狀態，以及回應的形狀 |

## 通用碼

通用碼不加前綴，全站共用；下表九個是目前全部的通用碼，格式與定義見 `api-envelope` spec 的「錯誤碼為大寫底線格式並定義第一批通用碼」（`AUTH_REQUIRED`、`CSRF_FAILED` 兩個由 change `login-auth-guard` 加進那條 Requirement，`PERMISSION_DENIED` 由 change `authz-steps-3-4` 加進）。

| `code` | HTTP | 訊息鍵 | 在哪裡產生 | 會回這個碼的端點 |
| :--- | :--- | :--- | :--- | :--- |
| `NOT_FOUND` | `404` | `common.not_found` | `app/core/errors.py` 的 `handle_http_exception`（路由找不到）；`app/core/authz.py` 丟 `NotFoundError`：`require_permission` 讀到的路徑參數無法轉換（任務識別碼不是 UUID、作用角色不是三種任務角色之一），所以格式錯的任務識別碼回的是它而不是 `422`；`Authorizer` 在授權第 2 步發現這個任務沒有生效的成員身分（不是成員、已停用、仍在邀請中），或指定的作用角色不是他的生效角色；授權第 4 步的附加條件遇到看不到的資源，含讀標準答案的操作（`GroundTruthBarrier` 對任何人都回它）。訊息與路由找不到相同，不說明原因 | 沒有端點自己回；`/api/v1` 底下不存在的路徑由路由層回；`API_DOCS_ENABLED=false` 時 `/docs`、`/docs/oauth2-redirect`、`/redoc`、`/openapi.json` 沒有註冊，也由路由層回 |
| `METHOD_NOT_ALLOWED` | `405` | `common.method_not_allowed` | `app/core/errors.py` 的 `handle_http_exception`（方法不允許） | 每個 `/api/v1` 路徑用它沒有的 method 呼叫，例：[`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) 用 `GET` 以外的 method；帶著 access cookie 的 `POST`／`PUT`／`PATCH`／`DELETE` 會先經 CSRF 判定，驗不過時回的是 `403 CSRF_FAILED` |
| `NOT_ACCEPTABLE` | `406` | `common.not_acceptable` | `app/core/middleware.py` 的 `LocaleMiddleware`，接住 `NotAcceptableError` | 每個 `/api/v1` 請求（CORS 預檢除外：它在 `LocaleMiddleware` 外層就回應），含 [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) |
| `VALIDATION_FAILED` | `422` | `common.validation_failed` | `app/core/errors.py` 的 `handle_validation_error` | [`createSession`](/view/diagrams/architecture/api.openapi#op/createSession)、[`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh)、[`createGoogleSession`](/view/diagrams/architecture/api.openapi#op/createGoogleSession)：body 缺欄位、超過上限、有未宣告的欄位或不是 JSON；[`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) 沒有被驗證的輸入 |
| `AUTH_REQUIRED` | `401` | `common.auth_required` | `app/core/auth.py` 定義的 `AuthenticationRequiredError`，經 `handle_app_error` 轉成外層。丟出的地方：`get_current_principal`（cookie 不在、token 驗不過或過期，或 `AccountPrincipalLoader.load` 拒絕）；`app/modules/account/router.py` 的 `create_session_refresh` 在請求沒有 refresh cookie 時；`SessionService.current` 在判定通過後帳號已不存在時 | [`getCurrentSession`](/view/diagrams/architecture/api.openapi#op/getCurrentSession)：沒有可通行的登入狀態，不分原因；[`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh)：請求沒有 refresh cookie（不清 cookie）；之後每個掛 `get_current_principal` 的端點 |
| `CSRF_FAILED` | `403` | `common.csrf_failed` | `app/core/csrf.py` 的 `CsrfMiddleware` 在路由之前直接組錯誤外層（碼取自 `CsrfFailedError`）；缺 `X-CSRF-Token` 或 CSRF cookie、access token 簽章不對，或兩者任一不等於 `HMAC(csrf key, sid)` | 目前沒有：本次的四個寫入端點都在放行清單；之後每個不在放行清單、而且帶著 access cookie 的 `POST`／`PUT`／`PATCH`／`DELETE`（沒有 access cookie 的寫入不驗） |
| `PERMISSION_DENIED` | `403` | `common.permission_denied` | `app/core/authz.py` 定義的 `PermissionDeniedError`，由 `Authorizer`（經 `require_permission` 依賴）在授權第 3 步丟出，經 `handle_app_error` 轉成外層：權限鍵不在白名單或尚未啟用、鍵的層級與操作不符、矩陣版本列不存在、生效角色的格缺列或全部為關。平台層的鍵一律回它；任務層的鍵只在第 2 步已確認呼叫者是這個任務的生效成員之後才會走到這裡。訊息不帶權限鍵、角色、矩陣版本或拒絕在哪一步，也不動 cookie | 目前沒有：沒有端點掛 `require_permission`；之後每個掛它的端點。授權第 2 步與第 4 步遇到看不到的資源回的是 `404 NOT_FOUND`，不是這個碼 |
| `INTERNAL_ERROR` | `500` | `common.internal_error` | `app/core/middleware.py` 的 `UnhandledExceptionMiddleware`；`app/core/errors.py` 的 `handle_http_exception`（沒有對應碼的 `HTTPException`） | 每個 `/api/v1` 請求，含 [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) |
| `DATABASE_UNAVAILABLE` | `503` | `common.database_unavailable` | `app/modules/health/service.py` 的 `HealthService.check()` 丟 `DatabaseUnavailableError`，由 `handle_app_error` 轉成外層 | [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth)：資料庫連不上或逾時 |

訊息鍵的字串在 `app/i18n/zh-TW/messages.json` 與 `app/i18n/en/messages.json`；每一層怎麼把例外變成外層，見 [後端模組與基礎建設的「錯誤怎麼對到 envelope」](./backend-modules.mdx#錯誤怎麼對到-envelope)。

:::note{title="API 文件的宣告、測試用路由與成功碼" collapsible}
- 上表的「會回這個碼的端點」寫的是實際會回的情況，不是 API 文件的宣告。`app/main.py` 的 `API_V1_ERROR_RESPONSES` 讓每個 `/api/v1` 操作都宣告 `404`、`405`、`406`、`500`；[`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) 另在 `app/modules/health/router.py` 宣告 `503`。所以 [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) 在 `openapi.json` 裡有 `404`，實際不會回
- [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) 沒有宣告 `422`，`openapi.json` 裡也沒有
- `422` 與 `500` 的整合測試靠 `backend/tests/probe.py` 的測試用路由觸發；它們只由 `backend/tests/conftest.py` 掛上，不在正式的 app 與 `openapi.json` 裡，見 [端點授權的「不在本表的路徑」](./endpoint-authorization.mdx#不在本表的路徑)
- `NotFoundError` 在 `app/core/errors.py` 已定義；授權依賴會丟它，但目前沒有端點掛 `require_permission`，所以實際的 `404` 仍都來自路由找不到。授權第 4 步「看得到但狀態不允許」不用這兩個碼，由條件所屬模組的碼表定
- `406` 的 body 一律是 zh-TW；`messages.json` 的 en 字串只為了兩個語系的鍵一致而存在
- 成功外層的 `code` 是 `OK`（訊息鍵 `common.ok`），不是錯誤碼，不列在上表；定義見 `api-envelope` spec 的「成功回應包一層六欄位外層」
:::

## 模組專屬碼

每個模組一張表，欄位與 [§通用碼](#通用碼) 相同；碼要加模組前綴。程式端要做的事見 [後端模組與基礎建設的「新增業務模組的檢查清單」](./backend-modules.mdx#新增業務模組的檢查清單)。

### account

前綴 `ACCOUNT_`；七個錯誤都定義在 `app/modules/account/service/errors.py`、不帶參數，由 service 丟出，經 `handle_app_error` 轉成外層。登入失敗鎖定（規格 01-05 Q3）還沒有，所以沒有它的碼，見[後端模組與基礎建設的「已知限制」](./backend-modules.mdx#已知限制)。

| `code` | HTTP | 訊息鍵 | 在哪裡產生 | 會回這個碼的端點 |
| :--- | :--- | :--- | :--- | :--- |
| `ACCOUNT_INVALID_CREDENTIALS` | `401` | `account.invalid_credentials` | `PasswordLoginService.login` | [`createSession`](/view/diagrams/architecture/api.openapi#op/createSession)：帳號不存在、密碼不符、停用、已匿名化、沒有本地密碼或 Email 正規化後超過 254 字，全部同一個碼 |
| `ACCOUNT_SESSION_EXPIRED` | `401` | `account.session_expired` | `SessionService.refresh` | [`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh)：已過 90 天或 7 天；同時撤銷這段登入狀態並清掉三個 session cookie |
| `ACCOUNT_SESSION_INVALID` | `401` | `account.session_invalid` | `SessionService.refresh` | [`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh)：帶著 refresh cookie 但不能用：token 查不到、登入狀態已失效、帳號停用或已匿名化，或寬限期外重用（疑似被盜用，同時撤銷這個帳號全部的登入狀態），不分原因；回應清掉三個 session cookie；沒有 cookie 時回 `AUTH_REQUIRED` |
| `ACCOUNT_REFRESH_CONFLICT` | `409` | `account.refresh_conflict` | `SessionService.refresh` | [`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh)：同一張 token 在寬限期內被用到第三次以上；什麼都不改，cookie 不動 |
| `ACCOUNT_GOOGLE_UNAVAILABLE` | `409` | `account.google_unavailable` | `GoogleLoginService.begin`、`complete` | [`getGoogleAuthorization`](/view/diagrams/architecture/api.openapi#op/getGoogleAuthorization)、[`createGoogleSession`](/view/diagrams/architecture/api.openapi#op/createGoogleSession)：部署沒有設定 Google |
| `ACCOUNT_GOOGLE_FLOW_INVALID` | `400` | `account.google_flow_invalid` | `GoogleLoginService.complete` | [`createGoogleSession`](/view/diagrams/architecture/api.openapi#op/createGoogleSession)：流程 cookie 不在、簽章不對或已過期、`state` 不符、換 token 或驗 `id_token` 失敗；回應清掉流程 cookie |
| `ACCOUNT_GOOGLE_REJECTED` | `401` | `account.google_rejected` | `GoogleLoginService.complete` | [`createGoogleSession`](/view/diagrams/architecture/api.openapi#op/createGoogleSession)：沒有已連結的帳號，且 Google 的 Email 未驗證、正規化後超過 254 字、沒有 Email 相同的帳號，或 Email 相同的帳號已連結另一個 Google 帳號；也含停用與已匿名化的帳號（維護者 N2），不分原因；回應清掉流程 cookie |
