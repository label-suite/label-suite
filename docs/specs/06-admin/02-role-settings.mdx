:::info{title="這一頁是權限矩陣的唯一設定處"}
平台的每一個操作最終都要過這張矩陣。這一頁定的是**矩陣本身怎麼被看、怎麼被改、哪些格永遠不能改**，以及矩陣在授權判斷裡的位置——**矩陣格不單獨賦予任何存取權**，它只是其中一個必要條件。

**33 條舊編號全數對應**，見[§附錄：舊編號對照](#附錄舊編號對照)；`pnpm check:specs` 會驗證零缺漏。

:::warning{title="但「33 條全數對應」不等於來源的需求全部搬完"}
來源的三個「驗收情境」區段裡，**只有 2 條有編號**（`AC-3.4`、`AC-3.5`，分別是 v1.2.0 與 v1.3.0 才補上的）；其餘 **9 個驗收情境完全沒有編號**，寫法是 `1. **Given** …`。

## 目標

| 目標 | 誰受益 |
| :--- | :--- |
| 讓:ref[系統管理員]{id="term.system-admin"}在**一個地方**看完整平台每個角色能做什麼，而不是去翻 18 份規格 | 要回答「這個人為什麼做不了這件事」的系統管理員 |
| 讓矩陣的修改**改得掉、也擋得住**：預設唯讀、要先按編輯、有未儲存變更會攔、同時有兩個人改會擋 | 整個平台——矩陣是最高風險的設定，誤改的影響是全站的 |
| 讓**核心管理權限永遠關不掉**，平台不會把自己鎖在門外 | 平台本身 |
| 讓每一次真的改過的儲存都**查得到是誰、什麼時候、改了哪一格** | 事後追查的系統管理員與稽核 |
| 讓矩陣**只是授權的必要條件之一**，而不是唯一條件 | 資料安全——矩陣格通過不等於這個人能碰那一筆資料 |

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

| 角色 | 這一頁能做什麼 | PRD §權限矩陣的上限 |
| :--- | :--- | :--- |
| :ref[系統管理員]{id="term.system-admin"} | R／E | 「06 角色設定」給系統管理員 `R/E` |
| :ref[平台成員]{id="term.platform-member"} | **進不來** | 同一列給平台成員 `—` |

- 這一頁**沒有新增、沒有刪除**：矩陣的格是既有的，只能開關，不能增減
- R 與 E 分別由**兩個權限**控制：進來要「**進入角色權限設定頁**」，改與存要「**編輯並儲存角色權限矩陣**」
- 兩者都成立才改得動；只有前者的系統管理員**看得到矩陣但按不了編輯**
- 系統管理員的身分**本身**仍是硬邊界：矩陣**不能**授權平台成員繞過它（見[§授權判斷的順序](#授權判斷的順序)）
- 這一頁與[規格 06-01 使用者管理](./01-user-management.mdx)是同一個模組的兩個分頁，互相以分頁連結

### 改一次角色權限

- 觸發：系統管理員在[使用者管理](./01-user-management.mdx)點「角色設定」分頁
- 前置條件：使用者是系統管理員，而且有「進入角色權限設定頁」權限
- 主流程：
  1. 系統驗**身分與進入權限** → 都過才繼續
  2. 系統載入矩陣，以**閱覽模式**顯示 → 這時候改不動
  3. 使用者點「編輯」→ 進入**編輯模式**
  4. 使用者調整格 → 頁首出現**未儲存變更**的提示
  5. 使用者點「儲存」→ 系統**帶著版本**驗樂觀鎖
  6. 版本相符 → 寫入矩陣、版本與稽核事件，顯示已儲存並**回到閱覽模式**
- 替代流程：
  - A1（第 4 步後）使用者點「取消」而且**有**未儲存變更 → 顯示**確認對話框**；選「放棄變更」就回到閱覽模式並回復上次已儲存狀態，選「繼續編輯」就留在編輯模式，流程結束
  - A2（第 4 步後）使用者點「取消」而且**沒有**未儲存變更 → **直接**回到閱覽模式，不顯示對話框，流程結束
- 例外流程：
  - E1（第 1 步）身分或進入權限不過 → **平台成員導回儀表板、未登入導向登入**，流程結束（見 [§卡控機制](#卡控機制)）
  - E2（第 5 步）**版本不符** → 顯示版本衝突橫幅與「重新載入」，**拒絕這次儲存**、不覆蓋別人的變更，流程結束
  - E3（第 5 步）**一般儲存失敗** → 顯示錯誤並**保留未儲存的修改**，留在編輯模式，流程結束
- 結果：矩陣、版本與稽核事件一起更新；或者什麼都沒變，而使用者知道為什麼

### 查誰改了什麼

- 觸發：系統管理員點矩陣區塊右上角的「操作紀錄」
- 前置條件：使用者進得來這一頁
- 主流程：
  1. 使用者點「操作紀錄」→ 系統開啟**右側抽屜**
  2. 抽屜依時間列出每一筆變更：**時間、操作者、改了哪一格** → 看得到歷史
  3. 使用者關閉抽屜 → 回到主頁面，**矩陣的編輯狀態不受影響**
- 替代流程：
  - A1（第 2 步）還沒有任何紀錄 → 抽屜顯示**空狀態**，流程結束
- 結果：使用者知道誰在什麼時候改了哪一格，而且中途開關抽屜不會弄丟正在編輯的內容

## 規格

### 這一頁定什麼、不定什麼

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 頁首大標是 `角色設定`，副標是 `設定系統角色與任務角色的功能存取權限`
2. 這一頁定**矩陣本身**：它長什麼樣、誰能改、怎麼改、哪些格不能改、改了留什麼紀錄
3. 這一頁**不定**各個功能自己的規則——某個操作除了矩陣格之外還要滿足什麼條件，寫在那個功能自己的規格裡
4. **矩陣格不單獨賦予任何存取權**：它只是授權判斷的**必要條件之一**（見[§授權判斷的順序](#授權判斷的順序)）
5. 這一頁的角色名稱**與平台其他地方一致**，不另立一套

### 怎麼進來、誰進得來

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 入口只有一個：[使用者管理](./01-user-management.mdx)頁上的「**角色設定**」分頁
2. 兩頁的分頁列是同一組：`使用者管理`、`角色設定`；兩頁**同屬系統管理模組**，側欄的第一層都停在「系統管理」（見[規格 07-01](../07-shared/01-sidebar.mdx)）
3. 存完**留在這一頁**，使用者可以自己點「使用者管理」分頁回去
4. 取消編輯**也留在這一頁**，不自動導頁
5. **平台成員**直接開這一頁或使用者管理頁 → **拒絕並導回儀表板**
6. **未登入**直接開這兩頁 → **導向登入頁**
7. 第 5、6 條的檢查**兩頁都要做**，而且**頁面入口與每一次操作都要在伺服器端再驗一次**；前端的按鈕狀態**不能代替**伺服器的授權
8. 沒有權限的使用者**連矩陣的資料都不得讀到**

### 兩層授權模型：系統角色與任務角色

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 矩陣有**兩層**，而且頁面要**明確標示**它們是兩層、不是同一層：
   - **系統角色**：:ref[平台成員]{id="term.platform-member"}、:ref[系統管理員]{id="term.system-admin"}
   - **任務角色**：:ref[專案負責人]{id="term.project-leader"}、:ref[審核員]{id="term.reviewer"}、:ref[標記員]{id="term.annotator"}
2. 兩層**不能互相推導、也不能繼承**——系統管理員不會因為是管理員就取得任務層的權限
3. 表頭分成兩組：`系統角色`、`任務角色`；整列的第一欄是 `功能權限`
4. 矩陣的列**依模組分段**，六個段落的標題是 `帳號（Account）`、`儀表板（Dashboard）`、`任務管理（Task Management）`、`標記（Annotation）`、`資料集（Dataset）`、`系統管理（Admin）`
5. 畫面上的角色欄名與術語表**用了不同的中文**，見[§待釐清](#待釐清) Q4

3. 第 1、2 條合起來是 **22 個鍵**；它們依**所屬模組**分成六段呈現，而**模組與層級是兩回事**——任務管理那一組就同時有平台層（檢視任務列表、建立新任務）與任務層的鍵
4. 「進入使用者管理頁」與「新增／編輯／停用使用者、指派系統角色」沿用[規格 06-01](./01-user-management.mdx)已經用的名字，**不改名**
5. 「看任務統計」與「看品質分析」沿用[規格 05-01](../05-dataset/01-analysis-list.mdx#使用角色)已經用的名字，**不改名**
6. **「刪除草稿任務」對不上任何授予刪除的格。** PRD §權限矩陣整個 03 模組的四列**沒有任何一格有 `D`**。這個落差[規格 03-01](../03-task-management/01-task-list.mdx#使用角色)已經明寫過，**這一頁不默默放寬**；PRD 的改動由 Issue #85 處理
7. **「處置最終例外」與「裁定爭議」超出那一格的上限。** PRD 給專案負責人的上限是 `R`，而這兩個動作是**寫入**。這個落差[規格 04-02](../04-annotation/02-annotation-workspace.mdx#使用角色)已經明寫過，理由相同：PRD 另有一句「專案負責人在標記工作區只處理審核員無法收斂的例外」，說的是**範圍**不是權限字母。**這一頁同樣不放寬**
8. PRD 給專案負責人「05 資料匯入與版本 `R/C`」，但**來源沒有任何對應的鍵**，見[§待釐清](#待釐清) Q2
9. 每一列左邊同時顯示**權限鍵的原始名稱**與**中文說明**
10. 「管理任務成員與任務角色」與「編輯任務設定」的分界有一條容易誤讀的地方：**審核與仲裁名冊的寫入**歸前者，而**資料集重綁仍歸後者**。來源在 v1.3.0 只把名冊那一半搬過去，**沒有**把任務詳情的其他寫入面一起搬

### 56 個適用格，錯層的不存

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 適用格共 **56 個**：**10 個平台鍵 × 2 個系統角色**，加上 **12 個任務鍵 × 3 個任務角色**
2. 不適用的格**不是「關閉」，而是根本不存在**——它們是**錯層**：平台層的角色拿不到任務層的鍵，反之亦然
3. 錯層的格在畫面上顯示 `需任務角色` 徽章，而且**不儲存任何資料列**
4. 矩陣區塊的說明文字就是在解釋這件事：`設定各角色對平台功能的存取權限。「需任務角色」徽章表示需透過任務角色授權，不由系統角色直接控制。鎖頭圖示表示核心管理權限，不可關閉。`
5. 每一個**已啟用**的鍵，它**全部適用角色的格都要在**；缺一個就是不合法
6. 每一格的值是**開或關**兩種。「唯讀」不是第三種值，而是**兩個鍵的組合**：「檢視任務詳情」開、「編輯任務設定」關——畫面在那一列加 `（唯讀）` 標示
7. 來源在 `SC-011` 同時留著舊的 **42** 格與現行的 **56** 格，並註明「原文逐字保留」。**現行值是 56**；42 是 v1.3.0 之前的（9 個平台鍵 × 2 ＋ 8 個任務鍵 × 3）

### 固定格不能改

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 下面這些格是**固定的**，矩陣裡**不能改**：

| 格 | 固定成 |
| :--- | :--- |
| 系統管理員 × 所有系統管理類的鍵 | **固定開啟** |
| 平台成員 × 所有系統管理類的鍵 | **固定關閉** |
| 兩種系統角色 × 檢視儀表板 | **固定開啟** |

2. 固定格在畫面上有**鎖頭圖示**
3. 第 1 條第一列的理由是**平台不能把自己鎖在門外**：系統管理員的管理權限一旦關得掉，就可能再也沒有人能開回來
4. 矩陣**不能**把平台成員的系統管理類格提升成開啟——那等於繞過系統角色這道硬邊界
5. 新增系統管理類的鍵時，它的固定格要**一次建立到位**：系統管理員開、平台成員關

### 五個已登錄、待啟用的鍵

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 有 **5 個鍵**的狀態是「**已登錄、待啟用**」：推進任務生命週期、刪除草稿任務、處置最終例外、裁定爭議、檢視全平台統計
2. 它們已經完成三項審查（層級、操作對應、完整種子），**只剩安全測試**要等正式後端實作並有實際證據之後，由另一個經審查的變更確認
3. 在啟用之前，**用這五個鍵做的授權判斷一律按「認不得的鍵」拒絕**
4. 第 3 條的意思**不是**那些操作做不了：它們**維持原本的角色與資源閘門**，**不得**改成只憑矩陣格放行
5. 但矩陣**仍然要收下它們全部的適用列**——所以 56 這個數字已經含它們
6. 四個任務層鍵的**種子值**由維護者裁定載明：專案負責人**開**、審核員**關**、標記員**關**
7. 第六條那個「種子值由裁定載明」是例外。**其他**新鍵的可配置格**預設是關**，而且在層級、操作映射、完整種子資料與安全測試都審查完成前**不得啟用**
8. 系統管理員刪除草稿任務走的是[規格 03-01](../03-task-management/01-task-list.mdx)的平台層窄規則，**不經過任務層的格**
9. 系統管理員的**全平台統計**依它自己的**固定格**與**系統管理員硬邊界**判斷，**不經過那個待啟用的鍵**——所以第 3 條的「按認不得的鍵拒絕」不會讓這個能力消失

### 授權判斷的順序

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

矩陣是授權的必要條件之一，不是唯一條件。伺服器的判斷有**固定順序**。

1. 先驗**當前帳號**與它的登入憑證族
2. 再讀**當前的系統角色**，以及在那個任務內**生效的成員身分**
3. 再檢查這個操作對應的**已啟用權限鍵**，以及適用角色那一格是不是**開啟**
4. 最後檢查**資源條件**：任務擁有權、任務狀態、指派、答案隔離
5. 下面幾種情況**一律拒絕**：**認不得的鍵**、**缺列**、**錯層**、**沒有成員身分**、**成員身分已停用**、**成員身分還在邀請中**
6. **沒有成員身分時，一個任務層的鍵都拿不到**——不是拿到關閉的格，是根本沒有身分可以查
7. **矩陣格通過不等於能碰那一筆資料**——第 4 條還要過
8. 前端的能力提示（按鈕能不能按）**不能代替**第 1 到 4 條

### 一人多任務角色：聯集與作用角色

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 同一個人在**同一個任務**可以同時有**多個任務角色**
2. 不是標記工作區的任務頁面：取那個任務**生效成員身分的允許權限聯集**
3. 但**每一個操作仍然要滿足它自己的資源條件**——聯集只放寬「有沒有這個權限」，不放寬資源檢查
4. 進入標記工作區時**必須選定一個作用角色**
5. 標記或審核的**寫入**只依**那個作用角色**當前生效的成員身分與對應的格判斷，**不因為其他任務角色的聯集而放寬**
6. 網址上的角色或人員參數**不能建立身分或指派**
7. 第 1 到 6 條與[規格 04-02](../04-annotation/02-annotation-workspace.mdx)是同一套；這一頁是它的授權依據

### 閱覽模式與編輯模式

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 頁面**預設是閱覽模式**，矩陣**改不動**
2. 要改得先點 `編輯` → 進入編輯模式
3. 編輯模式下顯示 `儲存` 與 `取消`；閱覽模式下顯示 `編輯`
4. `操作紀錄` 按鈕在**矩陣區塊的右上角、`編輯` 的右側**，**兩種模式下都顯示**，而且是**只有圖示**的按鈕
5. **儲存成功**後回到閱覽模式
6. **取消**之後也回到閱覽模式

### 取消要先確認

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 編輯模式下點 `取消`，而且**有**未儲存的變更 → 先顯示確認對話框：
   - 標題 `有未儲存的變更`
   - 說明 `確定要放棄目前的修改？取消後所有變更將遺失。`
   - 兩個按鈕：`繼續編輯`、`放棄變更`
2. 選 `繼續編輯` → 關閉對話框，**保留**未儲存的變更繼續編輯
3. 選 `放棄變更` → 回到閱覽模式，並**回復到上一次已儲存的狀態**
4. **沒有**未儲存變更時點取消 → **直接**回到閱覽模式，**不顯示**這個對話框
5. 取消之後**留在這一頁**，不自動導頁

### 未儲存變更的提示

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 編輯模式下只要有任何一格被改過且還沒存 → 頁首顯示一條橫幅，標題是 `有未儲存的變更`
2. 這條橫幅是**持續性的狀態指示**，它**本身沒有任何按鈕**
3. 它與[§取消要先確認](#取消要先確認)的對話框是**互補**的：橫幅告訴你「現在有未存的東西」，對話框才是真正攔住「取消」的那一道
4. 儲存成功、或在對話框確認放棄之後 → 橫幅**隨即隱藏**
5. 這條橫幅要能被螢幕報讀器**主動宣告**

### 儲存用樂觀鎖，版本衝突要重新載入

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. **每一次儲存都要帶版本**驗證，**包含沒有任何變更的那一次**
2. 版本不一致、或版本資料根本不存在 → **拒絕儲存**並提示衝突，**不得覆蓋別人的變更**
3. 衝突時在頁首顯示橫幅：
   - 標題 `版本衝突：設定已被其他管理員修改`
   - 說明 `請重新載入最新設定後再進行編輯，以避免覆蓋他人變更`
   - 一個 `重新載入` 按鈕，按了會載入最新的矩陣並清掉衝突狀態
4. 這條橫幅**預設隱藏**，只在衝突時出現
5. 衝突之後**不得**沿用過期的版本繼續儲存
6. **真的沒有變更而且版本相同**時：**不遞增版本、不寫稽核事件**
7. 第 6 條有一個前提：**即使沒有變更也要先檢查版本**；版本資料不存在就拒絕

### 儲存成功與失敗的回饋

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 儲存成功 → 顯示通知 `角色權限設定已儲存`
2. 版本衝突 → 顯示通知 `版本衝突，請重新載入最新設定`，並同時出現[§儲存用樂觀鎖](#儲存用樂觀鎖版本衝突要重新載入)第 3 條的橫幅
3. 通知出現在頁面**右下角**，**4 秒**後自動消失，也可以手動關掉
   - **目前的畫面與這一條不符**：它讓成功通知 **3 秒**後消失、錯誤通知**永不自動消失**。來源要求規格與畫面不一致時要明確記錄，見[§待釐清](#待釐清) Q11
4. 通知有成功與錯誤**兩種圖示**，依結果切換
5. 儲存失敗**不得默默失敗**：要顯示看得懂的原因
6. **一般儲存失敗**要**保留**未儲存的修改與未儲存狀態，讓使用者可以修正後再送
7. 儲存的內容不合法時，除了拒絕，還要**指出是哪一個角色與權限的組合有問題**，並**保留**未儲存的修改
8. 第 6、7 條與版本衝突**處理方式不同**：前者保留修改讓人改，後者要人**重新載入**最新設定
9. 畫面另有**第三種**通知：`儲存的矩陣含未知或違反固定格的權限鍵，已拒絕並還原預設值`。它的觸發時機與第 1 到 8 條**都不一樣**——它在**載入**已儲存的矩陣時才出現，見[§待釐清](#待釐清) Q5

### 操作紀錄抽屜

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 點 `操作紀錄` → 從**右側**開啟抽屜
2. 抽屜的標題是 `操作紀錄`，副標是 `角色權限矩陣`
3. 抽屜列出**所有**歷史變更紀錄，每一筆有：**時間**、**操作者名稱**、**改了哪一格**
4. 第 3 條那個「改了哪一格」的格式是 `角色 · 權限鍵  OFF → ON`——**角色與權限鍵都原樣顯示原始名稱**，開關也是原樣的 `ON`／`OFF`，不翻譯（畫面上的例子長這樣：`reviewer · dataset.export  OFF → ON`）
5. 每一筆還標著動作名稱 `權限更新`；操作者前面有 `操作者：` 的前綴
6. 還沒有任何紀錄時顯示空狀態 `尚無操作紀錄`
7. 抽屜有 `關閉` 按鈕，關掉就回到主頁面
8. **開關抽屜不影響矩陣的編輯狀態**——正在編輯的內容不會因此丟掉

### 稽核事件與保存期限

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 儲存**而且真的有變更**時，系統要寫一筆稽核事件，**與矩陣和版本的更新一起完成**
2. 那一筆事件要保存：**操作者**、**時間**、**版本的前後值**，以及**變更前後的格子差異**
3. 第 2 條的差異**由伺服器依已儲存的列自己算**，**不得**直接相信前端送上來的差異
4. 稽核紀錄**至少保留 1 個曆年**
5. **儲存失敗**或**沒有變更**時**不產生**這筆事件
6. 這筆事件寫進平台**共用的稽核事件**，不是這一頁專屬的紀錄

### 矩陣儲存的五個拒絕條件

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 儲存時下面五種內容**一律拒絕**：

| 拒絕的情況 | 說明 |
| :--- | :--- |
| 非白名單的鍵 | 不在那 22 個裡 |
| 錯層 | 平台層的角色配任務層的鍵，或反之 |
| 多列 | 同一個角色與鍵的組合出現兩次以上 |
| 缺列 | 某個已啟用的鍵少了某個適用角色的格 |
| 違反固定格 | 想改[§固定格不能改](#固定格不能改)的任何一格 |

2. 錯層的格**不儲存**，所以它不算「缺列」
3. 矩陣**仍然要收下**那五個「已登錄、待啟用」鍵的全部適用列
4. 新增鍵要照[§五個已登錄、待啟用的鍵](#五個已登錄待啟用的鍵)第 7 條的預設拒絕與啟用程序

### Seeder 管理員永遠不可被移除

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 平台初次建立的那一位:ref[Seeder 管理員]{id="term.seeder-admin"}**永遠不可被移除**——**刪除、停用、降級都不行**
2. 第 1 條與[§固定格不能改](#固定格不能改)是同一個目的的兩道保險：一道守**權限**不被關掉，一道守**人**不被拔掉
3. 這一條的落地在[規格 06-01](./01-user-management.mdx)；這一頁只重申它是矩陣改不掉的邊界

### 不同螢幕寬度的呈現

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 在 **375、768、1440** 三種寬度下，矩陣都要**看得完整**，而且**內容不得重疊**
2. 寬度 **767 以下**時，矩陣要**依角色類型或模組分段呈現**
3. 第 2 條的分段要讓使用者**完整檢視並編輯**矩陣
4. **主要的檢視與編輯流程不得依賴橫向捲動**
5. 若仍保留輔助性的橫向捲動，**不得造成欄位被截斷到讀不出來**

### 這一頁碰不到的東西

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

1. 這一頁**不能新增或刪除權限鍵**——清單由後端白名單定義
2. 這一頁**不能新增或刪除角色**
3. 這一頁**不能**管理帳號；那在[規格 06-01](./01-user-management.mdx)
4. 這一頁**不能**改任何一個任務的成員身分；那在[規格 03-03](../03-task-management/03-task-detail.mdx)
5. 這一頁**不能**放寬 PRD §權限矩陣 的上限——只能在表內收窄

### 預設矩陣：每一格的初始值

<PrototypeFrame page="admin/role-settings" caption="角色設定" client:idle />

來源把這張表列為**初始值**，同時也是**回歸測試的基準**，所以逐格照收。`⛔` 是錯層、不儲存資料列。

1. **平台層的 10 個鍵**對兩個系統角色的初始值：

| 中文權限名稱 | 平台成員 | 系統管理員 |

## 卡控機制

- 平台成員開這一頁或使用者管理頁 → **拒絕並導回儀表板**
- 未登入開這兩頁 → **導向登入頁**
- 沒有「進入角色權限設定頁」權限 → 進不來，**連矩陣資料都不得讀到**
- 只有「進入角色權限設定頁」、沒有「編輯並儲存角色權限矩陣」 → 看得到矩陣但**按不了編輯**
- 只靠前端控制授權 → 違規；**頁面入口與每一次操作都要在伺服器端再驗**
- 矩陣想把平台成員的系統管理類格改成開啟 → **拒絕**；不得繞過系統角色硬邊界
- 想關掉系統管理員的任何系統管理類權限 → **拒絕**
- 想改兩種系統角色的「檢視儀表板」 → **拒絕**（固定開啟）
- 儲存含**非白名單**的鍵 → 拒絕
- 儲存含**錯層**的格 → 拒絕
- 同一個角色與鍵的組合出現**兩次以上** → 拒絕
- 某個已啟用的鍵**少了**某個適用角色的格 → 拒絕
- 儲存**違反固定格** → 拒絕
- 以那五個「已登錄、待啟用」的鍵做授權判斷 → 按**認不得的鍵**拒絕；對應操作**維持原本的閘門**，不得只憑矩陣格放行
- 矩陣**不收**那五個鍵的適用列 → 違規；它們的列仍要被收下
- 新鍵未完成層級、操作映射、完整種子與安全測試審查就啟用 → 違規
- 新的系統管理類鍵啟用時固定格**沒有一次建立到位** → 違規
- 授權判斷時遇到**認不得的鍵、缺列、錯層、失效的成員身分** → **一律拒絕**
- 只憑矩陣格就放行而**沒檢查資源條件** → 違規
- 進入標記工作區**沒有選定作用角色** → 違規
- 標記或審核的寫入**因為其他任務角色的聯集而放寬** → 違規
- 用網址上的角色或人員參數**建立身分或指派** → 違規
- 閱覽模式下矩陣**可以直接改** → 違規
- 有未儲存變更時點取消**沒有先確認** → 違規
- 沒有未儲存變更時點取消**卻跳出確認** → 違規
- 儲存**沒有帶版本** → 違規；**包含沒有變更的那一次**
- 版本不一致或版本資料不存在 → **拒絕儲存**並提示衝突，**不得覆蓋**別人的變更
- 衝突後**沿用過期版本**繼續儲存 → 違規
- 真的沒有變更而且版本相同 → **不遞增版本、不寫稽核事件**
- 儲存失敗**默默失敗** → 違規；要顯示看得懂的原因
- 一般儲存失敗**丟掉**未儲存的修改 → 違規
- 內容不合法時**沒有指出**是哪個角色與權限的組合 → 違規
- 稽核事件的差異**直接相信前端送來的** → 違規；要由伺服器依已儲存的列自己算
- 稽核紀錄保存**不足 1 個曆年** → 違規
- 儲存失敗或沒有變更**卻寫了**稽核事件 → 違規
- 開關操作紀錄抽屜**弄丟**正在編輯的內容 → 違規
- :ref[Seeder 管理員]{id="term.seeder-admin"}被刪除、停用或降級 → **拒絕**
- 寬度 767 以下時**主要檢視與編輯流程依賴橫向捲動** → 違規
- 輔助橫向捲動造成**欄位截斷到讀不出來** → 違規
- 這一頁**放寬** PRD §權限矩陣 的上限 → 違規；只能在表內收窄

## 邊界情況（Edge Case）

- **進入與權限**
  - 矩陣**載入失敗** → 顯示錯誤狀態與重試入口，**不顯示不完整的配置**
  - 系統管理員只有進入權限、沒有編輯權限 → 看得到矩陣，`編輯` 按不了
  - 系統管理員在別的分頁被降為平台成員 → 下一次操作就進不來（見[規格 06-01](./01-user-management.mdx)）
- **編輯與儲存**
  - 進了編輯模式但**什麼都沒改**就按儲存 → **仍要帶版本檢查**；版本相同就不遞增、不寫稽核事件
  - 進了編輯模式但什麼都沒改就按取消 → **直接**回閱覽模式，不跳確認
  - 改了一格又改回原值 → 來源沒有定義這算不算「有變更」；依[§儲存用樂觀鎖](#儲存用樂觀鎖版本衝突要重新載入)第 6 條的「真的沒有變更」判斷，屬實作前要定的細節
  - **兩個人同時編輯**，其中一個先存 → 另一個的儲存被拒絕並看到版本衝突橫幅
  - 版本衝突後按 `重新載入` → 載入最新矩陣、清掉衝突狀態；**未儲存的修改不保留**（那是衝突與一般失敗的差別）
  - 一般儲存失敗後再按儲存 → 修改還在，可以直接重送
  - 儲存的內容缺了某個已啟用鍵的一格 → 拒絕，並指出是哪個角色與權限的組合
- **固定格與待啟用的鍵**
  - 想把系統管理員的系統管理類格關掉 → 那一格有鎖頭、改不動
  - 送出的內容硬是改了固定格 → 儲存被拒絕
  - 以待啟用的鍵做授權判斷 → 按認不得的鍵拒絕，而對應操作**仍然做得到**（走原本的閘門）
  - 待啟用的鍵在矩陣上**仍然有格**，而且算進 56 這個數字
- **操作紀錄**
  - 還沒有任何變更紀錄 → 抽屜顯示 `尚無操作紀錄`
  - 編輯到一半開抽屜再關 → 正在編輯的內容**都還在**
  - 儲存失敗 → **沒有**新的紀錄（失敗不寫事件）
- **載入已儲存的矩陣時發現它不合法**
  - 開頁時發現已儲存的矩陣含認不得的鍵或違反固定格 → 畫面顯示 `儲存的矩陣含未知或違反固定格的權限鍵，已拒絕並還原預設值`；**來源沒有定義這件事**，見[§待釐清](#待釐清) Q5
- **螢幕寬度**
  - 寬度 767 以下 → 依角色類型或模組分段，不靠橫向捲動也能看完與改完
  - 1440 寬度 → 矩陣完整可見且不重疊

### Q1. 「匯出資料」這個權限歸哪一個模組？來源與 PRD 放在不同地方

- [ ] 以來源為準：留在資料集那一段，但在說明裡註明它對應 PRD 的「03 匯出標記結果」
- [ ] 其他（請說明）

> 需要決定的人：維護者
> 依據狀態：來源把這個鍵歸在**資料集**模組，PRD §權限矩陣 把匯出放在「**03 匯出標記結果**」那一列（專案負責人 `C`）。兩邊**都有明文**但落位不同。

## Q&A

### Q. 為什麼矩陣格通過了還不夠？

因為矩陣回答的是「**這個角色允不允許做這類事**」，而不是「**這個人可不可以碰這一筆**」。一位專案負責人的「編輯任務設定」格是開的，但那只代表他能編輯**他負責的**任務；他不會因此編輯得了別人的任務，也不會因此在任務已完成之後還改得動設定。所以伺服器的判斷是四段：先確認你是誰、再看你在這個任務是什麼身分、再看矩陣格、最後才看這一筆資料的擁有權、狀態與隔離條件。少了最後一段，矩陣就會從「必要條件」變成「唯一條件」。

### Q. 為什麼有五個鍵「已登錄」卻「待啟用」？登錄了不就該能用嗎？

因為「登錄」只完成了三件事：確定它屬於哪一層、確定它對應哪些操作、確定它的初始值。**還沒完成的是安全測試**——而那要等正式後端實作出來、有實際的執行證據才做得了。在那之前，如果讓這五個鍵真的參與授權，等於用一個沒有被測過的閘門取代原本測過的閘門。所以來源的作法是：矩陣照常收下它們的格（這樣啟用的那一天不用改資料結構），但**授權判斷把它們當成認不得的鍵拒絕**，而那些操作**維持原本的角色與資源閘門**——使用者完全感覺不到差別，因為功能照常可用。

### Q. 為什麼「沒有變更」也要帶版本去檢查？

因為「我以為沒有變更」和「真的沒有變更」是兩件事。如果在你開著頁面的這段時間裡別人存過一次，你畫面上的矩陣就已經是舊的——此時即使你一格都沒動，你送出的那份「沒有變更」描述的也是**過期的狀態**。先檢查版本才知道「沒有變更」是相對於哪一版說的。而真正沒有變更、版本又相同時，系統就不遞增版本也不寫稽核事件——否則稽核紀錄會被一堆「什麼都沒改」的事件淹掉，真正的變更反而找不到。

### Q. 為什麼「唯讀」不是第三種值？

因為唯讀不是一種權限，而是**兩種權限的組合**：看得到、改不得。矩陣上就是「檢視任務詳情」開、「編輯任務設定」關。把它做成第三種值會有兩個問題：一是每個鍵都得多定義一次「唯讀對這個鍵是什麼意思」，二是「看得到但改不得」以外的組合（例如改得動但看不到）就沒辦法表達了。保持每一格只有開和關，組合的意義由鍵自己承擔。
