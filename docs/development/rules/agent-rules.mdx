# Agent 開發規範

本文說明七條不分 backend／frontend／e2e 都適用的跨領域規範，展開它們的適用路徑、例外與檢查方式。
`AGENTS.md` 是規則本體（single rule source），兩邊說法不同時以 `AGENTS.md` 為準並回報維護者；本 repo 不建立 `.claude/rules/` 這種第二份 canon。
標題帶「摺疊」字樣的區塊（正例、反例、細節）預設收起，點開才看；技術基準（選型、分層、ADR 效力）在 [architecture.mdx](../architecture.mdx)，不在這裡重複。

## 這一份管什麼

跨領域的規範在本文，分領域的規範各有一份說明文件：

| 領域 | 說明文件 |
| :--- | :--- |
| 跨領域（本文件） | `docs/development/rules/agent-rules.mdx` |
| 後端分層、資料庫、背景工作 | [backend-agent-rules.mdx](backend-agent-rules.mdx) |
| 授權、答案隔離、設定驅動邊界 | [security-agent-rules.mdx](security-agent-rules.mdx) |
| API 契約同步、單一前端 Client | [api-agent-rules.mdx](api-agent-rules.mdx) |
| 前端依賴方向、型別安全、UI 共用 | [frontend-agent-rules.mdx](frontend-agent-rules.mdx) |
| 測試分層、雙資料庫驗證、交付證據 | [testing-agent-rules.mdx](testing-agent-rules.mdx) |

**大多數規範還沒有任何自動檢查**：`backend/`、`frontend/` 與 `e2e/` 都還不存在，所以「檢查方式」大多標「待建置」，不得因為文件存在就宣稱規則已被強制。
標「**人工／獨立審查**」的規範現在就要做，只是沒有工具代勞：本文的 R1、R3、R4、R5、R6、R7 與 [backend-agent-rules.mdx](backend-agent-rules.mdx) 的 B8，共七條。自動 gate 的清單與歸屬在 [testing-agent-rules.mdx](testing-agent-rules.mdx) 的 T9。

## 規範

每一條都交付適用路徑、禁止事項、例外與檢查方式；正例與反例收在摺疊區塊。來源條文在 [§附錄：來源對照](#附錄來源對照)。

### R1 先搜尋再新增

開工前先讀那一區既有的匯出、呼叫端與共用工具；沒搜尋過既有實作，不新增 helper、util、型別、常數或相依套件。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | 搜尋過、確認沒有，且在 commit body 或 PR 寫明搜過什麼 |
| **檢查方式** | **人工／獨立審查**。沒有自動檢查——`grep` 搜過什麼無法事後驗證，所以要寫在 PR 裡 |

為什麼現在只靠人工、元件索引與 hook 強制什麼時候再評估，見 [ADR-001 的 D1](../adr/001-agent-engineering.mdx#d1-先搜尋再新增)。

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：要格式化日期 → 先 grep 既有的日期工具 → 找到就用它。
- 反例：直接寫一個新的 `formatDate()`，而同一個資料夾已經有一個。
:::

### R2 依賴方向

被依賴的那一層不得回頭 import 依賴它的那一層。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/`（還不存在，所以這一條**現在沒有適用對象**）。**`backend/` 由 [backend-agent-rules.mdx](backend-agent-rules.mdx) 的 B1 取代**——那一條寫明了層級與允許的 import，比這裡具體 |
| **例外** | 無 |
| **檢查方式** | **待建置**。後端的具體分層由 B1 定，前端由 [frontend-agent-rules.mdx 的 F1](frontend-agent-rules.mdx#f1-分層與允許的-import) 定；兩邊的自動檢查都要等實際有程式 |

模組內分層（`app/modules/<module>/`）見 [architecture.mdx](../architecture.mdx)，後端的落地規則見 B1；前端那一半落地後，這一條只剩跨領域的原則敘述。

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：前端 `pages` → `features` → 共用的 `components/ui`（具體分層見 [frontend-agent-rules.mdx 的 F1](frontend-agent-rules.mdx#f1-分層與允許的-import)）。後端版本見 B1。
- 反例：`components/ui` 的元件 import `features` 的東西；或共用層回頭依賴頁面層。
:::

### R3 最小變更

只改本次請求要求的程式、註解與排版；本次改動之前就存在的死碼不刪，提出來即可。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | 本次改動**自己造成**的孤兒（變成沒人用的 import、變數、函式）要清掉；本次改動呼叫、修改或取代的既有實作如果是**錯的**，在同一張 PR 直接修並寫明錯在哪，不繞過、不另加規則補救（[ADR-001 的 D2](../adr/001-agent-engineering.mdx#d2-範圍內直接修正錯誤實作)） |
| **檢查方式** | **人工／獨立審查**。測試是「每一行改動都能直接追到請求本身」 |

不設固定的檔案數或行數門檻，見 [§附錄：刻意不採用的來源條文](#附錄刻意不採用的來源條文)。

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：只改那一行；發現旁邊有死碼 → **提出來**，不刪。
- 正例：新功能要呼叫的既有函式算錯了 → 在這張 PR 修掉它，PR 寫明錯在哪；旁邊另一個沒被呼叫的函式也有錯 → 只提出來、另開 issue。
- 反例：既有函式算錯了，新程式在呼叫後自己再修正一次結果，或在 `AGENTS.md` 加一條「呼叫 X 之後要記得……」。
- 反例：順手把整個檔案重排版，讓 diff 從 3 行變 300 行。
:::

### R4 不過度抽象

不為單一使用點建立抽象，不加入沒被要求的「彈性」或「可設定性」，不為不可能發生的情境寫錯誤處理。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | 共用的邏輯、驗證與常數**必須**只有一處定義（`AGENTS.md` 的「No hardcoded task logic」，即硬性規則 5 的精神） |
| **檢查方式** | **人工／獨立審查** |

DRY 與 KISS 衝突時**以 KISS 為先**：重複兩次而語意不同，不是抽象的理由。

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：兩個地方有同一段邏輯，而它**確實是同一個概念** → 抽成一個小的共用函式。
- 反例：兩個地方剛好長得像、但語意不同 → 硬抽成一個帶 `mode` 參數的函式。
:::

### R5 衝突處理

兩套慣例衝突時，照本 repo 已確認的決議；沒有決議可循就回報維護者並停下來，不以「比較新」或「比較好測」為理由自行選邊，也不靜默挑一個。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | 無 |
| **檢查方式** | **人工／獨立審查**。`scripts/check-specs.mjs` 的 `BASES` 只驗規格頁的決議有沒有寫出依據，不驗程式層的慣例衝突 |

這一條刻意與參考來源相反：本 repo 已經有一套「已確認決議」的機制（五個依據、機械檢查），自行選邊會繞過它。

:::note{title="查哪裡與反例（摺疊）" collapsible}
- 正例：發現兩套相反的慣例 → 先查本 repo 的已確認決議（`docs/specs/` 的已確認決議、`architecture.mdx` 的 ADR 效力表、`AGENTS.md`）→ 有決議就照決議。
- 反例：「A 的寫法比較新，所以照 A」然後繼續做下去。
:::

### R6 範圍鎖定後不得以 YAGNI 刪驗收條件

實作階段不得以「用不到」為理由，刪掉或略過 issue／規格已承諾的驗收條件；延後的需求回到 Issue 或規格決策，不藏在程式註解。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | **範圍還開著的時候**（規劃階段、`/sdd` 的那個停點）可以主張某項不做，但要寫進該 change 的 `proposal.md` 或 issue，不是寫在程式裡 |
| **檢查方式** | **人工**。打勾的工作項與實際交付物的對照目前沒有自動檢查 |

註解裡的待辦是第二個沒有人讀的 backlog。

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：覺得某條驗收條件不該做 → 回到那張 issue 或規格頁提出來，由維護者決定。
- 反例：`// YAGNI: 這個情境應該不會發生，先不做` 然後把 tasks 的那一項打勾。
:::

### R7 不確定就明說

任何一步沒有完整驗證，就不當成通過；不靜默失敗。

| | |
| :--- | :--- |
| **適用路徑** | 全部 |
| **例外** | 無 |
| **檢查方式** | **人工／獨立審查**。`AGENTS.md` 的 Required Behaviors 已有「工具呼叫失敗兩次就回報確切錯誤」 |

:::note{title="正例與反例（摺疊）" collapsible}
- 正例：「這個 job 只能在 runner 上驗證，本機驗不到」寫進 PR 的 Test Plan 並留未勾。
- 反例：Test Plan 全部打勾，而其中一項其實沒跑過。
:::

## 開工前置條件

[architecture.mdx](../architecture.mdx) §待決 的項目是前置條件，不是建議：沒有維護者的裁定，相關的程式工作不開工。

本文件目前沒有未裁定的項目；已裁定的項目與日期在 [§決策紀錄](#決策紀錄)，現行做法在 `architecture.mdx`。

只有真的有裁定紀錄的項目才算已核准，本文件不把建議寫成已核准。本期範圍以 PRD 為準，不自行擴增功能；要加功能另開可追溯的 Issue。

## 與 SDD 工作流程的分界

本文件提供規則來源與說明、跨領域規範、衝突處理與前置條件；不重複開發那十二個 agent 角色（`.claude/agents/`）、SDD schema 與 `openspec/config.yaml`、`/sdd` 指令與 clarify skill，也不新增人工關卡：`/sdd` 的那個停點（clarify）由 `AGENTS.md` 的 SDD Workflow 定義，本文件不另加。

## 附錄：刻意不採用的來源條文

參考來源有幾條以**數量**定成敗的規則，本 repo 不採用。

| 不採用的門檻 | 出處 | 為什麼不採用 |
| :--- | :--- | :--- |
| 「寫了 200 行而其實 50 行就夠 → 重寫」 | 原始 repo `general.md` | 行數不是複雜度。50 行的爛抽象比 200 行的直白程式更難改 |
| 「同一段程式出現 2 次以上 → 抽出共用」 | 原始 repo `general.md` | 出現兩次不代表是同一個概念。R4 的例外已經覆蓋真正該共用的情形 |
| 「一張 PR 不得超過 5 個檔案或 300 行 diff」 | 原始 repo `git-workflow.md`（Constitution Principle X） | 本 repo 以**單一目的**判斷 PR 大小（`AGENTS.md` 的 Pull Requests：一句話說不清就拆）。行數門檻會逼人把一個目的拆成兩張，反而更難審 |

不採用不等於不在意：R3 與 R4 管的是同一件事，只是用「能不能追到請求」與「是不是同一個概念」當判準，而不是數字。
