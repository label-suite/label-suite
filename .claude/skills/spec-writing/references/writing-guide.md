# 規格書撰寫指南

各章節的寫法、追問清單與技術用語黑名單。寫法參考
[規格書撰寫 - HOW 怎麼寫？](https://stevelin-notecraft.netlify.app/notes/%E8%A6%8F%E6%A0%BC%E6%9B%B8%E6%92%B0%E5%AF%AB-how-%E6%80%8E%E9%BA%BC%E5%AF%AB/)，
骨架參考 DutyMate 的 `docs/specs/`，另外加上「邊界情況（Edge Case）」章節。

## 章節總覽

| 章節 | 回答的問題 | 必要 |
| :--- | :--- | :--- |
| 目標 | 為什麼要做？誰受益？ | 是 |
| 使用角色 | 誰能看、新增、編輯、刪除？ | 是 |
| 業務流程 | 這件事從誰開始、經過誰、在哪分岔、結束在哪？（含流程圖） | 是（不適用就寫「不適用」與原因） |
| 規格 | 有哪些功能、資料長什麼樣？（含 prototype 嵌入） | 是 |
| 卡控機制 | 系統擋什麼？ | 是（沒有就寫「無」與原因） |
| 邊界情況（Edge Case） | 合法但極端的情況，使用者看到什麼？ | 是 |
| 驗收標準 | 怎樣算做完？ | 是 |
| 待釐清 | 還沒決定的事 | 有未決項目才寫 |
| 已確認決議 | 追問過、已決定的事與理由 | 有決議才寫 |
| 變更紀錄 | 規格因哪個 Issue 改過、改了什麼？ | 是（初版寫「初版」） |
| Q&A | 規則背後的理由、常被問的問題 | 選用 |

## 目標

先回答「為什麼要做、解決誰的什麼問題」。之後的規格、卡控、驗收有爭議時，都回頭對齊目標。

| 要寫 | 不寫 |
| :--- | :--- |
| 「提供 X，讓 Y 可以 Z」：動詞＋對象＋目的 | 實作方式（屬於「規格」） |
| 對應到具體角色 | 無法驗證的形容詞：更好用、更直覺、提升體驗 |
| 尚未確認的目標用 `*` 開頭標註 | 待釐清的問題（移到「待釐清」） |

## 使用角色

權限寫錯，後面的卡控、驗收、畫面條件會一起錯。用 R／C／E／D 明確列出。

```md
:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）
:::

- :ref[管理員]{id="term.admin"}：R/C/E/D
- :ref[檢視者]{id="term.viewer"}：R（部分欄位遮蔽，見 [§資料欄位](#資料欄位)）
```

| 要寫 | 不寫 |
| :--- | :--- |
| 每個角色的 R/C/E/D 組合 | 尚未定義的角色（列入待釐清） |
| 角色名稱連到術語表，全文一致 | 「Admin／User」這種通用詞取代業務角色 |
| 「只能操作自己的資料」寫成 `R(o)/E(o)`，並在下方說明 o＝own | 功能說明（「管理員可以匯出」屬於規格） |
| 不能使用此功能的角色也要列出：`業務：無權限` | |

## 業務流程

「規格」寫每個畫面怎麼操作，「業務流程」寫**一件事怎麼從頭走到尾**：誰觸發、經過哪些角色與判斷、例外時回到哪裡、結束時是什麼狀態。
寫法參考使用案例的主流程／替代流程／例外流程，再用泳道圖畫出來（見 [flow.md](flow.md)）。

**什麼時候要寫**

| 情況 | 寫法 |
| :--- | :--- |
| 跨兩個以上角色交接（送審 → 審核 → 通知） | 必寫，附流程圖 |
| 有簽核、審核或狀態流轉（草稿 → 送出 → 核准／退回） | 必寫，附流程圖 |
| 沒有畫面的功能（排程、匯入、自動通知） | 必寫，附流程圖；這類規格不放 prototype 嵌入 |
| 要跨多個頁面或規格才能完成一件事 | 必寫，附流程圖；跨到的規格寫成連結「見 [規格 NN-NN](…)」（見「引用與連結」） |
| 單一角色在單一畫面完成的增刪改查 | 選用：步驟 3 詢問；不寫時章節內容寫「不適用：單一角色在同一畫面完成，操作見 [§規格](#規格)」 |

**一段業務流程的寫法**

```md
- **刪除聯絡紀錄**
  - 觸發：管理員發現紀錄登錄錯誤或重複
  - 前置條件：管理員已在客戶詳情頁，該客戶至少有一筆聯絡紀錄
  - 主流程：
    1. 管理員在紀錄右側點擊「刪除」 → 系統顯示確認視窗
    2. 管理員點擊「刪除」 → 系統移除紀錄，顯示「已刪除聯絡紀錄」
    3. 目前頁還有資料 → 列表停留在目前頁
  - 替代流程：
    - A1（第 2 步）管理員點擊「取消」 → 關閉確認視窗，紀錄保留，流程結束
  - 例外流程：
    - E1（第 3 步）目前頁刪到沒有資料 → 改顯示前一頁，流程結束（見 [§邊界情況](#邊界情況edge-case)）
  - 結果：紀錄從列表移除，無法在畫面上復原
```

| 部分 | 寫法 |
| :--- | :--- |
| 粗體標題 | 業務事件名稱：「動詞＋對象」，例：送審報價單、刪除聯絡紀錄；流程圖的流程 tab 用同一個名稱 |
| 觸發 | 誰、因為什麼開始這個流程；排程類寫時間（例：每天 00:00） |
| 前置條件 | 開始前必須成立的狀態：登入身分、資料狀態、所在頁面 |
| 主流程 | 編號步驟，每步「誰做什麼 → 系統或下一個角色的回應」；只寫一切順利時的路徑 |
| 替代流程 | `A1`、`A2`…：合法但不同的選擇（取消、退回、改走另一條路）。寫「（第 N 步）條件 → 結果」，最後寫回到第幾步或「流程結束」；只寫和主流程不同的部分 |
| 例外流程 | `E1`、`E2`…：卡控擋下、失敗、資料被他人變動。格式同替代流程；條件與提示文字以 §卡控機制、§邊界情況為準，這裡只寫分岔與回到哪 |
| 結果 | 流程結束時資料是什麼狀態、誰看得到或收到什麼 |

**和其他章節的分工**

- 和「規格」：業務流程寫到「誰做了什麼」為止；按鈕文案、欄位、預設值、排序寫在規格大項，不在這裡重複
- 和「卡控機制」「邊界情況」：每個例外流程都要能對到一條卡控或邊界情況；提示文字只在那兩章寫一次
- 和「驗收標準」：主流程至少一條正向 Scenario，每個替代與例外流程至少一條 Scenario
- 和 PRD §模組架構與串接：規格的業務流程以**角色**為泳道、只寫這一頁；流程跨到其他模組時，交接點寫成連結「見 [PRD §跨模組流程](../00-prd.mdx#跨模組流程)」，不重寫模組之間的交接

| 要寫 | 不寫 |
| :--- | :--- |
| 角色名稱與「使用角色」一致 | 系統內部怎麼處理：寫入、計算、同步、排程機制 |
| 每個判斷的兩個出口都有下文 | 只有「是」沒有「否」的判斷 |
| 例外流程寫明回到第幾步或流程結束 | 「視情況處理」這種沒有結論的分支 |
| 跨規格的交接寫成連結「見 [規格 NN-NN](…)」 | 把其他規格的步驟抄一份 |
| 流程圖（見 flow.md） | 畫面細節：按鈕位置、欄位順序（屬於規格／prototype） |

## 規格

把目標拆成可開發的功能清單，**宏觀 → 微觀**兩段：

1. **宏觀**：切出大項，例如「列表、篩選、新增、編輯、刪除、匯出」，每個大項一個粗體或第一層清單
2. **微觀**：每個大項寫成「摘要句＋操作流程＋補充規則」，資料規則寫進「資料欄位」表格

**大項的寫法**

```md
- **新增**

  管理員在「聯絡紀錄」區塊點擊「新增聯絡紀錄」，在對話框登錄一次聯絡；任何往來狀態的客戶都可以新增。
  1. 對話框帶入預設值：聯絡日期為今天，聯絡方式未選，內容空白
  2. 填寫後點擊「儲存」→ 對話框關閉，顯示「已新增聯絡紀錄」，列表回到第 1 頁
  3. 點擊「取消」→ 不儲存，已填的內容捨棄
  - 負責人由系統帶入目前登入者，不出現在表單上
```

| 部分 | 寫法 |
| :--- | :--- |
| 摘要句 | 一句話交代誰、在哪個頁面／區塊、什麼情況下、做什麼 |
| 操作流程 | 編號步驟，每步「操作 → 系統回應」；一步只有一個操作，之後可直接對應驗收的 Scenario |
| 補充規則 | 不屬於流程的規則（排序、分頁、預設值、顯示格式、誰看不到按鈕），用無編號條列放在最後 |

**5W1H 是檢查清單，不是輸出格式**：寫完每個大項後，用下面兩張表確認都有交代到；
不要把 WHAT／WHO／WHERE／WHEN／HOW 當成小標題或條列標籤寫進規格。功能面寫在摘要句與操作流程，資料面寫在「資料欄位」表格。

**功能面 5W1H**

| | 要交代 |
| :--- | :--- |
| WHAT | 是什麼功能 |
| WHO | 誰能用（對齊「使用角色」） |
| WHERE | 在哪個頁面、哪個區塊 |
| WHEN | 什麼情況下用到：前置條件、資料狀態、時間 |
| HOW | 使用者怎麼操作、系統怎麼回應（回扣目標） |

**資料面 5W1H**

| | 要交代 |
| :--- | :--- |
| WHAT | 是什麼資料 |
| WHO | 誰能看、誰能改（對齊權限，含遮蔽） |
| WHERE | 資料從哪來（使用者輸入、其他頁面、匯入） |
| WHEN | 什麼時候更新、要不要即時 |
| HOW | 怎麼呈現：排序、格式、空值顯示 |

**資料敏感度**：每個欄位都要交代型別細節，不然就是把業務決策丟給工程師。用表格列出欄位：

| 型別 | 必須交代 |
| :--- | :--- |
| 數字 | 最大／最小、可否負值、可否小數、小數位數、進位方式（進位／捨去／四捨五入）、單位 |
| 日期 | 顯示格式、是否含時間、時間精度（分／秒）、時區、一週從星期幾開始 |
| 布林 | 是／否各代表什麼、預設值 |
| 文字 | 長度上下限、允許的字元、是否必填、是否可重複 |
| 檔案 | 支援格式、大小上限、保留期限 |
| 選項 | 單選／多選、選項清單、可否自訂、預設值 |

```md
| 欄位 | 型別 | 必填 | 規則 | 檢視者看到 |
| :--- | :--- | :--- | :--- | :--- |
| 客戶名稱 | 文字 | 是 | 1–100 字，不可與其他客戶重複 | 原值 |
| 電話 | 文字 | 否 | 數字與「-」，8–20 字 | 遮蔽（顯示「—」） |
```

「檢視者看到」是業務規則（誰看得到什麼），可以寫；遮蔽怎麼實作不寫。

| 要寫 | 不寫 |
| :--- | :--- |
| 每個功能的 WHO | 沒有對應目標的功能（沒有 WHY 就是過度設計） |
| 欄位的型別細節 | 「之後再決定」的欄位規則（移到待釐清） |
| 畫面上的操作與回饋：按鈕、提示文字、確認視窗 | 資料表、欄位名稱、API、框架、元件名稱 |
| 每個大項開頭的 `PrototypeFrame` 嵌入（見 SKILL.md 步驟 7） | 色碼、像素、動畫曲線、版面位置（畫面以 `design/prototype/` 為準） |

## 卡控機制

「不能做什麼、系統會擋什麼」，是驗證規則與反向測試的依據。

| 要寫 | 不寫 |
| :--- | :--- |
| 「條件 → 結果」：`客戶名稱已存在 → 無法儲存，欄位下方顯示「此名稱已被使用」` | 「應該要擋」這種模糊語氣 |
| 資料合法性：必填、格式、長度、範圍、唯一 | 顏色、動畫等 UI 呈現（屬於規格／prototype） |
| 狀態限制：例如「已停用的客戶不能被編輯」 | 重複規格段的功能描述 |
| 權限限制：例如「檢視者看不到編輯按鈕」 | 擋在哪一層（前端／後端）——一律寫「系統擋下」 |

**測試集保護**（`AGENTS.md` 硬性規則 6）：頁面涉及標準答案或測試集時，卡控一律寫一條「標註員能接觸到的任何地方（畫面、匯出、通知、錯誤訊息）都看不到標準答案」，
並在驗收標準寫對應的 Scenario。只把答案藏起來不算保護；系統端怎麼做到由 OpenSpec change 的 design 與 spec delta 寫明，規格不寫。

## 邊界情況（Edge Case）

「合法但極端」的情況。和卡控的差別：卡控擋**非法**操作，邊界情況處理**合法但容易被忽略**的情況。
依規格大項分組，每條都寫死「使用者看到什麼結果」。

| 類別 | 例子 |
| :--- | :--- |
| 空狀態 | 還沒有任何資料、篩選後沒有結果 |
| 極值 | 名稱剛好 100 字、一次選取 1,000 筆、數值為 0 |
| 時間 | 跨月、跨年、月底 31 號、閏年、時區 |
| 並發 | 兩人同時編輯同一筆、編輯中資料被別人刪除 |
| 載入失敗 | 網路中斷、儲存失敗後重試、連點儲存按鈕 |
| 資料變動 | 引用的資料被停用或刪除、權限在使用中被取消 |
| 顯示 | 名稱過長、特殊字元、窄螢幕 |

| 要寫 | 不寫 |
| :--- | :--- |
| 預期行為：顯示什麼、保留什麼、能不能繼續操作 | 「要處理一下」這種沒有結論的記錄 |
| 和待釐清的關聯（例：「覆寫策略依 Q2」） | 卡控的內容（非法輸入） |
| | 實作細節：交易、鎖、快取、重試機制 |

## 驗收標準

Given／When／Then 表格，是相關人員判斷「做完了沒」的共同約定。

```md
| Scenario | Given | When | Then |
| :--- | :--- | :--- | :--- |
| 成功新增客戶 | 管理員在客戶列表頁 | 填寫必填欄位並點擊「儲存」 | 列表出現新客戶，顯示「已新增」提示 |
```

| 要寫 | 不寫 |
| :--- | :--- |
| 正向：照預期操作能達成目標 | 實作：「呼叫 POST /customers」→ 改寫「點擊儲存」 |
| 反向：每條卡控至少一條 | 沒有 Then 的 Scenario |
| 邊界：每條邊界情況至少一條 | 一條 Scenario 有多個 When（拆成多條） |
| 權限：每個角色至少一條（含無權限） | 「正常運作」這種無法驗證的 Then |
| 流程：業務流程的每個替代與例外流程至少一條 | |
| 使用者語言 | |

Scenario 名稱要唯一，後續 OpenSpec 的 specs 會沿用。

## 待釐清

每題一個 `###`，用勾選清單列選項，附建議與理由：

```md
### Q1. 檢視者能不能匯出客戶清單？

- [ ] 可以，但遮蔽欄位維持遮蔽
- [ ] 不可以
- [ ] 其他（請說明）

> 建議：不可以。匯出檔離開系統後無法再控管，檢視者有查詢需求時可以在畫面上檢視。
> 需要決定的人：業務主管
```

決定後：把該題搬到「已確認決議」，勾選選中的選項並標 `（已定案）`。

## 已確認決議

```md
### Q1. 檢視者能不能匯出客戶清單？（已定案，2026-10-28）

- [ ] 可以，但遮蔽欄位維持遮蔽
- [x] 不可以

> 理由：匯出檔離開系統後無法再控管。
```

## 追問清單

步驟 4 用。每一項都對輸入檢查一次，**答案不明確且會影響驗收結果**就要問。

**範圍**
- 這次包含哪些功能、明確不包含哪些？
- 是新頁面，還是改既有頁面？和其他頁面的進出關係？

**目標與角色**
- 誰受益？要解決什麼問題？
- 有哪些角色會用到？各自的 R/C/E/D？
- 有沒有「只能看自己的」或「只能看部分欄位」？
- 沒有權限的人進到這頁會看到什麼？

**業務流程**
- 誰觸發？觸發的時機或原因？
- 中間有沒有交給其他角色（審核、確認、接手）？交接後原本的人看得到什麼？
- 每個判斷的「否」走向哪裡：退回、重來、結束？
- 例外發生後回到哪一步，還是整個流程結束？
- 流程結束時資料是什麼狀態？誰會知道（畫面、通知）？
- 有沒有其他規格接在前面或後面？

**規格**
- 每個大項的 5W1H 是否都有交代（寫在摘要句與操作流程，不當標籤）？
- 每個欄位的資料敏感度是否都有交代？
- 列表：預設排序、每頁筆數、可排序／篩選／搜尋的欄位、搜尋是完全比對還是部分比對？
- 表單：哪些必填、預設值、儲存後去哪裡？
- 刪除：能不能復原？要不要確認？刪除後相關資料怎麼辦？
- 通知：誰會收到什麼通知？

**卡控**
- 唯一性、格式、範圍限制？
- 狀態限制：什麼狀態下不能做什麼？
- 違反時的提示文字？

**邊界情況**
- 空狀態、極值、跨期、並發、載入失敗、資料變動，各類是否適用？

**驗收**
- 怎樣算成功？有沒有數量或時間上的要求（例：匯出 1 萬筆內完成）？

**需求變更**（依 Issue 修改既有規格時）
- 這次變更推翻了哪一條「已確認決議」？Issue 有沒有說清楚為什麼改？
- 會不會跟既有的卡控、邊界情況、Scenario 互相矛盾？矛盾時以哪個為準？
- 既有資料怎麼辦（例：選項拿掉後，已經選了該選項的舊資料要怎麼顯示）？
- 引用這份規格的其他規格，有沒有跟著要改的地方？
- Issue 的描述與評論結論不一致時，以哪個為準？

## 需求變更

依 GitHub Issue 修改既有規格時用。新增規格不需要變更標示，「變更紀錄」寫「初版」即可。

### 變更標示

規格只標**最近一次**變更：開始修改前先清掉上一次的標示，再標這次改的地方。歷次變更只留在「變更紀錄」。

| 變更 | 標示方式 |
| :--- | :--- |
| 改了一句話、一個條目 | 把變動的文字包進 `<mark>`，緊接上標連到 Issue |
| 表格某一格 | 只包有變動的儲存格 |
| 新增一列表格、一個條目 | 包住該列第一格或整個條目 |
| 新增整個大項、整段流程 | 只包大項或流程的名稱，底下內容視為一起新增 |
| 刪掉規則 | 正文直接刪除，不留刪除線；在「變更紀錄」寫明原本的規則 |
| 新的決議 | 不加 `<mark>`，在決議的理由下方加一行 `> 來源：[Issue #N](網址)` |

```mdx
做：- 單選：<mark>電話、Email、會面、視訊會議、其他</mark><sup>[#12](https://github.com/org/repo/issues/12)</sup>
不做：- 單選：電話、Email、會面、視訊會議、其他（#12 新增）
不做：- 單選：~~電話、Email、會面、其他~~ 電話、Email、會面、視訊會議、其他
```

- 上標的連結文字固定寫 `#N`，連到 Issue 的網址，不連到「變更紀錄」
- 頁首狀態 badge 後面加 `:badge[變更 #N]{variant="info" href="Issue 網址"}`，讓讀者一打開就知道這份規格最近改過
- 一個 Issue 的所有變更都要標，包含業務流程、卡控、邊界情況、驗收標準；漏標的地方讀者會以為沒變
- 清掉上一次標示：用 Grep 找 `<mark>`、`<sup>[#`、`:badge[變更 #`，拿掉標籤、保留文字
- 流程圖元件與 prototype 嵌入不加標示；元件內容依變更更新即可

### 變更紀錄

放在「已確認決議」與「Q&A」之間，新的在上面，一個 Issue 一列，不刪舊的列。

```md
## 變更紀錄

| Issue | 日期 | 變更章節 | 原本 | 修改後 | 對應決議 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| [#12](https://github.com/org/repo/issues/12) | 2026-10-30 | §規格、§資料欄位、§驗收標準 | 聯絡方式只有電話、Email、會面、其他 | 加上「視訊會議」 | Q14 |
| 初版 | 2026-10-28 | 全部 | — | — | Q1–Q13 |
```

- 「原本」「修改後」各用一句話寫業務規則的差異，不貼整段原文
- 刪掉的規則在「修改後」寫「刪除」
- 推翻既有決議時，「對應決議」寫新的題號；被推翻的舊決議依 SKILL.md 步驟 5 標註被哪一條取代

## 引用與連結

規格裡指到其他段落時，一律寫成可以點擊的連結，讀者不用自己捲動找。語法與錨點規則見 `docs/development/notecraft-writing.md`「內部連結與錨點」。

| 引用對象 | 寫法 |
| :--- | :--- |
| 同一份規格的章節 | `見 [§卡控機制](#卡控機制)` |
| 章節裡的分組（例：邊界情況的「新增」） | 連到章節，分組名稱留在連結外：`見 [§邊界情況](#邊界情況edge-case) 新增` |
| 其他規格 | `見 [規格 02-01](../02-customer/01-customer-list.mdx)` |
| 其他規格的章節 | `見 [規格 02-01 §卡控機制](../02-customer/01-customer-list.mdx#卡控機制)` |
| 已確認決議、待釐清的題目 | 連到章節，題號留在連結外：`見 [§已確認決議](#已確認決議) Q13` |
| 術語 | 用 `:ref[名詞]{id="term.xxx"}`，不用連結 |

- 範本固定的章節錨點：`#目標`、`#使用角色`、`#業務流程`、`#規格`、`#資料欄位`、`#卡控機制`、`#邊界情況edge-case`、`#驗收標準`、`#待釐清`、`#已確認決議`、`#變更紀錄`、`#qa`；搬移的規格另有 `#附錄舊編號對照`
- 不連到單一 Q 題：Q 標題的錨點包含問題與日期，題目改寫或定案後就失效
- 連結文字保留「§」與「規格 NN-NN」的格式，印出來或複製到別處時仍看得懂
- 頁首的「相關規格」也寫成連結
- 流程圖元件裡的文字（走查卡片的「對應：」、步驟代號）不加連結

## 技術用語黑名單

規格書不出現以下用語。自我檢查時用 Grep 掃一次（不分大小寫），命中就改寫成使用者語言：

```
API|端點|endpoint|GET |POST |PUT |PATCH |DELETE |HTTP|status code|狀態碼 4|狀態碼 5|
資料表|table|欄位型別|varchar|int\b|uuid|主鍵|外鍵|index|索引鍵|SQL|query|migration|
JSON|payload|request|response|token|JWT|OIDC|session|cookie|cache|快取|
React|NestJS|TypeORM|Postgres|component|元件|hook|redux|store|前端擋|後端擋|
service|controller|DTO|class|function|middleware|guard
```

例外：
- 業務上真的叫這個名字（例如產品名稱、外部系統名稱）可以保留，第一次出現時在術語表說明
- 「索引」指的是規格文件的索引頁時不算
- `docs/specs/index.mdx` 這類文件路徑不算
- 連結網址（例如變更標示連到的 Issue 網址）不算
- `PrototypeFrame` 的 `import` 與嵌入標籤不算（含 `@notes/components/prototype-frame` 路徑）
- 測試集保護：可以寫「標準答案」「測試集」「標註員看不到答案」等業務用語；系統端怎麼做到（不隨回應送出、只在伺服器比對）仍不寫，留給 OpenSpec change
