# Doc Writing

此 skill 管的是 `docs/` 底下**不是規格**的文件怎麼寫：架構、流程、agent 規則、工具說明。
規格（`docs/specs/`）不在範圍內，PRD 用 `prd-writing`、單頁規格用 `spec-writing`。
NoteCraft 的語法、連結與錨點規則見 `docs/development/notecraft-writing.md`；本 skill 只管「寫什麼、寫在哪、寫多少」。

## 何時使用

- 新寫一份 `docs/development/` 或 `docs/` 其他非規格文件
- 既有文件太長、同一件事記在好幾處、現行規則和決策過程混在一起，要精簡
- 維護者做了一個裁定，要寫進文件
- 要確認一份文件是否符合本 skill 的寫法

## 何時不使用

- `docs/specs/` 底下的 PRD、規格、術語表、模組索引 → `prd-writing`／`spec-writing`
- 只改錯字、連結、一兩句措辭 → 直接改，不必走本 skill
- `openspec/` 的規劃產物 → 由 SDD 流程的角色撰寫
- `AGENTS.md`、`CLAUDE.md` → 它們是規則本身，改動另依該檔的流程

## 鐵律

1. **不改決策，只改寫法**：改寫既有文件時，規則的內容、適用範圍與例外一條都不能變；改寫中發現決策互相矛盾、或看不出現行做法是哪一個，停下來問維護者，不自行選邊（`AGENTS.md` §Agent Rules Index：Conflicts are not yours to settle）
2. **不腦補理由**：理由只寫來源裡找得到的；找不到就不寫，不要自己補一句看起來合理的
3. **未經同意不寫檔**：新建先確認大綱；改寫先給維護者看一節的前後對照，同意風格後才整份改
4. **鎖定的範圍不縮減**：既有文件承諾過的檢查、例外、待辦，不因為「精簡」就刪掉；移到它該在的地方（決策紀錄、待決、issue），不能消失

## 提問格式

凡是本文寫「依提問格式」詢問的地方，一律用下面的文字格式提問，然後**停下來等使用者回覆**，不要自行選擇或繼續往下做：

```markdown
**Q1｜{章節或主題}**：{問題}

1. {選項}（建議）— {選這個選項的影響}
2. {選項} — {影響}
3. {選項} — {影響}

（回覆編號即可，也可以直接輸入其他答案）
```

- 每題 2～4 個選項，最推薦的放第一個並標「（建議）」
- 一次最多 4 題，題號連續；使用者可以用「Q1:1、Q2:3」一次回覆
- 開放式問題（例如「這次要寫哪個頁面？」）不列選項，直接問
- 使用者回覆前，不寫檔、不提交

## 文件形狀

**不規定章節。** 依主題自由分節，只有三個固定部分：

| 部分 | 必要性 | 寫什麼 |
| :--- | :--- | :--- |
| 副檔名 | 一律 `.mdx` | 新文件一律用 `.mdx`；改寫既有的 `.md` 時一併改名，見下方「改名成 `.mdx`」 |
| 開頭 | 一律要有 | frontmatter（`title`、`description`、`tags`）之後兩三句：這份文件管什麼、不管什麼、和其他文件說法衝突時以誰為準 |
| 正文 | 一律要有 | 依主題分節，每節套用下面的寫法規則 |
| `## 待決` | 有未決事項才加 | 一張表：`#｜問題｜卡住什麼｜誰決定` |
| `## 決策紀錄` | 有裁定才加，放最後 | 一張表：`日期｜決策｜取代了什麼｜來源` |

### 改名成 `.mdx`

`.mdx` 才能嵌圖與互動元件（規則 6），所以一律優先 `.mdx`，不等到要加圖才改。改名時：

1. 用 `git mv` 改名，保留歷史
2. `grep -rn "<舊檔名>.md" docs/ .claude/ .agents/ openspec/ AGENTS.md CLAUDE.md`，把連結全部改成 `.mdx`
3. MDX 會把內文的 `{` `}` 當成 JSX、把 `<` 開頭的字當成標籤：改寫成 `\{` `\}`、`&lt;`，或放進行內程式碼（`notecraft-writing.md` §撰寫規範）
4. 改名和內容改寫分成兩個 commit，review 時才看得出哪些是改名、哪些是改寫

## 寫法規則

### 1. 正文只寫現在怎麼做

正文不寫日期、不寫「裁定」、不寫「原本是……後來改成……」、不寫「原文是筆誤」。這些全部進 `## 決策紀錄`。
標題也不帶日期或「（某某裁定）」：標題文字會變成錨點，帶日期的錨點會隨改寫失效（`notecraft-writing.md` §內部連結與錨點）。

| 不要 | 要 |
| :--- | :--- |
| **目錄分層已定案（維護者 2026-11-10 裁定）：模組內分層** `app/modules/<module>/`……ADR-022 的扁平寫法記為被覆寫 | 一個業務模組一個資料夾 `app/modules/<module>/`，裡面放自己的 router、service、repository 與 schemas。 |
| `### 相依套件的升級邊界（維護者 2026-11-15 裁定）` | `### 相依套件的升級邊界` |

### 2. 一個決策只寫一處

每個決策挑一個「家」：讀者最可能找它的那一節。其他地方只放一句話加錨點連結，不重述內容。
總表、追溯表、落差表這類彙整表只放代號、一句話與連結，不放第二份說明。

| 不要 | 要 |
| :--- | :--- |
| 同一個「模組內分層」寫在 ADR 效力總表、§後端分層、§矛盾與落差、§待決清單四處，每處各有一段說明 | 只在 §後端分層 寫；ADR 效力總表那一列寫「被覆寫，見 [§後端分層](#後端分層)」；決策紀錄一列 |

### 3. 每節先給結論，再給表或圖，最後才用文字

每節第一句是「這節要讀者記住的那一句」。接著用表、清單或圖呈現細節，文字段落只補表或圖說不清的地方。
表或圖前面那句只寫結論，不把表裡已經有的東西（來源、日期、連結、列數）再說一次；`## 待決` 與 `## 決策紀錄` 本身就是表，不加導言。

| 不要 | 要 |
| :--- | :--- |
| 開頭先講 SameSite 的原理、再講子網域攻擊、第三段才說要加 CSRF token | 「每個會改資料的請求都要帶綁定 session 的 CSRF token，由單一 middleware 驗。」接著是要素表 |
| 決策紀錄表上面寫「來源標 #105 的八列，逐題討論在 Issue #105 的留言」，而每列的來源欄已經連到那則留言 | 標題下面直接放表 |

### 4. 理由最多一句

每條規則的「為什麼」寫一句，完整論證（逐筆查證、選項比較、反例）留在 issue 或 ADR，文件只放連結。
例外：理由本身就是規則的一部分（拿掉它讀者會做錯）時可以多寫，但要放在規則的同一列或緊接的一句，不另起段落。

| 不要 | 要 |
| :--- | :--- |
| 三段編號論證，說明 dependabot 警示為什麼可以不升（scope、閘門、上游鎖版本） | 「目前不升：警示全在 development scope，而且被 `notecraftapp` 鎖住，升不上去（論證見 #N）。」接著列解除條件 |

### 5. 待決只放一處

未決事項只列在 `## 待決`。決定之後整列移進 `## 決策紀錄`、把結論寫進正文，**不留刪除線、不留「已裁定」的空列**。
正文裡碰到未決的地方，寫一句「未決，見 [§待決](#待決) 第 N 列」。

### 6. 流程與分層優先畫圖

依序發生的步驟、分層、元件之間的呼叫，用圖取代 `text` code block 或長條列；圖依 `content-visualize` skill 生成，樣式依 `docs/development/notecraft-visualize.md`。
查表式的內容（欄位、選項、對照）維持表格，不硬畫成圖。只有三五步、一眼看得完的流程，維持條列即可。

## 決策紀錄的寫法

```mdx
## 決策紀錄

| 日期 | 決策 | 取代了什麼 | 來源 |
| :--- | :--- | :--- | :--- |
| 2026-11-10 | 後端採模組內分層 `app/modules/<module>/`（[§後端分層](#後端分層)） | ADR-022 的扁平 `app/services/` | [#105](https://github.com/label-suite/label-suite/issues/105) |
| 2026-11-10 | 身分只認 httpOnly cookie | 原文「不接受 `Authorization` header 以外的來源」是筆誤 | [#107](https://github.com/label-suite/label-suite/issues/107) |
```

- 新的在下面；一個決策一列
- 「決策」欄一句話，後面連到正文的家；不在這裡重述細節
- 「取代了什麼」寫被推翻的 ADR、舊規則或筆誤；沒有就寫「—」
- 「來源」放 issue、issue 留言或 ADR 的連結；只有口頭裁定時寫「維護者口頭裁定」，並建議補一則 issue 留言

## 步驟

### 步驟 1：判斷模式

| 模式 | 判斷 |
| :--- | :--- |
| 新建 | 文件不存在 |
| 改寫 | 文件存在，使用者要精簡、整理，或要寫入一個裁定 |
| 檢查 | 使用者只想知道文件是否符合寫法 → 跳到「檢查模式」 |

### 步驟 2：盤點

1. 讀整份文件，以及所有連到它的地方：`grep -rn "<檔名>" docs/ .claude/ .agents/ openspec/ AGENTS.md CLAUDE.md`。記下被連的錨點，改寫後不能斷
2. 列出文件裡的每一個決策，標出它出現在哪幾處（規則 2）
3. 列出每一處日期、「裁定」、演變說明、筆誤說明（規則 1）
4. 列出未決事項（規則 5）與適合畫圖的流程（規則 6）
5. 找出互相矛盾、或看不出現行做法的地方——這些交給步驟 3 提問，不自行判斷

### 步驟 3：確認方向

依「提問格式」一次問完（每批最多 4 題）：

- **新建**：大綱（分哪幾節、每節一句結論）、要不要待決與決策紀錄
- **改寫**：
  - 步驟 2-5 的每個矛盾一題，選項至少有「以 A 為準」「以 B 為準」
  - 每個決策的「家」放哪一節（只有不明顯時才問）
  - 要畫成圖的流程：**現在生成（建議）**／之後再生成／維持文字
- 改寫時先挑一節做前後對照給維護者看，風格確認後再改整份（鐵律 3）

### 步驟 4：撰寫

依「文件形狀」與六條寫法規則撰寫。改寫時：

1. 先建 `## 決策紀錄`，把步驟 2-3 列出的日期與裁定逐條移進去
2. 再逐節改正文，每改完一節對照步驟 2 的決策清單，確認沒有遺漏或改變內容（鐵律 1、4）
3. 標題改名時，用 Grep 找 `#舊錨點` 並一併更新；外部連過來的錨點能不改就不改

### 步驟 5：自我檢查

- [ ] 正文與標題沒有日期、「裁定」、演變與筆誤說明（`grep -n "裁定\|20[0-9][0-9]-[0-9][0-9]-[0-9][0-9]"`，只應出現在決策紀錄與待決）
- [ ] 每個決策只有一個「家」，其他地方是連結
- [ ] 每節第一句是結論；表或圖前面那句沒有重述表裡的欄位，待決與決策紀錄沒有導言
- [ ] 沒有超過一句的理由段落，除非拿掉會讓讀者做錯
- [ ] 待決表沒有已決的列，沒有刪除線
- [ ] 步驟 2 的決策清單逐條對過：內容、範圍、例外都沒變；原本承諾的檢查與待辦都還在（鐵律 1、4）
- [ ] 步驟 2-1 記下的外部錨點都還連得到
- [ ] 副檔名是 `.mdx`；改名後沒有指向舊 `.md` 的連結
- [ ] 全文繁體中文、全形標點；符合 `notecraft-writing.md`

### 步驟 6：驗證與提交

1. 停掉 `docs:serve` 之後跑 `pnpm exec notecraftapp build docs`；改了 `.notecraft/components/` 的元件時加 `--rebuild`。build 完重開 serve，在瀏覽器看過頁面
2. 依 `AGENTS.md` §Commits 提交：type 用 `docs`、subject 結尾帶 `(#N)`；沒有對應的 open issue 時先回報、不提交

### 步驟 7：回報

```markdown
## 文件已更新

- 檔案：docs/development/xxx.mdx（原 N 行 → M 行）
- 決策紀錄：n 列；待決：n 列
- 搬動：{哪些內容從正文移到決策紀錄、待決或 issue}
- 圖：{生成了哪些、哪些維持文字}
- 未處理：{步驟 3 還沒答的矛盾}；沒有就寫「無」
```

---

## 檢查模式

只讀不寫。逐條套用步驟 5 的檢查清單，用表格回報（規則、位置、問題、建議改法），再依「提問格式」問：**依 doc-writing 改寫（建議）**／**只修指出的幾處**／**先不處理**。改寫是新工作，依 `AGENTS.md` 要先有 issue。

---

## 邊界

- 不改 `docs/specs/`、`openspec/`、`AGENTS.md`、`CLAUDE.md`、`design/prototype/`
- 不新增、不改變決策；只改它們在文件裡的寫法與位置
- 不關閉 issue；只在使用者同意後留言

## 輸出風格

繁體中文；對話中的回報簡短，細節寫在文件裡。
