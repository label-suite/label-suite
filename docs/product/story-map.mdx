# 使用者故事地圖

這份文件把 `docs/specs/` 的 20 頁規格，依使用者一路要做的事串成一張地圖：每個 story 是一個使用者目標，標出誰在做、寫在哪一頁規格、屬於 [產品路線圖](roadmap.mdx) 的哪個 Epic。它不管順序，順序只看路線圖；也不管需求內容，story 和規格說法不同時以規格為準。

## 活動主幹

活動由左到右，依 :ref[專案負責人]{id="term.project-leader"} 走完一個任務的順序排列；「個人設定與共用介面」不屬於任何一段，橫跨所有活動。

| # | 活動 | 涵蓋的規格頁 |
| ---: | :--- | :--- |
| 1 | 進入平台 | 01-01、01-02、01-03、01-05 |
| 2 | 查看儀表板 | 02-01 |
| 3 | 建立任務 | 03-02、05-03 |
| 4 | 管理任務與成員 | 03-01、03-03、05-02 |
| 5 | 執行標記 | 04-01、04-02 |
| 6 | 審核與仲裁 | 03-03、04-02 |
| 7 | 分析資料集 | 05-01、05-02 |
| 8 | 系統管理 | 06-01、06-02 |
| — | 個人設定與共用介面 | 01-04、07-01、07-02、07-03、07-04 |

每個 story 取自規格的目標、業務流程與驗收標準，一個使用者目標一列；角色用 [PRD §使用者角色](../specs/00-prd.mdx#使用者角色) 的角色。

## 互動 story map

story 的 Epic 依它連到的規格頁在路線圖 Feature 裡的位置決定，所以同一頁規格的 story 都在同一個 Epic，只有設了 `epicOverride` 的例外（側欄的未讀通知歸 E7）；E0 基礎建設收尾沒有規格頁，那一列是空的。

角色篩選選了 :ref[專案負責人]{id="term.project-leader"}、:ref[標記員]{id="term.annotator"} 或 :ref[審核員]{id="term.reviewer"} 時，:ref[平台成員]{id="term.platform-member"} 的 story 也會亮起，因為任務角色持有者本身就是平台成員（[規格 02-01 §使用角色](../specs/02-dashboard/01-dashboard.mdx#使用角色)）；選審核員時 :ref[仲裁者]{id="term.arbiter"} 的 story 也會亮起，因為仲裁者是被指定的審核員。

## 怎麼更新

story 只改 `.notecraft/components/story-map-data.ts`，圖跟著更新；本文的表要照同一份資料逐列改，兩邊不能各寫各的。

| 時機 | 要改什麼 |
| :--- | :--- |
| 規格新增、刪除或改了使用者目標 | 該頁的 story：新增、刪除或改寫那一列，角色照規格的使用角色 |
| 新增一頁規格 | 在 `SPECS` 加這一頁，story 放進對應的活動；路線圖還沒有它的 Feature 時，Epic 先標待確認並列進待決 |
| 路線圖的 Epic 改了範圍或拆併 | 不改這份的資料，Epic 從 `roadmap-data.ts` 讀；只檢查待確認與設了 `epicOverride` 的 story 是否仍然成立 |
| 待決有了結論 | 拿掉該 story 的 `epicPending`；結論和依規格頁推出的 Epic 不同時改設 `epicOverride`，把待決那一列移進決策紀錄 |
