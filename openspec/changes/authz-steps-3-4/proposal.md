# Proposal

本份是 change `authz-steps-3-4`（issue #755）的提案。範圍、設計與契約分別以 `system-analysis.md`、`system-design.md`、`ui-design.md`、`api-contract.md` 為準，這裡只收斂成「為什麼做、改了什麼、動到哪些 capability」。

**決定來源**：`system-analysis.md` 的待決 1–17 與 `system-design.md` 的 N1–N5，已在 2026-11-27 的 clarification 停點處理完（`clarification.md`）：四題由維護者決定（Q1–Q4），其餘依明確問題（P1–P13）處理。本份照決定寫，不再有條件分支；各項後面的括號是 clarification 的編號，完整對照見 [§待決問題的處理](#待決問題的處理)。

## Why

授權四段目前只做到第 1、2 段的系統角色（`openspec/specs/auth-guard/`，login-auth-guard 待決 11 已決）：伺服器知道「是誰、帳號還能不能用、系統角色是什麼」，但沒有任何一處把操作對到權限矩陣的格，也沒有附加條件的檢查位置（`backend-modules.mdx` §已知限制「授權四步的第 3、4 步」）。#720 側欄、#721 無權限與找不到頁，以及 03-02、03-03、04-01、05-02 的第一張子卡（#759、#763、#773、#782）都 blocked-by 本單；維護者在 #753 檢查點 D1（2026-11-27）裁定第 3、4 段排在 #720 前面獨立做、矩陣先以預設值 seed、編輯畫面留給 #729。依 `AGENTS.md` 的 Shared infrastructure first，這套共用機制要在第一個需要它的功能單之前交付。

## What Changes

**授權第 3 段：操作對到白名單內、已啟用的權限鍵，要求對應角色那一格為開**

- 共用層提供一份權限鍵白名單：24 個鍵（平台層 10、任務層 14）與鍵本身的屬性（層級、所屬段落、啟用與否、固定格、初始值），集中在一份登錄表（P2，`system-design.md` 方案組 B 的 B1）。鍵名沿用 repo 既有的 5 個（含 `admin.user_management.view`、`manage`），其餘 19 個採 `system-design.md` 方案組 B 的提案名；規格 06-02 寫明「沒有原始名稱」的兩個鍵也用提案名，不改規格書（P2；規格 06-02 §權限鍵與它們對應的 PRD 格 第 1–11 條、§適用格，錯層的不存 第 1–7 條）
- 判斷順序固定，任一步不通過就停、沒有預設允許：認不得的鍵與待啟用的鍵一律拒絕；鍵的層級與操作範圍不符拒絕；矩陣版本不存在拒絕；任一生效角色的格缺列拒絕（缺列不當成「關」）；生效角色的格全部為關拒絕（規格 06-02 §授權判斷的順序 第 1–8 條；ADR-004 D6；security-agent-rules S3）
- 5 個待啟用的鍵在登錄表標為未啟用，判斷時一律按認不得的鍵拒絕，矩陣仍收下它們的適用列；它們「原本的角色與資源閘門」由各操作所屬的功能卡定（P4；06-02 §五個已登錄、待啟用的鍵 第 1–10 條）
- 只看這次判斷用到的格：缺列或層級不符就拒絕該操作，不在每個請求驗整份矩陣；固定格由資料庫的檢查約束保證，系統管理員在矩陣有問題時仍進得了角色設定頁（P3，方案組 E 的 E1）
- 不快取矩陣，每次判斷讀版本與所需的格，矩陣一改下一次判斷就依新值；系統角色與任務成員身分也每次從資料庫讀（P10，方案組 D 的 D1；ADR-004 D2、D6；S3）
- 「矩陣之外」的路徑（系統管理員刪除草稿任務、全平台統計）不在共用判斷開旁路，由各自的功能卡處理（P5）
- 不放寬 PRD §權限矩陣 的任何一格，不新增任何角色；系統管理員沒有任務角色時拿不到任何任務層的鍵（PRD §權限矩陣 表下第 2 條、06-02 §授權判斷的順序 第 6 條）

**授權第 2 段的任務成員身分與第 4 段的附加條件**（Q1，方案組 A 的 A1）

- 共用層定義兩種介面：讀「某人在某任務生效中的任務角色」，以及第 4 段的一種附加條件；由持有資料的模組實作、在組裝點接上，與第 1、2 段的身分讀取同一種接法（ADR-004 D6、ADR-003 D12）。`task`、`dataset` 模組尚無程式，本次以測試替身驗證
- 任務範圍的操作，沒有生效成員身分（不是成員、已停用、仍在邀請中）一律拒絕（06-02 §授權判斷的順序 第 2、5 條）
- 一人在同一任務有多個任務角色時，任務頁面取生效角色的允許聯集，標記工作區只依選定的作用角色（P6；06-02 §一人多任務角色 第 1–7 條、§已確認決議 Q8）
- 第 4 段在格通過之後依序檢查附加條件，格為開也蓋不過它們；附加條件取 S3 與 ADR-004 D6 的四類（任務歸屬與狀態、指派與審核者身分、資料集可見性、答案隔離；`system-design.md` 方案組 A 拆成六種），每一種不通過各有一個負向測試（S3；issue #755 驗收條件第 3 列）
- **答案隔離**：宣告會讀標準答案的操作，對任何登入的人一律拒絕，沒有任何矩陣設定能打開它；這一種不需業務資料，本次實測（PRD §不是角色的讀取對象、Hard Rule 6、S5）
- 測試集辨識資訊依**作用角色**遮蔽（Q4）：本次只在附加條件預留依作用角色判斷的條件種類，**不實作遮蔽**（04-01、04-02 尚無測試集資料）

**權限矩陣的資料落地**（Q2，方案組 C 的 C1）

- 本次開 `admin` 模組：models、repository、service，加上沒有對外路由、不掛進 app 的 router 與 schemas 兩層（分層契約要求每一層都存在，`system-design.md` 技術待決 N3）；`admin` 的 service 經共用層定義的介面提供矩陣（ADR-003 D14、ADR-004 D6）
- 建 `admin_role_permission` 與 `admin_role_permission_version` 兩張表（資料表字典與 ER 既有的候選表首次落地），以一個可逆的 Alembic data migration 寫入 62 個適用格與版本列；SQLite 與 PostgreSQL 都要升級、降級、再升級
- 初始矩陣依規格 06-02 §預設矩陣 的逐格值（P1；sa 已逐格比對 PRD §權限矩陣，沒有放寬），也是回歸測試的基準；固定格（系統管理員 × 系統管理類鍵開、平台成員 × 系統管理類鍵關、兩種系統角色 × 檢視儀表板開）不能被改成別的值（06-02 §固定格不能改 第 1–5 條）
- 初始矩陣由 migration 寫入，不寫稽核事件（P11），本次不依賴 #757
- #729 只加編輯、樂觀鎖、稽核與角色設定頁，不必再建表或換資料來源

**拒絕對到的結果**（Q3，方案 R1）

| 拒絕在哪一步                                                    | 結果                                      |
| :-------------------------------------------------------------- | :---------------------------------------- |
| 第 1 步：沒有可用的登入狀態                                     | `401 AUTH_REQUIRED`（既有，不變）         |

## Capabilities

### New Capabilities

- `permission-authorization`：授權判斷在第 1、2 段（`auth-guard`）之後的行為——任務範圍操作的任務成員身分、操作對到白名單內且已啟用的權限鍵、鍵與操作範圍的層級相符、生效角色的格存在且至少一個為開、聯集與作用角色兩種取法、第 4 段附加條件優先於格、答案隔離、矩陣更新後下一次判斷依新值，以及各步拒絕的結果與錯誤外層不外露的資訊（Q1、Q3、P3–P6、P10）
- `role-permission-matrix`：權限矩陣這份資料本身——24 個權限鍵與它們的層級、啟用狀態、適用格（62 個，錯層的格不存在）、固定格的永久值、每一格的初始值與矩陣版本，以及它們落在資料庫、版本列不存在時一律拒絕（Q2、P1、P2、P4）。#729 之後在這個 capability 加編輯、樂觀鎖與讀回驗證

### Modified Capabilities

- `api-envelope`：Requirement「錯誤碼為大寫底線格式並定義第一批通用碼」的通用碼與 HTTP 狀態對應加入 `PERMISSION_DENIED`（403）（`api-contract.md` §錯誤契約：PERMISSION_DENIED）
- `database-migration`：加一條 Requirement——帳號組之後的 `admin` 組遷移建立兩張表、在 SQLite 與 PostgreSQL 產生相同的欄位與約束名稱、寫入 62 格與版本列，降回時依相反順序刪除（Q2）

不修改的既有 capability：

- `auth-guard`：第 1、2 段的行為與既有端點都不變（P9）
- `user-management`：沿用既有鍵名 `admin.user_management.view`、`manage`，拒絕回 `403` 與 R1 一致（P2、Q3）
- `backend-code-boundaries`：新的 `admin` 模組由「每個模組都受檢」的既有寫法自動涵蓋，`app.core` 仍不 import 業務模組
- `ci-quality-gates`：覆蓋率關鍵路徑清單加檔案屬清單內容，Requirement 不變

## Impact

- **後端程式**：`backend/app/core/` 新增權限鍵登錄表與第 2b、3、4 段的判斷、依賴、介面與錯誤型別；新增 `app/modules/admin/`；`app/main.py` 組裝時接上矩陣提供者（任務成員身分的實作由 `task` 模組落地時接上，沒接上時任務層的判斷大聲失敗，N2）；`app/i18n/{zh-TW,en}/messages.json` 加 `common.permission_denied`；測試新增任務成員身分與附加條件的替身，整合測試以只在測試掛載的探測路由代替受保護端點（`system-design.md` §分層與類別）
- **資料庫**：一個 Alembic revision 建兩張表並寫入初始矩陣，可逆；資料表字典與 ER 已有這兩張表，實作後標記已落地與 revision（`system-design.md` §資料模型異動）
- **API**：無新增或修改端點；錯誤契約新增 `PERMISSION_DENIED`（403）。`backend/openapi.json` 不變
- **前端**：無（`ui-design.md`）
- **常駐文件**：`error-codes.mdx`（`PERMISSION_DENIED` 與各步的 `403`／`404` 分配）、`backend-modules.mdx`（`admin` 一節、`core/` 各列、app factory、錯誤對應、新增模組檢查清單、測試輔助、已知限制）依實作校正；`endpoint-authorization.mdx` 的已知限制依實作校正；`docs/development/architecture.mdx` §待決 第 2 列結案
- **品質門檻**：授權與權限檢查的覆蓋率關鍵路徑清單加三個檔
- **後續卡**：#720、#721、#728、#729 與 #759、#763、#773、#782 依賴本次的判斷機制；`task` 模組（#763 起）實作任務成員身分的介面，`task`、`dataset` 模組實作各自的附加條件；#773、#777 追蹤 Q4 的規格回寫與遮蔽
