# 01-03 用一次性連結設定密碼

:badge[已定案]{variant="success"} :badge[變更 #291]{variant="warning"} :badge[帳號]{variant="neutral"}

> 來源：舊 repo `specs/account/004-forgot-reset-password/spec.md`（25 條），釘在 `singyichen/label-suite@faf83356`，見 `docs/specs/legacy/01-03-reset-password.ids` 的首行
> 參考畫面：`design/prototype/pages/account/forgot-password.html` 與 `design/prototype/pages/account/reset-password.html`。
> reset 頁上那三顆切換連結狀態的按鈕（有效／已過期／已使用）是 prototype 為了演示三種結果而加的，不是產品功能，規格不寫它們
> 相關規格：[規格 01-01 登入](./01-login.mdx)、[規格 01-02 註冊](./02-register.mdx)、[規格 01-05 登入狀態與安全](./05-login-state.mdx)、[規格 06-01 使用者管理](../06-admin/01-user-management.mdx)

## 目標

- 讓忘記密碼的人自己拿回帳號，不必找 :ref[系統管理員]{id="term.system-admin"}
- 在申請的那一步不透露某個 Email 有沒有註冊過，讓這一頁不能被當成查詢工具
- 讓連結失效的人看得懂下一步該做什麼，而不是停在一個打不開的畫面

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

這兩頁都在登入之前，沒有任何角色能從它們讀到既有的業務資料。

- 未登入的訪客：R（只有這兩頁本身的內容）／C（送出一次重設申請）／E (o)（用有效的連結改自己的密碼）
- :ref[平台成員]{id="term.platform-member"}、:ref[系統管理員]{id="term.system-admin"}、:ref[Seeder 管理員]{id="term.seeder-admin"}：都可以用這條路拿回自己的密碼；這一頁不區分系統角色
- 已經登入的人直接開這兩頁會怎樣，比照 [規格 01-01 §已確認決議](./01-login.mdx#已確認決議) Q3（直接前往儀表板）
- 管理員替別人開帳號、以及重發設定密碼信，都在 [規格 06-01 使用者管理](../06-admin/01-user-management.mdx)
- **受邀的使用者「設定密碼」那個畫面由這一頁擁有**（[§已確認決議](#已確認決議) Q6）：06-01 明寫「設定密碼的頁面屬於帳號模組」，把畫面交了出來，而這一頁的範圍因此從「忘記與重設密碼」擴成「**用一次性連結設定密碼**」——兩條路的畫面行為同型（開啟連結、連結失效時顯示說明與重新申請），而且 06-01 的業務流程 A1／E3 描述的就是這個 prototype
- ⚠️ **PRD 對這一頁的描述還是舊的**（`00-prd.mdx` 的 §範圍內 與 §Site Map 都寫「忘記與重設密碼」）。這一頁不改 PRD——改動由 [Issue #85](https://github.com/label-suite/label-suite/issues/85) 處理

## 規格

### 申請重設密碼

<PrototypeFrame page="account/forgot-password" caption="忘記密碼" client:idle />

1. 使用者開啟申請頁 → 顯示頁首（品牌與語言切換）、卡片標題與副標、Email 欄、「寄送重設連結」按鈕與「返回登入」
2. 使用者沒填 Email 就送出 → Email 欄旁顯示必填的說明，停在申請頁
3. 使用者填了 Email 送出 → 進入送出中（見 [§規格 › 送出中的狀態](#送出中的狀態)）
4. 送出完成 → 表單隱藏，顯示成功面板

- 這一頁只檢查 Email 有沒有填，不檢查格式也不檢查這個 Email 有沒有註冊過——理由見下一節

### 申請後看到什麼

<PrototypeFrame page="account/forgot-password" caption="忘記密碼" client:idle />

1. 不管送出的 Email 有沒有註冊過 → 一律顯示「若此 Email 已註冊，重設連結已寄出，請查收信箱。」
2. 成功面板上有「返回登入」，讓使用者直接回去等信
3. **寄不出信的時候也顯示同一句話**（[§已確認決議](#已確認決議) Q5）——告知寄信失敗就等於承認這個 Email 存在
4. 送出之後平台沒有回應 → 顯示一句可以重試的說明，Email 欄已填的內容**保留**（同 Q5）
5. 同一個人連續申請的次數上限是**每小時 5 次**；被擋住時顯示的訊息同樣不得透露帳號存不存在（同 Q5；次數的來源見[規格 01-05 §已確認決議](./05-login-state.mdx#已確認決議) Q3）

- **這句話刻意不透露這個 Email 有沒有帳號**，和 [規格 01-01 §登入失敗](./01-login.mdx#登入失敗) 的立場一致：說了就等於讓任何人把這一頁當成查詢某個 Email 有沒有註冊過的工具
- [規格 01-02](./02-register.mdx#已確認決議) Q1 已於 2026-11-09 裁定改成寄驗證信、送出一律顯示「驗證信已寄出」，所以三頁的立場現在**一致**了
- 第 3 條和[規格 06-01](../06-admin/01-user-management.mdx)相反：那一頁的新增帳號在寄信失敗時會明確告知管理員並且**不建立帳號**。差別在這條路上「告知」本身就是洩漏

### 設定新密碼

<PrototypeFrame page="account/reset-password" caption="重設密碼" client:idle />

1. 使用者點開信裡還能用的連結 → 顯示新密碼與確認密碼兩欄、「更新密碼」按鈕，以及表單底部的「返回登入」
2. 新密碼沒填 → 該欄旁顯示必填的說明
3. 新密碼要**套用和註冊同一套組成規則**：至少 8 個字元，含大寫英文、小寫英文與數字，而且**在欄位旁顯示規則**（[§已確認決議](#已確認決議) Q3）
4. 確認密碼沒填，或和新密碼不一致 → 該欄旁顯示對應的說明
5. 兩欄都通過檢查 → 進入送出中，完成後顯示成功面板
6. 成功面板上有「前往登入」，讓使用者用新密碼登入
7. 成功面板上**還要說一句**：這次重設會讓**所有裝置**的登入狀態失效，都要用新密碼重新登入（[§已確認決議](#已確認決議) Q4）

- 重設成功之後，使用者**所有裝置**上的登入狀態一律失效，都要用新密碼重新登入；這條規則由[規格 01-05 登入狀態與安全](./05-login-state.mdx)擁有，本頁不重複定義
- 第 3 條那套規則和[規格 01-02 §密碼規則](./02-register.mdx#密碼規則)**完全相同**，所以兩條路設出來的密碼強度一致；沒有這一條的話，重設就是一個繞過註冊規則的入口（[§已確認決議](#已確認決議) Q3）
- 第 7 條那一句是必要的：不說的話，使用者在另一台電腦上突然被登出會不知道為什麼（[§已確認決議](#已確認決議) Q4）

### 連結無法使用

<PrototypeFrame page="account/reset-password" caption="重設密碼" client:idle />

1. 連結的有效期是 **30 分鐘**，而且**只能使用一次**（[§已確認決議](#已確認決議) Q1）
2. 使用者點開的連結已經不能用 → 隱藏兩個密碼欄，顯示一個說明面板
3. 面板上的訊息**不分原因，一律是「連結無法使用，請重新申請」**——過期、已經用過、被作廢都是同一句（[§已確認決議](#已確認決議) Q2）
4. 面板上有「重新申請」→ 點它回到申請頁
5. 連結被作廢（例如使用者又申請了一次、密碼改過、Email 換過或帳號被停用） → **不能設定密碼，也不會顯示成重設成功**
6. **使用者再申請一次時，先前的連結一律作廢**：同一時間只有最新那一條能用（[§已確認決議](#已確認決議) Q7）

- 第 3 條**不分開講**的理由和申請頁同一條線：拿到連結的人無法從訊息差異推測帳號的狀態。它和[規格 06-01 §Q&A](../06-admin/01-user-management.mdx#qa)對設定密碼信的選擇一致
- ⚠️ 第 3 條**推翻來源自己的 `SC-004` 與使用者故事 3 的兩條驗收情境**（那兩處各要求一種面板一句話），而同一份來源的 `FR-009A` 又要求只回通用訊息——**來源自己打掃**。維護者 2026-11-09 裁定照 `FR-009A`；<mark>畫面那一側已於 2026-11-12 落地（[Issue #195](https://github.com/label-suite/label-suite/issues/195)，[PR #290](https://github.com/label-suite/label-suite/pull/290)）。那一句中文的字面是「連結無法使用，請重新申請」，英文是「This link can no longer be used. Please request a new one.」（維護者 2026-11-12 裁定）；註冊的驗證連結落地頁**共用同一句**，見[規格 01-02 §註冊成功](./02-register.mdx#註冊成功)。</mark><sup>[#291](https://github.com/label-suite/label-suite/issues/291)</sup>
- 第 6 條的理由：使用者連點幾次之後手上會有好幾封信，只讓最新的能用比較不會讓他用到舊的那一封而困惑

### 密碼的顯示與隱藏

<PrototypeFrame page="account/reset-password" caption="重設密碼" client:idle />

1. 新密碼欄與確認密碼欄預設都遮住內容 → 各自右側有一個切換顯示的按鈕
2. 使用者點某一個 → 只有那一欄變成看得見；再點一次 → 變回遮住
3. 按鈕的說明文字隨目前狀態改變，讓只讀文字的人也知道按下去會發生什麼
4. 使用者在密碼顯示中切換語言 → 保持顯示中，只有說明文字換語言

- prototype 目前切換語言時**沒有**更新這兩個按鈕的說明文字（登入頁有做到）。來源的 `FR-011`、`FR-012` 要求一致，所以規格照來源寫；實作時要補上 prototype 這一塊

### 送出中的狀態

<PrototypeFrame page="account/forgot-password" caption="忘記密碼" client:idle />

1. 使用者送出申請或送出新密碼 → 畫面立即顯示進行中的指示
2. 送出中 → **整頁其餘部分都不可互動**，包含語言切換與「返回登入」
3. 使用者在送出中重複點送出 → 只會送出一次

## 卡控機制

| 條件 | 結果 |
| :--- | :--- |
| 申請頁的 Email 為空 | 擋下送出，欄位旁顯示必填的說明 |
| 新密碼為空 | 擋下送出，欄位旁顯示必填的說明 |
| 確認密碼為空或與新密碼不一致 | 擋下送出，欄位旁顯示對應的說明 |
| 重設連結已經不能用 | 隱藏兩個密碼欄，不接受任何新密碼 |
| 連結被作廢但沒被用過 | 不設定密碼，也**不顯示成重設成功** |
| 正在送出中 | 整頁其餘部分不可互動，只會送出一次 |
| 使用者想從申請頁得知某個 Email 有沒有註冊 | 不管有沒有，回應都是同一句話 |
| 寄不出信 | **仍顯示同一句通用訊息**——告知寄信失敗就等於承認這個 Email 存在 |
| 新密碼不符組成規則 | 擋下送出，欄位旁顯示規則的說明 |
| 連結不能用 | 訊息**不分原因**，一律「連結無法使用，請重新申請」 |
| 使用者再申請一次 | 先前的連結**一律作廢**，只有最新那一條能用 |
| 同一個人每小時申請超過 5 次 | 擋住，訊息不得透露帳號存不存在 |

## 邊界情況（Edge Case）

| 情況 | 使用者看到什麼 |
| :--- | :--- |
| 送出一個從來沒註冊過的 Email | 和註冊過的一模一樣：「若此 Email 已註冊，重設連結已寄出，請查收信箱。」 |
| 同一個人連續申請很多次 | 每次都看到同一句話；**先前的連結一律作廢、只有最新那一條能用**；**每小時最多 5 次**，超過就擋住且訊息不透露帳號存不存在 |
| 兩個密碼欄都填了但不一致 | 確認密碼欄顯示不一致的說明，新密碼欄不報錯 |
| 在密碼顯示中切換語言 | 密碼保持顯示中，只有說明文字換語言 |
| 切換語言時某欄位正顯示錯誤 | 錯誤先清掉，重新送出時再依新語言顯示 |
| 送出中點語言切換或「返回登入」 | 不起作用，頁面與語言都維持原狀 |
| 同一個連結被點開兩次 | 第二次顯示連結無法使用的面板 |
| 使用者改完密碼後又去點舊的連結 | 顯示連結無法使用的面板，不能再改一次 |
| 送出後平台沒有回應 | 顯示一句可以重試的說明；已填的內容都還在 |
| 瀏覽器不讓平台記住語言，或記住的值不是兩種語言之一 | 當成繁體中文，不出現錯誤畫面 |

## 已確認決議

### Q1. 重設密碼的連結能用多久？（已定案，維護者裁定 2026-11-09）

- [x] **30 分鐘**，沿用舊 repo 既有的唯一數字
- [ ] 24 小時，與設定密碼信一致

> ⚠️ **這個數字在裁定之前依據不足。** 來源的條文（`FR` 與 `SC`）**沒有定義有效期**，只定義了「過期」是連結的其中一種狀態；30 分鐘出現在**來源隨規格歸檔的那張技術序列圖**（「一次性、有效 30 分鐘」）與它引用的 `docs/adr/013-email-service-resend.md`（`expires 30 min`）。而來源**明寫「不得以圖面作為裁定依據」**，所以這個數字需要維護者確認才算定案。
> 對照：術語表的 :ref[設定密碼信]{id="term.password-setup-email"} 與[規格 06-01](../06-admin/01-user-management.mdx)給設定密碼信定的是「**24 小時**內有效、只能使用一次」。兩種信性質接近但期限差 48 倍——**刻意不同**：重設密碼是使用者自己當下發起的，30 分鐘內就會去收信；設定密碼信是管理員代為發起的，收件人可能隔天才看到（#183）。

### Q2. 連結不能用的時候，要不要告訴使用者是哪一種原因？（已定案，維護者裁定 2026-11-09）

- [x] **不分開講**，一律顯示「連結無法使用，請重新申請」
- [ ] 分開講：過期、已經用過各自一句話

> ⚠️ **來源自己打掃。** `FR-009A` 要求被作廢的連結**只能回通用的「連結無法使用」、不得顯示「已使用」**；但同一份來源的 `SC-004` 與使用者故事 3 的驗收情境**又各要求兩種面板各一句**。
> 而 **#195 之前的 prototype 是分開講的**（「此連結已過期，請重新申請。」與「此連結已使用，請重新申請。」），那兩句現在畫面上已經沒有了。
> 維護者裁定照 `FR-009A`：拿到連結的人無法從訊息差異推測帳號的狀態，和[規格 06-01 §Q&A](../06-admin/01-user-management.mdx#qa)對設定密碼信的選擇一致。
> **所以這一條不只改文案**：`SC-004` 與那兩條驗收情境在[§附錄：舊編號對照](#附錄舊編號對照)註明經裁定改寫，<mark>畫面那一側已於 2026-11-12 落地（[PR #290](https://github.com/label-suite/label-suite/pull/290)）</mark><sup>[#291](https://github.com/label-suite/label-suite/issues/291)</sup>。

### Q3. 重設時的新密碼要不要套用和註冊一樣的組成規則？（已定案，維護者裁定 2026-11-09）

- [x] **要**，與[規格 01-02](./02-register.mdx#密碼規則)一致：至少 8 個字元，含大寫英文、小寫英文與數字，而且在欄位旁顯示規則
- [ ] 不要，只檢查必填與兩次一致

> 理由：**來源的重設流程只驗必填與一致，沒有任何組成規則**——所以在這一條之前，走這條路可以把密碼改成一個字元。註冊那條路有規則、重設這條路沒有，等於留了一個**繞過規則的入口**（#183）。

### Q4. 重設成功後要不要在畫面上告訴使用者「所有裝置都會被登出」？（已定案，維護者裁定 2026-11-09）

- [x] **要**，在成功面板多一句說明
- [ ] 不要，只顯示重設成功

> 理由：「所有裝置的登入狀態一律失效」這件事**來源已經拍板**——來源在條文之外明寫這個結果由 `account-020` 定義（也就是[規格 01-05](./05-login-state.mdx)），該處的 `FR-007` 要求重設成功時撤銷**全部**登入狀態，並特別註明「不得用圖面省略推定舊登入狀態仍然有效」；prototype 的成功文案「密碼重設成功，請重新登入。」也站在同一邊。
> **真正沒人交代的只有「要不要在畫面上說一句」**。不說的話，使用者在另一台電腦上突然被登出會不知道為什麼。
> 這一題和[規格 01-05 §已確認決議](./05-login-state.mdx#已確認決議) Q4（被動登出的文案）是同一組，同日一併裁定（#183）。

### Q5. 寄不出信、送出失敗或同一個人連續申請很多次，使用者看到什麼？（已定案，維護者裁定 2026-11-09）

- [x] 寄不出信時**仍顯示同一句通用訊息**；送出失敗顯示可以重試的說明並保留已填；申請次數**每小時 5 次**
- [ ] 其他

> 理由：來源因為只做前端原型都沒有定義「送出失敗」。送出失敗那一半是**帳號模組四頁統一**的裁決（另見[規格 01-01](./01-login.mdx#已確認決議) Q1、[規格 01-02](./02-register.mdx#已確認決議) Q3、[規格 01-04](./04-profile.mdx#已確認決議) Q9）。
> **寄不出信這一半比較特別**：[規格 06-01](../06-admin/01-user-management.mdx)的新增帳號在寄信失敗時會明確告知管理員並且不建立帳號，但這一頁**不能那樣做**——告知就等於承認這個 Email 存在。
> 申請次數的 5 次／小時由[規格 01-05 §已確認決議](./05-login-state.mdx#已確認決議) Q3 同日定下（#183）。

### Q6. 受邀的使用者「設定密碼」那個畫面由哪一份規格擁有？（已定案，維護者裁定 2026-11-09）

- [x] **本頁一併擁有**：兩條路都是用一次性連結設定密碼，畫面也共用同一個 prototype
- [ ] 另開一頁規格

> 理由：[規格 06-01](../06-admin/01-user-management.mdx)明寫「設定密碼的頁面屬於帳號模組」，把畫面交了出來；而這一頁原本只寫忘記密碼這條路，等於**這個畫面在 18 頁裡沒有任何一頁擁有**。
> 兩條路的畫面行為同型（開啟連結、連結失效時顯示說明與重新申請），而且 06-01 的業務流程 A1／E3 描述的就是這個 prototype。
> **所以這一頁的範圍擴成「用一次性連結設定密碼」，標題也跟著改**（原本是「忘記與重設密碼」）。模組索引與[規格總索引](../index.mdx)的模組地圖已同步。
> ⚠️ **PRD 對這一頁的描述還是舊的**（§範圍內 與 §Site Map 都寫「忘記與重設密碼」）——這一頁不改 PRD，改動由 [Issue #85](https://github.com/label-suite/label-suite/issues/85) 處理（#183）。

### Q7. 使用者再申請一次時，先前的連結要不要作廢？（已定案，維護者裁定 2026-11-09）

- [x] **要**，只有最新一條連結能用
- [ ] 不要，每一條在自己的有效期內都能用

> 理由：來源的 `FR-009A` 把「重發過」列為連結被作廢的原因之一，但那是 06-01 那條路的用語（而且 06-01 的重發**只對尚未設定密碼的帳號**出現，忘記密碼的人一定已經設過密碼，套不上）。
> 忘記密碼這條路對應的動作是「再申請一次」，而**來源沒有任何條文說再申請會不會讓先前的連結失效**。
> 裁定作廢的理由：使用者連點幾次之後手上會有好幾封信，只讓最新的能用比較不會讓他用到舊的那一封而困惑（#183）。

### Q8. 申請成功的訊息要不要透露這個 Email 有沒有註冊過？（已定案，沿用舊來源）

- [x] 不透露，一律顯示同一句通用訊息
- [ ] 透露

> 理由：來源的 `FR-004` 明訂「成功面板文案必須為不揭露帳號存在性的通用提示」，`SC-002` 與邊界情況也各寫了一次；prototype 的文字「若此 Email 已註冊，重設連結已寄出，請查收信箱。」與它一致。
> 這和 [規格 01-01](./01-login.mdx) 的登入失敗訊息是同一個立場（#71）。

### Q9. 送出中其他東西能不能點？（已定案，沿用舊來源 2026-05-22）

- [x] 整頁其餘部分都不可互動，包含語言切換與「返回登入」
- [ ] 只有送出按鈕停用

> 理由：來源的 Clarifications 已拍板「全頁不可互動（包含語言切換、返回登入等連結）」，`FR-003`、`FR-008` 與 `SC-006` 也各寫了一次。與 [規格 01-01](./01-login.mdx) 的送出中處理一致（#71）。

### Q10. 被作廢但沒用過的連結要怎麼回應？（已定案，沿用舊來源）

- [x] 不能設定密碼，回覆通用的「連結無法使用」，不得顯示「已使用」或重設成功
- [ ] 顯示「已使用」

> 理由：來源的 `FR-009A` 與 `SC-004A` 明訂這條。連結會被作廢的情況包含又申請了一次、密碼改過、Email 換過或帳號被停用；顯示「已使用」會讓使用者以為是自己用掉的，顯示成功更會讓他以為密碼改好了（#71）。

### Q11. 連結失效的面板上要放什麼操作？（已定案，沿用舊來源）

- [x] 一個「重新申請」，導向申請頁
- [ ] 只顯示說明，不給操作

> 理由：來源的 `FR-010` 明訂。使用者在這個畫面只有一條路可走，直接給他比讓他自己找回去快（#71）。

## Q&A

:::tip{title="為什麼申請頁連 Email 格式都不檢查？" collapsible}
因為檢查了也沒有用。這一頁不管使用者填什麼都回同一句話，格式錯的 Email 自然收不到信——結果和填了一個沒註冊過的 Email 一樣。多一道格式檢查只會讓「填對格式但沒註冊」和「格式就錯了」兩種人看到不同的畫面，反而多洩漏一點資訊。
:::

:::tip{title="為什麼寄不出信也不能告訴使用者？" collapsible}
告訴他就等於承認這個 Email 在平台上有帳號——否則平台根本不會去寄信。這和 [規格 06-01](../06-admin/01-user-management.mdx) 新增帳號時寄信失敗要明確告知管理員不一樣：那裡的管理員本來就知道這個帳號存在，是他自己填的。
:::

:::tip{title="為什麼改完密碼之後，舊的連結就不能再用一次？" collapsible}
一個重設連結代表一次「我忘記密碼了」的申請。密碼改好之後那個申請就結束了。如果連結還能用，任何拿到那封信的人（包括日後翻到舊信的人）都能再改一次密碼，而真正的帳號主人不會收到任何通知。
:::
