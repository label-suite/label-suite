# 候選資料表字典與關聯限制

:badge[Issue #235]{variant="neutral"} :badge[規劃結構，非已落地]{variant="warning"}

> 這一份是 [#233](https://github.com/label-suite/label-suite/issues/233) 三步的**第二步**。
> 第一步是[資料欄位盤點總帳](./data-field-inventory.mdx)（哪些資料要存），第三步是 [#236](https://github.com/label-suite/label-suite/issues/236)（以 ER 外掛呈現）。
>
> **第三步已經交付**：[候選資料表 ER 圖](/view/diagrams/architecture/database-schema.er)。那份 `docs/diagrams/architecture/database-schema.er.json` 是**從本文件產生的**——表名、中文標籤、型別、可空性、單欄 FK、分組與表說明都來自這裡，所以本文件改了而圖沒跟著重新產生，就是圖錯了，不是本文件錯了。
> 圖上**畫不出來**的兩類東西——**複合 FK** 與**只能在應用層擋的限制**——只在本文件裡，逐條內容在各組的「組的關聯與限制」小節（[`admin`](#admin-組的關聯與限制)、[`dataset`](#dataset-組的關聯與限制)、[`run`](#run-組的關聯與限制)、[`annotation` 與 `review`](#annotation-與-review-組的關聯與限制)），以及 `task_reviewer_roster_member` 與 `task_trial_round` 自己的限制表。**圖上沒有線不代表沒有限制。**
> **複合 FK 不寫條數**：初版的「34 組」把三個指路格重複計入，而 §十 自己的數法對「延後」「自指」這兩種寫法沒有定（見[§十 統計與驗收對照](#十統計與驗收對照)）。應用層與 DB 的條數留著，那兩個數有精準的數法。

:::warning{title="這裡沒有任何已落地的資料結構"}
`backend/` 不存在、`backend/alembic/versions/` 沒有任何 revision、也沒有 ORM model。**本文件每一張表都是候選設計**。

要查「實際落地了什麼」，唯一的辦法是讀 Alembic revision 與資料庫 metadata——**不是讀這一份**。prototype 的 `localStorage` 與 fixture 也不是資料表。
:::

| 邊界 | 說明 |
| :--- | :--- |
| 權威是規格 | 每一欄的「規格來源」指回 `docs/specs/`。原始規劃的六份字典與原始 repo 的 `database-schema.er.json` 是**對照組**，它的結論要經本專案規格驗證才採用 |

| 不裁決 | 規格沒定的一律標待決並指回盤點總帳的編號，**不以原始 repo 或 prototype 代答** |

## 一、範圍與起點

### 候選表從 40 張變成 37 張

| 項目 | 數 | 說明 |
| :--- | ---: | :--- |
| 原始規劃 | **40 張 / 352 欄 / 34 單欄 FK** | 解析原始 repo 的 `database-schema.er.json` 核對過 |
| D7 移除 | **−3 張 / −22 欄 / −2 單欄 FK** | `refresh_tokens`、`shared_idempotency_record`、`task_run_reviewer_candidate`——**本專案規格完全沒提到**，維護者 2026-11-11 裁定先拿掉 |
| 本文件 | **37 張 / 328 欄 / 38 單欄 FK** | 複合 FK 另列於各組的§關聯 |

移除不是「不需要那個機制」。更新權杖、冪等紀錄與審核員候選名單在實作時都可能真的需要，但那時要另開 issue 寫清楚為什麼——**這樣字典裡每一張表都追得到規格**。其中 **4 張是另一種形態**：結構由別頁的規則決定、本來就沒有自己的條文（維護者 2026-11-12 裁定 D11，見[盤點總帳 §五](./data-field-inventory.mdx#五裁定紀錄與待裁決)）。

**維護者 2026-11-11 另裁：D7 的理由同樣適用到欄位。** 所以原始規劃有、但本專案規格完全沒提到的**六個欄位**也一併不收：

| 原始欄位 | 原本是什麼 |
| :--- | :--- |
| `users.google_subject` | Google 帳號的固定識別碼 |
| `users.is_seeder` | 系統初始化建立的超管 |
| `users.credential_version` | 高風險憑證事件的版本，用來讓舊 JWT 立即失效 |
| `task_config_version.schema_version_no` | 同列的資料結構版本 |
| `task_config_version.schema_digest` | 規格化 outputs 與欄位用途的摘要 |
| `task_config_version.schema_registry_version` | 驗證定義的版本 |

同一條原則：**沒有規格依據就不留**，需要時另開 issue 寫清楚為什麼。所以本文件比原始這 37 張的 330 欄**少這六欄、另新增四欄**，合計 328。

### 逐欄要記的九項

| 欄 | 內容 |
| :--- | :--- |
| 識別碼 | 英文欄名。表名與欄名**一律英文**，讓程式與資料庫精確引用 |
| 中文意義 | 這一欄在業務上是什麼。讀圖與讀字典時用 |
| 型別 | 候選型別。`timestamptz` 一律 **UTC 儲存、顯示時依瀏覽者裝置時區轉換**（依[規格 06-01](../../specs/06-admin/01-user-management.mdx#資料欄位)的時區判例） |
| 可空 | `NOT NULL`、**可空**（空值有業務意義，意義寫在備註）、或**系統寫入**（使用者不能直接改） |
| 鍵／限制 | PK、唯一、FK（含刪除行為）、CHECK、索引。**只寫能落在 DB 的** |
| 規格來源 | 指回 `docs/specs/` 的頁與章節。**沒有來源的欄位不得存在** |
| 分類 | 沿用[盤點總帳](./data-field-inventory.mdx)的六種：持久／內嵌／推導／暫時／瀏覽器／待決。字典只收**持久**與**內嵌** |

每一張表另記**用途、寫入者、讀取權限、不可變與版本界線、保留規則**；**推導欄位不進字典**，它們列在每組的§不進表的推導值。

**有三頁規格不持有業務資料，所以沒有任何一張表以它們為來源**（維護者 2026-11-11 裁定，見[盤點總帳 §五](./data-field-inventory.mdx#五裁定紀錄與待裁決) D9）。**這不是推測，三頁的規格自己就這樣寫**：[07-01 側欄](../../specs/07-shared/01-sidebar.mdx#資料欄位)「側欄自己不持有業務資料，只讀取與記住使用者的偏好」、[07-02 工作區頁籤](../../specs/07-shared/02-workspace-tabs.mdx#資料欄位)「頁籤是使用者自己的工作狀態，不含任何業務資料」、[05-01 分析列表](../../specs/05-dataset/01-analysis-list.mdx#資料欄位)「這一頁的欄位**全是唯讀摘要**；**沒有任何一欄含答案內容**」（完成率是「上游算好的摘要，列表不得推導或計算」，它讀的是 05-02 的計算結果）。
這和帳號層的**權威頁慣例**是同一回事：缺的不是來源，是一句說明。

## 二、`account` 帳號（5 張）

**權威頁是 [01-05 登入狀態](../../specs/01-account/05-login-state.mdx#資料欄位)**——規格自己寫明它「不定義任何畫面欄位，上表是其他頁共用的規則依據」，而且「表中沒有任何一欄是使用者可以直接編輯的」。所以帳號層欄位的來源一律記 01-05，01-01 到 01-04 是讀它。

### `users` — 平台帳號

一列代表一位可登入的使用者。**PRD 明寫帳號沒有刪除，只有停用與啟用**，所以**不得有軟刪除欄**。

| 識別碼 | 中文意義 | 型別 | 可空 | 鍵／限制 | 規格來源 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | 帳號的內部識別碼 | `uuid` | NOT NULL | **PK** | — |
| `email` | 登入帳號，也是寄信地址 | `varchar(254)` | NOT NULL | **唯一**（`lower(email)`） | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：**正規化後判重**；上限 254 字**在正規化之後計算** |
| `name` | 顯示名稱 | `varchar(100)` | NOT NULL | CHECK 長度 1–100 | [01-04](../../specs/01-account/04-profile.mdx#資料欄位)：1–100 字；[06-01](../../specs/06-admin/01-user-management.mdx#資料欄位)：**可以和其他帳號重複** |
| `contact_info` | 使用者自填的聯絡方式 | `varchar(255)` | NOT NULL，**預設空字串** | CHECK 長度 ≤ 255 | [01-04](../../specs/01-account/04-profile.mdx#資料欄位)：可留空；最多 255 字。規格只說「可留空」、沒說怎麼表示空，所以**沿用原始規劃的 `NOT NULL default ''`**，與本文件其他「選填但欄位必填」的欄一致 |
| `avatar_url` | 頭像位置 | `text` | **可空** | — | [01-04](../../specs/01-account/04-profile.mdx#資料欄位)：空值＝未上傳，**顯示預設頭像**。檔案另存，這裡只存位置 |
| `hashed_password` | 密碼雜湊 | `varchar` | **可空** | — | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：**空值＝沒有本地密碼，只能用 Google 登入**；[01-04](../../specs/01-account/04-profile.mdx#密碼設定) 的密碼區塊因此少一欄。**原文不得落庫** |
| `role` | 平台層級角色 | `varchar` | NOT NULL | CHECK 限 `user`／`super_admin` | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：平台成員／系統管理員。**不是任務內角色**（那在 `task_membership.task_role`） |
| `is_active` | 是否啟用 | `boolean` | NOT NULL | — | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：**停用立刻讓所有登入狀態失效**；[06-01](../../specs/06-admin/01-user-management.mdx#資料欄位)：新增的帳號為啟用 |
| `created_at` | 建立時間 | `timestamptz` | 系統寫入 | — | [06-01](../../specs/06-admin/01-user-management.mdx#資料欄位)：**不可修改**；列表顯示到日，依瀏覽者裝置時區 |
| `updated_at` | 最後修改時間 | `timestamptz` | 系統寫入 | — | — |

**待決的兩欄**（原始規劃有、本專案規格沒有對應）：

| 原始欄 | 為什麼不收 |
| :--- | :--- |
| `google_subject` | 01-05 只寫「沒有本地密碼時只能用 Google 登入」，**沒有定** Google 帳號怎麼識別。那是實作機制；需要時另開 issue |
| `is_seeder`、`credential_version` | 本專案規格完全沒提到系統初始超管與憑證版本。同 D7 的理由——**沒有規格依據就不留** |

| | |
| :--- | :--- |
| **寫入者** | 本人改 `name`、`contact_info`、`avatar_url`、`hashed_password`（[01-04](../../specs/01-account/04-profile.mdx)）；系統管理員改 `role`、`is_active`（[06-01](../../specs/06-admin/01-user-management.mdx)）；`email` **只能走換 Email 流程**，不直接改 |
| **讀取權限** | 本人讀自己全部；系統管理員讀全部（[06-01](../../specs/06-admin/01-user-management.mdx) 那六列**平台成員一律看不到**）；其他角色只讀 `name` 與頭像 |
| **不可變** | `id`、`created_at` |
| **保留** | **沒有刪除**。PRD 明寫只有停用與啟用 |

### `account_session` — 一次登入的工作階段

一列代表一次登入。[01-05](../../specs/01-account/05-login-state.mdx#資料欄位) 的四個時間與狀態欄全在這裡。

| 識別碼 | 中文意義 | 型別 | 可空 | 鍵／限制 | 規格來源 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | 一次登入的識別碼 | `uuid` | NOT NULL | **PK**；`(user_id, id)` 另供複合 FK 父鍵 | — |
| `user_id` | 這次登入的帳號 | `uuid` | NOT NULL | **FK → `users.id`，RESTRICT**；索引 | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位) |
| `started_at` | 登入狀態的開始時間 | `timestamptz` | NOT NULL | — | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：絕對上限從這一刻起算，**之後的使用不會改變它** |
| `last_seen_at` | 最後一次使用的時間 | `timestamptz` | NOT NULL | — | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：閒置限制從這一刻起算，**每次使用就更新**。**原始規劃沒有這一欄，本專案新增** |
| `revoked_at` | 失效時間 | `timestamptz` | **可空** | — | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：空值＝未失效。**任何原因都算**，含登出、安全撤銷與自然到期 |
| `logged_out_at` | 明確登出的時間 | `timestamptz` | **可空** | **CHECK** `logged_out_at IS NULL OR (revoked_at IS NOT NULL AND logged_out_at <= revoked_at)` | [01-05](../../specs/01-account/05-login-state.mdx#資料欄位)：**只記可驗證的明確登出**；有值時該段必然已失效，**且不晚於失效時間** |

**`RESTRICT` 的理由**：工時區間（`task_work_interval`）與歷程事件（`annotation_history_event`）都參照登入工作階段當責任證據，刪掉它會讓歷史無法追溯。而帳號本來就沒有刪除，所以 `RESTRICT` 不會卡住任何合法操作。

| | |
| :--- | :--- |
| **寫入者** | 全部**系統寫入**。[01-05](../../specs/01-account/05-login-state.mdx#資料欄位) 明寫「表中沒有任何一欄是使用者可以直接編輯的」 |
| **讀取權限** | 本人與系統管理員 |
| **不可變** | `started_at` 建立後不再變；`revoked_at` 一旦有值不再回復 |
| **保留** | 保留期限**未定**，見盤點總帳的[待決 D3](./data-field-inventory.mdx#五裁定紀錄與待裁決)（[#196](https://github.com/label-suite/label-suite/issues/196)） |

### `account_password_token` — 密碼重設與邀請連結

重設密碼與受邀設定密碼**共用一張一次性連結表**。

| 識別碼 | 中文意義 | 型別 | 可空 | 鍵／限制 | 規格來源 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `id` | 流水號 | `bigint` | NOT NULL | **PK** | — |
| `user_id` | 連結所屬帳號 | `uuid` | NOT NULL | **FK → `users.id`，CASCADE**；索引 | — |
| `purpose` | 用途 | `varchar` | NOT NULL | CHECK 限 `reset`／`invite` | [01-03](../../specs/01-account/03-reset-password.mdx#資料欄位) 重設；[06-01](../../specs/06-admin/01-user-management.mdx#資料欄位) 的「重發設定密碼信」 |
| `token_hash` | 連結權杖的雜湊 | `char(64)` | NOT NULL | **唯一** | **原文不得落庫**。[01-03](../../specs/01-account/03-reset-password.mdx#資料欄位) 的連結只能用一次 |
| `expires_at` | 到期時間 | `timestamptz` | NOT NULL | — | [01-03](../../specs/01-account/03-reset-password.mdx#資料欄位)：**有效期 30 分鐘** |
| `used_at` | 成功使用的時間 | `timestamptz` | **可空** | — | [01-03](../../specs/01-account/03-reset-password.mdx#資料欄位)：空值＝尚未成功使用，**不代表仍有效** |
| `invalidated_at` | 作廢時間 | `timestamptz` | **可空** | — | [01-03](../../specs/01-account/03-reset-password.mdx#資料欄位)：空值＝未作廢，**仍須核對期限與 `used_at`** |
| `created_at` | 寄出時間 | `timestamptz` | 系統寫入 | — | — |

**三個欄位不能合成一個狀態欄。** [01-03](../../specs/01-account/03-reset-password.mdx#資料欄位) 的「重設連結的狀態」是**推導值**：不能用含過期、已用過、被作廢**三種**，而規格要求**畫面上不分原因**——那是顯示規則，不是儲存規則。稽核仍要分得出來是哪一種。

| | |
| :--- | :--- |
| **寫入者** | 全部系統寫入 |
| **讀取權限** | **沒有任何使用者讀得到**；只有驗證流程比對雜湊 |

## 六、`run` 發布與執行（8 張）

這一組承接[盤點總帳§二](./data-field-inventory.mdx#二九條流程的反查)九條流程反查出的**六項**——發布週期、設定與資料的發布快照、紀錄有效性、審核單位、仲裁定址、匯出請求與執行分離。前四項落在這一組。

**這組的複合 FK 最多，而理由只有一個**：[#235](https://github.com/label-suite/label-suite/issues/235) 工作項 4 要求「避免合法 ID 被錯接到另一個上下文」。單欄 FK 只保證「那個 ID 存在」，擋不住「它屬於另一個任務／另一個週期」。

### IAA 的兩套東西，不可混用

[#235](https://github.com/label-suite/label-suite/issues/235) 工作項 7 要求核對試標閘門 IAA 與分析報告的關係。盤點結果是**兩套，不是一套**：

| | 試標閘門 | 分析報告 |
| :--- | :--- | :--- |
| 落在哪 | **`task_trial_iaa_result`**（每回合最多一份） | **不落表**——維護者 2026-11-11 裁定[全部現算](./data-field-inventory.mdx#五裁定紀錄與待裁決)（D4） |
| 規格頁 | [03-03](../../specs/03-task-management/03-task-detail.mdx#資料欄位) 的「最新 IAA」（**唯讀**） | [05-02](../../specs/05-dataset/02-analysis-detail.mdx#資料欄位) 的逐型 IAA 與標記員層級分析 |
| 誰算 | 發布後的計算，狀態記在 `task_trial_round.iaa_computation_status` | 每次讀取重算 |
| 用途 | **狀態機的前置條件**：轉入「等待 IAA 確認」要有可信的結果 | 給人看的品質監控 |
| 可追溯性 | `algorithm_version` 加 `input_digest` 加 `result_schema_version` 三欄一起，讓同一次計算可重現 | 現算，不需要追溯——重算就是最新的 |

**「最新 IAA」的擁有者是 05-02 而不是 03-03。** [03-03](../../specs/03-task-management/03-task-detail.mdx#資料欄位) 明寫它「**唯讀**；怎麼算由 05-02 擁有」。而 [05-02](../../specs/05-dataset/02-analysis-detail.mdx#資料欄位) 的「IAA 狀態」是 [05-01](../../specs/05-dataset/01-analysis-list.mdx#資料欄位) 徽章的**唯一來源**，且**不得由單一型別代表整體**。

所以資料流是單向的：`task_trial_iaa_result` 存閘門需要的結果 → 03-03 唯讀顯示「最新 IAA」；05-02 現算逐型報告 → 05-01 的徽章讀 05-02。**兩條路不交叉，也不互為來源。**

**`answer_payload` 的結構**（[04-02](../../specs/04-annotation/02-annotation-workspace.mdx#資料欄位) 的「標記員的作答」逐欄）：

**`note` 這一欄留著但本專案不渲染。** [04-02](../../specs/04-annotation/02-annotation-workspace.mdx#工作區不得有存不了的備註欄) 明寫工作區「**不渲染任何沒有持久化路徑的備註欄**」，而它確實有持久化路徑——所以不是「不該存」而是「目前沒有畫面」。**吸附單位不進表**：規格明寫它「只影響滑鼠落點，不影響存下來的值」。

| §關聯與限制 的限制條數 | **24 條落在 DB**、**22 條只能在應用層擋**。數法：**表頭正好是「限制／層級/內容」的那五張表**合計 46 列——`admin`、`dataset`、`run`、`annotation` 與 `review` 四個組的「組的關聯與限制」，加上 `task_reviewer_roster_member` 自己的限制表。`dataset_version` 的「怎麼落」表（它的三列是 `dataset` 組那張的重述）與 `task_trial_round` 的「條件/層級/內容」表（跨欄位條件，不是限制）**不計入** |
