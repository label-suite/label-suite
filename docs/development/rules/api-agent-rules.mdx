# API 契約與前端 Client 規範

這份文件說明 API 契約與前端 client 這一塊的規則，由 `AGENTS.md` 的 Agent Rules Index 指過來；`AGENTS.md` 是規則本體，兩邊說法不同時以 `AGENTS.md` 為準，並回報給維護者。
跨領域規範在 [agent-rules.mdx](agent-rules.mdx)、後端分層與資料在 [backend-agent-rules.mdx](backend-agent-rules.mdx)、授權與答案隔離在 [security-agent-rules.mdx](security-agent-rules.mdx)，這裡不重複。
各規範的反例、例外與檢查方式收在收合區塊，預設收起；那是實作與審查時才查的細節。

**`backend/` 與 `frontend/` 目前都不存在**，所以下面每一條的「檢查方式」幾乎都還沒有自動檢查。標「待建置」就是字面意思：那些檢查要等實際有程式與 CI 才寫得出來，**不得因為這份文件存在就宣稱契約已被強制**。

## 前提

開工前先確認這六件事；各自的完整規則在對應的 A 條。

| 前提 | 現行做法 | 規則在 |
| :--- | :--- | :--- |
| 路徑前綴 | **`/api/v1`**（見 [architecture.mdx §API 契約](../architecture.mdx#api-契約)） | A1 |
| operationId | 由 FastAPI 的 `generate_unique_id_function` 固定成「動詞加資源」，不手寫也不逐個覆寫 | A1 |
| 成功回應格式 | 包一層 envelope；`204` 無 body、檔案與串流是明文例外 | A1 |
| 前端型別與 client 生成 | **Orval**，由後端匯出的 `openapi.json` 產生到 `frontend/src/api/generated/` | A5 |
| Bruno | 可選的手動工具，沒有 pre-PR 關卡；唯一的契約真相是 `api-contract.md` 加 `openapi.json` | A4 |
| i18n | 兩層；前端只負責 UI 字串，後端 `detail` 由後端依 `Accept-Language` 解析 | A8 |

## 規範

每一條都有適用路徑、禁止事項、正例；反例、例外、檢查方式收在收合區塊。

### A1 路由、HTTP status、operationId 與回應外層

每個端點都掛在 `/api/v1` 底下、資源名直接接在後面，operationId 由 `generate_unique_id_function` 算成全專案唯一的「動詞加資源」，`200` 的回應包一層 envelope。
envelope 的欄位未決，見 [§待決](#待決) 第 1 列。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**` 的 router、`openspec/changes/*/api-contract.md` |
| **禁止** | 端點不帶 `/api/v1` 前綴；路徑在 `/api/v1` 之後插一段模組名；operationId 與既有端點撞名卻不處理；手寫或逐個覆寫 operationId；讓 operationId 從 Python 函式名推導；自由心證地擴大 envelope 的例外；非 CRUD 動作用動詞式路徑而不在 api-contract 寫理由；建立成功回 `200`、刪除成功回 `200` 帶 body |
| **正例** | `GET /api/v1/tasks` → `listTasks`；集合端點用複數名詞；**operationId 全專案唯一**；非 CRUD 動作寫成 subresource（`/tasks/{id}/assignments`）、狀態轉移資源（`/submissions/{id}/status-changes`）或命令資源（`/exports`）。成功 status：讀取與更新 `200`、**建立 `201` 並帶 `Location` header**、刪除 `204` 無 body。`200` 的回應包一層 envelope；`204`、檔案與串流在 api-contract 標成例外 |

:::note{title="A1 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `POST /api/v1/tasks/{id}/doPublish`（動詞式又沒記理由）；`@router.get(..., operation_id="get_task_by_id_v2")`（逐個覆寫）；「這個端點只回一個布林，所以不包 envelope」 |
| **例外** | `204` 無 body、檔案下載與串流不套 envelope。**例外要逐一寫進該 change 的 `api-contract.md` 並寫出理由**，不逐案自由心證（見 [architecture.mdx §API 契約](../architecture.mdx#api-契約)） |
| **檢查方式** | **待建置**。前綴與複數名詞可用自寫腳本掃匯出的 `openapi.json`；operationId 的穩定性靠 A10 的 snapshot diff。兩者都要等 `backend/` 與 CI 存在 |
:::

:::note{title="A1 的路徑不帶模組段" collapsible}
原始 repo 的 route pattern 寫 `/api/v1/[module]/[resource]`，本 repo 沿用但去掉模組段，依據是本 repo 自己的例子：[architecture.mdx](../architecture.mdx) §非同步任務 的流程圖寫的是 `GET /api/v1/submissions/{id}/status`，**資源直接接在 `/api/v1` 後面**；非 CRUD 的三個 pattern（`/tasks/{id}/assignments`、`/submissions/{id}/status-changes`、`/exports`）也都不帶；而 operationId 是「動詞加資源」，模組名不進那個名字。後端的模組邊界由目錄（`app/modules/<module>/`）表達，不由路徑表達。
:::

:::note{title="A1 的 operationId 撞名與函式名" collapsible}
**「全專案唯一」不等於「動詞加資源」就自動成立。** 兩個不同父資源底下的同名子資源會算出同一個名字：`/api/v1/tasks/{id}/members` 與 `/api/v1/projects/{id}/members` 都是 `listMembers`。規則：**撞名時在該 change 的 `api-contract.md` 把名字加上父資源**（`listTaskMembers`），並寫一行理由；不改成手寫覆寫，`generate_unique_id_function` 仍是唯一的產生處。

**operationId 不得依賴函式名自動生成。** `generate_unique_id_function` 必須從 **method 與資源路徑**算出「動詞加資源」，**不得從 handler 的 Python 函式名推導**；否則把 `get_task` 重新命名成 `read_task` 會悄悄改掉前端 hook 的名稱。原始 repo 要求每條 route 顯式寫 `operation_id=` 來防這件事，本專案採不同機制，見 [附錄：刻意不採用的來源條文](#附錄刻意不採用的來源條文)。
:::

### A2 request 驗證與 response 建模

每個 request 的 body、query、path 都要宣告型別與範圍，每個 response 都要明確建模、不回裸 ORM model；未知欄位政策是 `extra="forbid"`，在共用 base 上設定一次。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**/schemas/**`、同模組的 router |
| **禁止** | 回傳裸 ORM model；省略 `response_model=`；body、query、path 任一處少了型別或範圍驗證；未知欄位政策靠框架預設而沒寫出來；敏感欄位先回前端再由前端遮蔽；逐個端點把 `extra` 改成 `ignore` |
| **正例** | 所有 schema 繼承共用 base（`from_attributes=True`、`extra="forbid"`，一處設定全專案生效）；`limit: int = Field(ge=1, le=100)`；query 參數宣告型別讓 FastAPI 轉型；回應明確建模，欄位與 nullable 都寫進 api-contract |

理由：Pydantic v2 的預設 `ignore` 會把打錯的欄位名靜默丟掉，呼叫端以為設定生效、實際沒有；代價是前端先部署、後端還沒加那個欄位時整個請求會被拒絕，而不是忽略多餘欄位。

:::note{title="A2 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `return task`（直接回 SQLAlchemy model）；`@router.get("/tasks")` 沒有 `response_model=`；後端回完整的 `email` 再由前端顯示成 `***` |
| **例外** | 檔案串流端點沒有 `response_model`；不碰業務資料的健康檢查端點 |
| **檢查方式** | **待建置**。`response_model=` 是否齊全可用自寫 AST 檢查；欄位遮蔽的規則在 [security-agent-rules.mdx](security-agent-rules.mdx) 的 S4，跨角色的負向驗收矩陣在 S10 |
:::

:::note{title="A2 的 from_attributes 與 query 未知參數" collapsible}
**共用 base 的 `from_attributes=True` 與 S4 的「不得 `from_attributes` 全收」不衝突。** S4 擋的是「回應 model 照抄整列 ORM 欄位」；`from_attributes=True` 只允許從 ORM 物件**建構**一個已經明列欄位的 schema，沒宣告的欄位不會被帶出去。所以兩條並存：**base 設定開著，但每個回應 schema 仍要明列欄位**，不得用它當作省略欄位清單的理由。

**`query` 的未知參數擋不到，所以要用別的方式收齊。** `extra="forbid"` 只作用在 body 的 model 上；FastAPI 對沒宣告的 query 參數是直接忽略，沒有地方可以設成拒絕。所以 query 這一半的政策是：**每個被接受的參數都要宣告並寫進 `api-contract.md` 的 Request 表**，沒寫進去的就是不支援；畫面把狀態放在網址時，不認得的值照規格的既有做法處理（規格 03-01 §查詢條件保留在網址：無效值忽略、改用預設並把網址整理過），不是回 `422`。`path` 參數由路由本身決定，型別與範圍仍要宣告。
:::

### A3 分頁

所有列表端點用同一組 offset 分頁：query 參數 `limit`（預設 20、上限 100）與 `offset`（預設 0），回應固定七個欄位，排序一律帶唯一的尾鍵。

| | |
| :--- | :--- |
| **適用路徑** | 所有列表端點與它們的 `api-contract.md` |
| **禁止** | 各模組自選 `page`／`page_size`／cursor；`limit` 沒有上限；`offset >= total` 時回 `404`；用非唯一的排序鍵做 offset 分頁；讓前端自己算下一頁的 offset |
| **正例** | 回應七個欄位 `items`、`total`、`limit`、`offset`、`has_more`、`total_pages`、`next_offset`，後三者由前四者**推導**、不另外查資料庫；排序一律帶唯一的尾鍵（例 `updated_at DESC, id DESC`）；`offset >= total` 回空 `items` 與 `has_more: false` |
| **逐端點寫進契約** | 每個列表端點的 `api-contract.md` 要寫出 **`limit` 上限**、**預設排序鍵（含用來打破同值的尾鍵）**與**空頁的行為** |

理由：兩列同一個時間時，單鍵排序會讓翻頁重複或漏掉其中一列。

:::note{title="A3 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `GET /api/v1/tasks?page=2&page_size=50`；`ORDER BY updated_at DESC` 單鍵（兩列同一個時間時，翻頁會重複或漏掉其中一列）；`offset=999` 回 `404`；前端自己算 `offset = page * size` |
| **例外** | cursor 分頁允許，但該 change 的 `api-contract.md` 要寫出**理由、response schema、穩定排序鍵與測試** |
| **檢查方式** | **待建置**。`limit` 的上限可由共用的 query schema 一處約束；空頁與排序穩定性要靠整合測試，等 `backend/` 存在 |
:::

:::note{title="A3 的數字依據與欄位為什麼是七個" collapsible}
**20 與 100 這兩個數字有本 repo 自己的依據。** 原始 repo 的架構常數是 `PAGINATION_DEFAULT_LIMIT = 20`、`PAGINATION_MAX_LIMIT = 100`，而本 repo 兩份**已定案**規格寫的是同一組：規格 03-01 §排序與分頁「每頁預設 20 筆，可以改成 50 或 100」與規格 06-01「每頁預設 20 筆，可以切換為 50 或 100 筆」（`docs/specs/03-task-management/01-task-list.mdx`、`docs/specs/06-admin/01-user-management.mdx`）。兩邊一致，所以這組數字不是沿用來的猜測。

**`total` 與 `total_pages` 是規格要的欄位，不是多餘的。** 規格 06-01 要顯示「共 24 筆 · 第 1 / 2 頁」；規格 03-01 §排序與分頁 更明確：分頁列要顯示「共幾筆、目前第幾頁、**總共幾頁**」，而且「中間還有幾個頁碼可以直接點（以目前頁為中心，最多五個）」。只有 `next_offset` 做不到這幾件事。所以原始 repo `api.md` 只提三個欄位是它的文字不完整，不是契約只有三個欄位。

**排序穩定性那一條是本文件推出來的。** 原始 repo 只在 cursor 分頁那一句要求穩定排序鍵；但 offset 分頁同樣會因為非唯一的排序鍵而在翻頁時重複或漏列，而規格 03-01 的預設排序正是「依更新時間由新到舊」。所以這一條套用到所有列表端點。
:::

### A4 三份契約產物的分工

契約有三份產物各管一件事：`api-contract.md` 是規劃依據、`openapi.json` 是實作真相、`frontend/src/api/generated/` 是前端產物，三者都不得手改，實作要偏離規劃時先改 `api-contract.md` 再改程式。

| | |
| :--- | :--- |
| **適用路徑** | `openspec/changes/*/api-contract.md`、後端匯出的 `openapi.json`、`frontend/src/api/generated/**` |
| **禁止** | 手改 `frontend/src/api/generated/`（含加檔與格式化）；手改匯出的 `openapi.json`；實作與規劃版契約不一致時直接改程式不改契約；把 Bruno collection 當成契約真相 |
| **正例** | `api-contract.md` 是**規劃依據**（前後端同時開工用）、`openapi.json` 是**實作真相**（後端匯出）、`frontend/src/api/generated/` 是**前端產物**（Orval 從前者產生）。實作要偏離規劃時**先改 `api-contract.md` 並寫原因**，再改程式 |

:::note{title="A4 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | 在產物裡補一個後端還沒有的欄位讓前端先動工；`openapi.json` 與程式不一致時手動修 JSON；「Bruno 裡能跑就算對」 |
| **例外** | 無。Bruno 保留成**可選的手動工具**，既不是契約也沒有 pre-PR 關卡 |
| **檢查方式** | **待建置**。產物未被手改要靠 A5 的 CI 重產比對；`api-contract.md` 與 `openapi.json` 的一致性目前只有人工與獨立審查 |
:::

### A5 重產與 drift 檢查

一條命令走完「後端匯出 `openapi.json` → Orval 產 `frontend/src/api/generated/`」，契約、`openapi.json` 與產物放同一個 commit，CI 重新產生並比對、有差異即失敗。

| | |
| :--- | :--- |
| **適用路徑** | `backend/` 的匯出設定、`frontend/orval.config.ts`、`frontend/src/api/generated/**`、CI |
| **禁止** | 只改後端不重產前端產物；本機重產後不提交產物；用 Orval 以外的工具產型別或 client；把型別漂移當成警告而不是失敗 |
| **正例** | 一條命令走完「後端匯出 `openapi.json` → Orval 產 `frontend/src/api/generated/`」；**契約、`openapi.json` 與產物同一個 commit**；CI 重新產生並比對，有差異即失敗 |

:::note{title="A5 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | 後端加了一個欄位、PR 只有後端檔案（前端 typecheck 看不到破壞性變更）；手動補產物讓 CI 過 |
| **例外** | 無 |
| **檢查方式** | **待建置**，而且這一條特別容易被誤以為已經有。原始 repo 要求這道 CI gate，但它自己的歸檔紀錄明寫「OpenAPI export／type generation command **未實作**」（`specs/foundation/000-foundation/spec.md` v1.12.4 的 (c) 項），所以**不得引用它當成已存在的機制** |
:::

### A6 單一 HTTP 邊界

前端所有 API 呼叫只走 Orval 的 mutator 這一個出口，業務元件不自己 `fetch`、不自己組 header。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/api/**`（Orval 的 mutator 與它的設定）；反面適用於 `frontend/src/pages/**` 與 `frontend/src/features/**` |
| **禁止** | 業務元件自行 `fetch`／`axios`；另寫與契約重複的型別或 DTO；在元件裡設 base URL 或組 header；用 ad-hoc 旗標做取消；在元件裡 try/catch 吞掉錯誤 |
| **正例** | Orval 的 mutator 是唯一出口，集中七件事：**base URL**、**`credentials: 'include'`**（cookie 認證必要）、**`Accept-Language`**、**CSRF 的自訂 header**（值從 `__Host-` 前綴的 cookie 複製，見 [security-agent-rules.mdx](security-agent-rules.mdx) 的 S2）、**`AbortSignal`**（TanStack Query 傳進來的 signal 直接轉給 `fetch`）、**錯誤轉成單一 error 型別**（帶 `status` 與 correlation id）、以及 **request timeout** |

:::note{title="A6 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | 原始 repo 的實作 `frontend/src/shared/services/api-client.ts` 就是反例：它**沒有 `credentials: 'include'`**，所以 httpOnly cookie 根本不會隨請求送出；也沒有 `Accept-Language`、沒有 CSRF header、沒有 timeout。元件裡 `const r = await fetch('/api/v1/tasks')` 同樣是反例 |
| **例外** | 檔案上傳與下載不走 JSON 解析，但仍然走同一層（base URL、credentials、CSRF、取消都一樣要） |
| **檢查方式** | **待建置**。可用 lint 規則禁止 `pages/` 與 `features/` 直接用 `fetch`／`axios`，並禁止 import 產物目錄以外的 API 型別。security-agent-rules.mdx 的 S2 把一條測試指派到這裡：斷言元件不自己帶 `credentials`（`credentials` 的統一責任位置就是這一層），那條測試等 `frontend/` 存在才寫得出來 |
:::

:::note{title="A6 的自訂 header 只加在寫入請求上" collapsible}
原始 repo 那支 client 的註解寫得對：`application/json` 不在 CORS safelist 裡，所以只在有 body 時才設 `Content-Type`，免得每個 `GET` 都觸發 preflight。CSRF 的自訂 header 同理，**只在會改變狀態的請求加**，`GET` 不加，才留得住那個免 preflight 的好處。寫入請求本來就有 body，preflight 無論如何都會發生。這一層的強度等於 CORS allowlist 的嚴格程度（security-agent-rules.mdx 已記）。
:::

### A7 錯誤處理與安全訊息

錯誤只在 A6 那一層轉成單一 error 型別，畫面依 status 分流顯示；`401` 的 refresh 同時只允許一個在飛，`403` 不重試。

| | |
| :--- | :--- |
| **適用路徑** | 後端的 exception handler、`frontend/src/api/**` 的錯誤轉換、TanStack Query 的 `QueryClient` 設定 |
| **禁止** | 用錯誤字串猜 status；`403` 自動重試；把「看不到的資源」回 `403`；顯示原始堆疊、資料庫錯誤或未處理的 HTTP 物件；在元件各自 try/catch 吞錯；`401` 時讓多個 refresh 同時在飛 |
| **正例** | 單一 error 型別帶 `status`、`detail` 與 correlation id。`401`：先試 refresh，**同時只允許一個在飛**（single-flight），其餘請求等它的結果。**refresh 成功就更新 session 並重放原請求**；**refresh 失敗就清掉前端的登入狀態並導向登入**，而且要往上傳明確的 auth failure 旗標，讓 `QueryClient` 的 `retry` 對 auth error 回 `false`。`403`：不重試，顯示無權限狀態。`404`：同時代表不存在與刻意隱藏。`409`：**在表單情境**顯示在表單上（refresh 併發也會回 `409`，那一種由 A6 那層處理、不進畫面）。`400`：與 `422` 分開，`400` 是語意或應用規則錯誤、`422` 是 schema 驗證失敗，兩者都回到觸發它的欄位或表單。`422`：`detail` 是 `ErrorDetail[]`，逐欄位顯示。`5xx`：顯示通用錯誤並附 correlation id |

:::note{title="A7 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `if (String(err).includes('403'))`；讓 TanStack Query 的預設 retry 跟 refresh 搶，這樣**最多疊出六次冗餘請求**；把使用者看不到的任務回 `403`（洩漏它存在）；把 `detail` 的 `ErrorDetail[]` 直接 `JSON.stringify` 貼到畫面 |
| **例外** | FastAPI 預設的 `422` `RequestValidationError` **不在 i18n 契約內**（[architecture.mdx](../architecture.mdx) §i18n 兩層），要本地化得另註冊 handler；A6 提到的最後手段診斷字串（回應沒有 body 或不是 JSON 時由 client 自己合成）留英文 |
| **檢查方式** | **待建置**。`retry` 對 auth error 回 `false` 可用前端單元測試鎖住；`403`／`404` 的隱藏行為屬 security-agent-rules.mdx 的 S10 驗收矩陣 |
:::

:::note{title="A7 的 single-flight 與 correlation id" collapsible}
**single-flight 與重放是本文件從「併發 refresh」推出來的，不是原始 repo 條文的內容。** 原始 repo 只要求兩件事：refresh 失敗要往上傳明確的 auth failure 旗標、`QueryClient` 的 `retry` 對 auth error 回 `false`。前端只排一個 refresh 在飛、成功後重放原請求，是為了不讓同時發生的多個 `401` 各自換一次 token。**後端那一面另有來源**：原始 repo 對 refresh token 的併發採有界 grace（30 秒內、`rotated` 且未被重發過的 token 可多發一次，資格已被占用時回 `409 Conflict`），所以前端排隊與後端 grace 是互補的兩層，不是同一條。

**correlation id 不送第三方。** Sentry 本期不做，所以 correlation id 只進錯誤物件與 log，不送任何第三方。
:::

### A8 i18n 的兩層分工

前端只負責 UI 字串，後端的 `detail` 由後端依 `Accept-Language` 解析成已本地化的字串，前端當不透明字串直接顯示。

| | |
| :--- | :--- |
| **適用路徑** | 後端的 i18n 字串與 exception handler、前端的語系檔與錯誤顯示 |
| **禁止** | 前端把後端的 `detail` 再翻譯一次或對照 key；語系檔放後端 `detail` 的副本；後端在商業邏輯內嵌人看得懂的訊息字面值；**`detail` 回傳 i18n key 本身或原始英文字面值**；前端不送 `Accept-Language` 而自己決定語言 |
| **正例** | 前端送 `Accept-Language`（由 A6 那一層統一加），把 `detail` 當成**已經本地化的不透明字串**直接顯示；後端解析 q-value、`*` 通配、`q=0` 拒絕，fallback 到 `zh-TW`，全部被拒時回 `406` |

:::note{title="A8 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `t(error.detail)`；在 `zh-TW/common.json` 放一份後端訊息；`raise HTTPException(400, "任務名稱重複")`（字面值寫在商業邏輯裡）；`detail: "task.name.duplicate"`（回了 key，前端照「不透明字串直接顯示」會把 key 貼到畫面上） |
| **例外** | `422` 的 `ErrorDetail[]`（見 A7）；client 在沒有後端 body 時合成的診斷字串 |
| **檢查方式** | **待建置**。後端可用整合測試斷言同一條錯誤在 `zh-TW` 與 `en` 下的 `detail`；前端可 grep 語系檔裡有沒有後端訊息的副本 |
:::

### A9 server state 與快取

server state 只放 TanStack Query，query key 一律來自 Orval 產物匯出的 `get*QueryKey`，換人或換任務時清掉前一個人的快取。

| | |
| :--- | :--- |
| **適用路徑** | `frontend/src/**` 用到 TanStack Query 的地方、`QueryClient` 的設定 |
| **禁止** | 把 API 回應複製進全域 store；在元件或 hook 裡用 inline 字串陣列當 query key；mutation 成功後不失效相關查詢；切換登入者或任務之後沿用前一個人的快取 |
| **正例** | query key 的**唯一來源是 Orval 產物匯出的 `get*QueryKey`**；mutation 成功後用它失效對應的 list 與 detail；登出、切換帳號、`credential_version` 變動時整個 `queryClient.clear()`；切換任務時失效帶 `taskId` 的 key；**mutation 進行中，送出入口 disabled**，避免同一筆被送兩次 |

:::note{title="A9 的反例、例外與檢查方式" collapsible}
| | |
| :--- | :--- |
| **反例** | `useQuery(['tasks', id], ...)` 手寫 key（另一處寫成 `['task', id]`，失效就打不中）；把 `listTasks` 的結果再存一份進 Zustand；登出只清 cookie 不清 cache，下一個在同一台機器登入的人會先看到上一個人的列表 |
| **例外** | 表單狀態與純 UI 狀態**不**進 TanStack Query（[architecture.mdx](../architecture.mdx) §前端） |
| **檢查方式** | **待建置**。inline key 可用 lint 規則擋；跨帳號不外洩要有前端測試：登出再登入另一個帳號後列表不得出現前一個帳號的資料 |
:::

:::note{title="A9 的三個失效事件與 query key factory" collapsible}
**S4 的三個失效事件在前端各有不同的落點。** 帳號停用、系統角色變更與任務成員身分變更的失效規則在 [security-agent-rules.mdx](security-agent-rules.mdx) 的 S4。帳號停用與系統角色變更會讓 session 失效，下一個請求拿到 `401`，由 A7 清掉整個 cache。**任務成員身分變更不會讓 session 失效**：使用者還登著，只是某個任務不再屬於他。那一格的做法是：收到該任務的 `403` 或 `404` 時，失效帶那個 `taskId` 的 key 並退回列表（規格 03-01 §點任務進入任務詳情 已經寫了「停在列表並顯示無權限」），**不是整個 `clear()`**。

**不手寫 query key factory。** 原始 repo 要求手寫 `frontend/src/shared/constants/query-keys.ts` 的 factory，採 `[module, resource, id?, subresource?]` 階層。本專案採 Orval 之後，key 由產物產生，再手寫一份就是**兩個真相**；而且 `shared/` 那個路徑已被 `pages/` 加 `features/` 的目錄決定覆寫。要保留的是它的用意：**全專案只有一套 key 慣例，不准 inline**。
:::

### A10 相容性與破壞性變更

刪欄位、改型別、改語意、改 operationId 都是破壞性變更，要在 `design.md` 寫出影響範圍，並由規劃審閱、程式審查與 CI 的 snapshot diff 三個落點把關。

| | |
| :--- | :--- |

| **正例** | 破壞性變更要在該 change 的 `design.md` 寫出影響範圍；每個 major version 一份獨立的 OpenAPI artifact；deprecated 端點在 OpenAPI description 或 changelog 標出 migration path；operationId 的變動由 artifact 的 snapshot diff 在 CI 偵測 |

| | |
| :--- | :--- |
| **反例** | 把 `listTasks` 改名成 `getTaskList` 當成單純重構（前端 hook 名稱跟著變）；把回應從 envelope 改成裸物件而不走版本（版本前綴的用意見 [ADR-003 的 D5](../adr/003-backend-architecture.mdx#d5-api-路徑前綴與成功回應外層)） |

:::
