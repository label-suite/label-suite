# UI Design

本次無 UI 變更。

理由：本 change 只動容器編排、設定範例檔、根目錄指令、`e2e/` 骨架與 CI（system-analysis §範圍）。沒有新增或修改任何路由、頁面、元件、介面文字、語言檔鍵或 design token，也不改 `design/prototype/`（system-analysis §範圍「這次不包含」最後一項；前端容器建置只**讀取** `design/prototype/assets/`）。沒有 `docs/specs/` 規格可對照（spec-migration D4），也沒有對應的 `design/prototype/pages/` 頁面。

下面各節**不是設計**，只記錄一件事：Issue #506 驗收條件 1 與 `e2e/` 的健康檢查旅程要觀察的，是 #505 已經做好的開發用健康檢查頁 `/dev/health`。這一頁的畫面基準、元件樹與四種狀態已由歸檔的 `openspec/changes/archive/2026-11-20-frontend-skeleton/ui-design.md` 與主規格 `openspec/specs/dev-health-page`、`frontend-routing`、`frontend-i18n` 定下，本文只指過去，並寫出 e2e 可以依賴哪些可觀察的行為，讓 `system-design` 與 `tasks.md` 不必回頭從程式逆推。

## 頁面與路由

| 路由          | 頁面                         | 對應的規格                                                                                                   | 需要的角色                                                                                      |
| :------------ | :--------------------------- | :----------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
| `/dev/health` | 健康檢查頁（既有，本次不改） | 無 `docs/specs/` 規格；主規格 `dev-health-page` 全部 requirement、`frontend-routing`「兩頁只在開發模式註冊」 | 無：公開、不需登入（`dev-health-page`「未登入時看到與任何呼叫端相同的內容」）；只在開發模式存在 |

- 這一頁**只在開發模式註冊**，正式建置剪除它與 `/dev/` 字串，正式建置的 `/` 只有空殼、不發任何後端請求（`frontend-routing`「正式建置不含開發頁與測試替身」）。
- 所以容器若服務的是前端**正式建置**，e2e 在容器裡**到不了**這一頁；要在畫面上看到健康檢查結果，前端必須是開發伺服器。這正是 system-analysis 需求矛盾 1 與待決 #1 的來源，本文不選邊，兩種做法對 e2e 的影響見 [§依待決 #1 的兩種情境](#依待決-1-的兩種情境)。

## 畫面狀態

四種狀態的呈現與文案以 `dev-health-page` 主規格為準，這裡只摘要並標出 e2e 怎麼看。介面語言依瀏覽器語言決定（`frontend-i18n`「介面語言依瀏覽器語言決定」），下表文案是 `zh-TW` 時的樣子。

| 狀態                     | 呈現（摘自 `dev-health-page`）                                                                                                                                                             | e2e 的觀察方式                                                                                                                                                                                  |
| :----------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| loading                  | 狀態文字「正在檢查後端狀態…」（`role="status"`）、三條隱藏於輔助科技的骨架、內容區 `aria-busy="true"`、「重新檢查」`aria-disabled="true"`                                                  | **不斷言**：時間太短、斷言它會讓測試不穩；以條件式等待跳過（T8 禁止固定等待）                                                                                                                   |
| 正常（旅程要看到的結果） | success 徽章「正常」、「後端與資料庫都可以用」，描述清單：服務 `ok`、資料庫 `ok`、檢查時間、traceId                                                                                        | 條件式等待「後端與資料庫都可以用」可見；斷言描述清單的服務與資料庫兩個值為 `ok`；斷言畫面上沒有 `role="alert"`。檢查時間與 traceId 每次不同，只斷言存在、不斷言值                               |
| error：後端回報錯誤      | error 提示（`role="alert"`）；`DATABASE_UNAVAILABLE` 時標題「資料庫無法連線」，其他錯誤碼標題「後端回報錯誤」；內文為後端 `message` 原樣；描述清單列錯誤碼與 traceId；「重新檢查」主色實心 | 旅程失敗時的診斷：看到「資料庫無法連線」代表後端起來了但資料庫不可用（Lite 的資料目錄或正式層的資料庫連線）                                                                                     |
| error：連不到後端        | warning 提示（`role="alert"`）標題「連不到後端」，提示 `VITE_API_BASE_URL`；描述清單錯誤類型 `network` 或 `timeout`、traceId「無（請求沒有送達）」                                         | 旅程失敗時的診斷：後端沒起來、前端呼叫位址指錯，或後端的允許來源沒有包含前端的來源（瀏覽器擋下跨來源請求時，呼叫層只看到連線失敗，顯示為 `network`）。後兩者都牽動設定範例檔的兩個值，見待決 #2 |
| empty                    | 不適用：健康檢查一定回傳結果，沒有「沒有資料」的狀態                                                                                                                                       | 不適用                                                                                                                                                                                          |
| 無權限（403）            | 不適用：公開端點，對所有呼叫端回應相同（`dev-health-page`、`health-check`）                                                                                                                | 不適用；e2e 這條旅程不需要 `e2e/shared/fixtures/` 的任何角色 `storageState`                                                                                                                     |
| 欄位被遮蔽               | 不適用：沒有遮蔽欄位                                                                                                                                                                       | 不適用                                                                                                                                                                                          |

其餘三種狀態（載入中、後端回報錯誤、連不到後端）以及「重新檢查」的防重複送出，已由 #505 的元件與頁面測試覆蓋（`frontend/src/features/system-health/*.test.tsx`、`frontend/src/pages/dev-health/dev-health-page.test.tsx`）。#506 要的是「一條健康檢查的全端旅程」（system-analysis §範圍），依 T8「一個 spec 一條旅程」，e2e 只走「開啟 → 看到正常」這一條；要不要另加需要關掉資料庫或後端的失敗旅程，#506 沒有要求，本文不新增。

### e2e 可以依賴的選擇器

依 T8 優先語意選擇器；這一頁沒有 prototype 的 `data-testid` 契約可沿用，也不需要為 e2e 新增 `data-testid`：

- 頁面已載入：role 為 `heading`、level 1、名稱為「系統健康檢查」
- 結果正常：文字「後端與資料庫都可以用」
- 沒有錯誤：沒有 role 為 `alert` 的元素
- 失敗時的診斷：role 為 `alert` 的元素與它的標題文字（「資料庫無法連線」「後端回報錯誤」「連不到後端」）

### 交給 `system-design` 與 `tasks.md` 的限制

這幾條是從既有主規格推出的限制，不是新的設計決定，也不替待決問題選答案：

1. **介面語言要在 e2e 設定裡固定。** 上面的文字選擇器依介面語言而變（`frontend-i18n`：`zh-TW` 與 `en` 的 h1 不同），瀏覽器語言沒有固定時，同一份 spec 在不同機器上會找不到文字。固定在哪一種語言由 `system-design` 決定；依 T8，這個設定和 `baseURL` 一樣集中在 e2e 的設定檔，不寫在 spec 裡。
2. **`baseURL` 指向能開到 `/dev/health` 的那個前端來源，不寫死埠號**（T8）。在待決 #1 未定前，這個來源是前端開發伺服器還是別的，`system-design` 只能列出兩種情境。
3. **前端呼叫位址與後端允許來源要互相對上**，否則旅程會停在「連不到後端」。這兩個值就是設定範例檔交接的兩個值（`frontend-skeleton/design.md` §跨 change 依賴），在容器裡成不成立取決於待決 #2。

## 依待決 #1 的兩種情境

待決 #1 尚未決定，本文不選。兩種做法對「畫面上看得到什麼」的差別如下，供 clarification 提問時參考：

| 待決 #1 的選項                                 | e2e 能不能在畫面上看到健康檢查頁                                                                                                                                                                                                                               |
| :--------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| (a) 容器裡直接看後端健康檢查回報正常           | 容器裡的前端若是正式建置，**沒有這一頁可看**，開啟 `/` 只有空殼、不發請求。此時「看到健康檢查成功」不是畫面行為；若 e2e 仍要走瀏覽器旅程，得另外起前端開發伺服器。只用 HTTP 呼叫後端驗證則屬 integration 而不是 e2e（T1 反例），e2e 骨架就沒有一條真瀏覽器旅程 |
| (b) e2e 跑在前端開發伺服器上，看健康檢查頁正常 | 可以：照 [§畫面狀態](#畫面狀態) 的「正常」那一列觀察。驗收條件 1 的「頁顯示成功」字面上由這條滿足                                                                                                                                                              |
| 兩者都要                                       | 容器驗後端回報正常，e2e 在開發伺服器上驗畫面；兩邊各自獨立                                                                                                                                                                                                     |

測試集答案不外露（Hard Rule 6）：不適用。這一頁只在開發模式存在、標記員在正式建置到不了，畫面與 e2e 旅程都不碰任何答案資料；`e2e/` 這次的旅程也不需要 fixture。
