# 授權與答案隔離規範

本文說明授權與答案隔離的十條開發規範，由 `AGENTS.md` 的 Agent Rules Index 指過來；`AGENTS.md` 是規則本體，兩邊說法不同時以 `AGENTS.md` 為準，並回報給維護者。
跨領域的規範在 [agent-rules.mdx](agent-rules.mdx)，後端的在 [backend-agent-rules.mdx](backend-agent-rules.mdx)，技術選型在 [architecture.mdx](../architecture.mdx)，這裡不重複。

**這份管的是產品不變量，不是 UI 約定。** 每條的「禁止」被違反，影響的是誰能看到什麼資料，不是體驗好不好。

**`backend/` 與 `frontend/` 都已存在，但在 CI 跑的只有 S2 的 CORS 萬用來源檢查與 S8 的 `eval`／`exec` 檢查**（job 與指令寫在各條的「檢查方式」）；S2、S8 沒建的部分與其餘各條仍標「待建置」。標「待建置」就是字面意思：**不得因為這份文件存在就宣稱授權已被強制**。

每條規範的反例與檢查方式收在摺疊區塊，預設收起；適用路徑、禁止、正例與例外在表裡。

## 規範

### S1 身分只來自驗證完成的 session

可接受的身分來源只有 httpOnly cookie；認證 dependency 驗 cookie 裡的 access JWT，其餘來源一概不看。理由見 [ADR-004 的 D1](../adr/004-auth-and-security.mdx#d1-認證-token-放在-httponly-cookie)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 的認證 dependency 與每一個受保護端點 |
| **禁止** | 從 `Authorization` header、查詢字串、自訂 header 或請求內文推定身分；複製外部 IdP 的 dev-token 路由（例如一個「非 dev 模式回 404」的 `/dev/auth/token`） |
| **正例** | 認證 dependency 驗 httpOnly cookie 裡的 access JWT，取 `sub`、`sid`、`credential_version` |
| **例外** | **無。** Google SSO 走 OIDC 回調換發自己的 cookie，那是發 cookie 的流程，不是另一種身分來源 |

:::note{title="S1 的反例與檢查方式" collapsible}
- **反例**：`token = request.headers.get("Authorization")`；或為了本機方便加一條發 token 的端點
- **檢查方式**：**待建置**。可用整合測試斷言「帶 `Authorization` header 但沒有 cookie → 401」
:::

### S2 token 不離開 cookie；CSRF 與 CORS 的統一位置

前端不碰 token，CSRF 由單一 middleware 驗綁定 session 的 double-submit token，CORS 來源逐一列出。CSRF 的理由見 [ADR-004 的 D3](../adr/004-auth-and-security.mdx#d3-csrf-用綁定-session-的-double-submit-token)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 的 middleware；`frontend/src/**` 全部 |
| **禁止** | 前端儲存或讀取 token（`localStorage`、`sessionStorage`、非 httpOnly cookie、記憶體 store 都算）；從可修改的 UI state 判斷權限；`allow_origins=["*"]`（`AGENTS.md` 硬性規則 7）；在端點各自處理 CSRF |
| **正例** | **session cookie** 一律 `httpOnly`、`Secure`、`SameSite=Lax`（CSRF cookie 是唯一例外，見 [architecture.mdx](../architecture.mdx) 的 token 表）；請求帶 `credentials: 'include'`；**CSRF 由單一 middleware 驗綁定 session 的 double-submit token**（值是 `HMAC(secret, sid)`、cookie 加 `__Host-` 前綴、前端複製到自訂 header）；CORS 來源逐一列出 |
| **例外** | CSRF token 那個 cookie **刻意可被 JS 讀取**，那是 double-submit 的設計，不是漏洞；它靠 `__Host-` 前綴與 HMAC 綁定 session 來守住 |

:::note{title="S2 的反例與檢查方式" collapsible}
- **反例**：把 token 放進 Zustand 或任何前端 store——`httpOnly` 的意義就是 JS 讀不到它，會這樣寫表示架構被誤解了；每個寫入端點各自檢查 CSRF；**或把 CSRF 做成只比對 cookie 與 header 是否相等**——那種擋不住子網域覆寫 cookie
- **檢查方式**：CORS 的 `allow_origins=["*"]` 由 CI 的 `semgrep` job 擋：它先跑 `semgrep --test .semgrep/` 驗規則對得上回歸樣本，再跑 `semgrep scan --error --config .semgrep/label-suite.yml backend/ frontend/ e2e/`，規則 `label-suite-cors-wildcard-origin` 命中即失敗（使用官方映像 `semgrep/semgrep:1.186.0`）。CSRF 的負向測試（「缺 CSRF header」「header 與 cookie 不符」「HMAC 無效」三種）**待建置**，要等有 CSRF middleware 與 session 才寫得出來；前端不碰 token 也沒有機械檢查
- **統一責任位置**：`credentials` 在 [api-agent-rules.mdx](api-agent-rules.mdx) 的單一前端 HTTP client，cookie flags 在後端單一發 cookie 的 helper；兩者各要一條測試（斷言沒有第二處設 cookie、斷言元件不自己帶 credentials）
:::

### S3 授權的四段順序

授權依序判定四件事，未知值或缺失一律拒絕，不走「預設允許」。理由見 [ADR-004 的 D2](../adr/004-auth-and-security.mdx#d2-授權用的角色每次從資料庫讀)與 [D6](../adr/004-auth-and-security.mdx#d6-權限矩陣當授權輸入)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 的授權判定 |
| **禁止** | 把 JWT 的 `role` 當授權真相；讓系統管理員自動取得任務權限；未知的 permission key、缺少的矩陣列或層級不符時放行 |
| **正例** | 依序判定四件事：(1) 登入者、帳號啟用、`credential_version`、token family 仍有效；(2) 從 **DB** 讀目前的系統角色，任務範圍的操作另讀該任務目前有效的成員身分；(3) 操作解析成已啟用、在白名單內的 permission key 與它所屬的層，要求對應角色的 cell 為 `allowed=true`；(4) 再檢查附加條件（任務歸屬與狀態、指派與審核者身分、資料集可見性、答案隔離） |
| **例外** | 無 |

權限上限以 PRD §權限矩陣 為準，**不得放寬**；超出時照 07-01 的做法明寫上限並交給 [#85](https://github.com/label-suite/label-suite/issues/85)。

**系統角色與任務成員身分不得快取。** 它們每次請求都從 DB 取，所以一改，**授權**在下一個請求就生效。但這句話只涵蓋這兩樣——授權第 (3) 段要讀的**權限矩陣列、cell 與矩陣版本列**是典型的快取對象，要快取就**以矩陣版本列為失效鍵**。

**「下一個請求就生效」不適用於 JWT 裡的 `role`**：它在 access token 裡，效期 15 分鐘，所以顯示用的角色最多 stale 15 分鐘。真正的失效規則見 S4。

:::note{title="S3 的反例與檢查方式" collapsible}
- **反例**：`if jwt["role"] == "super_admin": allow`——`role` 只供顯示；或 cell 為 `true` 就放行而不看第 (4) 段的附加條件
- **檢查方式**：**待建置**。第 (4) 段的每一種附加條件都要有負向測試
:::

### S4 遮蔽與 allowlist 在後端

後端決定回什麼、遮蔽什麼；前端只負責渲染，藏按鈕不是授權。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/modules/**` 的回應 schema；`frontend/src/**` 的渲染 |
| **禁止** | 回傳裸 ORM model；前端自己依角色決定要不要藏值；用「前端藏按鈕」代替後端拒絕 |
| **正例** | 回應 schema **明確 allowlist** 欄位；該遮蔽的由後端標記（例如欄位列在遮蔽清單裡），前端只負責把它渲染成「已遮蔽」 |
| **例外** | 無 |
| **session 與快取的失效規則** | PRD §權限矩陣 已定：「停用後該帳號登入狀態失效；角色變更從下一次操作起生效」。落地方式：**帳號停用，以及[規格 01-05](../../specs/01-account/05-login-state.mdx#四種改動讓所有裝置重新登入) 列出的改動，`credential_version` 加一並撤銷該使用者的 refresh token family**——照 [architecture.mdx](../architecture.mdx) 已有的 SSO 綁定做法（同一筆交易內加一並撤銷所有 session）。**系統角色變更不撤銷任何登入狀態**：下一次操作依 S3 從 DB 讀到新角色，立即生效（規格 01-05 的[每一次操作都用最新的身分判定](../../specs/01-account/05-login-state.mdx#每一次操作都用最新的身分判定)為準，維護者裁定 2026-11-26）。權限矩陣若要快取，失效鍵是矩陣版本列 |

:::note{title="S4 的反例與檢查方式" collapsible}
- **反例**：`return task`（ORM 物件直接序列化，將來加一個欄位就外洩）；或前端 `if (role !== 'project_leader') hideField()`——那是體驗，不是授權
- **檢查方式**：**待建置**。可用「回應 model 必須明列欄位、不得 `from_attributes` 全收」的審查項；遮蔽欄位用 Decision Table 驗
:::

### S5 答案隔離的覆蓋面

標記員能到達的每一個出口，都不得出現標準答案或測試集辨識資訊；這是 `AGENTS.md` 硬性規則 6。理由見 [ADR-006 的 D4](../adr/006-task-config-and-answer-isolation.mdx#d4-答案隔離涵蓋標記員能到達的每個出口)。

| | |
| :--- | :--- |
| **適用路徑** | 標記員能到達的**每一個**出口 |
| **禁止** | 在標記員能接觸到的任何地方出現標準答案或測試集辨識資訊——**覆蓋面包括** API 回應、列表與詳情、下載與匯出、輪詢結果、快取、瀏覽器 bundle 與 source map、公開 fixture 與 mock handler、錯誤訊息與 log |
| **正例** | 以標記員身分打他能到達的每一個端點，斷言 payload 裡沒有答案；fixture 與 mock 用不帶答案的資料 |
| **例外** | 無 |

:::note{title="S5 的反例與檢查方式" collapsible}
- **反例**：錯誤訊息裡回「期望值是 X」；或 mock handler 直接複製一份含答案的真實回應
- **檢查方式**：**待建置**。`acceptance-verifier` 的檢查清單已有這一項（以標記員身分逐端點斷言），但它要等有端點才跑得起來
:::

### S6 受控答案表與 worker 的讀取邊界

答案存在獨立、受存取控制的資料表，只在 worker 行程內讀取，不離開 worker。理由見 [ADR-006 的 D4](../adr/006-task-config-and-answer-isolation.mdx#d4-答案隔離涵蓋標記員能到達的每個出口)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**`、Celery task、`frontend/src/**` |
| **禁止** | 瀏覽器下載答案再算分；在 API 行程裡讀答案表；把答案表與一般標記資料放同一張表 |
| **正例** | 答案存在**獨立、受存取控制的資料表**；`load_answers()` 只在 **worker 行程內**執行，答案不離開 worker；計分與 IAA 在後端算完才回結果 |
| **例外** | 無 |

:::note{title="S6 的反例與檢查方式" collapsible}
- **反例**：前端 `GET /answers` 然後在瀏覽器比對——答案一旦進 bundle 就等於公開
- **檢查方式**：**待建置**。負向驗收要涵蓋**跨角色與跨任務的直接請求**（標記員直接打審核員的端點、打別的任務的資源）
:::

### S7 設定驅動的界線

新增一種研究任務只改設定、不改核心程式；任務類型不寫死在核心路徑。理由見 [ADR-006 的 D1](../adr/006-task-config-and-answer-isolation.mdx#d1-任務類型由設定決定核心不寫任務專屬邏輯)與 [D2](../adr/006-task-config-and-answer-isolation.mdx#d2-任務設定用-input_type-加-outputs-組合)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 的核心路徑 |
| **禁止** | 用任務名稱特判；寫死 `task.type` 的分支；**為了新增一種研究任務而改核心程式** |
| **正例** | 任務用 `input_type` 加 `outputs[]` 的組合模型；既有 output type 的 UI、驗證與評分透過**明確的 registry 邊界**擴充 |
| **例外** | **新增一個 output primitive 是程式工作**，與「只改任務設定」要分清楚：前者要開 issue 走正常流程，後者不該碰程式 |

:::note{title="S7 的反例與檢查方式" collapsible}
- **反例**：`if task.name == "醫療文本情感分類": ...`；或 `match task.type: case "sentiment": ...`
- **檢查方式**：**待建置**。`acceptance-verifier` 的清單已有「換一種 `input_type` 加 `outputs[]` 的組合，同一條路徑仍然走得通」
:::

### S8 設定的驗證與 span 的表示

任務設定是使用者可控輸入，必須經 schema 驗證；span 一律用半開字元 offset，理由見 [ADR-006 的 D3](../adr/006-task-config-and-answer-isolation.mdx#d3-序列標記用半開字元-offset-span)。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 讀任務設定的地方；序列標記相關的程式 |
| **禁止** | **`eval` 或任何動態執行設定提供的程式**；接受未經 schema 驗證的設定；回退已淘汰的 token 對齊模型 |
| **正例** | 設定走 schema 驗證加允許清單；**驗證 output 之間的依賴與循環**；`sequence_tagging` 的 span **不得重疊**，每個字元最多屬於一個 span；span 用**半開字元 offset** |
| **例外** | 無 |

:::note{title="S8 的反例與檢查方式" collapsible}
- **反例**：`eval(config["scoring_expr"])`——設定是使用者可控輸入，等於遠端執行；或用 token index 表示 span；或讓 `sequence_tagging` 的兩個 span 覆蓋同一個字元
- **檢查方式**：「不得出現 `eval`／`exec`」由 CI 的 `backend-sqlite` job 的 `uv run ruff check .` 擋：`backend/pyproject.toml` 選用的 `S` 規則組含 `S307`（`eval`）與 `S102`（`exec`）。循環依賴與 span 重疊的測試**待建置**
:::

### S9 稽核、脫敏與保留

稽核列只增不改，log 不帶 PII 與 secret，XSS 靠輸出轉義而不是改寫輸入。

| | |
| :--- | :--- |
| **適用路徑** | `backend/app/**` 寫稽核的地方；所有 log |
| **禁止** | 更新或刪除 `audit_events` 的列；把 PII 或 secret 寫進 log；對帶答案的歷史做匿名化或單獨刪除；**為了「清理輸入」而改寫研究原文** |
| **正例** | **刪除與保留的規則本體在 [backend-agent-rules.mdx](backend-agent-rules.mdx) 的 B8**（`audit_events` append-only、過了最短保留期只能墓碑化、帶答案的歷史不匿名化不單獨刪除），本條不重寫它、只補安全面：log 裡的 PII 與 secret **脫敏**；XSS 由**安全渲染**處理（輸出轉義），**不是改輸入** |
| **例外** | 無 |

:::note{title="S9 的反例與檢查方式" collapsible}
- **反例（append-only）**：`UPDATE audit_events SET actor_id = NULL WHERE ...`——補救 PII 不能靠改稽核列，要用墓碑化
- **反例（脫敏）**：`logger.info(f"reset_url={url}")`——寄信降級把設定密碼連結印在伺服器 log，那條 log 本身就是敏感資料，不得再帶進一般 log 管道
- **反例（保留規則）**：單獨 `DELETE` 一列帶答案的歷史 JSON——它要跟著所屬的資料集版本或 run 存續
- **反例（改寫原文）**：**為了防 XSS 把標記文本裡的 `<` 換成 `&lt;` 存進資料庫**——那會破壞 span 的字元 offset，而 offset 是序列標記的基礎
- **檢查方式**：**人工／獨立審查**加**待建置**。append-only 可用資料庫層的規則擋 `UPDATE`／`DELETE`；「不改寫原文」要靠審查
:::

### S10 驗收矩陣

每一個受保護端點的驗收都要蓋滿八種情形，不得用固定角色的假資料取代真實授權路徑。

| | |
| :--- | :--- |
| **適用路徑** | `backend/tests/**`、E2E |
| **禁止** | **用固定角色的假資料取代真實授權路徑**（例如測試裡直接塞一個 `role="super_admin"` 的假 user 繞過授權判定） |
| **正例** | 每一個受保護端點的驗收涵蓋：**未登入、帳號停用、session 失效、非該任務成員、換成另一個任務、矩陣列缺失、矩陣 cell 為拒絕、以及每一個有效角色**。帳號停用那一格**包含 `/auth/refresh`**：停用之後拿舊的 refresh token 換新 token 必須被拒 |
| **例外** | 無 |

:::note{title="S10 的反例與檢查方式" collapsible}
- **反例**：只測「管理員可以、匿名不行」兩種，中間那些（停用、失效、非成員、別的任務）全沒測——而那幾種正是實際會出事的
- **檢查方式**：**待建置**。測試分層與證據要求見 [testing-agent-rules.mdx](testing-agent-rules.mdx)，本條只定矩陣要蓋哪幾格
:::

| 外部 OIDC ＋ `Authorization: Bearer` ＋ token 只存記憶體 | scaffold `auth-oidc.md` §模式、§前端鐵律 | 架構不同。本專案走自己的 cookie／session（ADR-021），Google SSO 是直接 OIDC 整合換發自己的 cookie（ADR-035），不引入外部 IdP |
| `/dev/auth/token` 這類 dev-token 路由 | scaffold `auth-oidc.md` §模式 | 本文明文禁止。「非 dev 模式回 404」不是安全邊界，只是把風險藏起來 |
| 「寫入端點只給 `admin`，viewer 回 403」 | scaffold `auth-oidc.md` §後端鐵律 | 兩個角色的模型套不上本專案。本專案是系統角色加任務成員身分兩層，權限由 PRD §權限矩陣 的 cell 決定 |
| **「角色只從 token 取：不讀 query、body、header（除 `Authorization`）或 DB 裡前端可改的欄位來決定角色」** | scaffold `auth-oidc.md` §後端鐵律 2 | **本專案正好相反**：系統角色每次從 **DB** 讀，JWT 的 `role` 只供顯示（ADR-037）。照這一條做就是 S3 明文禁止的「把 JWT 的 `role` 當授權真相」。**這是整份來源裡最危險的一條**，所以單獨列出來 |
