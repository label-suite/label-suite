# 07-04 通知事件

> 參考畫面：**沒有獨立頁面**。兩個消費端的畫面分別在 `design/prototype/pages/shared/sidebar.js`（通知入口與清單）與 `design/prototype/pages/dashboard/dashboard.html`（系統管理員版面的「最近提醒」），事件本身沒有畫面。

:::

## 目標

- 讓「哪些事會通知人」只有一份清單，而不是側欄一份、儀表板一份——這正是 [02-01 Q5](../02-dashboard/01-dashboard.mdx#已確認決議) 與 [07-01 Q4](./01-sidebar.mdx#已確認決議) 各自把這件事推出去之後留下的缺口
- 讓 :ref[平台成員]{id="term.platform-member"}知道自己會因為什麼事被通知，而[規格 01-04 §通知設定](../01-account/04-profile.mdx#通知設定)讓他逐事件決定要不要收
- 讓 :ref[系統管理員]{id="term.system-admin"}在儀表板的「最近提醒」只看到與**全平台**有關的那些，不是每個人的個人事務

## 使用角色

:::tip{title="權限代號"}
R：Read（可讀取）　C：Create（可新增）　E：Edit（可編輯）　D：Delete（可刪除）　(o)：只限自己的資料　—：無權限
:::

通知是系統產生的，沒有人能新增或編輯一則通知；使用者能做的是讀自己的、把自己的標為已讀，以及在[規格 01-04](../01-account/04-profile.mdx#通知設定)決定要不要收。

- :ref[平台成員]{id="term.platform-member"}：R (o)／E (o)（只有「標為已讀」這一種編輯）
- :ref[系統管理員]{id="term.system-admin"}：R (o)／E (o)；另外在儀表板看得到全平台那一組（[規格 02-01](../02-dashboard/01-dashboard.mdx)）
- :ref[Seeder 管理員]{id="term.seeder-admin"}：與系統管理員相同
- 未登入的訪客：無權限

PRD §權限矩陣目前給「07 共用介面」的上限是 R；這裡的 E (o) 只作用在使用者自己的已讀狀態，不碰任何業務資料。依[規格 07-01 §已確認決議](./01-sidebar.mdx#已確認決議) Q1，PRD 會放寬到 `R／E (o)`，改動由 [Issue #85](https://github.com/label-suite/label-suite/issues/85) 處理。

## 業務流程

**不適用**：這一頁定義的是一份清單與它的歸屬，不是一段操作流程。使用者怎麼看通知寫在[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)，怎麼調偏好寫在[規格 01-04 §規格 › 通知設定](../01-account/04-profile.mdx#通知設定)。

## 規格

### 這一頁定什麼、不定什麼

1. 這一頁定**平台層的通知事件清單**：有哪些事件、各自什麼時候發生、誰收得到，以及它出現在哪一個消費端
2. 這一頁**不定畫面**：側欄通知入口與清單的行為（未讀數量、`9+`、全部標為已讀、每一則顯示什麼）全部由[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)定義，本頁不重複也不覆寫
3. 這一頁**不定儀表板的區塊行為**：「最近提醒」每筆有標題與內容、為空時顯示佔位文字，由[規格 02-01](../02-dashboard/01-dashboard.mdx#已確認決議) Q11 與該頁 §規格 定義
4. 這一頁**不定使用者偏好**：哪些事件可以逐一開關、用站內還是電子郵件、預設值，由[規格 01-04 §規格 › 通知設定](../01-account/04-profile.mdx#通知設定)定義

### 兩個消費端

同一份清單有兩個去處，它們的讀者與範圍不同。

| 消費端 | 誰看得到 | 範圍 | 行為定義在 |
| :--- | :--- | :--- | :--- |
| 側欄的通知清單 | 每一個登入後的使用者，只看得到與自己有關的 | 與這個人有關的事件 | [規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知) |
| 儀表板的「最近提醒」 | 只有系統管理員版面有這個區塊 | **只取與全平台有關的那些**（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q5） | [規格 02-01](../02-dashboard/01-dashboard.mdx) |

- 同一個事件可以同時出現在兩邊，也可以只出現在一邊；**哪一個事件落在哪一邊**是[§待釐清](#待釐清) Q2 要決定的事
- 側欄那一則要顯示「發生了什麼事、相關的任務、是誰做的，以及多久以前發生」（[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)第 6 條），所以清單上每一個事件都要說得出這四件事

### 不在本頁範圍

1. **寄給使用者的信**不是這裡的通知事件：驗證信（[規格 01-02](../01-account/02-register.mdx)）、重設密碼信（[規格 01-03](../01-account/03-reset-password.mdx)）、設定密碼信（[規格 06-01](../06-admin/01-user-management.mdx)）各自由那些頁定義，它們是帳號流程的一步，不進通知清單
2. **頁面內的操作回饋**不是通知事件：例如[規格 06-02 §規格](../06-admin/02-role-settings.mdx#規格)那種儲存成功或失敗、幾秒後自動消失的提示，它屬於那一頁自己的回饋
3. **頁面裡的提醒區塊**不是通知事件：例如 03-03 的「異常提醒」、IAA 條件清單上的「提醒」圖示，它們是那一頁的內容
4. **通知怎麼送達**（站內、電子郵件、兩者）屬 [規格 01-04](../01-account/04-profile.mdx#通知設定) 的偏好設定與實作，本頁只定「有哪些事件」

## 卡控機制

- 同一件事發生 → 只產生一則通知，不因為它同時出現在兩個消費端就變成兩則
- 使用者在[規格 01-04](../01-account/04-profile.mdx#通知設定)關掉某個事件的站內通知 → 那個事件不再進他的側欄通知清單（哪些事件可以關見[§待釐清](#待釐清) Q4）
- 事件與某個任務有關、而收件者在那個任務上沒有角色 → 不送給他；通知不得成為繞過任務成員身分的旁路
- 儀表板的「最近提醒」 → 只取與全平台有關的事件（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q5），不把每個人的個人事務放上去

## 邊界情況（Edge Case）

- **沒有事件**
  - 使用者一則通知都沒有 → 側欄不顯示未讀數量（[規格 07-01 §規格 › 通知](./01-sidebar.mdx#通知)第 3 條，本頁不重複定義）
  - 系統管理員的「最近提醒」一筆都沒有 → 顯示佔位文字（[規格 02-01 §已確認決議](../02-dashboard/01-dashboard.mdx#已確認決議) Q11，本頁不重複定義）
- **收件者的狀態變了**
  - 事件發生後，收件者在那個任務上的角色被移除 → 那一則通知還在不在、點了會怎樣**尚未決定**（[§待釐清](#待釐清) Q3）；點進去之後的畫面由[規格 07-03 無權限與找不到](./03-denied-and-not-found.mdx)定義
  - 事件相關的任務被刪掉 → 同上，點進去之後的畫面由 07-03 定義
- **同一件事通知很多人**
  - 一個事件有多個收件者 → 每個人各自一份已讀狀態，一個人標為已讀不影響其他人

## 驗收標準

| Scenario | Given | When | Then |
| :--- | :--- | :--- | :--- |
| 正向：清單只有一份 | 某個事件同時出現在側欄與儀表板 | 比對兩邊的敘述 | 兩邊講的是同一個事件，不是兩套說法 |
| 正向：關掉的事件不再進清單 | 使用者在個人設定關掉某個事件的站內通知 | 那個事件再次發生 | 他的側欄通知清單沒有新增那一則 |
| 反向：通知不得成為權限旁路 | 某事件與某任務有關，而這個人在那個任務上沒有角色 | 那個事件發生 | 他收不到那一則通知 |
| 反向：儀表板不收個人事務 | 某事件只與某一個人有關 | 系統管理員查看「最近提醒」 | 那一則不出現在「最近提醒」裡 |
| 邊界：多個收件者各自已讀 | 一個事件通知了兩個人，其中一人把它標為已讀 | 另一個人查看自己的通知 | 他那一則仍然是未讀 |
| 邊界：同一件事不重複 | 某事件同時符合兩個消費端的條件 | 那個事件發生 | 只產生一則通知 |

## 待釐清

### Q1. 平台層的通知事件清單有哪些事件？

- [ ] 就是[§規格 › 候選事件](#候選事件)那八列
- [ ] 只收第 1 到 6 列（01-04 來源給的那六個），第 7、8 列不算通知事件
- [ ] 要增減：請指出哪幾列
- [ ] 其他（請說明）

> 建議：**八列都收**。第 1 到 6 列有 01-04 來源的識別名；第 7 列是 03-03 已定案條文裡明寫的「完成後通知下載連結」；第 8 列是 05-02 已定案條文把「從儀表板的 IAA 待確認提醒點進來」寫成合法入口——三個出處都不是我自己想的。
> 需要決定的人：維護者。這一題定下來之前，[規格 02-01](../02-dashboard/01-dashboard.mdx) 的「最近提醒」與[規格 07-01](./01-sidebar.mdx)的通知清單都還是只定行為、不定內容。

### Q2. 每一個事件落在哪一個消費端、誰收得到？

- [ ] 照建議：第 1 到 6 列進側欄（與那個人有關），第 7 列進側欄（給按下匯出的人），第 8 列**兩邊都進**（側欄給專案負責人、儀表板給系統管理員）
- [ ] 另一種分法（請說明）

> 建議：如上。理由是 02-01 Q5 寫的「儀表板只取其中與**全平台**有關的」——第 1 到 7 列都是某一個任務或某一個人的事，只有第 8 列（某任務的試標 IAA 待確認）是會讓系統管理員想知道平台進度的那一種，而它正好就是畫面上那一筆寫死示例。
> 需要決定的人：維護者。

### Q3. 收件者後來失去那個任務的角色時，已經送出的通知怎麼處理？

- [ ] 通知留著，點進去之後由[規格 07-03](./03-denied-and-not-found.mdx)的無權限畫面處理
- [ ] 通知從他的清單上移除
- [ ] 其他（請說明）

> 建議：沒有強烈建議，兩種都說得通——留著比較誠實（他確實收過），移除比較不會讓人一直點到進不去的東西。**但不論選哪一種，通知本身不得洩漏他已經看不到的內容**（標題與敘述只提任務名稱，不提內容）。
> 需要決定的人：維護者。

### Q4. 第 7、8 列能不能像前六列那樣逐一關掉？

- [ ] 能：[規格 01-04 §規格 › 通知設定](../01-account/04-profile.mdx#通知設定)那張表從六列變八列
- [ ] 不能：它們一律送達，01-04 那張表維持六列
- [ ] 其他（請說明）

> 建議：**維持六列**。01-04 那六列有來源的識別名，是那一頁已定案的內容；加列等於改那一頁的條文，而第 7、8 列的性質也不同（匯出完成是使用者自己按下的動作的結果，IAA 待確認是要人去做決定的事）。
> 需要決定的人：維護者。這一題的答案會改到 01-04，所以要連同那一頁一起折。

## Q&A

:::tip{title="為什麼事件清單不乾脆寫在側欄那一頁？" collapsible}
因為事件來自任務管理、標記作業與資料集三個模組，而側欄只是其中一個顯示的地方。[規格 07-01 §已確認決議](./01-sidebar.mdx#已確認決議) Q4 的理由就是這個：來源自己把事件模型劃在範圍外，而清單會牽動三個模組，不該由側欄那一頁決定。儀表板那一邊（[02-01 Q5](../02-dashboard/01-dashboard.mdx#已確認決議)）同日也做了相同的判斷。
:::

:::tip{title="畫面上那兩筆提醒示例算不算需求？" collapsible}
不算。[規格 02-01](../02-dashboard/01-dashboard.mdx#已確認決議) Q5 寫得很明白：`FR-008C` 只要求「以清單呈現、每項含提醒標題與提醒內容、為空時顯示佔位文字」，**沒有列出任何一種提醒**，畫面上那兩筆是走查資料。本頁把其中一筆（IAA 待確認）列為候選，依據**不是那筆示例**，而是[規格 05-02](../05-dataset/02-analysis-detail.mdx#兩個合法入口)已定案的條文把「從那個提醒點進來」寫成合法入口。
:::
