## 錯誤契約：PERMISSION_DENIED

新的通用碼，不加模組前綴（產生的位置在 `app/core/`，任何模組的端點都可能回它）。

| 項目          | 值                                                                                                                                                                                                          |
| :------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `code`        | `PERMISSION_DENIED`                                                                                                                                                                                         |
| HTTP          | `403`                                                                                                                                                                                                       |
| 訊息鍵        | `common.permission_denied`                                                                                                                                                                                  |
| 訊息（提案）  | zh-TW `你沒有執行這個操作的權限`；en `You do not have permission to perform this action.`。兩個語系都要有這個鍵（`MessageCatalog` 啟動時檢查兩邊的鍵一致）                                                  |
| 產生的位置    | `app/core/authz.py` 的 `PermissionDeniedError`（繼承 `AppError`，不帶 `params`），由 `Authorizer` 經 `require_permission` 丟出，`handle_app_error` 轉成錯誤外層                                             |
| 觸發條件      | 授權第 3 步不通過：權限鍵不在白名單、鍵尚未啟用、鍵的層級與操作的範圍不符、矩陣版本列不存在、某個生效角色的格缺列、生效角色的格全部為關；**而且**被拒的資源對呼叫者來說看得到（看不到的回 `404`，見下一節） |
| 不帶的資訊    | `message` 是固定的一句，不帶 `params`；`errors` 為 `null`（只有 `422` 才有逐欄位錯誤）。不回權限鍵、角色、任務 ID、矩陣版本、拒絕在哪一步或缺的是哪一格，也不回堆疊                                         |
| 回應的 cookie | 不動任何 cookie（與 `CSRF_FAILED` 不同，權限不足不代表登入狀態有問題）                                                                                                                                      |

錯誤外層照 `api-envelope` spec「錯誤回應使用同一個錯誤外層」，例：

```json
{
  "success": false,
  "code": "PERMISSION_DENIED",
  "message": "你沒有執行這個操作的權限",
  "data": null,
  "timestamp": "2026-11-27T08:15:30.123Z",
  "traceId": "0f8e5c7a-3b1d-4e2a-9c6f-1a2b3c4d5e6f",
  "errors": null
}
```

欄位與順序以 `api-envelope` spec 與 `app/core/schemas.py` 的 `ErrorResponse` 為準；上例只示意 `code`、`message` 與 `errors` 為 `null`。

**`api-envelope` spec 要跟著改**：那條 Requirement「錯誤碼為大寫底線格式並定義第一批通用碼」逐一列了通用碼與 HTTP 狀態的對應，`PERMISSION_DENIED`（403）要由 `planner` 以 MODIFIED delta 加進去（`login-auth-guard` 加 `AUTH_REQUIRED`、`CSRF_FAILED` 時是同一種做法）。

**OpenAPI 宣告**：`API_V1_ERROR_RESPONSES` 不加 `403`（不是每個操作都會回）；掛 `require_permission` 的端點由該端點的 router 宣告 `403`（與 `404`），由那張卡的 `api-contract.md` 寫。本次 `openapi.json` 不變。

## 授權拒絕對到的 HTTP 狀態

這一節是**待決 12** 的內容，維護者在 clarification 定案前，下表是 sd 建議（方案 R1），另兩個方案列在後面。不論選哪個方案，兩條規則不變：

- **看不到的資源一律回 `404 NOT_FOUND`**，不得用 `403` 洩漏它存在（`openspec/config.yaml` 的 api-contract 規則、architecture §授權四步 第 4 條、S10）
- 授權第 1 步不通過一律是既有的 `401 AUTH_REQUIRED`，本次不變

### 方案 R1（sd 建議）

| 拒絕在哪一步                                                                                      | HTTP 與 `code`              | 理由                                                                                       |
| :------------------------------------------------------------------------------------------------ | :-------------------------- | :----------------------------------------------------------------------------------------- |
| 第 1 步：沒有可用的登入狀態                                                                       | `401 AUTH_REQUIRED`（既有） | 不變                                                                                       |
| 第 2 步（方案 A1）：在這個任務沒有生效的成員身分（不是成員、已停用、仍在邀請中）                  | `404 NOT_FOUND`             | 不是成員就不該知道任務存在；系統管理員沒有任務角色時也一樣                                 |
| 第 2 步（方案 A1）：指定的作用角色不是他在這個任務的生效角色                                      | `404 NOT_FOUND`             | 網址上的角色不能建立身分（06-02 §一人多任務角色 第 6 條）；回 `403` 等於確認了這個任務存在 |
| 第 3 步，平台層的鍵                                                                               | `403 PERMISSION_DENIED`     | 平台層的頁面本來就公開存在；`user-management` 既有契約已寫 `403`                           |
| 第 3 步，任務層的鍵（已確認是生效成員）                                                           | `403 PERMISSION_DENIED`     | 他已是成員，知道任務存在，回 `404` 不保護任何東西；07-03 的「無權限」頁對應它              |
| 第 4 步：附加條件遇到看不到的資源（不是他的任務、不是他被指派的項目、看不到的資料集、讀標準答案） | `404 NOT_FOUND`             | 不洩漏存在；`GroundTruthBarrier` 也回 `404`，不說明有答案                                  |
| 第 4 步：看得到但狀態不允許（例：任務狀態不符）                                                   | 由該條件所屬的功能卡定      | 通常是 `409`，碼加該模組前綴，寫在那張卡的 `api-contract.md`                               |

### 另兩個方案

| 方案 | 做法                                                                               | 後果                                                                                                                                                                                                  |
| :--- | :--------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R2   | 任務範圍的操作，第 2、3、4 步的拒絕**全部**回 `404`；`403` 只給平台層              | 最保守，任務層完全不透露「存在但你不能做」；但已經看得到任務詳情的審核員按「編輯」被擋時也是「找不到」，07-03 的「無權限」頁在任務層用不到，與 07-03 §返回操作的去處 的「被權限矩陣擋下」那一種對不上 |
| R3   | 授權的拒絕**全部**回 `403`（包括沒有成員身分），只有路由層與資源真的不存在回 `404` | 前端判斷最單純；但非成員能藉 `403` 與 `404` 的差別探出任務 ID 是否存在，違反「看不到的資源回 404」的 api-contract 規則與 S10，**sd 不建議**，列出只為完整                                             |

選 R2 時，`error-codes.mdx` 的 `PERMISSION_DENIED` 一列仍成立（平台層仍回它），不必改；選 R3 時，與 `openspec/config.yaml` 的規則衝突，要先由維護者處理規則本身。

## 角色、欄位遮蔽與測試集答案隔離

- **角色**：本次沒有端點，沒有新的角色要求。授權各步怎麼判斷角色見 `system-design.md` §授權判斷的固定順序；權限上限以 PRD §權限矩陣 為準，本次沒有放寬任何一格
- **欄位遮蔽**：無。`PERMISSION_DENIED` 與授權產生的 `404` 都只帶錯誤外層的固定欄位，不帶任何資源、權限鍵、角色或矩陣的資訊
- **測試集答案隔離**：無風險。本次沒有任何讀或回任務、資料集、標記資料的端點；錯誤外層不含答案或測試集辨識資訊。授權層的 `GroundTruthBarrier` 對讀標準答案的操作回 `404`（R1），訊息與一般的找不到相同，不透露「這裡有答案」。測試集辨識資訊要不要在授權層依作用角色關閉，仍是待決 N1
