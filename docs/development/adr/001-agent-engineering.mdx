# ADR-001 Agent 工程

這份 ADR 管 agent 寫程式時的工程紀律：開工前怎麼找既有實作、碰到錯誤的既有實作怎麼處理，以及 agent hook 的設定與阻擋策略。agent 的角色分工與 SDD 流程不在這裡，見 `AGENTS.md` 的 SDD Workflow。
規則本體在 `AGENTS.md`、[agent-rules.mdx](../rules/agent-rules.mdx) 與 [agent-hook-contract.mdx](../rules/agent-hook-contract.mdx)，本文只寫為什麼；衝突時的優先序見 [ADR 索引](index.mdx#衝突時以誰為準)。

## D1 先搜尋再新增

### 背景

agent 常在已經有同樣功能的地方再寫一份 helper、型別或元件；要決定的是，現在用什麼方式讓「先搜尋」真的發生。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| `backend/`、`frontend/` 還不存在 | 索引既有程式的工具現在沒有東西可索引 |
| 沒有任何 agent hook 接上線，見 [agent-hook-contract.mdx](../rules/agent-hook-contract.mdx) | 用 hook 強制，要先把 hook 的基礎建起來 |
| Session 開始的 hook（H1）只能提醒、不能阻擋 | 在開工那一刻「強制」搜尋，現有的事件做不到 |
| Claude Code 和 Codex 的 hook 能力不一樣 | 只在一邊做得到的強制，另一邊會漏 |
| 「grep 搜過什麼」事後無法從程式驗證 | 證據只能由 agent 自己寫下來，交給審查的人看 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 只靠規則 | 不用任何工具 | 完全靠自覺，審查的人看不到搜過什麼 | 不採用 |
| B 規則加上在 commit body 或 PR 寫明搜過什麼 | 現在就能做；審查的人有東西可以對 | 仍然是人工檢查，寫了不代表真的搜過 | 採用 |
| C 元件索引加上查詢工具：新增前先查有沒有相近的元件，附相似度 | 搜尋變便宜，結果可以重現 | 沒有程式可索引，現在建只是空殼 | 延後：`frontend/` 的第一個模組合併之後 |
| D 開分支或開 session 時用 hook 強制先搜尋 | 不靠自覺 | 現有事件只能提醒；兩個平台不一致；要先寫 hook 契約 | 延後：hook 契約另案處理 |

### 決定

現在用選項 B：開工前先讀那一區既有的匯出、呼叫端與共用工具，新增 helper、型別、常數或相依套件時，在 commit body 或 PR 寫明搜過什麼。規則本體見 [agent-rules.mdx 的 R1](../rules/agent-rules.mdx#r1-先搜尋再新增)。

### 後果

**變容易**

- 審查的人有搜尋紀錄可以對，「這裡已經有一個了」可以在 review 指出來
- 在還沒有程式的時候，不必先維護一套索引工具

**變困難**

- 仍然靠 agent 照實寫；寫了搜過、其實沒搜，只有審查的人看得出來
- PR 多一段要寫、也多一段要讀

### 什麼情況要重新討論

- `frontend/` 或 `backend/` 的第一個模組合併之後：評估選項 C
- agent hook 契約接上線之後：評估選項 D
- review 發現重複的 helper，而那張 PR 寫了「搜過、沒有」

## D2 範圍內直接修正錯誤實作

### 背景

新的改動常會碰到寫錯的既有實作；要決定的是，agent 應該繞過它、另加一條規則補救，還是直接修掉它。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| [R3 最小變更](../rules/agent-rules.mdx#r3-最小變更)：每一行改動都要追得到請求 | 修既有實作要有清楚的界線，不能變成順手重構 |
| 一張 PR 只有一個目的（`AGENTS.md` §Pull Requests） | 修正要和這次的目的同一件事，不能另起一件 |
| 在錯誤實作上疊規則或繞道，規則和繞道只會越來越多 | 只提出來、不修，錯誤會被新程式依賴得更深 |
| [R6 範圍鎖定](../rules/agent-rules.mdx#r6-範圍鎖定後不得以-yagni-刪驗收條件)：已承諾的驗收條件不能縮 | 修正只能加，不能拿來當刪驗收條件的理由 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 一律只提出來、另開 issue（原本 R3 的做法） | diff 最乾淨 | 新程式得繞過錯誤實作，繞道留在程式裡；常常變成再加一條規則補救 | 不採用 |
| B 看到錯就修 | 錯誤最快消失 | diff 漂出範圍，PR 失去單一目的，違反 R3 | 不採用 |
| C 這次改動會碰到的程式路徑內直接修，其餘照 R3 | 錯誤在被依賴之前就修掉；範圍有界線 | 審查的人要判斷修正是不是真的在路徑上 | 採用 |
| D 先把修正加進 issue 的工作項才能修 | 每一項修正都可追溯 | 每次都要回 issue 補一項，成本高，實際上常被省略、改成繞道 | 不採用 |

### 決定

這次要改的行為所呼叫、修改或取代的既有實作如果是錯的，就在同一張 PR 直接修，不加繞道、不另加規則補救，並在 PR 寫明修了什麼、為什麼是錯的；碰不到的地方照 R3，只提出來、另開 issue。規則本體見 `AGENTS.md` 的 Required Behaviors，落地說明見 [agent-rules.mdx 的 R3](../rules/agent-rules.mdx#r3-最小變更)。

### 後果

**變容易**

- 錯誤實作不會被新程式依賴得更深
- 規則數量不會因為補救錯誤實作而一直增加

**變困難**

- 審查的人要判斷每一處修正是不是在這次改動的路徑上
- 修正改到的行為若還有其他呼叫端，這張 PR 要一併顧到，diff 會變大

### 什麼情況要重新討論

- review 一再發現 PR 用這個例外把範圍外的改動帶進來
- 某次路徑內的修正弄壞了其他呼叫端

## D3 兩個平台的 hook 設定手寫兩份，不做生成器

### 背景

同一個 hook 在 Claude Code 與 Codex 各要一份設定；要決定的是，用什麼方式讓兩份設定不漂移。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 設定檔位置不同：`.claude/settings.json` 與 `.codex/hooks.json` | 同一個 hook 一定有兩個註冊點 |
| 兩邊的事件集合與工具名不同，例如寫檔在 Claude 是 `Edit｜Write｜NotebookEdit`，在 Codex 是 `apply_patch` | 兩份設定不能逐字相同 |
| 專案根佔位符只有 Claude 有（`${CLAUDE_PROJECT_DIR}`），Codex 要用 `git rev-parse --show-toplevel` | 腳本路徑的寫法在兩份設定裡不同 |
| 改一邊忘了另一邊，不會有任何報錯 | 需要有東西抓得到漂移 |
| 兩邊指向的是同一支腳本 | 差異只在設定，不在檢查邏輯 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 手寫兩份，由 H1 的環境檢查核對兩份設定指向的腳本是否都存在 | 兩份各自照自己平台的格式與事件寫，差異收在設定裡 | 一致性靠這道檢查，不靠結構保證 | 採用 |
| B 單一來源，用生成器產出兩份設定 | 兩份由同一處產出，一致性由結構保證 | — | 不採用 |

### 決定

兩份設定手寫兩份、都指向同一支腳本，由 H1 核對兩份設定指向的腳本是否都存在、兩邊是否都實際生效，不做單一來源生成器。做法見 [agent-hook-contract.mdx 的 H1](../rules/agent-hook-contract.mdx#h1-session-開始環境自我檢查)。

### 後果

**變容易**

- 每份設定直接照自己平台的事件、工具名與佔位符寫

**變困難**

- 改一個 hook 要改兩處
- H1 核對的是腳本存不存在與 hook 有沒有生效，不是兩份設定的內容是否等價

### 什麼情況要重新討論

- 某次改一邊漏了另一邊，而 H1 的核對沒有抓到

## D4 H3 只回報診斷，不自動修

### 背景

編輯後的快速檢查（H3）會產生診斷；要決定的是，檢查有結果之後，hook 要不要替 agent 把檔案修好。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| `PostToolUse` 在兩邊都撤銷不了已發生的編輯，能做的只是替換 model 看到的結果 | H3 不能當閘門，只能提醒；真正的閘門是 H4、H5 與 H7 |
| 自動改檔或 `git add` 會動到工作區裡其他未暫存的修改 | 自動修與「只動 agent 本意改的檔」互相衝突 |
| PR 的 diff 要只含 agent 本意的改動 | 自動套用的改動會混進 diff |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 只回報診斷（走 stderr），由 agent 依診斷自己修 | hook 不會動到工作區裡其他未暫存的修改，PR 的 diff 不會混進不是 agent 本意的改動 | agent 要自己修 | 採用 |
| B 自動套用 formatter | agent 不必自己處理排版診斷 | 會動到未暫存的修改，diff 混進非本意的改動 | 不採用 |
| C 自動修檔並自動 `git add` | agent 不必自己處理診斷 | 同上，而且動到暫存區 | 不採用 |
| D 把診斷放進 `PostToolUse` 替換後的結果交給 model | 診斷直接出現在 model 看到的結果裡 | 診斷被藏在替換後的結果裡，失敗變得不明顯 | 不採用 |

### 決定

H3 只回報診斷，不改檔、不自動 `git add`、不自動套用 formatter，也不以 exit `2` 阻擋；要修由 agent 依診斷自己修。做法見 [agent-hook-contract.mdx 的 H3](../rules/agent-hook-contract.mdx#h3-編輯後按路徑跑快速檢查)；Git pre-commit 的排版（H4）是另一個 hook，不在這個決定內。

### 後果

**變容易**

- 工作區與暫存區只被 agent 自己的動作改動，PR 的 diff 容易對得上意圖

**變困難**

- 每個診斷都要 agent 自己修，不會有 hook 替它收尾
- H3 不擋任何事，漏掉診斷的編輯要等 H4、H5 或 CI 才會被擋下

### 什麼情況要重新討論

- 診斷反覆被 agent 略過，導致同一類問題一再留到 H4 或 CI 才被擋下

## D5 H2 失敗時由腳本自己 exit 2

### 背景

H2 要在動作發生前擋下 `AGENTS.md` 硬性規則 2、3、10 禁止的命令；要決定的是，檢查器本身不存在或無法判斷時，動作要放行還是擋下。

| 限制 | 對選擇的影響 |
| :--- | :--- |
| 兩個平台的預設都是 fail-open：hook 失敗、timeout 或輸出不合法時，動作照做（Claude 文件寫路徑打錯或 crash 的 policy hook「lets everything through」） | 不寫任何處理，檢查器壞了就等於沒有 H2 |
| Claude 的宣告式 fail-closed 開關 `onFailure: "block"` 需要 v2.1.295，本機是 2.1.330（見 [agent-hook-contract.mdx 的查核方式](../rules/agent-hook-contract.mdx#查核方式)） | Claude 這一邊可以用，但還沒有在本機實測，採不採用見該文件的[待決](../rules/agent-hook-contract.mdx#待決) |
| Codex 沒有等價欄位（官方文件未見） | 就算 Claude 升級，Codex 那邊仍沒有 |
| 選 exit `2` 的理由不是欄位名不同：`PreToolUse` 的欄位名兩邊一致 | 理由只剩下面這一列 |
| Codex 的 `PreToolUse` 回傳不支援的欄位（`continue`、`stopReason`、`suppressOutput`）時，該次 hook 被標為失敗並繼續執行那個工具 | 用 JSON 欄位表達阻擋有被誤放行的風險 |

### 考慮過的選項

| 選項 | 好處 | 代價 | 結論 |
| :--- | :--- | :--- | :--- |
| A 兩邊都由腳本自己在無法判斷時 exit `2`：包裝腳本先確認檢查器存在且可執行，不存在就 exit `2` | 兩個平台都能用；exit `2` 沒有 Codex 不支援欄位的風險 | 靠腳本自己負責；設定裡的路徑打錯或腳本本身 crash 時仍是 fail-open，不得假設會被擋下 | 採用 |
| B Claude 用 `onFailure: "block"` | 宣告式的 fail-closed | 要 v2.1.295 以上（本機 2.1.330 已滿足）；Codex 沒有等價欄位，只有一邊；尚未在本機實測 | 延後：是否採用見 [agent-hook-contract.mdx 的待決](../rules/agent-hook-contract.mdx#待決) |
| C 不處理，靠預設 | 不用寫任何東西 | 預設是 fail-open，不得假設不寫就會擋 | 不採用 |
| D 以 `permissionDecision: "deny"` 加 `permissionDecisionReason` 當主要的阻擋方式 | 兩邊都收 | 同一條路徑上若回傳 Codex 不支援的欄位，會讓該次 hook 失敗並繼續執行工具 | 不當主要做法，優先 exit `2` |

### 決定

H2 兩邊都由腳本自己在無法判斷時 exit `2`、原因寫 stderr；不用 `|| true` 把判斷不了變成通過，優先用 exit `2` 而不是 JSON 欄位。做法見 [agent-hook-contract.mdx 的 H2](../rules/agent-hook-contract.mdx#h2-工具執行前破壞性命令與受保護目標)。

### 後果

**變容易**

- 檢查器不存在或無法判斷時，兩個平台都能擋下動作

**變困難**

- 每支 H2 的包裝腳本都要自己負責 fail-closed，沒有宣告式的開關可以靠
- 腳本以外的失敗（設定路徑打錯、腳本 crash）仍然放行

### 什麼情況要重新討論

- 在本機實測 `onFailure: "block"` 確實擋下缺檔的 hook 之後：評估選項 B
- Codex 出現等價的 fail-closed 欄位
