# 端點授權

這份記 `main` 上每個 `/api/v1` 端點開給哪些系統角色與任務成員身分、對到 PRD 權限矩陣的哪一格、哪些欄位依角色遮蔽（答案欄位另加標記）；**只寫已合併的程式有的東西**。
權限的上限是 [PRD 的權限矩陣](../../specs/00-prd.mdx#權限矩陣)，本文只引用、不改它；授權怎麼判定、遮蔽在哪一層做，規則在 [security-agent-rules 的 S3](../../development/rules/security-agent-rules.mdx#s3-授權的四段順序) 與 [S4](../../development/rules/security-agent-rules.mdx#s4-遮蔽與-allowlist-在後端)；端點的路徑、request 與 response 以 `backend/openapi.json` 為準，本文只用 `operationId` 對過去。
本文與程式不一致時，是本文錯了：以程式為準，並回頭改本文。

各節的收合區塊是實作或規劃時才要查的細節，預設收起。

## 誰改、什麼時候改

規劃時先改本文，change 的 `api-contract.md` 只寫本文的路徑與異動摘要，不重抄本文的內容。

| 時機 | 誰 | 做什麼 |
| :--- | :--- | :--- |
| 規劃（寫 `api-contract.md`） | `sd` | 新端點加進 [§端點](#端點)；既有端點的角色、矩陣格或遮蔽欄位改了，改那一列。`api-contract.md` 的「常駐文件異動」節寫出本文路徑與異動摘要 |
| 規劃審閱 | `design-reviewer` | 核對本文與這次的 `api-contract.md` 一致，每一列都沒有超出 PRD 權限矩陣 |
| 實作後 | `backend-developer` | 實作出來的授權依賴或遮蔽和設計不同時，依程式校正本文 |
| 程式審查 | `code-reviewer` | 再核對一次本文與實作一致；不一致時列為審查意見 |
| 驗收 | `acceptance-verifier` | 以本文對照每個受保護端點的 [S10 驗收矩陣](../../development/rules/security-agent-rules.mdx#s10-驗收矩陣)；實際放行的角色與遮蔽和本文不同時記為缺陷 |

四份文件各管一件事：

| 文件 | 管什麼 |
| :--- | :--- |
| PRD 的權限矩陣 | 業務層的上限：每種角色對每個功能能做什麼 |
| 本文 | 合併之後全系統的端點：每個端點放行誰、對到矩陣哪一格、依角色遮蔽哪些欄位（含答案） |
| change 的 `api-contract.md` | 這次每個端點的角色、欄位遮蔽與測試集答案隔離的完整說明 |
| `backend/openapi.json` | 每個端點的路徑、request 與 response 的形狀 |

## 端點

目前 `/api/v1` 有八個端點：健康檢查與帳號模組的七個。帳號模組的 handler 都在 `app/modules/account/router.py`；只有 `getCurrentSession` 掛授權依賴，其餘六個不檢查登入，寫入的那幾個也都在 CSRF 放行清單（`app/core/csrf.py` 的 `CSRF_EXEMPT_OPERATIONS`）。

| `operationId` | Method 與路徑 | 系統角色 | 任務成員身分 | PRD 權限矩陣 | 遮蔽的欄位（含答案） | 出處 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| [`getHealth`](/view/diagrams/architecture/api.openapi#op/getHealth) | `GET /api/v1/health` | 不檢查；未登入也可呼叫 | 不檢查 | 無對應的格：矩陣外刻意公開的端點 | 無；回應只有 `status` 與 `database`，不讀任務、資料集或答案 | `app/modules/health/router.py` 的 `get_health` 沒有任何認證或授權依賴；`openspec/specs/health-check/` 的「健康檢查刻意公開」 |
| [`getAuthOptions`](/view/diagrams/architecture/api.openapi#op/getAuthOptions) | `GET /api/v1/auth-options` | 不檢查；未登入也可呼叫 | 不檢查 | 無對應的格：PRD 權限矩陣管的是登入之後的功能，登入前的訪客對不到任何一列（規格 01-01 §使用角色） | 無；只有兩個布林（是否開放自行註冊、是否設定 Google），不讀帳號、任務或答案 | `app/modules/account/router.py` 的 `get_auth_options`；沒有授權依賴；`openspec/specs/` 的 `account-login` |
| [`createSession`](/view/diagrams/architecture/api.openapi#op/createSession) | `POST /api/v1/sessions` | 不檢查；未登入的訪客送出登入 | 不檢查 | 無對應的格：PRD 權限矩陣管的是登入之後的功能，登入前的訪客對不到任何一列（規格 01-01 §使用角色） | 無依角色的遮蔽；回應只明列 `user.id`、`user.name`、`user.email`、`user.role`，都是登入者自己的資料；`hashed_password`、`google_subject`、`credential_version`、`is_seeder` 與登入狀態的 `sid` 一律不在回應裡；不讀任務、資料集或答案 | `app/modules/account/router.py` 的 `create_session`；沒有授權依賴，在 CSRF 放行清單；`openspec/specs/` 的 `account-login` |
| [`getCurrentSession`](/view/diagrams/architecture/api.openapi#op/getCurrentSession) | `GET /api/v1/current-session` | 平台成員、系統管理員（含 Seeder 管理員）；以資料庫當下的角色判定 | 不檢查 | 依系統角色：01 帳號，平台成員 `R (o)`、系統管理員 `R (o)`（讀自己的帳號） | 無依角色的遮蔽；回應只明列 `user.id`、`user.name`、`user.email`、`user.role`，都是登入者自己的資料；`hashed_password`、`google_subject`、`credential_version`、`is_seeder` 與登入狀態的 `sid` 一律不在回應裡；不讀任務、資料集或答案 | `app/modules/account/router.py` 的 `get_current_session` 掛 `get_current_principal`（`app/core/auth.py`），判定由 `AccountPrincipalLoader.load` 讀資料庫；`openspec/specs/` 的 `auth-guard` |
| [`createSessionRefresh`](/view/diagrams/architecture/api.openapi#op/createSessionRefresh) | `POST /api/v1/session-refreshes` | 不檢查系統角色；持有 refresh cookie，且帳號啟用 | 不檢查 | 無對應的格：PRD 權限矩陣管的是登入之後的功能，登入前的訪客對不到任何一列（規格 01-01 §使用角色）；它延續既有的登入狀態，不讀業務資料 | 無依角色的遮蔽；回應只明列 `user.id`、`user.name`、`user.email`、`user.role`，都是登入者自己的資料；`hashed_password`、`google_subject`、`credential_version`、`is_seeder` 與登入狀態的 `sid` 一律不在回應裡；不讀任務、資料集或答案 | `app/modules/account/router.py` 的 `create_session_refresh`；沒有授權依賴，只讀 refresh cookie，在 CSRF 放行清單；`openspec/specs/` 的 `login-session` |
| [`deleteCurrentSession`](/view/diagrams/architecture/api.openapi#op/deleteCurrentSession) | `DELETE /api/v1/current-session` | 不檢查；登入狀態不能驗證時也要能清 cookie | 不檢查 | 依系統角色：01 帳號，`E (o)`（結束自己這一台的登入狀態）；不能驗證時只清本機 cookie | 無；`204` 沒有 body | `app/modules/account/router.py` 的 `delete_current_session`；沒有授權依賴，在 CSRF 放行清單；`openspec/specs/` 的 `login-session` |
| [`getGoogleAuthorization`](/view/diagrams/architecture/api.openapi#op/getGoogleAuthorization) | `GET /api/v1/google-authorization` | 不檢查 | 不檢查 | 無對應的格：PRD 權限矩陣管的是登入之後的功能，登入前的訪客對不到任何一列（規格 01-01 §使用角色） | 無；只回 Google 的授權網址，PKCE verifier 只在 httpOnly cookie | `app/modules/account/router.py` 的 `get_google_authorization`；沒有授權依賴；`openspec/specs/` 的 `account-login` |
| [`createGoogleSession`](/view/diagrams/architecture/api.openapi#op/createGoogleSession) | `POST /api/v1/google-sessions` | 不檢查；持有同一個瀏覽器的 Google 流程 cookie | 不檢查 | 無對應的格：PRD 權限矩陣管的是登入之後的功能，登入前的訪客對不到任何一列（規格 01-01 §使用角色） | 無依角色的遮蔽；回應只明列 `user.id`、`user.name`、`user.email`、`user.role`，都是登入者自己的資料；`hashed_password`、`google_subject`、`credential_version`、`is_seeder` 與登入狀態的 `sid` 一律不在回應裡；不讀任務、資料集或答案；Google 那一側的 `sub`、Email 與 `email_verified` 也不回 | `app/modules/account/router.py` 的 `create_google_session`；沒有授權依賴，在 CSRF 放行清單；`openspec/specs/` 的 `account-login` |

:::note{title="各欄怎麼填" collapsible}
- 「系統角色」與「任務成員身分」只列放行的角色，用 PRD 的角色名稱：系統角色是平台成員、系統管理員，任務成員身分是專案負責人、審核員、標記員；不檢查時寫「不檢查」
- 這兩欄列出的角色，就是 S10 驗收矩陣裡「每一個有效角色」那幾格要測的角色
- 「PRD 權限矩陣」寫對到的那一格：哪一張表（依系統角色或依任務角色）、哪一列、哪一欄與代號，例「依任務角色：05 資料集分析，審核員 R」；矩陣裡沒有對應的格時寫出原因
- 「遮蔽的欄位（含答案）」寫每個依角色遮蔽的欄位，範圍與 `api-contract.md` 的「欄位遮蔽」相同：欄位名、對誰遮蔽、遮蔽後的值；答案欄位另標「答案」；沒有就寫「無」與理由
- 「出處」寫掛授權依賴或做遮蔽的程式位置，以及描述這個行為的 `openspec/specs/` capability
:::

## 不在本表的路徑

下表的路徑由 `main` 上的程式提供或掛載，但不是 `/api/v1` 的業務端點，不進 [§端點](#端點)。

| 路徑 | 誰拿得到 | 為什麼不在本表 | 出處 |
| :--- | :--- | :--- | :--- |
| `/docs`、`/docs/oauth2-redirect`、`/redoc`、`/openapi.json` | `API_DOCS_ENABLED=true`（預設，Lite 與本機開發）：任何人，不需登入。`false`（正式層 compose）：沒有人，路由不註冊，回 `404` 的共通外層 | FastAPI 內建的 API 文件頁，不在 `/api/v1` 底下、不套外層，也不在 `openapi.json` 的 `paths` 裡 | `app/main.py` 的 `create_app` 依 `API_DOCS_ENABLED` 決定是否註冊（#592）；已歸檔的 [backend-skeleton `api-contract.md`](https://github.com/label-suite/label-suite/blob/main/openspec/changes/archive/2026-11-20-backend-skeleton/api-contract.md) §端點總覽 |
| `/api/v1/probe`（`GET`、`POST`）、`/api/v1/probe-crash`、`/api/v1/probe-bad-response`、`/api/v1/probe-db-error` | 只有後端的測試 | 只在測試掛載：`backend/tests/probe.py` 定義，`backend/tests/conftest.py` 的 `app` fixture 掛進 `/api/v1`；正式的 `create_app` 不掛，`openapi.json` 裡也沒有 | `backend/tests/probe.py`、`backend/tests/conftest.py` |
| 任何 `/api/v1` 路徑的 CORS 預檢（帶 `Origin` 與 `Access-Control-Request-Method` 的 `OPTIONS`） | 任何來源都可以送；只有允許清單內的來源拿到 CORS 標頭 | 由 `CORSMiddleware` 自己回，不到任何端點 | `app/main.py` 的 `CORSMiddleware` 設定；`api-envelope` spec 的「錯誤回應使用同一個錯誤外層」 |

前端的 `/dev/health`、`/dev/gallery` 是前端路由，不是 API 端點，見 [前端路由與骨架](./frontend-routes.mdx#路由)。
